## 2. Purpose

Define the application/persistence contract required to persist the active Reservation aggregate through the physical Booking root.

This specification resolves the contract gaps identified by 3G:

1. Reservation number;
2. Booking Customer context;
3. Booking status;
4. Booking dates;
5. currency and final amount;
6. Reservation persistence context;
7. create/update semantics;
8. retrieval and round-trip contract.

This document does NOT implement those decisions.

# 4. Contract Principles

The following principles are mandatory.

### 4.1 Domain Authority

The active Reservation domain model remains authoritative.

Persistence requirements MUST NOT force infrastructure-specific fields into the Reservation aggregate.

### 4.2 Application Boundary

Values required to persist Booking but not owned by Reservation SHALL enter through an explicit application/persistence context.

### 4.3 Persistence Neutrality

The domain and application contracts MUST NOT expose Prisma types.

### 4.4 Snapshot Preservation

Traveller, Journey and accommodation snapshots remain Reservation-owned historical state.

### 4.5 Lifecycle Separation

The following are distinct:

- GCT Reservation lifecycle;
- commercial/legacy Booking status;
- supplier operational Reservation status.

### 4.6 Round-Trip Requirement

A persisted Reservation MUST be reconstructable into the active Reservation aggregate without losing domain state.

# 5. Reservation Number Decision

## 5.1 Canonical Decision

The GCT Reservation number SHALL become an explicit Reservation application/domain property.

Physical mapping:

`Reservation.reservationNumber`
→ `Booking.bookingNumber`

The Reservation number is therefore part of the Reservation contract rather than an infrastructure-only value.

## 5.2 Generation

The Reservation number SHALL be generated by the application layer at Reservation creation.

It MUST NOT be generated implicitly by Prisma.

The generation mechanism MUST produce a unique GCT Reservation number according to the project's existing reservation-number convention.

If no existing convention is available in the active codebase, implementation MUST STOP rather than invent a numbering algorithm.

## 5.3 Lifecycle

The reservation number:

- exists from Reservation creation;
- is persisted with the Reservation;
- remains immutable;
- is returned by Reservation creation/retrieval;
- is usable for Reservation lookup.

## 5.4 Persistence

The repository SHALL persist the application Reservation number into:

`Booking.bookingNumber`

No second physical reservation-number field is permitted.

---

# 6. Booking Customer Context

## 6.1 Canonical Decision

`customerId` is Booking persistence context.

It is NOT a property of the Reservation aggregate unless an existing domain contract already establishes it.

## 6.2 Source

The application layer SHALL provide the Customer identity when creating a Reservation.

The Reservation creation workflow MUST have authoritative Customer context before persistence.

No implicit Customer creation is permitted.

## 6.3 Persistence

The Customer identity SHALL map to:

`Booking.customerId`

The repository SHALL receive the Customer identity through the persistence context.

## 6.4 Validation

Reservation persistence MUST reject a missing Customer context.

The repository MUST NOT:

- invent a Customer;
- derive Customer identity from email;
- create a Customer implicitly;
- use BookingContact as Customer identity.

---

# 7. Booking Status Decision

## 7.1 Separation

The GCT Reservation lifecycle is authoritative for Reservation behaviour.

Existing Prisma Booking status remains a separate physical/commercial status.

Supplier Reservation status remains operational supplier state.

They MUST NOT be treated as interchangeable.

## 7.2 GCT Lifecycle

The authoritative domain lifecycle is:

- `CREATED`
- `QUOTED`
- `CONFIRMED`
- `AMENDED`
- `CANCELLED`
- `COMPLETED`

## 7.3 Physical Mapping

The GCT lifecycle SHALL have a dedicated physical Reservation lifecycle representation.

It MUST NOT depend on the existing Booking status values.

The exact Prisma field/enum name SHALL follow existing project naming conventions during the physical implementation specification.

## 7.4 Ownership

The Reservation lifecycle is owned by the Reservation contract.

Booking status remains infrastructure/commercial status.

Supplier Reservation status remains supplier operational state.

---

# 8. Booking Dates Decision

## 8.1 Canonical Source

Booking-level dates SHALL be supplied by the Reservation application contract.

They MUST NOT be inferred solely from persisted accommodation rows during retrieval.

## 8.2 Required Values

The Reservation persistence context SHALL provide:

- booking start date;
- booking end date.

These represent the GCT Reservation travel/booking period.

## 8.3 Relationship to Journey

Journey snapshot dates MAY be used by the application when constructing the context, but Booking-level dates remain explicit persistence values.

The repository MUST NOT derive them from arbitrary Journey or accommodation records.

---

# 9. Currency Decision

## 9.1 Canonical Source

The final GCT Reservation currency is supplied by the Reservation pricing contract.

The active `PricingSnapshot.currency` remains the domain/application source.

## 9.2 Physical Mapping

The persistence layer maps the currency to:

`Booking.currencyId`

The repository MAY resolve the currency identifier through the existing Currency persistence model.

## 9.3 Constraint

The physical currency identifier MUST NOT leak into the domain model.

---

# 10. Final GCT Amount Decision

## 10.1 Canonical Source

The final GCT Reservation amount SHALL come from:

`PricingSnapshot.totalPrice`

## 10.2 Physical Mapping

The amount SHALL map to:

`Booking.totalAmount`

The currency SHALL map independently to:

`Booking.currencyId`

## 10.3 Constraint

Persistence MUST NOT:

- recalculate the amount;
- derive the amount from supplier prices;
- alter the domain pricing result.

---

# 11. Traveller Snapshot Decision

## 11.1 Canonical Domain Contract

The active Reservation contains:

`travellerSnapshots: ReadonlyArray<TravellerSnapshot>`

This collection is authoritative.

## 11.2 Cardinality

The persistence contract SHALL preserve:

**one-to-many ordered Traveller snapshots**

The physical representation MUST support:

- zero or more snapshots;
- deterministic order;
- complete snapshot data.

## 11.3 Ownership

Traveller snapshots are owned by the Reservation.

They are historical Reservation state.

They are NOT live Traveller foreign-key relationships.

## 11.4 Physical Representation

The physical Reservation root SHALL persist the Traveller snapshot collection as Reservation-owned snapshot data.

The exact physical JSON field/model representation SHALL be defined by 3I.

3H establishes the contract only.

## 11.5 Immutability

Changing the independent Traveller aggregate MUST NOT retroactively modify a persisted Reservation Traveller snapshot.

---

# 12. Journey Snapshot Decision

## 12.1 Canonical Contract

The active Reservation contains a Journey snapshot.

The Journey snapshot is Reservation-owned historical state.

## 12.2 Persistence Boundary

The Reservation persistence contract SHALL preserve the Journey snapshot directly.

No live Journey foreign-key dependency is required for Reservation reconstruction.

## 12.3 Constraint

This decision does NOT create:

- Prisma Journey;
- Journey repository;
- Journey aggregate persistence.

## 12.4 Immutability

Changes to package, itinerary or future Journey structures MUST NOT retroactively alter the persisted Reservation Journey snapshot.

---

# 13. Reservation Persistence Context

## 13.1 Decision

The existing:

`IReservationRepository.save(Reservation)`

contract is insufficient for Booking-root persistence.

An explicit persistence context SHALL accompany Reservation persistence.

## 13.2 Ownership

The context belongs at the application → repository boundary.

It MUST remain persistence-neutral.

It MUST NOT contain Prisma models or Prisma-generated types.

## 13.3 Canonical Context

The conceptual contract is:

`ReservationPersistenceContext`

Required information:

- Customer identity;
- reservation number;
- Booking dates;
- Booking/commercial context required by persistence;
- final GCT currency;
- any existing package/itinerary association required by the active Reservation contract.

The Reservation aggregate remains separate from this context.

## 13.4 Lifecycle

The context SHALL be available for create and update persistence operations.

The context MUST NOT become a second Reservation aggregate.

---

# 14. Booking Status Context

The existing Booking status is not the GCT Reservation lifecycle.

Therefore the persistence context MAY contain the Booking/commercial status required by the existing physical model, but this value MUST remain separate from `ReservationStatus`.

If the Booking status can be derived safely from an existing application rule, infrastructure MAY derive it.

If it requires application input, the context SHALL carry it.

3I MUST use the actual existing Booking status contract and MUST NOT invent a new commercial status mapping.

---

# 15. Create Semantics

Reservation creation SHALL follow:

1. Application receives/create Reservation request.
2. Application establishes Customer context.
3. Application establishes Reservation number.
4. Application establishes final pricing.
5. Application establishes Booking dates.
6. Application establishes Reservation lifecycle.
7. Application constructs Traveller snapshots.
8. Application constructs Journey snapshot.
9. Application constructs accommodation snapshots.
10. Application passes Reservation plus persistence context to the repository.
11. Repository persists Booking and Reservation-owned state.

The repository MUST NOT invent missing business information.

---

# 16. Update Semantics

Reservation updates SHALL receive the same authoritative Reservation contract and required persistence context.

Updates MUST preserve:

- Reservation identity;
- reservation number;
- Traveller snapshots unless explicitly amended;
- Journey snapshot unless explicitly amended;
- historical accommodation state;
- final GCT pricing according to the domain lifecycle;
- supplier operational state.

The repository MUST NOT silently derive or replace domain state.

---

# 17. Retrieval Semantics

Reservation retrieval SHALL return the complete active Reservation aggregate contract.

The repository MUST load sufficient persistence state to reconstruct:

- identity;
- reservation number;
- Reservation lifecycle;
- Traveller snapshots;
- Journey snapshot;
- PricingSnapshot;
- accommodation snapshots;
- supplier references;
- timeline/metadata.

Retrieval MUST NOT require:

- live Hotelbeds calls;
- live catalogue calls;
- Customer reconstruction;
- Traveller reconstruction.

---

# 18. Reservation Query Graph

The physical query graph required by 3I SHALL include all persistence structures necessary to reconstruct the active Reservation.

At minimum this includes:

- Booking;
- Reservation lifecycle;
- Traveller snapshots;
- Journey snapshot;
- accommodation stops;
- rooms;
- occupancy;
- supplier pricing;
- supplier/provider references;
- supplier booking state;
- existing timeline/metadata required by the domain.

3I MUST derive the exact Prisma include/select graph from the active schema.

---

# 19. Round-Trip Contract

The following invariant SHALL hold:

`Reservation`
→ persistence
→ retrieval
→ `Reservation`

The resulting aggregate MUST preserve all information represented by the active Reservation contract.

At minimum:

- identity remains unchanged;
- reservation number remains unchanged;
- lifecycle remains unchanged;
- Traveller snapshot collection remains unchanged;
- Journey snapshot remains unchanged;
- pricing remains unchanged;
- accommodation snapshots remain unchanged;
- supplier references/state remain unchanged.

- [ ] Final amount maps from `PricingSnapshot.totalPrice`.
- [ ] Currency maps from `PricingSnapshot.currency`.
- [ ] Traveller snapshots remain an ordered collection.
- [ ] Traveller snapshots remain Reservation-owned historical state.
- [ ] Journey remains an immutable Reservation snapshot.
- [ ] No Journey physical aggregate is introduced.

- [ ] Round-trip preservation is mandatory.
