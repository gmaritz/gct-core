# 2. Purpose

Implement the accepted Reservation persistence contract defined by PERSISTENCE-B3H.

The implementation SHALL:

- persist the active Reservation aggregate through Prisma `Booking`;
- introduce the approved Reservation persistence context;
- persist the Reservation number;
- persist the GCT Reservation lifecycle separately from Booking/supplier status;
- persist ordered Traveller snapshots;
- persist the Journey snapshot;
- persist accommodation snapshots;
- persist room occupancy and child ages;
- persist supplier pricing separately from GCT pricing;
- persist per-stop supplier booking state;
- provide fully typed Reservation mapper/repository persistence handling;
- preserve complete Reservation round-trip reconstruction.

The domain Reservation MUST remain the authority.

# 4. Canonical Reservation Root

Prisma `Booking` SHALL be the physical commercial Reservation root.

Mapping:

- `Reservation.identity.id` → `Booking.id`
- `Reservation.reservationNumber` → `Booking.bookingNumber`
- Reservation lifecycle → dedicated physical Reservation lifecycle field
- final GCT amount → `Booking.totalAmount`
- final GCT currency → `Booking.currencyId`

The existing Prisma `Reservation` remains the supplier operational reservation.

Do not reinterpret the operational `Reservation` as the GCT Reservation aggregate.

---

# 5. Reservation Number

Add `reservationNumber` to the active Reservation application/domain contract where required by the current aggregate representation.

Rules:

- generated by the application at Reservation creation;
- unique;
- immutable after creation;
- returned by creation/retrieval;
- persisted as `Booking.bookingNumber`;
- usable by `findByReservationNumber()`.

Do not generate it implicitly in Prisma.

Do not introduce a second physical reservation-number field.

If an existing reservation-number generation convention exists, reuse it.

If none exists, STOP and report:

`BLOCKED — RESERVATION NUMBER GENERATION CONTRACT`

Do not invent a numbering algorithm.

---

# 6. Reservation Persistence Context

Introduce the persistence-neutral application/repository boundary concept:

`ReservationPersistenceContext`

It SHALL provide the information required by Booking persistence that is not part of the Reservation aggregate.

Required fields:

- `customerId`
- `bookingStartDate`
- `bookingEndDate`
- Booking/commercial status context where required by the existing Booking model
- package/itinerary association where required by the active application contract

The context MUST NOT contain:

- Prisma models;
- Prisma-generated types;
- database clients.

The context MUST NOT become a second Reservation aggregate.

---

# 7. Repository Contract

Extend the Reservation repository contract only as required to carry the approved persistence context.

Create/update persistence SHALL conceptually support:

`save(reservation, context)`

The exact TypeScript signature MUST follow existing repository conventions.

The public contract MUST remain persistence-neutral.

Prisma types MUST NOT leak into:

- domain;
- application commands;
- application services;
- repository interfaces.

---

# 8. Customer Context

`customerId` SHALL originate from the application workflow.

The repository SHALL persist it to:

`Booking.customerId`

Rules:

- Customer identity is required;
- no implicit Customer creation;
- no email-based Customer inference;
- no BookingContact substitution;
- no Customer redesign.

If the active Reservation creation workflow cannot supply Customer identity, STOP and report:

`BLOCKED — CUSTOMER CONTEXT`

# 9. Booking Status

Existing Booking status remains separate from the GCT Reservation lifecycle.

Do not map the complete Reservation lifecycle onto the existing Booking status.

If the existing Booking status is required by Prisma, preserve its existing semantics and obtain it through the approved persistence context or existing infrastructure rule.

Do not redesign Booking status.

---

# 10. GCT Reservation Lifecycle

Persist the authoritative domain `ReservationStatus` separately.

Required values:

- `CREATED`
- `QUOTED`
- `CONFIRMED`
- `AMENDED`
- `CANCELLED`
- `COMPLETED`

Implement the minimum Prisma enum/field required to persist this lifecycle.

The field belongs to the physical Booking Reservation root.

Supplier Reservation status remains separate.

---

# 11. Booking Dates

The persistence context SHALL provide:

- `bookingStartDate`
- `bookingEndDate`

These are Booking-level Reservation dates.

They MUST NOT be reconstructed by querying accommodation stops.

Journey dates MAY contribute to context construction, but the repository persists explicit Booking dates.

---

# 12. Final GCT Price

The authoritative source is:

`PricingSnapshot.totalPrice`

Persist:

- amount → `Booking.totalAmount`
- currency → `Booking.currencyId`

Persistence MUST NOT:

- recalculate pricing;
- derive GCT price from supplier pricing;
- alter the pricing result.

---

# 13. Traveller Snapshots

The active Reservation contract contains:

`travellerSnapshots: ReadonlyArray<TravellerSnapshot>`

Preserve this cardinality.

The physical representation SHALL be an ordered Reservation-owned snapshot collection.

Each snapshot MUST be independently identifiable and have deterministic ordering.

The snapshot MUST contain the information required to reconstruct the active `TravellerSnapshot`.

Do NOT:

- replace snapshots with a Traveller foreign key;
- use BookingContact;
- modify Customer;
- modify the Traveller aggregate;
- retroactively update snapshots from Traveller changes.

Use a dedicated Reservation-owned persistence structure or JSON representation only if it preserves the complete collection and ordering.

---

# 14. Journey Snapshot

The active Reservation contains a Journey snapshot.

Persist the Journey snapshot as Reservation-owned historical state.

Do NOT:

- create Prisma Journey;
- create Journey repository;
- create Journey foreign key;
- infer Journey identity from Package/Itinerary.

The physical representation MUST preserve sufficient information to reconstruct the active Journey snapshot.

---

# 15. Accommodation Snapshot Root

Create the minimum Reservation-owned accommodation stop structure required by APP-004.

Each stop MUST contain:

- `id`
- `bookingId`
- `packageId` where present in the active snapshot
- `packageStopId`
- `stopOrder`
- property snapshot
- check-in
- check-out
- supplier amount
- supplier currency
- pricing basis
- provider
- supplier booking reference
- supplier booking state
- created/updated timestamps

`stopOrder` MUST be deterministic and unique within the Booking.

Do not flatten stops into Booking.

---

# 16. Property Snapshot

Persist the selected property as historical Reservation data.

The representation MUST preserve the property identity and descriptive information required by the active `AccommodationSnapshot`.

Catalogue references MAY be retained but MUST NOT be the sole source for historical reconstruction.

Do not duplicate the entire accommodation catalogue.

---

# 17. Room Persistence

Each accommodation stop SHALL support one or more rooms.

Each room MUST preserve:

- room reference;
- room snapshot;
- rate reference;
- rate snapshot;
- adults;
- children;
- child ages.

Multiple rooms MUST remain independently identifiable.

Supplier room/rate references remain opaque.

---

# 18. Occupancy

Occupancy is room-level.

Rules:

- adults is a non-negative integer according to the existing accommodation contract;
- children is a non-negative integer;
- `childAges.length === children`;
- when children is zero, child ages is empty.

Do not replace room occupancy with Booking-level totals.

---

# 19. Supplier Pricing

Each accommodation stop SHALL persist:

- supplier amount;
- supplier currency;
- pricing basis.

Supplier pricing is separate from:

`Booking.totalAmount`.

No pricing calculation occurs during persistence.

---

# 20. Supplier Booking State

Supplier booking state belongs to each accommodation stop.

Required states:

- `PENDING`
- `REVALIDATION_REQUIRED`
- `VALIDATED`
- `BOOKING_ATTEMPTED`
- `CONFIRMED`
- `FAILED`
- `UNKNOWN`

Each stop may independently retain:

- provider;
- supplier booking reference;
- state;
- operational timestamps.

Supplier state updates MUST NOT overwrite immutable accommodation selection data.

---

# 21. Reservation Mapper

`reservation.mapper.ts` SHALL become fully typed.

It MUST support:

- domain → persistence;
- persistence → domain.

It MUST reconstruct:

- identity;
- reservation number;
- lifecycle;
- Traveller snapshots;
- Journey snapshot;
- PricingSnapshot;
- accommodation snapshots;
- supplier references;
- supplier state;
- existing Reservation timeline/metadata.

No `any` is permitted.

No `Record<string, any>` is permitted.

No suppression directives are permitted.

Use explicit persistence types and Prisma-generated payload types where appropriate.

# 22. Reservation Repository

`ReservationPrismaRepository` SHALL implement the approved repository contract.

The repository MUST:

- persist Booking root;
- persist Reservation context;
- persist snapshots;
- persist accommodation stops and rooms;
- persist supplier state;
- retrieve the complete Reservation graph.

The repository query graph MUST load every relation required by the mapper.

Do not type a relation-rich query as the base Prisma model.

# 24. Update Behaviour

Updates MUST preserve:

- Reservation identity;
- reservation number;
- Traveller snapshots unless explicitly amended;
- Journey snapshot unless explicitly amended;
- accommodation selection snapshots;
- final GCT price according to domain rules.

- supplier booking state;
- supplier booking reference;
- operational timestamps.

Do not silently overwrite historical selection data.

- rooms;
