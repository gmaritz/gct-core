## 2. Purpose

This document establishes the target architecture for accommodation availability within GCT Core.

The architecture is based on the actual Go Cape Tours business requirement:

- GCT sells private multi-day package tours.
- Packages range from approximately three to ten days.
- Packages contain multiple overnight stops.
- Each stop has a predetermined selection of approximately six to ten GCT-approved accommodation properties.
- Properties are generally four- and five-star establishments.
- Accommodation availability is obtained from one or more external accommodation suppliers.
- The first supplier integration is Hotelbeds.
- Clients may select both the accommodation property and room type.
- Clients may choose between multiple available rates for a room.
- The selected accommodation at every stop contributes to the final package price.
- GCT applies its own package pricing and sliding-scale per-person pricing.
- Accommodation supplier pricing is an input to package pricing, not the package price itself.
- The complete package accommodation availability is searched across all stops.
- Future suppliers must be supported without changing the canonical model.
- Selected accommodation must remain traceable through revalidation and eventual booking.

This architecture deliberately prevents Hotelbeds from becoming the canonical accommodation model.

---

## 3. Architectural Decision

GCT Core will model accommodation availability as a supplier-neutral commercial option capability within package search.

The architectural flow is:

Package Definition
→ Package Stops
→ GCT Approved Accommodation
→ Package Accommodation Search
→ Supplier Availability
→ Canonical Accommodation Options
→ Client Accommodation Selection
→ Package Pricing
→ Availability Revalidation
→ Supplier Booking

Accommodation availability is therefore not an isolated hotel lookup.

It is an input to the configuration and pricing of a GCT package.

## 4. Business Context

### 4.1 Package Structure

A GCT package consists of multiple journey stops.

Example:

    Package
    ├── Stop 1 — Stellenbosch
    ├── Stop 2 — Hermanus
    ├── Stop 3 — Oudtshoorn
    └── Stop 4 — Knysna

Each stop has its own accommodation configuration.

### 4.2 GCT Accommodation Selection

GCT, not the supplier, determines which properties are commercially offered for a package stop.

Example:

    Stop: Stellenbosch

    Approved Properties
    ├── Hotel A
    ├── Hotel B
    ├── Hotel C
    ├── Hotel D
    ├── Hotel E
    └── Hotel F

The supplier is queried only for the configured properties.

GCT does not delegate package accommodation product definition to Hotelbeds.

### 4.3 Client Selection

The client may select:

1. accommodation property;
2. room type;
3. available rate.

Example:

    Stop: Stellenbosch

    Hotel A
    ├── Standard Room
    │   ├── Flexible Rate
    │   └── Non-refundable Rate
    └── Luxury Room
        ├── Flexible Rate
        └── Non-refundable Rate

The client may therefore select:

    Hotel A → Luxury Room → Flexible Rate

### 4.4 Package Pricing

Supplier accommodation pricing is an input to package pricing.

Conceptually:

    Package Price
    =
    GCT Package Base Price
    +
    Selected Accommodation Components
    +
    Other Package Pricing Components
    +
    GCT Pricing Rules

The accommodation capability must not calculate or own the complete package price.

## 5. Architectural Principles

### 5.1 Supplier Neutrality

The canonical model must not represent Hotelbeds.

Hotelbeds-specific structures remain inside the Hotelbeds adapter.

Examples of supplier-specific data that must not become canonical field names:

- rateKey;
- rateType;
- rateClass;
- hotels.hotels;
- supplier-specific tax structures;
- supplier-specific cancellation structures;
- supplier-specific payment codes.

### 5.2 GCT Owns Product Definition

GCT determines:

- which packages exist;
- which stops exist;
- which accommodation properties are approved;
- which properties are presented to clients.

Suppliers provide inventory and commercial availability for those properties.

### 5.3 Availability Is Dynamic

Accommodation identity and static content are separate from dynamic availability.

Static accommodation:

- identity;
- name;
- category;
- location;
- content;
- amenities;
- descriptive information.

Dynamic availability:

- room options;
- rates;
- prices;
- occupancy;
- board;
- cancellation;
- taxes;
- payment;
- booking references;
- availability status.

### 5.4 Client Choice Is First-Class

The architecture must preserve all commercially relevant options required for the client to make a selection.

The system must not reduce availability to:

- cheapest rate;
- first rate;
- one preferred room;
- one hotel;
- availability boolean.

### 5.5 Multiple Suppliers

The canonical capability must support:

    Accommodation Availability
    ├── Hotelbeds
    ├── Supplier B
    ├── Supplier C
    └── Future Suppliers

Supplier selection, fallback, and aggregation remain application/provider concerns.

### 5.6 Booking Continuity

A selected accommodation option must remain identifiable through:

- package configuration;
- pricing;
- confirmation;
- revalidation;
- booking.

Supplier-specific references are retained as opaque values.

### 5.7 No Fabricated Availability

A supplier no-availability response must not fabricate an accommodation, room, rate, price, or booking reference.

---

## 6. Domain Boundaries

The accommodation architecture is divided into the following responsibilities.

### 6.1 Package Accommodation Configuration

Owns the GCT-defined accommodation offering for a package stop.

Responsibilities:

- package-stop accommodation associations;
- approved properties;
- property ordering;
- active/inactive configuration;
- GCT commercial eligibility.

Does not own live supplier availability.

### 6.2 Accommodation Availability

Owns:

- availability search request;
- supplier availability retrieval;
- canonical accommodation availability options;
- room options;
- rate options;
- dynamic commercial conditions.

Does not own:

- complete package pricing;
- package definition;
- customer booking;
- supplier transport.

### 6.3 Package Configuration / Selection

Owns the client's selected package options.

Responsibilities:

- selected accommodation per stop;
- selected property;
- selected room;
- selected rate;
- package configuration state.

### 6.4 Pricing

Owns:

- package pricing;
- GCT pricing rules;
- sliding-scale pricing;
- accommodation cost incorporation;
- final customer price.

Accommodation Availability provides pricing inputs but does not calculate the complete package price.

### 6.5 Reservations / Booking

Owns:

- booking;
- supplier booking requests;
- booking references;
- booking status;
- booking lifecycle.

The selected availability offer supplies the information required to initiate booking.

## 7. End-to-End Business Flow

    1. GCT defines package
            ↓
    2. GCT defines package stops
            ↓
    3. GCT assigns approved accommodation properties to each stop
            ↓
    4. Client searches package
            ↓
    5. GCT builds accommodation search for all stops
            ↓
    6. Supplier availability is requested
            ↓
    7. Supplier responses are translated into canonical availability
            ↓
    8. Complete accommodation options are returned for all stops
            ↓
    9. Client selects property + room + rate at each stop
            ↓
    10. Selected accommodation is incorporated into package pricing
            ↓
    11. Client confirms package
            ↓
    12. Selected accommodation offers are revalidated
            ↓
    13. Selected supplier offers are booked

## 8. Package Accommodation Configuration

A package stop may contain an ordered collection of approved accommodation properties.

Conceptually:

    PackageAccommodationConfiguration

    package
    stop
    properties[]

Each configured property represents a GCT-approved accommodation option.

Minimum conceptual information:

- package identifier;
- stop identifier;
- accommodation identifier;
- display/order information;
- active status;
- commercial eligibility.

The configuration must reference the canonical accommodation entity rather than supplier-specific identifiers where possible.

Supplier identifiers remain provider-specific mapping data.

---

## 9. Accommodation Candidate Selection

At search time, the system resolves the configured properties for each package stop.

Example:

    Stop 1
    Candidate Hotels: A, B, C, D, E, F

    Stop 2
    Candidate Hotels: G, H, I, J, K

    Stop 3
    Candidate Hotels: L, M, N, O, P, Q

These candidates are passed into the canonical availability request.

The supplier adapter translates them into supplier-specific property filters.

The canonical model must never require a Hotelbeds hotel-code collection.

---

## 10. Canonical Accommodation Availability Request

The canonical request represents the client's accommodation requirements independently of the supplier.

Conceptual structure:

    AccommodationAvailabilityRequest

    packageContext
    stopContext
    stay
    occupancy
    sourceMarket
    candidateAccommodations[]

### 10.1 Stay

The stay contains:

- check-in date;
- check-out date.

### 10.2 Occupancy

The canonical occupancy must support multiple rooms.

Conceptually:

    OccupancyRequest

    rooms[]

    RoomOccupancy

    adults
    children
    childAges[]

Each room is independently represented.

Example:

    Room 1
    2 adults
    1 child
    child age: 7

    Room 2
    2 adults
    0 children

Aggregate totals must not replace the individual room groups.

### 10.3 Candidate Accommodations

The request identifies the GCT-approved accommodation candidates for the stop.

The canonical request does not contain supplier-specific hotel filters.

---

## 11. Package-Level Availability Search

A package search must be capable of searching accommodation for all stops.

Conceptually:

    PackageAccommodationAvailabilitySearch

    package
    stops[]

    StopAccommodationAvailabilitySearch

    stop
    stay
    occupancy
    candidateAccommodations[]

Each stop may have different:

- dates;
- approved properties;
- availability;
- room options;
- rates.

The result must retain stop identity so that accommodation options cannot become detached from the package itinerary.

---

## 12. Canonical Search Result

The canonical package accommodation availability result is a collection of stop-specific availability results.

Conceptually:

    PackageAccommodationAvailabilityResult

    stops[]

Each stop contains:

    StopAccommodationAvailabilityResult

    stop
    results[]

Each result represents one accommodation property.

    AccommodationAvailabilityResult

    kind
    accommodation
    availabilityOptions
    requestedOccupancy
    metadata

The result is therefore hierarchical:

    Package
    └── Stop
        └── Accommodation
            └── Room Option
                └── Rate Option

---

## 13. Availability Result States

Availability results use explicit discriminated states.

### 13.1 Accommodation Result

    kind = ACCOMMODATION

Requirements:

- accommodation exists;
- availability options exist;
- room/rate options represent actual supplier availability;
- requested occupancy is preserved.

### 13.2 No Availability

    kind = NO_AVAILABILITY

Requirements:

- available = false;
- no fabricated accommodation;
- no fabricated room;
- no fabricated rate;
- no fabricated price;
- no fabricated supplier reference.

A no-availability result may be used when a specific configured property has been searched and the supplier confirms no availability.

### 13.3 Search-Level Empty Result

If no configured properties produce a result for a stop, the stop result may contain an empty result collection.

This must remain distinguishable from a property-level NO_AVAILABILITY.

---

## 14. Accommodation Result

A positive accommodation result contains stable accommodation information.

The `Accommodation` entity remains supplier-neutral and should contain appropriate stable information such as:

- identity;
- name;
- category;
- location;
- rating;
- provider reference;
- static content where applicable.

Dynamic room/rate availability must not be embedded into `Accommodation`.

---

## 15. Availability Options

Dynamic accommodation options are represented separately.

Conceptually:

    AvailabilityOptions

    roomOptions[]

The collection preserves the supplier's commercially available room choices after canonical translation.

No supplier DTO is exposed.

---

## 16. Room Option

A `RoomOption` represents a selectable room type offered for the accommodation.

Minimum conceptual properties:

- canonical room reference;
- display name;
- rate options.

Conceptually:

    RoomOption

    reference
    name
    rateOptions[]

A room option represents a room type, not an arbitrary supplier response object.

Room options must retain their relationship to their rates.

---

## 17. Rate Option

A `RateOption` represents a selectable commercial rate associated with a room option.

Conceptually:

    RateOption

    bookingReference
    status
    pricing
    occupancy
    board
    allotment
    payment
    packaging
    cancellationPolicies[]
    taxes[]

A rate must never be detached from its room option.

---

## 18. Rate Status

The canonical status must represent the business meaning rather than supplier-specific codes.

At minimum the architecture must support:

    BOOKABLE
    RECHECK_REQUIRED

Supplier-specific status values are translated by the supplier adapter.

A provider may introduce additional internal statuses, but those must not leak into the canonical model without an explicit architectural decision.

---

## 19. Supplier References

Supplier references are opaque canonical values.

Conceptually:

    SupplierReference

    provider
    opaqueReference

The canonical model must not call the opaque value `rateKey`.

For Hotelbeds:

    provider = HOTELBEDS
    opaqueReference = supplier rate reference

The Hotelbeds adapter owns interpretation of that value.

A selected rate reference must remain sufficient to identify the supplier offer in combination with its canonical room/accommodation context.

---

## 20. Room References

Room references must also remain supplier-neutral.

A room reference may contain:

- provider;
- opaque reference.

The canonical model must not require a Hotelbeds-specific room-code field.

If a supplier's rate reference already uniquely identifies the room/rate combination, the provider may use that relationship internally, but the canonical model must preserve the room option selected by the client.

---

## 21. Occupancy

Two distinct occupancy concepts are required.

### 21.1 Requested Occupancy

The occupancy submitted by the client.

    requestedOccupancy

    rooms[]

### 21.2 Offered Occupancy

The occupancy represented by an available rate.

    RateOption

    occupancy

Offered occupancy must preserve:

- room quantity/context;
- adults;
- children;
- child ages.

The architecture must not collapse child ages into an aggregate child count.

---

## 22. Multiple Rooms

Multi-room searches are first-class.

The canonical model must support:

    Room 1
    2 adults + child age 7

    Room 2
    2 adults

    Room 3
    1 adult + 1 child age 10

No canonical contract may assume one room.

Any current R3 or R8 one-room implementation restriction is an implementation limitation and must not define the target architecture.

---

## 23. Pricing

Pricing returned by accommodation availability represents the supplier's accommodation commercial offer.

It does not represent the complete GCT package price.

The canonical rate pricing must contain:

- amount;
- currency;
- pricing basis;
- tax inclusion semantics.

The architecture must support precise monetary handling and must not rely on arbitrary floating-point calculations for commercial totals.

Where the existing shared Money model is insufficient, it must be evolved as a shared canonical pricing primitive rather than creating an isolated Hotelbeds money type.

---

## 24. Pricing Basis

The pricing basis must explicitly describe what the amount represents.

The architecture must support at minimum:

    TOTAL_STAY

Additional bases may be introduced if required by the broader pricing architecture.

A raw amount without a defined basis is not a valid canonical rate price.

---

## 25. Net, Customer Price and Package Price

These are different concepts.

### Supplier Accommodation Price

The amount returned by the supplier and mapped into the canonical accommodation offer.

### GCT Accommodation Commercial Price

The amount GCT chooses to use for its own package pricing.

### Final Package Price

The total customer price after applying GCT's package pricing model.

The accommodation availability capability must not silently convert supplier price into final package price.

---

## 26. Currency

Currency is part of the canonical monetary representation.

The architecture must not assume that Hotelbeds' current currency set represents the complete GCT currency universe.

Currency representation must therefore be supplier-neutral and sufficiently extensible for supported commercial currencies.

---

## 27. Hotel-Level Minimum and Maximum Rates

Supplier-level `minRate` and `maxRate` values are treated as summaries.

They must not replace the individual room/rate prices.

The canonical architecture may retain derived summary pricing where commercially useful, but:

- individual rate prices remain authoritative;
- min/max values must be derivable from the available options;
- conflicting supplier summary values must not override rate-level prices.

---

## 28. Board / Meal Plan

Board information is part of the rate option.

The canonical concept must support:

- stable board code/reference where appropriate;
- display name;
- supplier-neutral semantics.

Hotelbeds board codes remain adapter data.

Example canonical concepts may include:

- ROOM_ONLY;
- BREAKFAST;
- HALF_BOARD;
- FULL_BOARD;
- ALL_INCLUSIVE.

Additional values must be handled explicitly rather than silently mapped to an incorrect category.

---

## 29. Allotment

Allotment represents supplier-reported availability capacity associated with the rate.

It may be retained as canonical availability information where commercially useful.

Allotment must not be interpreted as:

- package inventory;
- GCT inventory;
- guaranteed booking capacity beyond supplier semantics.

The provider owns supplier-specific interpretation.

---

## 30. Payment

Payment conditions are part of the rate option when they affect booking selection.

The canonical model must represent commercially meaningful distinctions such as:

- pay at property;
- pay supplier;
- prepayment;
- other provider-defined payment condition.

Supplier-specific payment codes must remain inside adapters.

If a supplier value cannot be mapped safely to a canonical payment condition, it must not be silently misclassified.

---

## 31. Packaging

Packaging information is retained only where it has commercial or booking significance.

A simple boolean may be insufficient if the supplier indicates that services or pricing are bundled.

The canonical model must therefore distinguish:

- whether packaging applies;
- relevant canonical packaging semantics where required.

Supplier-specific package structures remain provider-specific.

---

## 32. Cancellation Policies

Cancellation policies belong to the rate, not the static accommodation.

A rate may contain multiple ordered cancellation rules.

Each policy must be capable of representing:

- effective date/time;
- penalty amount;
- penalty currency;
- refundability semantics;
- applicable conditions.

Timezone information must not be discarded when it affects the cancellation deadline.

The canonical model must distinguish:

- refundable;
- partially refundable;
- non-refundable.

Supplier-specific cancellation structures remain adapter-specific.

---

## 33. Taxes and Fees

Taxes and fees belong to the rate offer.

The canonical representation must support:

- amount;
- currency;
- type;
- subtype where commercially meaningful;
- percentage where supplied;
- included/excluded status;
- tax/fee classification.

The model must prevent double-counting when constructing package prices.

Supplier-specific tax envelopes are translated inside the provider adapter.

---

## 34. Availability Selection

The client selection is a business object separate from the availability response.

A selection identifies:

    Package Stop
    → Accommodation
    → Room
    → Rate

The selected option must retain sufficient information for:

- package pricing;
- client confirmation;
- revalidation;
- supplier booking.

The selection must not require the application to reparse the original supplier response.

---

## 35. Selection Snapshot

Once a client selects an accommodation option, the application must preserve the relevant commercial selection state.

At minimum this includes:

- package stop;
- accommodation;
- room;
- rate;
- supplier/provider;
- opaque supplier reference;
- selected occupancy;
- selected pricing;
- applicable cancellation/payment conditions required by the booking workflow.

This is a selection snapshot, not merely a reference to a volatile availability result.

---

## 36. Revalidation

Availability data is dynamic.

Before final booking, selected accommodation options must be revalidated where required.

Revalidation must be capable of determining whether:

- the selected room remains available;
- the selected rate remains available;
- the price changed;
- cancellation conditions changed;
- payment conditions changed;
- the supplier reference remains valid.

A `RECHECK_REQUIRED` rate must not be treated as a guaranteed final booking price without the appropriate revalidation process.

---

## 37. Booking Continuity

The booking process must consume the selected canonical offer.

Conceptually:

    Package Selection
            ↓
    Selected Accommodation Offer
            ↓
    Revalidation
            ↓
    Supplier Booking Request

The supplier adapter translates:

- accommodation;
- room;
- rate;
- opaque supplier reference;
- occupancy;
- applicable booking conditions

into the supplier-specific booking request.

The booking domain must not need to understand Hotelbeds response structures.

---

## 38. Supplier Abstraction

The accommodation availability capability exposes a supplier-neutral provider contract.

Conceptually:

    AccommodationAvailabilityProvider

    search(request)

The provider contract operates on canonical request and canonical availability structures.

Supplier-specific adapters implement that contract.

Example:

    AccommodationAvailabilityProvider
    ├── HotelbedsAvailabilityProvider
    ├── FutureSupplierAvailabilityProvider
    └── FutureSupplierAvailabilityProvider

---

## 39. Hotelbeds Adapter Boundary

Hotelbeds translation is isolated to the provider adapter.

The adapter owns:

- Hotelbeds request structure;
- Hotelbeds authentication;
- Hotelbeds transport integration;
- Hotelbeds response envelope;
- Hotelbeds room structures;
- Hotelbeds rate structures;
- Hotelbeds rate keys;
- Hotelbeds tax structures;
- Hotelbeds cancellation structures;
- supplier-specific payment/packaging structures.

The adapter translates these into the canonical GCT availability model.

No Hotelbeds response structure becomes the canonical architecture.

---

## 40. Multiple Supplier Strategy

The architecture supports future supplier aggregation.

A future implementation may:

1. query one supplier;
2. query multiple suppliers;
3. use supplier priority;
4. use supplier fallback;
5. combine supplier offers.

The canonical result remains supplier-neutral.

Supplier selection and aggregation rules belong to the application/provider orchestration layer, not to the canonical domain objects.

---

## 41. Supplier Deduplication

If multiple suppliers return the same accommodation, the architecture must preserve provider identity on offers.

The application must not silently merge offers from different suppliers into one rate.

Two supplier offers may represent the same room type but remain separate commercial offers.

Example:

    Hotel A
    └── Luxury Room
        ├── Supplier A — Rate 1
        └── Supplier B — Rate 1

The client/application may later apply commercial selection rules, but provider identity must remain available for booking continuity.

---

## 42. Package Pricing Boundary

Accommodation availability supplies accommodation offer prices.

Package pricing consumes selected accommodation prices.

The package pricing model remains responsible for:

- base package price;
- per-person pricing;
- group-size/sliding-scale rules;
- accommodation adjustments;
- other package components;
- margins/markups;
- final customer price.

The accommodation supplier integration must not implement GCT's sliding-scale package pricing.

---

## 43. Accommodation Pricing Repository

GCT may maintain its own pricing configuration for packages.

This repository is distinct from supplier availability.

It may contain:

- package pricing rules;
- per-person base prices;
- group-size pricing;
- accommodation pricing adjustments;
- package-specific commercial rules.

Supplier availability prices are runtime inputs.

They must not overwrite GCT's package pricing configuration.

---

## 44. Search-Time Pricing

At package search time:

1. GCT retrieves package pricing configuration.
2. GCT resolves configured accommodation candidates.
3. Availability is obtained for all package stops.
4. Available room/rate options are returned.
5. Client selects accommodation options.
6. Pricing calculates the package price using those selections.

This allows accommodation selection to affect package pricing without coupling Availability to the complete pricing engine.

---

The eventual client-facing package search must be capable of representing:

    Package Search Result

    Package
    ├── Stop 1
    │   ├── Accommodation A
    │   │   ├── Standard
    │   │   │   ├── Rate 1
    │   │   │   └── Rate 2
    │   │   └── Luxury
    │   │       ├── Rate 1
    │   │       └── Rate 2
    │   └── Accommodation B
    │       └── ...
    │
    ├── Stop 2
    │   ├── Accommodation C
    │   └── Accommodation D
    │
    └── Stop N

The package search result must preserve stop identity and option hierarchy.

## 49. R2-R8 Boundary Alignment

The existing APP-008.3 R2–R8 boundaries remain valid but are interpreted within this broader architecture.

### R2 — Candidate Resolution

Resolves the GCT-approved accommodation candidates.

Does not query supplier availability.

### R3 — Request Construction

Converts canonical accommodation search requirements into supplier-specific requests.

Does not define canonical business semantics.

### R4-C1 — Transport

Handles:

- HTTP;
- TLS;
- mTLS;
- supplier transport concerns.

Does not interpret accommodation data.

### R5 — Response Mapping

Converts supplier responses into the canonical accommodation availability model.

R5 must support:

- multiple accommodations;
- rooms;
- multiple rates;
- pricing;
- occupancy;
- cancellation;
- taxes;
- booking references.

### R6 — Execution Protection

Provides execution protection such as retry/idempotency behaviour where applicable.

Does not define accommodation semantics.

### R7 — Application Orchestration

Coordinates:

- search;
- aggregation;
- multi-stop results;
- supplier provider execution;
- canonical result assembly.

### R8 — Controlled Verification

Provides controlled integration verification.

R8 must not define production canonical semantics.

## 50. Existing Architecture Impact

The following existing concepts require reassessment against this architecture:

- `AccommodationAvailabilityResult`;
- `AccommodationRate`;
- `AccommodationRateResult`;
- `AccommodationOccupancy`;
- `AccommodationOccupancyGroup`;
- existing accommodation inventory services;
- journey accommodation composition;
- merchandising/application consumers;
- existing supplier reference models.

Existing models must not be extended merely to avoid replacement.

A model should be retained only where its responsibility matches this architecture.

---

## 51. Existing Availability Result

The existing single-accommodation availability result is not sufficient as the complete package accommodation search contract.

It may be retained as an internal building block only if its semantics remain valid.

The target architecture is the higher-level package/stop result:

    Package
    → Stop
    → Accommodation Results
    → Room Options
    → Rate Options

The final canonical specification must derive from this architecture rather than force the architecture into the existing result shape.

---

## 52. Existing AccommodationRate

`AccommodationRate` must not automatically become the canonical `RateOption`.

It may be reused or refactored if its responsibility aligns with the final canonical rate model.

It must not constrain the new availability architecture.

---

## 53. Existing AccommodationRateResult

`AccommodationRateResult` is a separate contract unless an explicit architecture review determines otherwise.

It must not be embedded into package accommodation availability simply because it already contains rates.

---

## 54. Inventory

Inventory services must preserve the complete canonical availability hierarchy when required.

Freezing/cloning logic must preserve:

- accommodation;
- requested occupancy;
- room options;
- rate options;
- pricing;
- booking references;
- cancellation;
- taxes;
- metadata.

No consumer may silently discard the information required for client selection or booking continuity.

---

## 55. Immutability

Canonical availability structures must be immutable after creation.

This includes:

- result collections;
- stop collections;
- accommodation options;
- room options;
- rate options;
- occupancy;
- pricing;
- cancellation policies;
- taxes;
- supplier references;
- metadata.

Nested arrays must not expose mutable internal state.

---

## 56. Serialization

Canonical availability must be serializable without exposing supplier DTOs.

The client-facing representation must express:

- stop;
- accommodation;
- room;
- rate;
- price;
- board;
- cancellation;
- relevant payment conditions;
- availability status.

Supplier-specific names and structures must not be required by the client.

---

## 57. Security

Supplier credentials and authentication artefacts remain transport/provider concerns.

The canonical availability model must never expose:

- API credentials;
- certificates;
- private keys;
- passphrases;
- authentication tokens;
- raw supplier request/response envelopes unless explicitly required by an internal secured diagnostic facility.

Opaque supplier booking references must be treated as controlled application data.

---

## 58. Failure Semantics

The architecture distinguishes:

### Supplier Unavailable

The supplier cannot provide availability due to transport, authentication, or supplier failure.

### Property No Availability

The supplier successfully responds but the configured property has no availability.

### Stop No Availability

No configured property produces a valid accommodation option for the stop.

### Package Accommodation Incomplete

One or more required package stops cannot produce valid accommodation options.

These states must not be collapsed into fabricated accommodation records.

---

## 59. Partial Availability

A package may have availability at some stops and not others.

Example:

    Stop 1 — AVAILABLE
    Stop 2 — AVAILABLE
    Stop 3 — NO_AVAILABILITY
    Stop 4 — AVAILABLE

The architecture must preserve this information.

Package-level application rules determine whether such a package is:

- unavailable;
- partially configurable;
- eligible for an alternative property/supplier;
- presented with a warning.

Accommodation Availability must report facts rather than invent package-level commercial decisions.

---

## 60. Ordering

Ordering must be deterministic.

Preserve:

- package stop order;
- GCT property order where applicable;
- room option order;
- rate option order.

Supplier ordering must not silently replace GCT's configured accommodation ordering unless explicitly defined by application rules.

---

## 61. Accommodation Eligibility

Only GCT-approved accommodation properties for the relevant package stop are eligible for package presentation.

Supplier-discovered properties outside the configured candidate set must not automatically become package options.

This protects:

- GCT product positioning;
- quality level;
- negotiated/commercial relationships;
- package consistency.

---

## 62. Quality Level

GCT currently focuses on four- and five-star properties.

The architecture must support GCT accommodation eligibility rules without encoding "four-star" or "five-star" into the supplier adapter.

Eligibility is a GCT business rule.

---

## 63. Search Performance

A package search may involve:

- multiple stops;
- 6–10 properties per stop;
- multiple suppliers;
- multiple room/rate options.

The architecture must therefore support controlled parallel supplier searches while preserving:

- stop identity;
- candidate identity;
- supplier identity;
- deterministic aggregation.

Performance optimisation must not alter canonical semantics.

---

## 64. Supplier Quotas

Supplier request limits, QPS restrictions, batching, retries, and rate limits remain provider/execution concerns.

They must not appear in the canonical package accommodation model.

The current Hotelbeds R2–R8 work may be retained where it remains compatible with this architecture.

---

## 65. Caching

Availability data is dynamic and potentially time-sensitive.

Any caching strategy must respect:

- supplier availability freshness;
- rate validity;
- cancellation conditions;
- supplier reference validity;
- package search lifetime.

Caching must never cause stale accommodation selections to be treated as guaranteed booking availability.

---

## 66. Recheck and Booking

A supplier may return an offer that requires recheck.

The canonical architecture preserves this status.

The application must not present a recheck-required offer as an unconditional booking guarantee.

At booking:

    Selected Offer
    → Revalidate
    → Confirm Current Offer
    → Update Price/Conditions if required
    → Book

The exact commercial response to a changed price belongs to the package/reservation workflow.

---

## 67. Architecture Decision: What Hotelbeds Is

Hotelbeds is:

- a supplier;
- a provider of accommodation inventory;
- a provider of room/rate availability;
- a provider of supplier booking references.

Hotelbeds is not:

- the package model;
- the canonical accommodation model;
- the canonical room model;
- the canonical rate model;
- the GCT pricing model;
- the GCT product catalogue.

---

## 68. Architecture Decision: What GCT Owns

GCT owns:

- package products;
- package stops;
- approved accommodation selections;
- customer accommodation selection;
- package pricing;
- customer-facing commercial presentation;
- booking orchestration.

Suppliers own:

- live inventory;
- room availability;
- rate availability;
- supplier pricing;
- supplier booking conditions;
- supplier booking references.

## 70. Architectural Invariants

The following are mandatory.

1. Hotelbeds must never define the canonical accommodation model.
2. GCT-approved accommodation properties define the package accommodation candidate set.
3. Availability must support multiple properties.
4. Availability must support multiple room types per property.
5. Availability must support multiple rates per room.
6. Multi-room occupancy must be first-class.
7. Child ages must be preserved.
8. Room-to-rate relationships must be preserved.
9. Supplier references must remain opaque.
10. Supplier-specific response structures must remain inside adapters.
11. Supplier accommodation prices must remain distinct from final GCT package prices.
12. Client accommodation selection must be explicitly represented.
13. Selected accommodation must survive into package pricing.
14. Selected accommodation must survive into revalidation.
15. Selected accommodation must support future booking.
16. No-availability must not fabricate accommodation data.
17. Multiple suppliers must be supported without changing the canonical model.
18. Static accommodation data must remain separate from dynamic availability.
19. Package stop identity must be preserved throughout the search.
20. Canonical availability structures must be immutable.
21. Supplier failures must not be represented as valid accommodation offers.
22. Current one-room implementation limitations must not constrain the target architecture.

## 76. Final Architectural Decision

GCT Core will implement Accommodation Availability as a supplier-neutral package accommodation capability.

The fundamental business model is:

    GCT Package
    → Package Stop
    → GCT Approved Accommodation
    → Supplier Availability
    → Room Options
    → Rate Options
    → Client Selection
    → Package Pricing
    → Revalidation
    → Booking

Hotelbeds is the initial supplier adapter.

The canonical model will represent the GCT commercial requirement rather than the Hotelbeds response structure.

The architecture therefore deliberately separates:

- GCT product definition;
- supplier inventory;
- accommodation availability;
- client selection;
- package pricing;
- reservation/booking.

This decision is the architectural foundation for the next APP-008.3 implementation specifications.
