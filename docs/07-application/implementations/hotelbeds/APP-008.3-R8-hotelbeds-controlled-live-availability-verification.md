## 2. Purpose

APP-008.3-R8 performs the first controlled live verification of the complete accepted Hotelbeds Availability pipeline.

The verification SHALL exercise the real application path:

    R8 Controlled Verification Harness
        ↓
    R7 Application Availability Service
        ↓
    R2 Candidate Resolution
        ↓
    R3 Request Construction
        ↓
    R6 Supplier Protection
        ↓
    R4 mTLS Transport & Execution
        ↓
    Hotelbeds Availability
        ↓
    R5 Response Mapping
        ↓
    Canonical Availability Result

The purpose is to prove that the accepted architecture operates correctly against the real Hotelbeds supplier.

R8 SHALL remain a controlled verification exercise.

R8 SHALL NOT become a certification process.

---

## 3. Scope

### 3.1 In Scope

R8 SHALL:

- use the existing R8 test-only harness;
- support an explicitly configured list of Hotelbeds hotel codes;
- use the existing R7 application entrypoint;
- resolve hotel candidates through R2;
- construct Hotelbeds requests through R3;
- protect supplier execution through R6;
- execute through the corrected R4 mTLS transport;
- map responses through R5;
- return the existing canonical Availability result;
- perform a controlled live Hotelbeds test;
- verify multi-hotel request processing;
- preserve non-live automated-test safety.

### 3.2 Out of Scope

R8 MUST NOT implement:

- CheckRate;
- Booking;
- Cancellation;
- certification;
- persistence;
- daily quota accounting;
- room/rate expansion of the canonical result;
- alternative supplier execution paths;
- direct transport invocation from the harness;
- direct Hotelbeds request construction in the harness;
- production bootstrap changes;
- production catalogue modification;
- new retry logic;
- new QPS logic;
- new concurrency logic.

## 4. Live Verification Principle

The live supplier path SHALL be explicitly opt-in.

Normal application execution and normal automated regression MUST NOT make live Hotelbeds calls.

The live harness SHALL execute only when the operator explicitly enables it.

The live harness MUST fail closed when live verification is not explicitly enabled.

---

## 5. Live Enablement

The harness SHALL use:

    HOTELBEDS_AVAILABILITY_LIVE_VERIFY

Parsing rules:

| Value | Behaviour |
|---|---|
| absent | Disabled |
| empty | Disabled |
| `false` | Disabled |
| `0` | Disabled |
| `true` | Enabled |
| `1` | Enabled |
| any other non-empty value | Invalid and fail closed |

The flag MUST be evaluated before:

- live supplier configuration is used;
- provider construction for live execution;
- R7 invocation;
- any supplier call.

---

## 6. Live Hotel Scope

R8 SHALL support multiple explicitly configured hotel codes.

Use:

    HOTELBEDS_AVAILABILITY_LIVE_HOTEL_CODES

The value SHALL be a comma-separated list of hotel codes.

Example:

    HOTELBEDS_AVAILABILITY_LIVE_HOTEL_CODES=26976,26996,26999,27517,27758

The harness MUST:

- trim whitespace;
- reject empty entries;
- validate every code using the existing hotel-code validation rules;
- deduplicate codes while preserving deterministic order;
- require at least one valid code;
- pass the codes into the existing application-level search criteria.

The harness MUST NOT construct Hotelbeds-specific request bodies.

The harness MUST NOT construct Hotelbeds paxes.

The harness MUST NOT bypass R2.

## 9. Input Validation

The harness SHALL validate all live inputs before invoking R7.

Validation SHALL include:

- live verification flag;
- at least one hotel code;
- valid hotel-code format;
- valid check-in date;
- valid check-out date;
- check-out after check-in;
- positive adult count;
- non-negative child count;
- child ages when children are present;
- child-age count matching the child count;
- valid source market.

Invalid configuration MUST:

- fail before supplier execution;
- produce a clear non-sensitive error;
- make zero supplier calls.

## 11. mTLS

R4-C1 is now responsible for genuine mTLS transport.

R8 SHALL use the corrected R4 transport.

The harness MUST NOT:

- create an HTTPS client itself;
- configure certificates directly;
- bypass R4;
- introduce another transport;
- modify TLS behaviour.

If mTLS configuration is missing or invalid, the live verification SHALL fail safely through the existing R4 configuration/transport mechanism.

No non-mTLS fallback is permitted when mTLS is configured.

---

## 12. Test-Only Catalogue

The R8 harness SHALL use an isolated in-memory catalogue.

The catalogue SHALL contain one active entry for each configured live hotel code.

The fixture SHALL use the existing catalogue model.

Each entry MUST contain valid values required by the current catalogue contract, including:

- configured hotel code;
- valid 4- or 5-star grading;
- non-empty destination code;
- non-empty zone code;
- non-empty zone name;
- active status.

The catalogue fixture exists only in process memory.

It MUST NOT:

- modify production catalogue data;
- modify persistent storage;
- execute a database migration;
- create catalogue records.

R2 MUST still resolve the candidates through:

    HotelCatalogueService.select(...)

The harness MUST NOT inject candidates directly into R3.

---

## 13. R7 Composition

The intended composition is:

    InMemoryHotelCatalogueRepository
        ↓
    HotelCatalogueService

    InMemoryProviderRegistry
        ↓
    HotelbedsProvider
        ↓
    Existing R6/R4 execution
        ↓
    Existing R5 mapper

    HotelbedsAvailabilityRequestBuilder

    DefaultAccommodationAvailabilityService

The harness SHALL invoke only:

    DefaultAccommodationAvailabilityService.execute(...)

The harness MUST NOT invoke:

- HotelbedsTransport directly;
- HotelbedsClient directly;
- HotelbedsGateway directly;
- HotelbedsAvailabilityExecutor directly;
- HotelbedsAvailabilityResponseMapper directly.

## 14. Complete Expected Path

For the five configured hotels, the expected application path is:

    R8 Harness
        ↓
    R7 DefaultAccommodationAvailabilityService.execute
        ↓
    R2 HotelCatalogueService.select
        ↓
    InMemoryHotelCatalogueRepository.findActive
        ↓
    R3 HotelbedsAvailabilityRequestBuilder.build
        ↓
    ProviderRegistry.findProviders(AVAILABILITY)
        ↓
    HotelbedsProvider.executeAvailabilityRequests
        ↓
    R6 DefaultHotelbedsAvailabilityExecutor
        ↓
    R6 QPS / concurrency protection
        ↓
    R4 Hotelbeds authentication
        ↓
    R4 mTLS transport
        ↓
    Hotelbeds Availability
        ↓
    R4 structured raw response
        ↓
    R5 HotelbedsAvailabilityResponseMapper
        ↓
    Canonical AccommodationAvailabilityResult
        ↓
    R7 return

No stage may be bypassed.

## 15. Multi-Hotel Execution

The five configured hotels SHALL be submitted through one R7 Availability execution.

R3 remains responsible for request construction and batching.

R6 remains responsible for supplier protection.

The harness MUST NOT implement:

- its own batching;
- its own rate limiting;
- its own concurrency;
- its own retry logic.

The purpose of the five-hotel test is specifically to demonstrate that the existing R2-R7 architecture can process multiple hotel candidates through one application request.

---

## 16. Supplier Protection

The existing R6 supplier-protection mechanism SHALL remain authoritative.

R8 MUST NOT introduce additional:

- QPS limiting;
- concurrency limiting;
- retry mechanisms.

The existing R6 limits SHALL protect all supplier requests generated from the five-hotel execution.

The external Hotelbeds allowance of 50,000 requests/day is an operational constraint.

R8 SHALL NOT implement:

- daily counters;
- persistent quota state;
- quota services;
- daily quota databases.

The controlled five-hotel test is sufficiently small that no application-level daily quota accounting is required.

---

## 19. Live Verification Outcome

The live verification SHALL distinguish:

### Configuration Failure

Examples:

- live flag invalid;
- hotel-code list invalid;
- dates invalid;
- occupancy invalid;
- source market invalid;
- credentials unavailable;
- TLS configuration unavailable.

### Candidate Resolution Failure

The configured hotel code is not resolved by R2.

This SHALL prevent supplier execution for that candidate.

### Supplier Transport Failure

Examples:

- TLS handshake failure;
- certificate failure;
- timeout;
- network failure;
- authentication failure;
- HTTP failure.

### Supplier Successful Response

The supplier returns a valid response that reaches R5 mapping.

### Canonical Availability Result

R5 produces the existing canonical result.

A successful supplier HTTP response MUST NOT automatically be interpreted as available.

- invalid source market;

The harness MUST be explicitly invoked.
