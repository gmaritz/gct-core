# APP-008.3-R8 — Controlled Live Hotelbeds Availability Verification

**Document ID:** APP-008.3-R8  
**Status:** Draft — Revised for Architect Review  
**Capability:** Accommodation Availability  
**Provider:** Hotelbeds  
**Iteration:** R8  
**Depends On:** R1-R7, R4-C1  
**Execution Mode:** Explicitly invoked controlled live verification  
**Production Scope:** None

---

## 1. Purpose

APP-008.3-R8 provides an explicitly invoked, test-only runtime harness for performing a controlled live Hotelbeds Availability verification through the complete existing R2-R7 application path.

The purpose is to verify the integrated supplier path using:

- real Hotelbeds credentials;
- the configured Hotelbeds mTLS certificate and private key;
- five controlled Hotelbeds hotel codes;
- controlled availability criteria.

R8 is not production functionality.

R8 must not modify:

- production bootstrap;
- production catalogue data;
- persistence;
- database state;
- R2;
- R3;
- R4-C1;
- R5;
- R6;
- R7;
- the canonical Availability model.

---

## 2. Architectural Objective

R8 is an explicit test composition root.

Its responsibilities are limited to:

1. loading controlled runtime configuration;
2. loading `.env` only for explicit R8 execution;
3. resolving TLS certificate, private-key, and optional CA file paths;
4. loading TLS PEM material;
5. validating the effective Hotelbeds configuration;
6. constructing an isolated in-memory hotel catalogue;
7. constructing the existing R7 application path;
8. ensuring the actual Hotelbeds provider/executor receives the same effective configuration used for validation;
9. executing one controlled Availability request;
10. reporting only non-sensitive results.

R8 must not implement supplier business logic.

## 4. Explicit Live Safety Gate

Live execution is permitted only when:

    HOTELBEDS_AVAILABILITY_LIVE_VERIFY=true

Existing fail-closed behaviour remains authoritative.

| Value | Behaviour |
|---|---|
| absent | disabled |
| empty | disabled |
| `false` | disabled |
| `0` | disabled |
| `true` | enabled |
| `1` | enabled |
| other non-empty value | invalid and fail closed |

The live flag must be evaluated before:

- supplier configuration validation;
- provider construction;
- R7 execution;
- supplier transport.

Normal Jest execution must never invoke live verification.

## 7. R8 TLS File Adapter

The following variables represent TLS filesystem paths within R8:

    HOTELBEDS_TLS_CLIENT_CERTIFICATE
    HOTELBEDS_TLS_PRIVATE_KEY
    HOTELBEDS_TLS_TRUSTED_CA

The trusted CA is optional.

The R8 adapter must:

1. obtain the configured path;
2. resolve relative paths deterministically from the GCT Core project root;
3. support absolute paths;
4. verify required files exist;
5. verify required files are readable;
6. read PEM contents into memory;
7. construct an effective environment containing the PEM contents.

Relative path resolution must not depend solely on `process.cwd()`.

Node's built-in `path` and `fs` modules must be used.

No new npm dependency is required.

---

## 8. TLS Responsibility Boundary

R8 is responsible only for:

- path resolution;
- file existence validation;
- file readability validation;
- PEM file loading;
- effective environment construction.

R8 must not perform:

- private-key cryptographic parsing;
- private-key decryption;
- passphrase validation;
- certificate/private-key matching;
- TLS handshake validation.

Those responsibilities remain exclusively within R4-C1.

R8 must not call `crypto.createPrivateKey`.

## 9. Effective Hotelbeds Configuration

The effective runtime environment must be supplied to the existing `loadHotelbedsIntegrationConfig`.

The effective environment must contain:

    HOTELBEDS_API_KEY
    HOTELBEDS_SECRET
    HOTELBEDS_BASE_URL

    HOTELBEDS_TLS_CLIENT_CERTIFICATE
    HOTELBEDS_TLS_PRIVATE_KEY
    HOTELBEDS_TLS_PRIVATE_KEY_PASSPHRASE

    HOTELBEDS_TLS_TRUSTED_CA

The certificate, private key, and optional CA values must contain loaded PEM contents, not filesystem paths.

The private-key passphrase remains an environment value.

`HOTELBEDS_ENDPOINT` must not be introduced or supported as an alternative endpoint variable.

## 10. Critical R8 Configuration-Boundary Requirement

The effective R8 environment must be used not only for pre-validation but also by the actual Hotelbeds provider/executor used during live R7 execution.

This requirement resolves the identified R8 execution defect.

### Required Behaviour

The effective configuration flow must be:

    loadR8DotEnv()
            ↓
    createR8EffectiveEnvironment()
            ↓
    loadHotelbedsIntegrationConfig(effectiveEnvironment)
            ↓
    R4-C1 configuration validation
            ↓
    construct R7 composition
            ↓
    construct Hotelbeds provider/executor
            ↓
    provider/executor uses effectiveEnvironment
            ↓
    R2 → R3 → R6 → R4-C1 → Hotelbeds

The effective PEM-based environment must therefore reach the actual Hotelbeds configuration loader used by the live provider/executor.

### Prohibited Behaviour

The following pattern is prohibited:

    R8 effective environment
            ↓
    pre-validation
            ↓
    successful validation
            ↓
    HotelbedsProvider
            ↓
    DefaultHotelbedsAvailabilityExecutor
            ↓
    loadHotelbedsIntegrationConfig()
            ↓
    raw process.env

This causes R4-C1 to receive TLS filesystem paths instead of PEM material.

## 11. R8 Composition Requirement

The correction must remain within the R8 composition root.

The preferred implementation is to construct the existing Hotelbeds provider/executor with a configuration loader bound to the effective R8 environment.

Conceptually:

    effectiveEnvironment
            ↓
    configuration loader bound to effectiveEnvironment
            ↓
    HotelbedsAvailabilityExecutor
            ↓
    HotelbedsProvider

The existing application-facing interfaces must remain stable.

Do not redesign the executor globally solely to support R8.

Do not modify production composition.

Do not modify R4-C1.

Do not copy PEM contents into global `process.env`.

Do not create a second Hotelbeds configuration system.

If the existing executor API prevents this R8-only composition without modifying R1-R7 production components, stop implementation and report the architectural constraint.

## 14. Optional Trusted CA

`HOTELBEDS_TLS_TRUSTED_CA` is optional.

If absent or empty:

- no CA file is loaded;
- no CA value is added to the effective environment;
- R4-C1 retains normal Node trust behaviour.

If configured:

- resolve the path;
- validate existence and readability;
- read the PEM contents;
- place the PEM contents into the effective environment.

## 26. Failure Behaviour

Configuration and safety failures must fail closed.

If configuration validation fails:

    supplier requests = 0

If R4-C1 TLS configuration validation fails:

    supplier requests = 0

If the TLS handshake fails:

    supplier request = 1

with the failure reported at the transport boundary.

If Hotelbeds returns an HTTP error:

    supplier request = 1

with the HTTP status reported.

R8 must not implement additional retries.

Existing R6 retry behaviour remains authoritative.

## 32. Architectural Intent

R8 is a controlled verification harness, not a new application architecture.

The accepted application architecture remains:

    R2 → R3 → R6 → R4-C1 → R5 → R7

R8 supplies only:

    +
