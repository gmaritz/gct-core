# APP-008.2-R3

# Hotel Content Synchronization — Curated Hotel Scope

---

## Objective

Refine APP-008.2 so GCT Core synchronizes **only explicitly selected Hotelbeds hotel codes**.

GCT Core shall not attempt to build or maintain the complete Hotelbeds hotel-content portfolio.

The selected hotel list represents the accommodation inventory that Go Cape Tours intends to use.

---

## 1. Synchronization Scope

Change the APP-008.2 synchronization model from:

```text
Hotelbeds Portfolio
        ↓
Full Synchronization
        ↓
GCT Core
```

to:

```text
GCT Core Selected Hotel Codes
        ↓
Hotelbeds Content API
        ↓
Canonical Hotel Content
        ↓
Local Persistence
```

Only hotels explicitly selected by GCT Core shall be synchronized.

---

## 2. Hotelbeds Hotel Code

The Hotelbeds hotel code is the external selection key.

The synchronization process shall accept a collection of selected Hotelbeds hotel codes.

Example:

```text
Selected Hotels
├── 1234
├── 5678
├── 9012
└── 3456
```

Do not use hotel name as the selection key.

---

## 3. Selected Hotel Configuration

Implement the smallest suitable mechanism for maintaining the selected Hotelbeds hotel-code list.

Before creating a new configuration mechanism, inspect the existing repository for an appropriate pattern.

The selected list must be:

* explicit
* deterministic
* testable
* independent of Hotelbeds's complete portfolio
* available to synchronization processes

Do not hard-code the hotel list inside the synchronization service.

---

## 4. Initial Synchronization

Initial synchronization shall process **only the selected hotel codes**.

The implementation may use the Hotelbeds Content API's supported hotel-code filtering/request mechanism.

Do not request or persist the entire Hotelbeds hotel portfolio.

The synchronization shall:

1. obtain the selected hotel codes
2. request content for those hotels
3. map the response
4. persist the selected hotels
5. record successful synchronization state

---

## 5. Incremental Synchronization

Retain incremental synchronization.

Incremental synchronization shall operate only against the selected hotel scope.

Conceptually:

```text
Selected Hotel Codes
        +
Last Successful Synchronization
        ↓
Changed Selected Hotels
        ↓
Local Content
```

Do not allow incremental synchronization to expand the local portfolio automatically.

---

## 6. No Automatic Portfolio Expansion

A hotel returned by Hotelbeds must not automatically become a GCT Core hotel.

Only a hotel whose Hotelbeds code is present in the selected hotel list may be synchronized into the canonical local hotel-content store.

This is a critical business boundary.

---

## 7. Existing Local Hotels

If a selected hotel already exists:

* update its canonical content

If it does not exist:

* create it

If a hotel is removed from the selected list:

* do not automatically delete its canonical record unless the established lifecycle architecture explicitly requires deletion
* mark/handle it according to the existing canonical hotel lifecycle convention

Do not invent a destructive deletion rule.

---

## 8. Idempotency

Repeated synchronization of the same selected hotel codes must remain idempotent.

Verify:

```text
Same Hotel Code
      ↓
Same Canonical Hotel
      ↓
Update / Upsert
      ↓
No Duplicate
```

---

## 9. Synchronization Checkpoint

Checkpoint behaviour remains unchanged.

A successful checkpoint may only advance after the selected hotel synchronization has completed successfully.

A failed synchronization must not advance the successful checkpoint.

The checkpoint must not imply that the entire Hotelbeds portfolio has been synchronized.

---

## 10. Live Hotelbeds Test

Use the configured Hotelbeds **TEST** credentials.

For the controlled live verification:

* select a small number of known Hotelbeds hotel codes
* retrieve only those hotels
* verify the response
* map the content
* persist it
* verify idempotency

Do not perform a full portfolio synchronization.

Do not call:

* Availability API
* CheckRate
* Booking API
* cancellation
* post-booking operations

---

## 11. Existing 403

The previous live test processed 430 hotels before receiving HTTP 403.

Do not attempt to work around the 403 by retrying the full portfolio.

The R3 test must instead use the curated hotel-code scope.

If a 403 still occurs for a selected hotel request:

* report the exact request scope
* report the provider error category
* do not weaken authentication/error handling
* do not silently skip the failure

---

## 12. Tests

Update/add focused tests for:

### Selection

* selected hotel codes are loaded
* unselected hotels are excluded

### Synchronization

* selected hotels are synchronized
* unselected hotels are not persisted
* repeated synchronization is idempotent

### Incremental

* selected hotels can be updated
* synchronization scope does not expand

### Checkpoint

* success advances checkpoint
* failure does not advance checkpoint

### Persistence

* selected hotel is created
* selected hotel is updated
* duplicate is prevented

## 15. Scope Constraint

Do not implement:

* full Hotelbeds portfolio synchronization
* availability
* dynamic pricing
* CheckRate
* booking
* post-booking
* frontend
* new accommodation business rules

APP-008.2 remains **static hotel content synchronization only**.

---

## Completion Criteria

APP-008.2-R3 is complete when:

* GCT Core has an explicit selected Hotelbeds hotel-code list
* only selected hotel codes are synchronized
* unselected Hotelbeds hotels are ignored
* initial synchronization works for selected hotels
* incremental synchronization remains scoped to selected hotels
* canonical persistence works
* synchronization is idempotent
* checkpoint behaviour is safe
* controlled Hotelbeds TEST synchronization succeeds for selected hotels
* targeted tests pass
* APP-008.1 compatibility tests pass
* full regression passes
* type-check passes
* build passes
* startup smoke passes
* implementation report is updated

No further full-portfolio synchronization testing is required.
