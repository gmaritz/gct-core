# 1. Purpose

Implement supplier-neutral accommodation cancellation for an existing confirmed accommodation booking.

The capability SHALL support:

- cancellation eligibility;
- cancellation request;
- supplier cancellation;
- cancellation confirmation;
- cancellation charges;
- supplier cancellation status;
- reservation lifecycle integration;
- safe handling of supplier failures and unknown outcomes;
- future multi-supplier cancellation.

Hotelbeds SHALL remain an adapter implementation.

The canonical cancellation contract MUST NOT reproduce the Hotelbeds API model.

---

# 2. Business Context

GCT accommodation is one component of a private multi-day package.

A confirmed accommodation booking may subsequently need to be cancelled.

The cancellation operation applies to the accommodation reservation created through APP-008.5.

The package itself is NOT cancelled by APP-008.6.

APP-008.6 SHALL therefore operate on the accommodation reservation/booking boundary established by APP-004 and APP-008.5.

The GCT package price remains owned by APP-005.

---

# 3. Architectural Boundary

The canonical lifecycle is:

Accommodation Booking
→ Confirmed Reservation
→ Cancellation Eligibility
→ Accommodation Cancellation
→ Reservation Status

The application flow SHALL remain:

Application
→ Accommodation Cancellation Service
→ Accommodation Provider
→ Hotelbeds Adapter
→ Hotelbeds Booking API

Hotelbeds-specific DTOs MUST remain inside the Hotelbeds adapter.

# 5. Canonical Cancellation Request

The canonical request SHALL identify the confirmed accommodation booking to cancel.

It MUST contain:

- internal reservation identity where available;
- provider;
- supplier booking reference;
- cancellation intent;
- request correlation/idempotency information where required by the existing architecture.

The canonical request MUST NOT contain Hotelbeds-specific request structures.

The supplier booking reference used for cancellation is the booking confirmation reference created by APP-008.5.

It MUST NOT use the Availability `rateKey` or CheckRate offer reference as the cancellation identifier.

---

# 6. Reservation Ownership

APP-004 remains the owner of:

- reservation identity;
- reservation lifecycle;
- reservation status;
- supplier booking reference;
- reservation snapshot;
- persistence.

APP-008.6 SHALL integrate with APP-004.

It MUST NOT create a parallel reservation model.

If APP-004 does not currently expose a required cancellation operation, Copilot SHALL extend the existing provider-neutral reservation boundary only as necessary.

Do not create a second reservation repository or persistence mechanism.

---

# 7. Cancellation Eligibility

Cancellation SHALL be permitted only for a confirmed accommodation booking that is cancellable.

The implementation SHALL validate:

- reservation exists;
- reservation belongs to an accommodation booking;
- reservation is associated with the expected provider;
- supplier booking reference exists;
- booking is not already cancelled;
- booking is in a state where cancellation is permitted.

If the existing APP-004 reservation model contains explicit cancellation eligibility, reuse it.

If supplier cancellation eligibility is only known from the supplier, the provider may reject the cancellation.

Do not invent a new eligibility source when an existing canonical source is available.

---

# 8. Cancellation Status

Use the existing canonical reservation status model where possible.

The implementation SHALL distinguish at minimum:

- cancellation requested/processing where required;
- cancelled;
- cancellation failed;
- cancellation outcome unknown.

If APP-004 already has suitable lifecycle states, reuse them.

Do not create a parallel accommodation-specific reservation lifecycle.

---

# 9. Supplier Reference

The cancellation adapter SHALL use the confirmed supplier booking reference returned by APP-008.5.

The canonical application layer SHALL continue to represent supplier identity generically.

Conceptually:

SupplierReference

- provider
- opaqueReference

For cancellation, the opaque reference represents the confirmed supplier booking.

For Hotelbeds, the adapter translates the opaque reference into the Hotelbeds booking reference required by the Hotels Booking API.

The canonical model MUST NOT expose a Hotelbeds-specific reference name.

---

# 10. Hotelbeds Cancellation Operation

The Hotelbeds adapter SHALL use the Hotels Booking API cancellation operation associated with the confirmed booking.

Hotelbeds documents cancellation as a `/bookings` post-booking operation and states that the booking reference from confirmation is required for subsequent operations. :contentReference[oaicite:2]{index=2}

The exact Hotelbeds HTTP method/path/request DTO SHALL remain inside the adapter.

Do not expose the supplier endpoint through the canonical service.

---

# 11. Cancellation Simulation

If the Hotelbeds Hotels Booking API supports cancellation simulation for the selected operation, the implementation SHALL support a supplier-neutral cancellation simulation capability only if it can be mapped cleanly to the existing canonical contract.

Simulation means:

- determine whether cancellation charges apply;
- do not actually cancel the booking;
- return the expected cancellation outcome/charges.

Actual cancellation means:

- execute the supplier cancellation;
- return the confirmed cancellation result.

If the current Hotelbeds implementation or certification requirements require a simulation-before-cancellation workflow, Copilot SHALL implement it only where required by the supplier contract and this capability.

Do not add an unnecessary simulation workflow if the supplier's hotel cancellation contract does not require it.

---

# 12. Cancellation Charges

The canonical cancellation result SHALL preserve supplier cancellation charges where returned.

A cancellation charge represents an amount that the supplier applies because of the cancellation.

It MUST remain distinct from:

- original accommodation booking price;
- GCT package price;
- GCT markup;
- customer refund execution.

The canonical cancellation result SHOULD preserve:

- charge amount;
- currency;
- applicable effective date/time where supplied;
- supplier-provided description/reference where useful.

Do not calculate supplier cancellation charges from raw dates in the application if the supplier has already determined the applicable charge.

---

# 13. GCT Package Pricing Boundary

APP-008.6 MUST NOT calculate the GCT package cancellation/refund amount.

The supplier cancellation charge is an accommodation supplier value.

GCT package pricing remains owned by APP-005.

If a future package cancellation/refund capability needs to calculate:

- package refund;
- GCT cancellation fee;
- sliding-scale refund;
- combined multi-stop cancellation;

that SHALL be implemented as a separate capability.

APP-008.6 only returns the accommodation supplier cancellation result.

---

# 14. Cancellation Result

The canonical result SHALL distinguish successful cancellation from failure.

A successful cancellation result MUST preserve:

- internal reservation reference;
- provider;
- supplier booking reference;
- cancellation status;
- cancellation charge where supplied;
- cancellation timestamp where available;
- supplier response information required by APP-004.

The result MUST NOT expose the raw Hotelbeds response.

---

# 15. Already Cancelled

If the reservation is already canonically marked cancelled:

- do not issue another supplier cancellation call;
- return an idempotent/already-cancelled outcome using the existing canonical status model.

If the internal state says the booking is not cancelled but the supplier reports it as already cancelled, map the supplier result to the canonical cancelled state and preserve the supplier evidence required by APP-004.

---

# 16. Supplier Rejection

If Hotelbeds rejects the cancellation as a business operation:

- do not mark the reservation as cancelled;
- return the canonical cancellation failure;
- preserve the supplier error classification through the existing error model;
- do not retry unless the supplier error is explicitly retry-safe.

The supplier rejection MUST NOT be interpreted as a successful cancellation.

---

# 17. Transport Failure

If the supplier call fails at transport level:

- do not automatically mark the reservation cancelled;
- classify the result as cancellation outcome unknown where the request may have reached the supplier;
- use existing infrastructure error handling;
- do not blindly retry a state-changing cancellation request.

If the architecture can establish that the supplier request definitely did not reach the supplier, the existing canonical failure classification MAY be used.

---

# 18. Unknown Cancellation Outcome

Cancellation is a state-changing supplier operation.

If the client cannot determine whether the supplier processed the cancellation, the canonical result MUST distinguish:

UNKNOWN

from:

FAILED

and:

CANCELLED.

The implementation MUST NOT claim successful cancellation without confirmation.

The implementation MUST NOT automatically issue a second cancellation request when the first request may have succeeded.

A future booking-detail/reconciliation capability may resolve an unknown state.

APP-008.6 does not implement supplier reconciliation.

---

# 19. Retry and Idempotency

Cancellation requests MUST use the existing idempotency/duplicate-protection architecture where available.

The implementation MUST NOT use unrestricted automatic retries for cancellation.

A retry is safe only when the implementation can establish that repeating the supplier request cannot create an incorrect commercial state.

If safe retry cannot be established:

- return the appropriate failure/unknown outcome;
- do not invent a new persistence mechanism.

---

# 20. Reservation Update

After confirmed supplier cancellation:

APP-008.6 SHALL update the reservation through the existing APP-004 boundary.

The reservation SHALL reflect:

- cancelled status;
- supplier booking reference;
- cancellation information;
- cancellation charge where applicable;
- cancellation timestamp where available.

The supplier cancellation response MUST NOT be stored only in transient application memory if APP-004 provides a persistence mechanism for the reservation lifecycle.

---

# 21. Atomicity Boundary

Supplier cancellation and local reservation persistence are separate systems.

The implementation MUST NOT assume a distributed transaction.

If:

1. supplier cancellation succeeds; and
2. local persistence fails,

the result MUST NOT be represented as a normal supplier cancellation failure.

The implementation SHALL preserve enough information for the existing application/error architecture to identify that the supplier may already have cancelled the booking.

Do not falsely report that the supplier cancellation did not happen.

---

# 22. Hotelbeds Adapter Isolation

Hotelbeds-specific concepts remain inside the adapter, including:

- cancellation request DTO;
- cancellation response DTO;
- booking endpoint/path;
- supplier status values;
- supplier error structures;
- supplier cancellation charge structures;
- supplier booking-reference syntax.

The canonical cancellation service SHALL operate only on supplier-neutral contracts.

---

# 23. Provider Capability

The existing provider capability architecture SHALL be extended/reused so that cancellation is represented as a supplier-neutral capability.

Conceptually:

AccommodationProvider

- availability
- revalidation
- booking
- cancellation

Hotelbeds SHALL advertise cancellation support.

A future supplier may advertise cancellation independently.

The application MUST NOT assume every provider supports every capability.

---

# 24. Multi-Supplier Compatibility

The cancellation operation SHALL select the provider from the confirmed reservation/booking.

It MUST NOT simply use the first registered accommodation provider.

The provider associated with the original booking is authoritative for cancellation.

This ensures that future suppliers can coexist without changing the canonical cancellation contract.

---

# 25. Cancellation Eligibility and Supplier Policy

The canonical service may perform local eligibility checks.

Supplier-specific cancellation policy remains supplier-authoritative for the actual cancellation charge.

The implementation MUST NOT recompute supplier policy from the original availability response when the supplier provides a current cancellation outcome.

This is especially important because cancellation conditions may depend on destination date/time and supplier-side policy state.

---

# 26. Security

Cancellation requests contain commercially sensitive booking information.

The implementation MUST NOT log:

- API credentials;
- private keys;
- signatures;
- raw supplier authentication headers;
- unnecessary personal data.

Logs MAY contain safe operational identifiers such as:

- internal reservation ID;
- provider;
- supplier booking reference where permitted;
- cancellation outcome;
- correlation ID.

Follow the existing GCT security and logging architecture.

# 34. Final Architectural Statement

APP-008.6 establishes the accommodation cancellation boundary:

Confirmed Accommodation Booking
→ Cancellation Eligibility
→ Supplier Cancellation
→ Canonical Cancellation Result
→ APP-004 Reservation Lifecycle

The canonical GCT Core model owns the business cancellation operation.

Hotelbeds remains a supplier adapter.

The confirmed supplier booking reference, not the availability rate reference, identifies the supplier booking to cancel.

APP-004 remains responsible for reservation lifecycle and persistence.

APP-005 remains responsible for GCT package pricing.

APP-008.6 does not cancel an entire GCT package. It cancels one confirmed accommodation booking.

Future package-level cancellation, refund calculation, booking modification and supplier reconciliation SHALL be separate capabilities.
