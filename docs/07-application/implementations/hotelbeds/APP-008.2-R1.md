# APP-008.2-R1

# Implementation Clarification & Verification Specification

## Hotel Content Synchronization

---

# 1. Objective

Perform a focused clarification and correction pass on the completed APP-008.2 implementation.

The purpose is to resolve two outstanding points before APP-008.2 is formally approved:

1. Confirm whether the current hotel-content persistence is production persistence or only an in-memory test implementation.
2. Execute a controlled Hotelbeds Content API test using the configured Hotelbeds test credentials.

Do not redesign or expand APP-008.2.

---

# 2. Persistence Verification

Inspect the current APP-008.2 implementation and determine exactly how canonical hotel content is persisted.

## Required outcome

APP-008.2 production synchronization must persist hotel content using the established GCT Core persistence architecture.

If the current `in-memory` persistence implementation is:

### A. Test-only

No architectural change is required.

Confirm that:

* in-memory persistence is used only by tests
* production synchronization uses the existing persistence/repository architecture
* no production data is lost between application restarts

### B. Production implementation

If in-memory persistence is currently the actual production persistence mechanism, correct it.

The implementation shall:

* use the established GCT Core persistence architecture
* persist canonical hotel content durably
* preserve idempotent upsert behaviour
* preserve synchronization state/checkpoints
* preserve failure-safe checkpoint handling
* avoid direct database access from the synchronization service where repository patterns already exist

Do not introduce a new persistence architecture if an existing one can be reused.

---

# 3. Persistence Scope

Only implement the persistence required by APP-008.2.

The following must be durable where required:

* canonical hotel content
* Hotelbeds hotel identity/reference
* synchronization state
* successful synchronization checkpoint

Do not implement:

* availability persistence
* live rates
* CheckRate persistence
* booking persistence
* post-booking persistence

Those belong to later milestones.

---

# 4. Schema Changes

If durable persistence requires Prisma/schema changes:

* follow the existing Prisma architecture
* make the minimum required schema changes
* add migrations according to repository conventions
* preserve existing data
* do not modify unrelated schemas

If the required persistence model already exists, reuse it.

---

# 5. Hotelbeds Test Credentials

Use the Hotelbeds **test credentials already provided/configured by the developer**.

Do not request new credentials if the existing project configuration contains them.

Credentials must be supplied through the established `.env` / configuration mechanism.

Do not:

* hard-code credentials
* commit credentials
* print credentials
* include credentials in the implementation report
* expose signatures or authentication headers

---

# 6. Controlled Content API Test

Execute a controlled request against the **Hotelbeds test environment**.

The test shall:

* use the Hotelbeds test environment
* retrieve a limited Content API scope/page
* verify authentication/signature generation
* verify the Content API request succeeds
* verify the response can be mapped into the canonical hotel-content model
* verify the resulting content can be persisted
* verify the synchronization checkpoint behaviour

Do not perform:

* availability searches
* CheckRate
* bookings
* cancellations
* post-booking operations

---

# 7. Live Test Safety

The live test must be read-only with respect to Hotelbeds.

It must not:

* create a booking
* modify a booking
* cancel a booking
* call Booking API operations

Only the Content API shall be exercised.

---

# 8. Environment Verification

Before making the live request, verify that the configured Hotelbeds base URL/environment is the **test environment**.

If the configuration points to production, do not execute the live test.

Report the configuration issue instead.

---

# 9. Synchronization Verification

The controlled test should verify the complete APP-008.2 path:

```text
Hotelbeds Content API
        ↓
Hotelbeds Integration Foundation
        ↓
Content Mapper
        ↓
Canonical Hotel Content
        ↓
Local Persistence
        ↓
Synchronization Checkpoint
```

---

# 10. Idempotency Verification

Where practical, process the same controlled content twice.

Verify that:

* no duplicate hotel record is created
* the existing canonical hotel is updated/upserted
* synchronization remains consistent

---

# 11. Checkpoint Safety

Verify that a failed synchronization does not advance the successful checkpoint.

Verify that a successful synchronization advances the checkpoint only after content processing/persistence succeeds.

---
