# 2. Objective

Establish a persistent, GCT-owned curated accommodation catalogue containing only the Hotelbeds properties intentionally selected by Go Cape Tours.

The catalogue must support two accommodation-selection modes:

1. **Direct hotel-code selection** for existing/curated package tours.
2. **Attribute-based hotel filtering** for on-demand package construction.

The Hotelbeds Content API must only populate and maintain `HotelContent` for hotels contained in the curated catalogue.

The catalogue is the authoritative boundary for which Hotelbeds properties GCT Core is permitted to use.

---

# 3. Business Intent

Hotelbeds contains a very large accommodation portfolio. GCT Core does not require the entire Hotelbeds portfolio.

The final curated catalogue contains the properties specifically researched and selected by Go Cape Tours.

The selected properties are currently:

* 340 unique Hotelbeds hotel codes
* 162 GCT 4-star properties
* 178 GCT 5-star properties

The catalogue also contains:

* Hotelbeds destination code
* Hotelbeds zone code
* Zone name
* GCT Star Grading

`Star Grading` is a **GCT-owned commercial classification** and MUST NOT be treated as equivalent to Hotelbeds `categoryCode`.

---

# 4. Architectural Principle

The implementation MUST distinguish between:

### 4.1 GCT Hotel Catalogue

Owned by GCT Core.

Answers:

> Which Hotelbeds properties does Go Cape Tours choose to use?

### 4.2 Hotel Content

Sourced from Hotelbeds.

Answers:

> What content does Hotelbeds currently provide for those properties?

### 4.3 Live Availability and Rates

Sourced from Hotelbeds at search time.

Answers:

> Is this selected property available for the requested stay and at what rate?

The resulting architecture is:

```text
GCT Hotel Catalogue
        |
        | selected hotel codes
        v
Hotelbeds Content
        |
        | candidate properties
        v
Hotelbeds Availability / Rates
        |
        v
Customer/package accommodation result
```

| -------------------------- | -------------------------------------------------- |
| HOTEL                      | Human-readable hotel name at catalogue-import time |

| STAR GRADING               | GCT commercial star grading                        |

| ZONE NAME                  | Human-readable Hotelbeds zone name                 |

The final source contains **340 unique codes**.

The importer MUST reject duplicate hotel codes.

# 6. New Persistent Model

Introduce a dedicated Prisma model:

```prisma
model HotelCatalogueEntry {
  id                String   @id @default(uuid())
  hotelCode         String   @unique
  starGrading       Int
  destinationCode   String
  zoneCode          String
  zoneName          String
  active            Boolean  @default(true)

  createdAt         DateTime @default(now())
  updatedAt         DateTime @updatedAt

  @@index([destinationCode])
  @@index([zoneCode])
  @@index([starGrading])
  @@index([destinationCode, zoneCode])
  @@index([destinationCode, zoneCode, starGrading])
  @@map("hotel_catalogue_entry")
}
```

## 6.1 Ownership

`HotelCatalogueEntry` is a GCT Core business/application model.

It MUST NOT be treated as a Hotelbeds content cache.

---

# 7. Hotel Code Rules

`hotelCode` MUST:

* contain the Hotelbeds hotel code as a string;
* be unique;
* be non-empty;
* be normalized by trimming whitespace;
* preserve numeric Hotelbeds codes without numeric truncation;
* not be generated by GCT Core;
* not be replaced by the Hotelbeds hotel name.

Example:

```text
hotelCode = "676612"
```

The Hotelbeds hotel code remains the stable supplier identifier.

---

# 8. GCT Star Grading

The catalogue MUST store:

```text
starGrading
```

independently of Hotelbeds content.

Valid current values:

```text
4
5
```

The implementation MUST NOT populate `starGrading` from:

```text
Hotelbeds categoryCode
Hotelbeds categoryName
Hotelbeds starRating
```

The Excel catalogue is the authoritative source for the current GCT Star Grading.

Hotelbeds `categoryCode`, `categoryName`, and any supplier-provided rating remain separate HotelContent attributes.

---

# 9. Destination and Zone

The catalogue MUST retain both:

```text
destinationCode
zoneCode
```

They MUST NOT be collapsed into a single geographic field.

The catalogue MUST also retain:

```text
zoneName
```

for presentation, diagnostics and administration.

Destination and zone are Hotelbeds supplier geography.

They are not equivalent to GCT's own marketing regions.

Example:

```text
destinationCode = "CPT"
zoneCode        = "3"
zoneName        = "Stellenbosch"
```

# 10. Relationship to HotelContent

The existing `HotelContent` model remains the supplier-content store:

```prisma
model HotelContent {
  id                String   @id @default(uuid())
  provider          String
  providerHotelCode String
  name              String
  payload           Json
  lastUpdatedAt     DateTime
  isActive          Boolean  @default(true)

  createdAt         DateTime @default(now())
  updatedAt         DateTime @updatedAt

  @@unique([provider, providerHotelCode])
  @@index([provider])
  @@map("hotel_content")
}
```

Do not replace this model.

The relationship is logically:

```text
HotelCatalogueEntry.hotelCode
              |
              | matches
              v
HotelContent.providerHotelCode
```

The supplier content remains owned by the Hotelbeds integration.

# 11. Catalogue Integrity Rule

A Hotelbeds property MUST NOT be imported into `HotelContent` unless its `hotelCode` exists as an active `HotelCatalogueEntry`.

Therefore:

```text
Hotelbeds property
      |
      v
Is hotelCode in active GCT catalogue?
      |
   +--+--+
   |     |
  YES    NO
   |     |
 import  ignore
```

This is the primary protection against accidentally importing the wider Hotelbeds portfolio.

# 12. Initial Catalogue Import

Create a controlled catalogue-import mechanism capable of reading the two final Excel workbooks.

The import MUST:

1. Read all worksheets containing hotel selections.
2. Ignore title/header rows.
3. Read:

   * hotel name
   * hotel code
   * star grading
   * zone code
   * zone name
   * destination code.
4. Normalize values.
5. Validate every row.
6. Detect duplicate hotel codes.
7. Fail the import if duplicates exist.
8. Validate star grading.
9. Validate destination code.
10. Validate zone code.
11. Upsert catalogue entries.
12. Report inserted, updated, unchanged and rejected rows.
13. Never silently discard invalid records.

The final import MUST produce:

```text
340 unique active catalogue entries
```

---

# 13. Catalogue Import Idempotency

The import MUST be idempotent.

Running the same source files repeatedly MUST NOT create duplicate records.

The unique key is:

```text
hotelCode
```

If an existing catalogue entry changes, the import updates the GCT-owned attributes.

Examples:

```text
starGrading
destinationCode
zoneCode
zoneName
active
```

Hotel content is not modified by the catalogue importer.

---

# 14. Catalogue Deactivation

The catalogue MUST support deactivation.

A property removed from a future approved catalogue source MUST NOT automatically be physically deleted.

Instead:

```text
active = false
```

Deactivated properties MUST:

* stop participating in attribute-based searches;
* stop being eligible for future Hotelbeds content synchronization;
* remain available for historical/reference purposes.

Physical deletion is not part of this capability.

---

# 15. Hotelbeds Content Synchronization

The existing `HotelbedsContentSynchronizationService` MUST be changed so that the persistent catalogue is the authoritative source of selected hotel codes.

The current environment variable:

```text
HOTELBEDS_SELECTED_HOTEL_CODES
```

MUST no longer be the permanent source of the GCT hotel catalogue.

It may remain temporarily available for development/testing compatibility, but production synchronization MUST obtain active hotel codes from `HotelCatalogueEntry`.

---

# 16. Synchronization Scope

For every content synchronization:

```text
SELECT hotelCode
FROM HotelCatalogueEntry
WHERE active = true
```

Only these codes may be submitted to the Hotelbeds Content API.

The synchronizer MUST NOT perform destination-wide imports.

The synchronizer MUST NOT discover additional Hotelbeds hotels and automatically add them to the catalogue.

# 17. Batch Processing

The 340 selected hotels MUST be processed in controlled batches.

Do not place the complete catalogue into a single unbounded request.

Introduce a configurable batch size, for example:

```text
HOTELBEDS_CONTENT_BATCH_SIZE
```

The exact default may be selected during implementation based on the Hotelbeds Content API request constraints.

The implementation MUST support:

```text
340 hotels
→ batch 1
→ batch 2
→ batch 3
→ ...
```

The batch processor MUST:

* preserve the selected hotel codes;
* process batches sequentially or under a controlled concurrency limit;
* respect the configured Hotelbeds QPS limit;
* record progress;
* support retryable failures;
* avoid reprocessing successful batches unnecessarily;
* report total processed/failed counts.

Do not exceed the configured Hotelbeds QPS.

# 21. Dual Accommodation Selection Model

The accommodation discovery model MUST support two selection modes.

Introduce a canonical selection concept rather than implementing two unrelated search mechanisms.

## Mode 1 — Explicit Hotel Code Selection

Used by existing/curated package tours.

Input:

```text
hotelCodes[]
```

Example:

```text
hotelCodes = [
  "676612",
  "676754",
  "676884"
]
```

The result must be restricted to the specified codes.

This mode does not use `starGrading`, destination or zone to determine the candidate set.

---

# 22. Mode 2 — Attribute-Based Selection

Used by on-demand package construction.

Supported catalogue filters:

```text
destinationCode?
zoneCode?
starGrading?
```

Example:

```text
destinationCode = "CPT"
zoneCode = "3"
starGrading = 5
```

The catalogue query returns only active entries matching the supplied criteria.

Filtering MUST occur against `HotelCatalogueEntry`.

It MUST NOT be performed against Hotelbeds `categoryCode`.

---

Extend the existing `AccommodationSearchCriteria` without removing current fields.

Current fields remain supported:

```text

```

```typescript

```

These fields represent candidate-selection criteria.

They do not themselves constitute live availability.

# 24. Selection Precedence

The search engine MUST apply the following precedence:

### Explicit hotel codes

If `hotelCodes` is supplied and non-empty:

```text
hotelCodes
```

is the authoritative candidate set.

Optional geographic/rating criteria MAY further restrict that set if explicitly supplied, but MUST NOT expand it.

### Attribute search

If no explicit hotel codes are supplied:

```text
destinationCode
zoneCode
starGrading
```

are used to derive the candidate set from the active catalogue.

### No catalogue selection

A production package-builder search MUST NOT fall back to unrestricted Hotelbeds accommodation discovery.

The curated catalogue remains the GCT accommodation boundary.

---

# 25. Candidate Selection vs Live Availability

This distinction MUST be preserved.

The catalogue search determines:

> Which hotels are eligible candidates?

Hotelbeds availability determines:

> Which eligible hotels are available for the requested dates and occupancy?

Therefore:

```text
Catalogue selection
        ↓
Candidate hotel codes
        ↓
Hotelbeds Availability API
        ↓
Live availability/rates
```

The catalogue MUST NOT be treated as a source of live room availability or rates.

---

# 26. Direct Hotel-Code Package Use

Existing package tours may define a small set of eligible hotels for each overnight stop.

The expected business pattern is approximately:

```text
Overnight Stop
    |
    +-- Hotel A
    +-- Hotel B
    +-- Hotel C
    +-- Hotel D
```

The accommodation search/application layer MUST therefore support an explicit list of Hotelbeds hotel codes.

Do not require the package builder to reconstruct these properties using destination/zone/star grading.

---

# 27. Package Persistence Boundary

Do not introduce a large new package-accommodation persistence model as part of this capability unless the existing package/journey model demonstrably requires it.

For this capability:

* catalogue eligibility is persisted in `HotelCatalogueEntry`;
* explicit hotel-code selection is supported by the accommodation search/application contract;
* package-specific accommodation persistence remains aligned with the existing Journey/Package domain model.

If implementation reveals that package-specific hotel eligibility cannot be represented by the existing model, stop and report the gap rather than introducing an unrelated model.

# 28. Attribute Search Example

Given:

```text
destinationCode = CPT
zoneCode        = 3
starGrading     = 5
```

the catalogue query becomes conceptually:

```sql
SELECT *
FROM hotel_catalogue_entry
WHERE active = true
  AND destination_code = 'CPT'
  AND zone_code = '3'
  AND star_grading = 5
ORDER BY zone_name, hotel_code;
```

The result is a candidate list of Hotelbeds hotel codes.

Those codes are then passed to the live availability/rates capability.

---

# 29. Direct-Code Search Example

```text
hotelCodes = [
  "676612",
  "676754",
  "676884"

```

```sql
SELECT *
FROM hotel_catalogue_entry
WHERE active = true
  AND hotel_code IN ('676612', '676754', '676884');
```

The resulting hotel codes are passed to the live availability/rates capability.
