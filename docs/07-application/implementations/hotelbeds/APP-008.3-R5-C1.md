# APP-008.3-R5-C1 — Hotelbeds Availability Response Envelope Correction

**Document ID:** APP-008.3-R5-C1  
**Status:** Draft — Architect Review Required  
**Capability:** Accommodation Availability  
**Provider:** Hotelbeds  
**Iteration:** R5-C1  
**Depends On:** APP-008.3-R1 through R4-C1  
**Scope:** Hotelbeds Availability response mapping

---

## 1. Purpose

APP-008.3-R5-C1 corrects the Hotelbeds Availability response-envelope handling in the R5 response-mapping boundary.

The controlled live verification established that:

- R8 runtime configuration is valid;
- R2 resolved all five configured hotel candidates;
- R3 generated exactly one supplier request;
- the request used the corrected `hotels.hotel` supplier filter;
- R6 executed without retries;
- R4-C1 completed the TLS handshake successfully;
- R4-C1 completed mTLS client authentication successfully;
- Hotelbeds accepted the request and returned a successful response;
- R5 rejected the response before producing the canonical Availability result.

The application reported:

    Malformed Hotelbeds availability response: hotels collection missing.

A real Hotelbeds Availability response obtained from Postman establishes that the supplier response structure is:

    {
      "hotels": {
        "hotels": [
          ...
        ],
        "checkIn": "...",
        "total": ...,
        "checkOut": "..."
      }
    }

The current R5 mapper expects a hotel collection directly at:

    response.hotels

The verified Hotelbeds structure places the hotel collection at:

    response.hotels.hotels

The purpose of this iteration is therefore to correct the R5 response-envelope interpretation without changing the existing rate mapping or canonical Availability model.

---

## 2. Confirmed Root Cause

The current R5 mapper accepts the following response forms:

1. a top-level array;
2. a top-level `hotels` array;
3. `payload.hotels` when it is an array;
4. `payload` when it is an array.

The verified Hotelbeds Availability response instead contains:

    response.hotels.hotels[]

Therefore:

    response.hotels

is an object containing the supplier hotel collection rather than the collection itself.

The existing mapper therefore incorrectly concludes that the response contains no supported hotel collection and throws:

    Malformed Hotelbeds availability response: hotels collection missing.

This is an R5 response-contract mismatch.

No change to R3, R4-C1, R6, R7, or R8 is required.

## 5. R5 Responsibility

R5 is responsible for transforming a valid Hotelbeds Availability response into the canonical Availability representation.

The existing flow remains:

    Hotelbeds response
          ↓
    R5 response mapper
          ↓
    canonical Availability result

This iteration changes only the supplier response-envelope traversal required to locate the Hotelbeds hotel collection.

Once the hotel collection is obtained, the existing hotel, room, and rate mapping behaviour must remain unchanged unless a test proves that a separate defect exists.

---

## 6. Required Response Traversal

The mapper must recognize the verified Hotelbeds structure:

    response.hotels.hotels[]

The outer `hotels` object is the Hotelbeds Availability response envelope.

The inner `hotels` array contains the hotel results.

The implementation must therefore extract:

    response.hotels.hotels

as the hotel collection.

The implementation must not interpret the outer `response.hotels` object itself as the hotel collection.

---

## 7. Existing Supported Response Forms

The current mapper supports several response representations.

Before removing or changing any existing supported behaviour, verify whether those forms are covered by existing tests and are intentionally required by the established application contract.

The correction must not unnecessarily remove existing supported behaviour.

At minimum, the verified Hotelbeds production response must be supported:

    {
      "hotels": {
        "hotels": [...]
      }
    }

If existing tests demonstrate intentional support for other response forms, preserve them unless they conflict directly with the verified Hotelbeds contract.

Do not introduce speculative response variants merely because they are technically possible.

## 11. No-Availability Behaviour

R5 must distinguish between:

1. a valid Hotelbeds response containing an empty hotel collection;
2. a malformed response that does not contain the expected Hotelbeds response envelope;
3. a supplier error or warning response.

An empty:

    response.hotels.hotels[]

must not automatically be treated as a malformed response if the Hotelbeds contract establishes it as a valid no-availability response.

The mapper should preserve the existing canonical no-availability semantics where the response is structurally valid.

Do not invent unavailable semantics for an unrecognized response structure.

---

## 12. Malformed Response Handling

The mapper must continue to fail closed for structurally invalid responses.

A response that does not contain the required Hotelbeds Availability response structure must not silently produce a canonical availability result.

The existing generic error behaviour may remain, but it must no longer incorrectly reject the verified structure:

    response.hotels.hotels[]

as malformed.

Error messages must not expose:

- supplier credentials;
- audit tokens;
- authentication information;
- private keys;
- passphrases;
- unnecessary raw supplier payloads.

---

## 13. Audit Data

The supplier response contains an `auditData` object.

- server information;
- environment information.

R5-C1 must not expose or log supplier audit tokens or other sensitive response metadata.

No new audit-data mapping is required.
