## 2. Purpose

APP-008.3-R4-C1 corrects the identified R4 transport limitation preventing genuine mutual TLS execution against the Hotelbeds Availability mTLS endpoint.

The current R4 transport uses native `fetch` and passes TLS material through a non-standard `tls` property. Native Node `fetch` does not consume that property as client certificate/private-key configuration.

R4-C1 SHALL correct this within the existing R4 transport boundary.

The resulting execution path SHALL remain:

    R6 Supplier Protection
        ↓
    R4 Hotelbeds Gateway / Client
        ↓
    R4 Hotelbeds Transport
        ↓
    Node HTTPS mTLS connection
        ↓
    Hotelbeds Availability endpoint

R4-C1 SHALL NOT redesign the accepted R1-R7 architecture.

## 4. Locked Transport Design

The transport mechanism for R4-C1 is explicitly fixed.

R4-C1 SHALL use Node's built-in `https.request` internally within the existing `HotelbedsTransport` boundary.

The implementation MUST NOT introduce:

- Axios;
- a new HTTP client;
- Undici as a new direct dependency;
- another supplier transport;
- an alternative Hotelbeds execution path.

The existing `HotelbedsTransport` boundary SHALL remain the application-facing transport abstraction.

The change is an internal correction to the implementation of that boundary.

---

## 5. Existing TLS Configuration

R4-C1 SHALL reuse the existing Hotelbeds TLS configuration variables:

    HOTELBEDS_TLS_CLIENT_CERTIFICATE
    HOTELBEDS_TLS_PRIVATE_KEY
    HOTELBEDS_TLS_TRUSTED_CA

No new `HOTELBEDS_MTLS_*` configuration namespace SHALL be introduced.

No configuration migration SHALL be required.

The existing `hotelbeds-integration-config.ts` configuration model remains authoritative.

---

## 6. TLS Value Representation

The existing TLS configuration values SHALL represent PEM certificate/key material.

They SHALL NOT be interpreted as file paths.

R4-C1 MUST NOT introduce certificate or key file-reading logic.

The configured values SHALL be passed to the Node HTTPS TLS options as certificate material.

The implementation SHALL preserve the existing environment-driven configuration approach.

---

## 7. TLS Configuration Rules

The following rules SHALL apply.

### 7.1 No TLS Configuration

If neither client certificate nor private key is configured:

- normal non-mTLS transport remains supported;
- the transport MUST NOT fail solely because TLS material is absent.

### 7.2 Certificate and Key

Client certificate and private key SHALL be supplied together.

If only one is configured:

- configuration MUST fail safely;
- no supplier request SHALL be attempted.

### 7.3 Trusted CA

Trusted CA is optional.

If configured:

- it SHALL be passed to the Node HTTPS TLS configuration.

If not configured:

- Node's normal trusted certificate authorities SHALL remain in effect.

### 7.4 Certificate Verification

TLS certificate verification MUST remain enabled.

The implementation MUST NOT use:

    rejectUnauthorized: false

or any equivalent insecure bypass.

---

## 8. mTLS Transport Construction

When client certificate and private key are configured, the Node HTTPS request SHALL be constructed with the appropriate TLS options, including:

- `cert`;
- `key`;
- `ca` when configured.

The transport MUST establish genuine client-certificate TLS rather than merely forwarding TLS data through an unsupported fetch option.

The implementation MUST NOT silently fall back to a non-mTLS connection when mTLS material is configured.

---

## 9. Existing Transport Interface

The existing `HotelbedsTransport` interface SHALL remain stable unless a minimal internal change is technically unavoidable.

Callers MUST continue to interact with the existing transport abstraction.

The following layers MUST remain unaware of the underlying HTTPS implementation:

- R6 executor;
- Hotelbeds gateway;
- Hotelbeds client;
- Hotelbeds provider;
- R7 application service.

The mTLS implementation belongs entirely inside the R4 transport/configuration boundary.

---

## 10. Authentication Preservation

mTLS does not replace Hotelbeds API authentication.

The existing authentication mechanism SHALL remain unchanged.

Requests SHALL continue to contain:

- API key;
- X-Signature.

R4-C1 MUST NOT:

- duplicate signature generation;
- move authentication into the HTTPS transport;
- modify the existing authentication algorithm;
- change authentication headers.

The existing `hotelbeds-authentication.ts` implementation SHALL remain authoritative.

---

## 11. Endpoint Preservation

The existing environment-configured Hotelbeds endpoint SHALL remain authoritative.

R4-C1 MUST NOT hard-code:

- test credentials;
- production credentials;
- supplier-specific URLs outside the existing configuration mechanism.

The corrected transport SHALL be capable of connecting to the configured Hotelbeds Availability mTLS endpoint.

---

## 12. Request Preservation

The existing R4 request supplied to the transport SHALL remain unchanged.

R4-C1 MUST NOT alter:

- HTTP method;
- request URL construction;
- request payload;
- request batching;
- request ordering;
- Hotelbeds request DTOs.

The transport correction concerns connection establishment only.

---

## 13. Timeout Preservation

The existing `timeoutMs` configuration SHALL remain authoritative.

The `https.request` implementation SHALL preserve the existing timeout contract.

A timeout MUST:

- terminate the request;
- surface through the existing transport failure mechanism;
- remain distinguishable from a successful supplier response.

R4-C1 MUST NOT introduce a second timeout policy.

---

## 14. GZIP Preservation

The existing R4 GZIP behaviour SHALL remain unchanged.

The transport SHALL continue to:

- advertise GZIP support where currently required;
- receive compressed responses;
- detect `Content-Encoding: gzip`;
- decompress the response;
- expose the decompressed response body to the existing R4 execution layer.

R4-C1 MUST NOT introduce a second compression implementation.

---

## 15. Raw Response Preservation

The existing R4 raw-response contract SHALL remain unchanged.

The transport/execution boundary SHALL continue to preserve:

- request index;
- request payload;
- HTTP status;
- response headers;
- response body;
- supplier error payload;
- transport failure details.

mTLS support MUST NOT alter the structured R4 result contract.

---

## 16. Transport Error Handling

mTLS/TLS failures SHALL surface as transport/integration failures through the existing error mechanism.

Examples include:

- certificate loading failure;
- private-key loading failure;
- invalid certificate material;
- invalid private-key material;
- TLS handshake failure;
- certificate validation failure;
- connection failure;
- timeout.

The implementation MUST NOT convert TLS failures into:

    available = false

or any other successful Availability result.

The implementation MUST NOT silently retry using a non-mTLS transport.

---

## 17. Configuration Validation

Configuration validation SHALL enforce the following minimum rules:

| Configuration | Required Behaviour |
|---|---|
| Certificate absent + key absent | Valid non-mTLS configuration |
| Certificate present + key present | Valid mTLS configuration |
| Certificate present + key absent | Invalid |
| Certificate absent + key present | Invalid |
| CA present without certificate/key | Invalid or ignored according to existing configuration contract, but behaviour MUST be explicit and tested |
| CA present with certificate/key | Valid |

The implementation SHALL choose the smallest behaviour consistent with the existing configuration architecture for the CA-without-mTLS case and document that behaviour in code/tests.

No supplier request SHALL occur when mandatory TLS configuration is invalid.

---

## 18. Testability

The existing transport test seam SHALL remain available.

The current `HotelbedsFetchLike` abstraction exists to make transport behaviour testable without live supplier calls.

Because R4-C1 uses `https.request` internally, the implementation MAY replace or adapt this internal seam if necessary.

Any replacement SHALL:

- remain injectable;
- avoid real network access in automated tests;
- allow TLS options to be inspected;
- allow request/response behaviour to be controlled;
- preserve focused testing of timeout and response handling.

The change SHALL be limited to the smallest testability mechanism required by the new HTTPS implementation.

---

## 19. Focused Tests

R4-C1 SHALL add or update focused tests covering at minimum:

### Test 1 — No TLS Configuration

Verify that a valid configuration without TLS certificate/key remains usable for non-mTLS operation.

### Test 2 — Valid mTLS Configuration

Verify that certificate and private key are accepted together.

### Test 3 — Certificate Propagation

Verify that the configured certificate reaches the Node HTTPS TLS options.

### Test 4 — Private Key Propagation

Verify that the configured private key reaches the Node HTTPS TLS options.

### Test 5 — Optional CA

Verify that a configured trusted CA reaches the TLS options.

### Test 6 — Missing Private Key

Verify that certificate without private key fails safely before supplier execution.

### Test 7 — Missing Certificate

Verify that private key without certificate fails safely before supplier execution.

### Test 8 — Invalid TLS Material

Verify that invalid TLS configuration surfaces as a controlled configuration/transport failure.

### Test 9 — TLS Verification

Verify that certificate verification remains enabled and no insecure TLS bypass is configured.

### Test 10 — Authentication Preservation

Verify API-key and X-Signature headers remain present.

### Test 11 — Timeout Preservation

Verify the existing timeout contract remains intact.

### Test 12 — GZIP Preservation

Verify compressed responses continue to be handled correctly.

### Test 13 — Raw Response Preservation

Verify the existing R4 response contract remains intact.

### Test 14 — Existing Transport Regression

Verify existing Hotelbeds transport tests remain passing.

Tests MUST NOT:

- contain real supplier credentials;
- expose certificate/private-key contents;
- make live Hotelbeds calls.

## 24. Security Requirements

The implementation MUST:

- keep private keys outside source control;
- keep sensitive certificate material outside source control where appropriate;
- keep API credentials outside source control;
- never log certificate contents;
- never log private-key contents;
- never log API keys;

The transport uses Node's HTTPS mechanism with actual client certificate/private-key support.

Existing Hotelbeds TLS environment variables remain authoritative.

TLS values are treated as PEM material, not file paths.

### AC-04 — Certificate/Key Pair

Certificate and private key are required together when mTLS is configured.

### AC-05 — Optional CA

TLS certificate verification remains enabled.

The transport does not silently downgrade from configured mTLS to non-mTLS.

### AC-08 — Authentication

API key and X-Signature remain unchanged.

### AC-09 — Endpoint

The existing configured Hotelbeds endpoint remains authoritative.

### AC-10 — Request

R4 request payload and request semantics remain unchanged.

### AC-11 — Timeout

Existing timeout behaviour remains unchanged.

### AC-12 — GZIP

Existing GZIP behaviour remains unchanged.

### AC-13 — Raw Response

Existing R4 raw-response behaviour remains unchanged.

### AC-14 — Error Handling

TLS failures remain transport/integration failures.

### AC-15 — Testability

Automated tests can verify TLS configuration without network access.

### AC-16 — Focused Tests

All new or modified R4-C1 focused tests pass.

### AC-17 — Regression

Existing R4 and full project regression remain passing.

R4-C1 automated verification makes no live Hotelbeds calls.
