# 1. Purpose

Implement a supplier-neutral capability to retrieve the current state of a known confirmed accommodation booking.

The capability SHALL provide an authoritative supplier-state retrieval operation for an existing booking.

The primary flow is:

Known Accommodation Booking
→ Provider
→ Supplier Booking Details
→ Canonical Booking Details Result
→ APP-004 / Application

APP-008.8 is particularly required to support resolution of `UNKNOWN` outcomes produced by APP-008.6 and APP-008.7.

---

# 2. Business Context

GCT accommodation bookings are components of private multi-day packages.

After a booking has been:

- confirmed;
- cancelled;
- modified;
- or involved in an uncertain supplier operation,

the application may need to determine the current supplier state.

The booking-details operation provides that state.

It SHALL NOT:

- create a booking;
- modify a booking;
- cancel a booking;
- calculate package pricing;
- search for arbitrary bookings;
- replace the reservation architecture.

# 4. Architectural Boundary

The canonical application flow SHALL be:

Application
→ Accommodation Booking Details Service
→ Original Accommodation Provider
→ Supplier Adapter
→ Supplier Booking Details API

The provider SHALL be determined from the existing confirmed booking.

The operation MUST NOT perform provider discovery.

The operation MUST NOT search alternative suppliers.

Hotelbeds-specific request/response DTOs SHALL remain inside the Hotelbeds adapter.

---

# 5. Known Booking Requirement

APP-008.8 retrieves a specific known booking.

The canonical request MUST contain sufficient information to identify:

- internal reservation identity where available;
- provider;
- confirmed supplier booking reference.

The supplier booking reference is the confirmed booking reference returned by APP-008.5.

The availability `rateKey` or CheckRate offer reference MUST NOT be used as the booking identifier.

---

# 6. Provider Continuity

The original booking provider is authoritative.

For example:

Existing Booking
→ Hotelbeds

Booking Details
→ Hotelbeds

The service MUST NOT select another accommodation provider.

This preserves booking continuity and supports future multiple suppliers.

---

# 7. Canonical Request

The canonical request SHALL remain supplier-neutral.

Minimum information:

- provider;
- opaque supplier booking reference;
- internal reservation identity where available;
- correlation context where supported by the existing application architecture.

No Hotelbeds-specific booking DTO SHALL appear in the canonical request.

---

# 8. Canonical Result

The canonical result SHALL represent the current supplier state of the booking.

A successful result SHALL preserve, where returned and supported by the canonical model:

- provider;
- supplier booking reference;
- booking status;
- accommodation;
- room options/booked rooms;
- rate information;
- stay dates;
- occupancy;
- guests;
- holder;
- supplier price;
- cancellation policy/status;
- modification eligibility;
- supplier confirmation information;
- relevant supplier metadata.

The result MUST NOT expose raw supplier JSON.

---

# 9. Booking Status

The canonical result SHALL distinguish the supplier state.

At minimum the implementation SHALL support:

- `CONFIRMED`;
- `CANCELLED`;
- `MODIFIED`;
- `UNKNOWN`;
- `FAILED`.

Where the supplier exposes additional states, Copilot SHALL map them to the existing canonical reservation/booking state where an appropriate mapping exists.

Do not expose a Hotelbeds-specific status enum through the canonical contract.

---

# 10. Unknown-State Resolution

APP-008.8 SHALL provide the retrieval mechanism required to resolve uncertain supplier outcomes.

Examples:

APP-008.6:

Cancellation
→ UNKNOWN
→ APP-008.8 Details
→ Current Supplier State

APP-008.7:

Modification
→ UNKNOWN
→ APP-008.8 Details
→ Current Supplier State

If the retrieved supplier state proves the operation succeeded, the canonical result SHALL represent the confirmed supplier state.

If the supplier reports the booking as unchanged, the result SHALL represent that state.

APP-008.8 SHALL NOT itself perform a cancellation or modification to resolve uncertainty.

---

# 11. Supplier Reference

The confirmed supplier booking reference SHALL remain opaque at the canonical boundary.

Conceptually:

SupplierReference

- provider
- opaqueReference

For Hotelbeds, the adapter SHALL translate the opaque reference into the supplier-specific booking reference required by the Booking Details operation.

The canonical model MUST NOT expose Hotelbeds-specific reference names.

---

# 12. Hotelbeds Booking Details

Hotelbeds' Hotels Booking API provides booking-detail retrieval as part of its `/bookings` functionality. The API is designed to retrieve the details of a particular booking in addition to confirming, modifying and cancelling bookings. :contentReference[oaicite:1]{index=1}

Copilot SHALL inspect the current Hotelbeds documentation and existing adapter implementation to determine the exact:

- HTTP method;
- endpoint;
- request parameters;
- response structure;
- booking reference requirements;
- status values;
- error behaviour.

These details SHALL remain inside the Hotelbeds adapter.

Do not place Hotelbeds endpoint paths or DTO structures into the canonical contract.

---

# 13. Hotelbeds Transport

Reuse the established Hotelbeds infrastructure:

- authentication;
- signature generation;
- mTLS;
- HTTP gateway;
- timeout;
- transport;
- supplier error mapping;
- existing configuration.

Do not create a second Hotelbeds transport stack.

Do not change established transport behaviour unless a concrete booking-details requirement requires it.

---

# 14. Current Accommodation State

The result SHOULD preserve the current accommodation information returned by the supplier, including where available:

- accommodation identity;
- name;
- location;
- room information;
- board;
- rate;
- booking conditions.

Static accommodation content remains owned by the accommodation/content architecture.

Dynamic supplier booking information belongs to the booking-details result.

Do not duplicate the complete Hotelbeds Content API model.

---

# 15. Room State

The result SHALL preserve the current booked room information where returned.

For multiple rooms, preserve:

- room association;
- room identity/reference;
- room name/type where available;
- associated occupancy;
- associated rate information where available.

Do not flatten multiple booked rooms into one room.

Do not discard room-to-guest or room-to-rate relationships where the supplier returns them.

---

# 16. Rate State

Where the supplier returns current rate information, preserve the canonical rate concepts already established by APP-008.3.

The result MAY include:

- rate reference;
- rate classification;
- board;
- pricing;
- currency;
- occupancy;
- cancellation conditions;
- payment information;
- packaging information where returned.

Do not introduce a new parallel accommodation rate model.

Reuse or extend existing canonical structures where appropriate.

---

# 17. Occupancy and Guests

Where returned by the supplier, the booking-details result SHALL preserve:

- number of rooms;
- adults;
- children;
- child ages where available;
- guest identity;
- room association.

The implementation MUST support multiple rooms.

The supplier response SHALL NOT be reduced to aggregate occupancy if room-level information is available.

---

# 18. Booking Holder

Where returned, preserve canonical holder information:

- first name;
- surname;
- email;
- phone where available.

Do not expose supplier-specific holder DTOs.

---

# 19. Stay Dates

Where returned, preserve:

- check-in;
- check-out.

The canonical result SHALL use existing GCT date/value-object conventions.

Do not reinterpret supplier dates using application-local assumptions.

---

# 20. Supplier Price

Where returned, preserve the supplier-confirmed booking price.

The result SHALL distinguish the supplier booking amount from:

- GCT package price;
- GCT markup;
- GCT commission;
- customer-facing package price.

APP-008.8 MUST NOT calculate package pricing.

APP-005 remains responsible for GCT commercial pricing.

---

# 21. Cancellation / Modification Eligibility

Where the supplier returns current policies indicating whether the booking can be:

- cancelled;
- modified;

the canonical result SHOULD preserve those capabilities.

These values describe current supplier state.

They do not execute cancellation or modification.

APP-008.6 remains responsible for cancellation.

APP-008.7 remains responsible for modification.

---

# 22. Reservation Integration

APP-004 remains responsible for:

- reservation identity;
- reservation lifecycle;
- persistence;
- supplier references;
- reservation snapshots.

APP-008.8 SHALL integrate through the existing APP-004 boundary.

It MUST NOT create a parallel reservation model.

If APP-004 provides a suitable update/reconciliation mechanism, reuse it.

If APP-004 currently lacks a persistence operation required to record retrieved supplier state, Copilot SHALL report the limitation rather than inventing a new repository architecture.

---

# 23. Resolution of Unknown State

When APP-008.8 is explicitly used to resolve an existing `UNKNOWN` reservation state:

1. Retrieve current supplier details.
2. Map the supplier state canonically.
3. Return the authoritative current state.
4. Update APP-004 through the existing reservation boundary where supported.
5. Preserve the supplier booking reference.

APP-008.8 SHALL NOT automatically perform another state-changing operation.

---

# 24. Persistence Boundary

Retrieval itself is read-only against the supplier.

The supplier SHALL NOT be modified by APP-008.8.

Local reservation persistence MAY be updated if required to synchronize the known current supplier state through the established APP-004 architecture.

Do not introduce:

- new booking tables;
- new reservation repositories;
- new reconciliation stores;

solely for APP-008.8.

---

# 25. Supplier Failure

If the supplier rejects or cannot fulfil the booking-details request:

- return the canonical failure;
- preserve the original reservation state;
- preserve the supplier error classification;
- do not infer a new booking state without evidence.

A supplier failure retrieving details MUST NOT automatically mean:

- cancelled;
- modified;
- confirmed;
- failed booking.

---

# 26. Transport Failure

A transport failure SHALL remain distinguishable from a confirmed supplier booking state.

If the supplier cannot be contacted:

- return an appropriate canonical retrieval failure;
- do not change the booking status based solely on absence of response;
- preserve any existing `UNKNOWN` state.

Do not claim that the booking no longer exists merely because the supplier call failed.

---

# 27. Not Found

If the supplier explicitly reports that the booking reference does not exist:

- map to the canonical booking-details failure/not-found outcome;
- preserve the distinction from transport failure;
- do not automatically mark the reservation cancelled.

A future reconciliation capability may determine why a supplier booking cannot be found.

APP-008.8 MUST NOT invent that workflow.

---

# 28. Idempotency

Booking Details is a read operation.

It does not require booking-style write idempotency.

The implementation SHALL remain safe to call repeatedly.

Repeated retrieval MUST NOT:

- create bookings;
- modify bookings;
- cancel bookings;
- duplicate reservations.

Any local state synchronization SHALL use the established APP-004 mechanism.

---

# 29. Multiple Suppliers

The canonical capability SHALL support multiple accommodation suppliers.

Provider identity SHALL come from the original booking.

A future supplier can implement:

AccommodationProvider
→ getBookingDetails()

without changing the canonical application contract.

Supplier-specific booking-detail structures remain inside each adapter.

---

# 30. Security

Booking details may contain personal and commercially sensitive information.

The implementation MUST NOT log:

- API credentials;
- private keys;
- signatures;
- authentication headers;
- unnecessary guest personal data.

Logs MAY contain safe operational information such as:

- internal reservation ID;
- provider;
- supplier booking reference where permitted;
- retrieval result;
- correlation ID.

Follow the existing security and logging architecture.

# 38. Final Architectural Statement

APP-008.8 establishes the accommodation booking-details boundary:

Known Accommodation Booking
→ Original Provider
→ Supplier Booking Details
→ Canonical Current Booking State
→ APP-004 / Application

The capability is read-only against the supplier.

It does not create, modify or cancel bookings.

The confirmed supplier booking reference is the authoritative supplier identifier.

Hotelbeds remains an adapter.

APP-004 remains responsible for reservation lifecycle and persistence.

APP-005 remains responsible for GCT package pricing.

APP-008.8 provides the retrieval foundation required to resolve uncertain booking, cancellation and modification outcomes.

Future booking-list, supplier reconciliation, package-level reconciliation and operational booking-history capabilities remain separate concerns.
