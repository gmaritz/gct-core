# APP-008.3-R3-C1 — Hotelbeds Availability Hotel Filter Contract Correction

**Document ID:** APP-008.3-R3-C1  
**Status:** Draft — Architect Review Required  
**Capability:** Accommodation Availability  
**Provider:** Hotelbeds  
**Iteration:** R3-C1  
**Depends On:** APP-008.3 R1-R8  
**Scope:** Hotelbeds Availability R3 request contract and directly affected test consumers

---

## 1. Purpose

APP-008.3-R3-C1 corrects the Hotelbeds Availability hotel-filter contract from the currently generated `hotels.codes` property to the verified Hotelbeds Availability `hotels.hotel` property.

The controlled live verification established that:

- R8 runtime configuration is valid;
- five Hotelbeds hotel candidates resolve successfully through R2;
- R3 generates one supplier request;
- R6 executes normally;
- R4-C1 establishes HTTPS and mTLS successfully;
- Hotelbeds receives the request;
- Hotelbeds rejects the request because the hotel filter does not conform to the verified Hotelbeds Availability request structure.

The current application generates:

    hotels: {
      codes: [...]
    }

The known-working Hotelbeds Availability request uses:

    hotels: {
      hotel: [...]
    }

The correction must align the R3 request model and all directly affected consumers and test fixtures with the verified supplier contract.

---

## 2. Confirmed Root Cause

The current R3 Hotelbeds request builder constructs the hotel filter using the property `hotels.codes`.

The working Hotelbeds Availability request supplied during investigation uses `hotels.hotel`.

The controlled live Hotelbeds response was:

    The request must have unique filter. Options: Destination, Geolocation, Hotels

The investigation established that:

- Destination is not being added to the supplier request;
- Geolocation is not being added;
- hotel codes are being supplied;
- R2 candidate metadata is not incorrectly introducing destination or geolocation;
- the failure occurs at the R3 Hotelbeds request-construction boundary;
- the transport and mTLS path are functioning correctly.

A subsequent implementation attempt identified the following direct R3 dependency:

    hotelbeds-availability-execution-result.ts

This component directly reads and reconstructs the request using `request.body.hotels.codes`.

After correcting the R3 request model, the full regression additionally identified one test-only consumer:

    hotelbeds-availability-transport-execution.test.ts

Its `createAvailabilityRequest` fixture still constructs:

    hotels: {
      codes: hotelCodes
    }

This fixture must be updated because it represents the old R3 request contract.

The correction remains one contract change:

    hotels.codes → hotels.hotel

No new supplier-filter behaviour is introduced.

    hotel: ReadonlyArray<number>

instead of:

    codes: ReadonlyArray<number>

- preserve immutability;
- preserve existing typing conventions;
- preserve existing request-object immutability;
- preserve existing batching behaviour.

Do not retain a compatibility alias.

Do not emit both `hotel` and `codes`.

The exact supplier contract field must be:

    hotels.hotel
