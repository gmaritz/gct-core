# APP-008.2-R2

# Hotelbeds Content Response Investigation & Mapping Fix

---

## Objective

Resolve the live Hotelbeds Content API validation failure reported during APP-008.2 verification:

```text
Hotelbeds hotel 1 does not include a name.
```

Do not redesign APP-008.2.

---

## 1. Inspect the Actual Response

Using the existing Hotelbeds test credentials and **test environment only**, execute the same Content API request used during APP-008.2 verification.

Capture and inspect the actual JSON structure for the first returned hotel.

Determine:

* actual hotel identifier
* actual hotel name field/path
* response wrapper structure
* fields requested
* whether `fields=all` is being sent
* whether the response is being transformed before validation

Do not expose credentials or authentication headers.

---

## 2. Compare Against Hotelbeds Contract

Compare the actual response with the current Hotelbeds Content API Hotels response contract.

Hotelbeds documents the Hotels operation as the primary static hotel-content operation and recommends using `fields=all` for the initial content load.

Confirm that the request generated by the existing implementation is equivalent to the required Content API request.

---

## 3. Fix the Request if Necessary

If the current request does not request the required hotel content fields, correct the request.

The initial synchronization request should use the established equivalent of:

```text
GET /hotel-content-api/1.0/hotels
    ?fields=all
    &language=ENG
    &from=1
    &to=...
```

Use the existing request/configuration conventions.

Do not hard-code unnecessary query parameters.

---

## 4. Fix the Mapper if Necessary

If the Hotelbeds response contains the hotel name but the current mapper does not read it correctly:

* correct the mapper
* preserve the canonical hotel-content model
* do not weaken validation
* do not make the hotel name optional merely to bypass the failure

The canonical hotel content record must continue to require a valid hotel identity and name unless the established GCT Core model explicitly defines otherwise.

---

## 5. Preserve Validation

Do not change:

```text
missing required hotel name
        ↓
VALIDATION_ERROR
```

into a successful record.

The mapper must correctly consume the provider response rather than suppressing a genuine missing-data condition.

---

## 6. Test the Corrected Mapping

Add or update fixtures based on the **actual Hotelbeds response structure**.

Tests must verify:

* hotel code mapping
* hotel name mapping
* description mapping
* category mapping
* address/location mapping
* coordinates where supplied
* facilities where supplied
* images where supplied
* optional fields
* malformed/missing required hotel name

---

## 7. Re-run Controlled Live Test

Using the configured Hotelbeds TEST credentials:

1. Call the Content API Hotels operation.
2. Retrieve a limited page.
3. Map the response.
4. Persist the resulting canonical hotel content.
5. Verify synchronization checkpoint behaviour.

Do not call Booking API, CheckRate or any booking operation.

---

## 8. Persistence Verification

Confirm that the corrected content is written to the production persistence path established in APP-008.2.

Verify:

```text
Hotelbeds response
        ↓
Canonical hotel content
        ↓
Prisma/repository persistence
        ↓
Persisted hotel record
```

---

## 9. Idempotency

Process the same controlled content twice.

Verify:

* no duplicate hotel is created
* the same canonical hotel is updated/upserted
* record count remains stable

---

## 10. Checkpoint

Verify:

### Successful synchronization

```text
Content persisted
        ↓
Checkpoint advances
```

### Failed synchronization

```text
Content failure
        ↓
Checkpoint does NOT advance
```
