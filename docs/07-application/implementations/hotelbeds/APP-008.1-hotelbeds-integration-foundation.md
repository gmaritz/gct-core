# 1. Objective

Implement the foundational Hotelbeds integration boundary for GCT Core.

The purpose of APP-008.1 is to establish the infrastructure required for the later Hotelbeds accommodation capabilities without yet implementing the complete hotel search or booking workflow.

The foundation shall provide:

* Hotelbeds configuration
* authentication/signature generation
* HTTP client boundary
* provider-independent Hotelbeds gateway
* request/response handling
* canonical integration errors
* timeout handling
* retry classification
* correlation information
* provider adapter isolation
* integration tests
* public exports
* implementation report

The implementation shall establish the foundation for:

```text
APP-008.2 Content Synchronization
APP-008.3 Availability & Search
APP-008.4 CheckRate
APP-008.5 Booking
APP-008.6 Post-Booking
APP-008.7 GCT Accommodation Integration
```

---

# 2. Hotelbeds API Architecture

The Hotelbeds Hotels API Suite provides separate APIs for:

* Hotel Booking API
* Hotel Content API
* Hotel Cache API
* CDS API

The Booking API provides the dynamic booking workflow, including availability, CheckRate and bookings. The Content API provides static hotel information such as descriptions, images, facilities and address information.

GCT Core shall therefore keep static content and dynamic booking data architecturally separate.

# 5. Architectural Position

The intended architecture is:

```text
GCT Core Application
        │
        ▼
Hotelbeds Integration Port
        │
        ▼
Hotelbeds Adapter
        │
        ├── Authentication
        ├── HTTP Transport
        ├── Request Mapping
        ├── Response Mapping
        └── Error Mapping
        │
        ▼
Hotelbeds API
```

The rest of GCT Core must not depend directly on Hotelbeds SDK/API implementation details.

---

# 6. Provider Isolation

Hotelbeds-specific concerns shall remain inside the integration boundary.

The following must not leak into domain/application models:

* Hotelbeds request DTOs
* Hotelbeds response DTOs
* Hotelbeds API error structures
* Hotelbeds authentication headers
* Hotelbeds signature implementation
* Hotelbeds HTTP response structures
* Hotelbeds-specific transport types

The integration boundary translates between GCT Core and Hotelbeds.

---

Before implementation Copilot shall inspect the current repository for:

* integration ports
* external service clients
* HTTP client abstractions
* configuration management
* environment variable handling
* error/result patterns
* logging

* existing integration scaffolding

APP-008.1 shall reuse established patterns wherever they already exist.

# 8. Hotelbeds Integration Contract

Establish a canonical Hotelbeds gateway contract.

Conceptually:

```text
HotelbedsRequest
        ↓
HotelbedsGateway
        ↓
HotelbedsResult
```

The public application boundary shall not expose provider-specific request/response structures.

The exact TypeScript structure shall follow existing GCT Core conventions.

---

# 9. Configuration

Hotelbeds configuration shall be externalised.

At minimum, configuration shall support:

* API key
* secret
* environment
* base URL
* request timeout

Additional configuration may be introduced where required by the existing API integration.

Credentials must never be hard-coded.

---

# 10. Environments

The integration shall distinguish at minimum:

```text
TEST
PRODUCTION
```

The implementation must make environment selection explicit.

The default development environment shall not accidentally target production.

---

# 11. Credentials

Hotelbeds credentials shall be supplied through the established GCT Core configuration mechanism.

The implementation shall not:

* commit credentials
* log credentials
* expose credentials in errors
* expose credentials through API responses
* embed credentials in source files

---

# 12. Authentication

Hotelbeds Hotels APIs use API credentials and a calculated request signature.

The authentication mechanism shall be isolated inside the Hotelbeds integration layer.

The rest of the application shall provide no knowledge of:

* signature calculation
* authentication headers
* API-key header construction
* provider authentication details

The signature implementation shall follow the current Hotelbeds API documentation and test environment requirements.

---

# 13. Signature Generation

Implement a dedicated authentication/signature component.

Conceptually:

```text
API Key
+
Secret
+
Current timestamp
        ↓
Hotelbeds Signature
```

The implementation shall:

* use the canonical Hotelbeds signing algorithm
* generate signatures at request time
* avoid persisting signatures
* avoid logging signatures
* allow deterministic unit testing through controlled time input

---

# 14. Time Dependency

Because authentication signatures depend on time, the implementation shall isolate the clock dependency where practical.

Tests must not depend on the actual wall clock.

Use the established GCT Core time abstraction if one already exists.

If no such abstraction exists, introduce the smallest focused abstraction necessary for deterministic authentication tests.

---

# 15. HTTP Transport

Implement or reuse the established HTTP transport mechanism.

The transport shall support:

* HTTPS
* GET
* POST
* PUT
* DELETE where required by later Hotelbeds APIs
* JSON request bodies
* JSON responses
* request headers
* timeout
* response status handling

Do not introduce a provider-specific HTTP client abstraction when an existing GCT Core abstraction already provides the required behaviour.

---

# 16. Base URL

Hotelbeds endpoints shall be constructed from configured environment-specific base URLs.

Do not hard-code production URLs throughout the source tree.

Endpoint paths shall remain isolated from domain/application models.

---

# 17. Request Headers

The adapter shall construct Hotelbeds-specific headers internally.

The public application contract must not require callers to provide:

* API key
* signature
* provider authentication headers
* provider-specific transport headers

---

# 18. JSON

Use JSON as the canonical application transport format where supported by Hotelbeds.

Hotelbeds documentation identifies JSON as the preferred request/response representation for the Hotels API Suite.

The adapter shall translate transport data into canonical GCT Core integration structures.

---

# 19. Integration Result

Implement a canonical result boundary.

The result shall provide, at minimum:

* success/failure
* operation where applicable
* provider response where appropriate through a controlled representation
* error information
* retryability
* correlation/reference information

Results shall be immutable.

---

# 20. Integration Errors

Implement canonical Hotelbeds integration error categories.

At minimum:

```text
CONFIGURATION_ERROR
AUTHENTICATION_ERROR
AUTHORIZATION_ERROR
VALIDATION_ERROR
NOT_FOUND
RATE_LIMITED
TIMEOUT
NETWORK_ERROR
PROVIDER_ERROR
MALFORMED_RESPONSE
UNKNOWN_ERROR
```

Use existing GCT Core error conventions where available.

---

# 21. Provider Error Mapping

Hotelbeds-specific error responses shall be translated into canonical GCT Core integration errors.

Provider-specific error codes may be retained as diagnostic metadata where useful.

They must not become the application's primary error taxonomy.

---

# 22. Retry Classification

The integration foundation shall identify whether an error is retryable.

Typical retryable conditions include:

* temporary network failure
* timeout
* temporary provider failure
* rate limiting

Typical non-retryable conditions include:

* invalid credentials
* invalid request
* unsupported operation
* provider business rejection

Exact classification shall remain configurable by the provider adapter where necessary.

---

# 23. Retry Execution

APP-008.1 shall classify retryable failures.

It shall not implement an autonomous retry scheduler unless the repository already provides an approved retry infrastructure.

The expected responsibility is:

```text
Hotelbeds Adapter
        ↓
Retryable Result
        ↓
Application / Infrastructure Retry Mechanism
```

---

# 24. Timeout

Hotelbeds requests shall have an explicit timeout.

A timeout must result in a canonical timeout/integration failure.

The adapter must not leave unresolved promises or hanging requests.

---

# 25. Correlation

Integration requests shall carry a correlation/request identifier where the established GCT Core architecture supports it.

The purpose is to trace:

```text
Application Request
        ↓
Hotelbeds Request
        ↓
Hotelbeds Response
```

Do not expose sensitive authentication information in correlation data.

---

# 26. Logging

Integration logging shall follow the established GCT Core logging conventions.

Useful diagnostic information includes:

* operation
* endpoint category
* correlation ID
* response status
* duration
* retryability
* canonical error

Do not log:

* API secret
* signature
* full authentication headers
* unnecessary guest personal information
* complete provider responses where they contain sensitive data

---

# 27. Observability

The foundation should expose sufficient information to diagnose:

* connection failures
* authentication failures
* provider failures
* timeouts
* rate limits
* malformed responses

Do not introduce a new observability framework if one already exists.

---

# 28. Response Validation

The integration boundary shall verify that provider responses are structurally usable before exposing them to subsequent application capabilities.

At minimum, it shall detect:

* malformed JSON
* unexpected response structure
* missing required provider response elements

APP-008.1 shall not implement hotel business validation.

That belongs to later milestones.

---

# 29. Provider DTO Boundary

Hotelbeds API DTOs may be introduced inside the integration adapter.

They shall remain internal to the adapter.

Conceptually:

```text
Hotelbeds DTO
      ↓
Adapter Mapping
      ↓
GCT Core Integration Model
```

Do not export provider DTOs through the application root.

---

# 30. Authentication Testability

The authentication component shall be independently testable.

Tests shall verify:

* known input produces expected signature
* timestamp changes affect generated signature appropriately
* credentials are consumed correctly
* no credentials are exposed in result objects

Use controlled test values.

Do not make live Hotelbeds authentication calls part of normal unit tests.

---

# 31. HTTP Testability

The transport boundary shall be mockable.

Tests shall be able to simulate:

* successful response
* 4xx response
* 5xx response
* timeout
* network failure
* malformed response
* rate limit

No live network dependency is required for the standard test suite.

---

# 32. Production Safety

The integration shall fail safely when:

* credentials are missing
* configuration is invalid
* Hotelbeds is unavailable
* authentication fails
* the response is malformed

No failure may silently appear as successful Hotelbeds availability or booking data.

---

# 33. Domain Independence

The Hotelbeds integration must not introduce dependencies into:

* Traveller Aggregate
* Reservation Aggregate
* Journey Aggregate
* Invoice Aggregate
* other domain models

The dependency direction remains:

```text
Domain
   ↑
Application
   ↑
Integration Adapter
   ↑
Hotelbeds
```

---

# 34. Accommodation Boundary

Hotelbeds represents accommodation supply.

The provider integration shall not become the owner of the GCT Core Accommodation model.

Later milestones shall map Hotelbeds accommodation information into the canonical GCT Core accommodation model.

APP-008.1 only establishes the transport/integration foundation.

---

# 35. Static vs Dynamic Data

Hotelbeds distinguishes static hotel content from dynamic booking information.

Static content includes information such as:

* descriptions
* images
* facilities
* addresses

Dynamic information includes:

* prices
* availability
* cancellation policies
* fees.

The architecture shall preserve this distinction.

---

# 36. Content Boundary

Hotel Content API integration belongs to APP-008.2.

APP-008.1 shall not retrieve hotel content.

Hotelbeds recommends using a batch process and local database for Content API data rather than retrieving static information in real time.

---

# 37. Booking Boundary

Hotel Booking API integration belongs to later milestones.

The Booking API provides the dynamic booking workflow through:

```text
Hotels
   ↓
CheckRates where required
   ↓
Bookings
```

Hotelbeds documents this as its standard hotel booking flow.

APP-008.1 establishes the infrastructure required for that flow but does not implement it.

---

# 38. CheckRate Boundary

CheckRate is explicitly outside APP-008.1.

Later APP-008.4 shall implement CheckRate for rates requiring revalidation before booking.

Hotelbeds identifies rates with `RECHECK` requirements and uses CheckRate to obtain current availability/pricing before booking.

---

# 39. Booking Boundary

Hotel booking belongs to APP-008.5.

APP-008.1 must not implement:

* holder mapping
* room mapping
* pax mapping
* booking confirmation
* cancellation
* booking retrieval

Those belong to later milestones.

The normal test suite shall not depend on live Hotelbeds credentials or network connectivity.

* stubs
* fixtures

Tests shall verify that:

* API secrets are not present in errors
* signatures are not present in logs/results
* credentials are not returned through public contracts
* provider authentication headers are not exposed outside the adapter

* implement frontend behaviour

# 57. Expected Outcome

APP-008.1 establishes the stable technical boundary required for all subsequent Hotelbeds capabilities.

The fundamental responsibility is:

> **Provide a secure, testable and provider-isolated integration foundation through which GCT Core can communicate with Hotelbeds.**

The milestone deliberately stops before hotel business functionality so that the subsequent iterations can be implemented and verified independently.
