## 2. Purpose

This specification finalizes the canonical Accommodation Availability contract required before implementation of APP-008.3-R5-C2.

The contract must support the commercial requirement that a client searching a tour package can receive:

- one or more accommodation options;
- multiple rooms;
- independent occupancy per room;
- multiple room types;
- multiple rate options per room;
- pricing;
- board/meal-plan information;
- availability/bookability status;
- cancellation conditions;
- taxes and fees;
- payment information;
- packaging information;
- supplier-neutral booking references.

The canonical model MUST NOT be derived from or shaped around Hotelbeds.

Hotelbeds remains an infrastructure/provider adapter.

---

# 3. Architectural Principle

The canonical flow is:

    Client Search
        ↓
    Canonical Availability Request
        ↓
    Provider Adapter
        ↓
    Supplier Request
        ↓
    Supplier Response
        ↓
    Provider Adapter
        ↓
    Canonical Availability Result
        ↓
    Client Selection
        ↓
    Canonical Selection / Booking Reference
        ↓
    Provider-Specific Booking Request

The canonical contract MUST remain supplier-neutral.

Supplier-specific concepts such as Hotelbeds `rateKey`, supplier DTO names, supplier response envelopes, and supplier-specific tax/cancellation structures MUST NOT appear in canonical contracts.

# 4. Canonical Availability Request

## 4.1 Purpose

The request represents what the client is searching for, independently of supplier implementation.

The request MUST support multiple rooms with independent occupancy.

## 4.2 Contract

    AccommodationAvailabilityRequest

        stay
            checkIn
            checkOut

        occupancy
            rooms[]

        sourceMarket

        candidateSelection

### Stay

    StayRequest

        checkIn: LocalDate
        checkOut: LocalDate

Invariants:

- `checkIn` MUST precede `checkOut`.
- Dates represent the accommodation stay.
- Supplier-specific date formats MUST NOT appear in the canonical model.

### Room Occupancy

    OccupancyRequest

        rooms: RoomOccupancy[]

    RoomOccupancy

        adults: PositiveInteger
        children: NonNegativeInteger
        childAges: NonNegativeInteger[]

Invariants:

- `rooms` MUST contain at least one room.
- `adults` MUST be at least 1.
- `children` MUST equal `childAges.length`.
- Child ages MUST be represented individually.
- Room order MUST be preserved.
- Each room MUST have independent occupancy.
- The canonical request MUST NOT impose a one-room-per-search limitation.

No canonical field named `rooms: 1` is permitted as an architectural assumption.

### Source Market

    sourceMarket: CountryCode

The source market remains a canonical business input.

### Candidate Selection

Candidate selection MUST remain independent of supplier filter semantics.

Conceptually:

    CandidateSelection

        hotelCodes?: AccommodationCode[]
        destinationCode?: DestinationCode
        zoneCode?: ZoneCode
        other canonical selection criteria

The provider adapter determines how canonical candidate selection is translated into a supplier request.

The canonical model MUST NOT contain Hotelbeds-specific filter structures.

# 5. Canonical Availability Result

## 5.1 Discriminated Result

The canonical result MUST use an explicit discriminant.

    AccommodationAvailabilityResult =
        AccommodationAvailabilityResultAvailable
        | AccommodationAvailabilityResultUnavailable

### Available Result

    AccommodationAvailabilityResultAvailable

        kind: "ACCOMMODATION"

        accommodation: Accommodation

        requestedOccupancy: OccupancyRequest

        availabilityOptions: AvailabilityOptions

        available: true

        metadata: AccommodationResultMetadata

### No-Availability Result

    AccommodationAvailabilityResultUnavailable

        kind: "NO_AVAILABILITY"

        available: false

        metadata: AccommodationResultMetadata

The `NO_AVAILABILITY` result MUST NOT contain:

- accommodation;
- room options;
- rate options;
- pricing;
- cancellation policies;
- taxes;
- supplier booking references.

No accommodation, room, rate, or booking reference may be fabricated to represent supplier no-availability.

---

# 6. Accommodation

`Accommodation` represents relatively stable accommodation identity/content.

It MUST NOT contain dynamic room/rate availability.

The existing `Accommodation` model remains the conceptual owner of:

- accommodation identity;
- name;
- category;
- location;
- rating;
- images;
- amenities;
- static policies;
- contacts;
- provider reference.

Dynamic availability information belongs exclusively under `availabilityOptions`.

---

# 7. Availability Options

## 7.1 Contract

    AvailabilityOptions

        rooms: RoomOption[]

The collection MUST preserve supplier-independent room-option ordering.

A room option represents a commercially selectable room type for the requested stay and occupancy.

An availability response MUST NOT flatten rates across rooms.

---

# 8. Room Option

## 8.1 Contract

    RoomOption

        reference: SupplierReference

        name: string

        rateOptions: RateOption[]

The room option MAY contain additional canonical display attributes in future versions, but no supplier-specific fields are permitted.

## 8.2 Room Reference

The room reference MUST use the canonical supplier-reference abstraction.

    SupplierReference

        provider: ProviderIdentifier

        opaqueReference: string

The canonical field MUST be `opaqueReference`, not `rateKey`, `roomCode`, or another supplier-specific identifier.

The provider adapter MAY populate the opaque reference from a supplier identifier.

The opaque value MUST remain uninterpreted by canonical application logic.

---

# 9. Rate Option

## 9.1 Contract

    RateOption

        bookingReference: SupplierReference

        status: RateAvailabilityStatus

        pricing: RatePricing

        occupancy: OccupancyRequest

        board: BoardOption

        allotment: NonNegativeInteger?

        payment: PaymentOption

        packaging: PackagingOption

        cancellationPolicies: CancellationPolicy[]

        taxes: Tax[]

## 9.2 Rate Availability Status

The canonical status MUST be supplier-neutral.

    RateAvailabilityStatus

        BOOKABLE
        RECHECK_REQUIRED
        UNAVAILABLE

Rules:

- `BOOKABLE` means the provider reports the option as directly bookable subject to normal booking validation.
- `RECHECK_REQUIRED` means a booking must perform the provider's required revalidation before confirmation.
- `UNAVAILABLE` MUST NOT normally be returned as a selectable rate.
- Supplier-specific status strings MUST be translated by the provider adapter.

Hotelbeds `BOOKABLE` and `RECHECK` are supplier values and MUST NOT become canonical enum names.

---

# 10. Booking Continuity

## 10.1 Supplier Reference

The canonical booking reference is:

    SupplierReference

        provider
        opaqueReference

The reference MUST be associated with the selected rate.

The canonical application MUST NOT interpret the opaque reference.

For Hotelbeds, the adapter MAY place the Hotelbeds `rateKey` into `opaqueReference`.

The canonical contract MUST NOT expose:

    rateKey

as a field.

## 10.2 Booking Requirement

The availability result MUST preserve sufficient supplier reference information for a selected room/rate option to be translated into a future provider-specific booking request.

The booking layer remains responsible for validating reference freshness and supplier-specific recheck requirements.

---

# 11. Rate Pricing

## 11.1 Contract

    RatePricing

        amount: Money

        basis: PricingBasis

### Money

The canonical availability contract MUST use the shared canonical monetary representation established by the GCT Core pricing architecture.

Conceptually:

    Money

        amount
        currency

A bare numeric amount without currency MUST NOT be used.

## 11.2 Pricing Basis

    PricingBasis

        PER_STAY
        PER_ROOM
        PER_NIGHT
        PER_ROOM_PER_NIGHT

The provider adapter MUST translate supplier pricing semantics into one of the supported canonical bases.

If the supplier response cannot establish the basis reliably, the adapter MUST NOT invent one.

## 11.3 Tax Treatment

The pricing contract MUST explicitly indicate whether the represented amount includes the taxes/fees represented separately in `taxes`.

The exact shared pricing Money/tax implementation MUST remain compatible with the pricing bounded context.

---

# 12. Board / Meal Plan

## 12.1 Contract

    BoardOption

        code: string?
        name: string

The canonical board representation is supplier-neutral.

Supplier-specific board codes may be preserved as canonical opaque codes only where they have established business value, but supplier-specific semantics MUST NOT leak into the model.

---

# 13. Allotment

`RateOption.allotment` represents the supplier-reported availability quantity where meaningful.

Rules:

- It MUST be non-negative when present.
- It MAY be absent where the supplier does not provide meaningful allotment.
- It MUST NOT be interpreted as guaranteed inventory beyond the supplier's stated semantics.
- The provider adapter MUST not invent an allotment value.

---

# 14. Payment

## 14.1 Contract

    PaymentOption

        type: PaymentType

### Payment Type

The canonical type MUST represent business-relevant payment behavior rather than supplier-specific strings.

At minimum the architecture MUST support:

- payment at booking/provider;
- payment at property;
- other provider-defined payment arrangements where required.

The exact enum/value-object names MUST be finalized during implementation without exposing supplier-specific terminology.

---

# 15. Packaging

## 15.1 Contract

    PackagingOption

        packaged: boolean

Packaging MUST remain a canonical business concept.

The supplier adapter determines the meaning of supplier packaging indicators.

No supplier-specific packaging fields may be exposed.

# 16. Cancellation Policies

## 16.1 Contract

    CancellationPolicy

        effectiveFrom: DateTime

        amount: Money

        refundable: boolean

        conditions?: string

The policy collection MUST preserve ordering.

The model MUST support multiple cancellation stages.

Examples include:

- fully refundable before a deadline;
- partial cancellation charge after a deadline;
- fully non-refundable.

Supplier-specific cancellation structures MUST be translated into this canonical representation.

A provider MUST NOT silently discard cancellation information required to communicate the booking conditions.

---

# 17. Taxes and Fees

## 17.1 Contract

    Tax

        type: TaxType

        subtype?: string

        amount: Money

        percentage?: Decimal

        included: boolean

The canonical tax model MUST support:

- fixed amounts;
- percentage-based taxes;
- included/excluded status;
- tax classification;
- optional subtype.

Supplier-specific tax field names MUST remain inside the provider adapter.

---

# 18. Rate Occupancy

Each `RateOption` MUST preserve the occupancy to which that rate applies.

The canonical representation MUST use the same multi-room occupancy semantics as the request where applicable:

    OccupancyRequest

        rooms[]

            adults
            children
            childAges[]

The architecture MUST preserve child ages.

A supplier response MUST NOT be reduced to aggregate adults/children if the supplier provides room-specific occupancy information required for selection or booking.

---

# 19. Hotel-Level Pricing Summary

Hotel-level supplier fields such as:

- `minRate`;
- `maxRate`;
- aggregate `currency`;

MUST NOT automatically become canonical fields.

CAN-003 decision:

- rate-level pricing is authoritative for selectable commercial options;
- hotel-level min/max values are derived presentation summaries unless a future business requirement explicitly requires supplier-provided aggregate values;
- canonical application logic MUST NOT depend on supplier aggregate min/max fields.

Where required for presentation, min/max values SHOULD be derived from canonical selectable rate options using canonical pricing semantics.

---

# 20. Supplier Mapping Boundary

The provider adapter is responsible for translating supplier responses.

For Hotelbeds, the conceptual mapping is:

    Hotelbeds hotel
        → Accommodation

    Hotelbeds room
        → RoomOption

    Hotelbeds rate
        → RateOption

    Hotelbeds rateKey
        → SupplierReference.opaqueReference

    Hotelbeds rateType
        → RateAvailabilityStatus

    Hotelbeds net/currency
        → RatePricing

    Hotelbeds boardCode/boardName
        → BoardOption

    Hotelbeds cancellationPolicies
        → CancellationPolicy[]

    Hotelbeds taxes
        → Tax[]

The canonical model MUST NOT contain Hotelbeds DTOs.

# 21. R5 Mapping Contract

R5 MUST map a complete valid supplier availability response into the canonical hierarchy.

For a positive response:

    supplier response
        ↓
    Accommodation
        ↓
    AvailabilityOptions
        ↓
    RoomOption[]
        ↓
    RateOption[]

R5 MUST preserve:

- accommodation ordering;
- room ordering;
- rate ordering;
- room-to-rate relationships;
- pricing;
- currency;
- occupancy;
- board;
- status;
- cancellation;
- taxes;
- booking reference.

R5 MUST NOT:

- discard selectable room/rate information;
- fabricate commercial values;
- expose supplier-specific fields;
- convert supplier errors into availability;
- treat malformed responses as `NO_AVAILABILITY`.

---

# 22. No-Availability Mapping

A valid supplier no-availability response MUST map to:

    {
        kind: "NO_AVAILABILITY",
        available: false,
        metadata: ...
    }

The provider MUST distinguish:

- valid no availability;
- valid availability with rooms/rates;
- supplier error/warning;
- malformed response;
- transport failure.

Only the first maps to `NO_AVAILABILITY`.

---

# 23. R7 Orchestration

R7 remains responsible for application-level orchestration.

R7 MUST:

- accept the canonical R5 outcome;
- preserve the canonical discriminated result;
- provide application metadata;
- aggregate results where multiple candidates/providers are involved;
- avoid supplier-specific transformations.

R7 MUST NOT reconstruct Hotelbeds room/rate semantics.

# 24. Inventory Consumer

Inventory consumers MUST narrow the discriminated result before accessing:

    result.accommodation

For:

    kind === "ACCOMMODATION"

the consumer MAY access:

- accommodation;
- availabilityOptions;
- room options;
- rate options.

For:

    kind === "NO_AVAILABILITY"

the consumer MUST NOT attempt to access accommodation or options.

Inventory freezing/cloning MUST preserve:

- accommodation;
- availability options;
- rooms;
- rates;
- pricing;
- cancellation policies;
- taxes;
- supplier references.

---

# 25. Journey and Package Composition

Package-search and journey-composition consumers MUST receive sufficient availability information to allow downstream selection.

The architecture MUST support:

    Package Search
        ↓
    Accommodation
        ↓
    Room Option
        ↓
    Rate Option
        ↓
    Client Selection

The selected option MUST retain its canonical supplier reference for later booking.

Journey composition MUST NOT choose a room or rate by supplier-specific fields.

---

# 26. Client Selection

The availability result is intended to support a future client selection flow.

A client MUST be able to select:

- accommodation;
- room option;
- rate option.

The selection MUST preserve:

- accommodation identity;
- room reference;
- rate booking reference;
- selected pricing;
- selected occupancy;
- board;
- applicable cancellation policies;
- applicable taxes;
- payment information.

The selection contract itself may be defined by a later booking/package specification, but CAN-003 MUST provide all required source information.

---

# 27. Multi-Room Semantics

The architecture MUST support:

    Room 1
        2 adults
        1 child
        child age 7

    Room 2
        1 adult
        2 children
        child ages 5, 8

Room options and rate options MUST remain associated with their relevant occupancy.

The implementation MUST NOT collapse different room occupancies into one aggregate occupancy where doing so would lose commercial selection information.

---

# 28. Immutability

Canonical Availability objects MUST be treated as immutable application data.

Collections MUST be exposed as immutable/read-only collections.

Provider adapters MUST construct canonical objects without retaining mutable supplier DTO references.

Consumers MUST NOT mutate canonical availability results.

---

# 29. Validation Invariants

The implementation MUST enforce at least:

### Request

- valid stay dates;
- at least one room;
- at least one adult per room;
- child count equals child-age count;
- valid child ages.

### Available Result

- `kind === "ACCOMMODATION"`;
- accommodation exists;
- availability options exist;
- room options are valid;
- each room contains zero or more canonical rate options;
- selectable rates contain valid pricing;
- booking references are present for selectable supplier-backed rates.

### No Availability

- `kind === "NO_AVAILABILITY"`;
- `available === false`;
- no accommodation;
- no room options;
- no rate options;
- no booking reference.

---

# 30. Existing Model Strategy

## Accommodation

Retain and use for static accommodation information.

## AccommodationRate

Do not use as the complete Availability rate contract.

It MAY be refactored or reused for shared lower-level concepts where semantically correct.

Any reuse MUST NOT compromise the new Availability contract.

## AccommodationRateResult

Retain as a separate rate-query result contract.

It MAY share value objects with CAN-003.

It MUST NOT become the Availability result contract.

## AccommodationOccupancy

Retain where existing consumers require its aggregate semantics.

It MUST NOT constrain the new canonical Availability request to aggregate occupancy.

## AccommodationOccupancyGroup

Use as an implementation precedent where appropriate, but remove any conceptual dependency on one-room-per-group from the canonical contract.

## Money

Reuse the established pricing Money model if its bounded-context dependency and semantics are compatible.

Do not duplicate Money implementations.

## Cancellation and Tax

Reuse existing shared pricing concepts only after explicit semantic compatibility is confirmed.

Do not copy supplier DTO structures into canonical models.

---

# 31. Backward Compatibility and Migration

The introduction of the new canonical Availability contract is a deliberate contract evolution.

It MUST NOT be implemented through compatibility aliases such as:

    hotels.codes
    hotels.hotel

or supplier-specific duplicate fields.

The implementation MUST migrate affected consumers to the canonical contract.

Temporary compatibility logic MUST NOT be used to hide an architectural mismatch.

The legacy `"unavailable"` accommodation sentinel may remain only where required by existing R2/R3 behavior until separately migrated.

It MUST NOT represent supplier `NO_AVAILABILITY`.

# 40. Decision

The GCT Core canonical Accommodation Availability contract is defined as a supplier-neutral commercial availability graph:

    Accommodation
        ↓
    Availability Options
        ↓
    Room Options
        ↓
    Rate Options

The contract explicitly supports multi-room occupancy, detailed room/rate selection, pricing, cancellation, taxes, payment, packaging, allotment, and future booking continuity.

Hotelbeds is an adapter and MUST translate its supplier response into this canonical contract.

No Hotelbeds-specific response structure is permitted to define the canonical model.

Implementation MUST NOT begin until this specification is architect-approved.
