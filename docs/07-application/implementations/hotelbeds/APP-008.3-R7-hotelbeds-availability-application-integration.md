## 2. Purpose

APP-008.3-R7 connects the accepted Availability components into one application-level execution flow.

R1-R6 currently provide the required individual capabilities:

- R1 — Availability Foundation
- R2 — Catalogue Candidate Resolution
- R3 — Availability Request Construction
- R4 — Hotelbeds Transport & Execution
- R5 — Canonical Availability Result Mapping
- R6 — Supplier Protection

R7 establishes the application orchestration required to execute the complete Availability capability through those accepted boundaries.

The target flow is:

    Application Availability Request
            ↓
    R2 Candidate Resolution
            ↓
    R3 Availability Request Construction
            ↓
    R6 Supplier Protection
            ↓
    R4 Hotelbeds Transport & Execution
            ↓
    R5 Canonical Availability Mapping
            ↓
    Canonical Accommodation Availability Result

R7 is an integration/orchestration iteration.

R7 MUST NOT redesign the individual R1-R6 capabilities.

---

## 3. Architectural Baseline

R1-R6 are accepted contracts.

R7 SHALL compose those contracts.

R7 MUST preserve:

- the existing R2 candidate-resolution boundary;
- the existing R3 request-builder boundary;
- the existing R4 transport/execution boundary;
- the existing R5 canonical result contract;
- the existing R6 supplier-protection boundary.

R7 MUST NOT bypass R6 to call R4 transport directly.

R7 MUST NOT bypass R5 and construct a separate canonical Availability result.

## 5. Application Entry Point

R7 SHALL establish a single application-level entrypoint for the complete Accommodation Availability capability.

The entrypoint SHALL accept the existing canonical Availability query/request contract.

Use the existing application service/use-case boundary where one already exists.

If no suitable application Availability orchestration boundary exists, introduce the smallest appropriate application service/use case.

Do not introduce a second competing Availability entrypoint.

The application entrypoint MUST NOT expose Hotelbeds-specific transport details to callers.

---

## 6. Orchestration Sequence

The application Availability flow SHALL execute in this order:

### Step 1 — Receive Availability Request

Receive the existing canonical Availability request.

Do not introduce a new request contract unless the current application contract genuinely lacks a required field.

### Step 2 — Resolve Candidates

Invoke the accepted R2 candidate-resolution capability.

R7 MUST NOT independently resolve Hotelbeds hotel candidates.

### Step 3 — Construct Supplier Requests

Pass the resolved candidates and existing Availability context to the accepted R3 request-construction capability.

R7 MUST NOT reconstruct Hotelbeds request payloads.

### Step 4 — Execute Supplier Requests

Pass the R3-generated Availability requests through the accepted R6 supplier-protection/execution boundary.

R7 MUST NOT call the underlying R4 transport directly.

### Step 5 — Map Supplier Results

Pass the structured execution results to the accepted R5 response-mapping boundary.

R7 MUST NOT parse Hotelbeds responses itself.

### Step 6 — Return Canonical Result

Return the existing canonical Accommodation Availability result to the application caller.

R7 MUST NOT transform the result into a richer room/rate model.

---

## 7. No Candidate Behaviour

If R2 produces no eligible accommodation candidates:

- R3 MUST NOT be invoked;
- R6/R4 MUST NOT be invoked;
- no Hotelbeds request MUST be generated;
- the application SHALL return the existing canonical unavailable result.

The result SHALL remain consistent with the existing canonical Availability contract.

No supplier call is permitted for an empty candidate set.

---

## 8. No Request Behaviour

If R3 produces zero supplier requests:

- R6/R4 MUST NOT execute;
- no supplier calls MUST occur;
- the application SHALL return the canonical unavailable result according to the existing result contract.

R7 MUST NOT manufacture a supplier request.

---

## 9. Successful Availability

When:

- R2 resolves candidates;
- R3 creates valid supplier requests;
- R6/R4 executes successfully;
- R5 maps the supplier responses successfully;

R7 SHALL return the R5 canonical Accommodation Availability result unchanged.

R7 MUST NOT reinterpret the `available` value.

R7 MUST NOT add supplier-specific fields to the result.

---

## 10. Successful No Availability

When the complete supplier execution succeeds but no qualifying Availability exists:

R7 SHALL return the canonical result produced by R5.

R7 MUST NOT convert this into an application error.

The result SHALL remain:

`available = false`

according to the accepted R5 contract.

---

## 11. Failure Propagation

R7 SHALL preserve failures produced by the underlying accepted boundaries.

Failures MUST NOT be silently converted into:

`available = false`

unless the existing application contract explicitly defines that behaviour.

The following failures remain distinguishable:

- candidate-resolution failure;
- request-construction failure;
- supplier-protection failure;
- supplier transport failure;
- supplier response failure;
- response-mapping failure.

R7 MUST NOT create a second independent error-classification framework.

---

R7 SHALL only coordinate these capabilities.

## 13. Dependency Direction

The application orchestration layer MAY depend on the established application/domain contracts and the defined integration/application service interfaces.

R7 MUST NOT introduce reverse dependencies from infrastructure into the application orchestration layer.

R7 MUST NOT cause:

- Hotelbeds transport classes to depend on application services;
- R4 to depend on R5;
- R5 to depend on R7;
- R2 or R3 to depend on R7.

The orchestration dependency direction MUST remain one-way.

---

## 14. Hotelbeds Isolation

The application caller MUST NOT need to know:

- Hotelbeds endpoint;
- Hotelbeds authentication;
- Hotelbeds API key;
- Hotelbeds signature;
- Hotelbeds retry behaviour;
- Hotelbeds QPS limit;
- Hotelbeds concurrency limit;
- Hotelbeds transport implementation.

Those concerns remain inside the accepted integration boundary.

R7 MUST expose the application Availability capability, not the Hotelbeds supplier API.

---

## 15. Provider Selection

R7 SHALL use the existing accommodation-provider abstraction where one exists.

Do not hard-code Hotelbeds-specific provider logic into the application orchestration layer.

If the existing provider abstraction already selects the configured accommodation provider, R7 SHALL use that mechanism.

R7 MUST NOT introduce a second provider-selection mechanism.

For the current implementation, Hotelbeds remains the active Availability supplier.

---

## 16. Input Validation

R7 SHALL use the existing Availability request-validation boundary.

R7 MUST NOT create a second validation framework.

Invalid application Availability requests SHALL fail before supplier execution.

Validation failures MUST NOT result in Hotelbeds calls.

R7 MUST preserve existing R1 validation semantics.

---

## 17. Context Preservation

R7 MUST preserve the Availability request context throughout the pipeline.

The following information MUST NOT be lost or reconstructed:

- check-in;
- check-out;
- occupancy;
- child ages;
- source market;
- requested accommodation scope.

R2 remains authoritative for candidate resolution.

R3 remains authoritative for supplier request construction.

R7 SHALL pass existing contracts between these boundaries without rewriting their contents.

---

- add pricing;
- add currency;
- add `rateKey`;
- add BOOKABLE/RECHECK state;
- add cancellation information.

The existing canonical result remains:

- accommodation;
- available;
- metadata.

- create migrations;

## 20. External Supplier Safety

Automated R7 tests MUST NOT call Hotelbeds.

No supplier credentials are required for automated R7 tests.

Controlled live supplier verification remains a later iteration.

R7 is not a certification exercise.

R7 SHALL allow the application orchestration flow to be tested without real infrastructure.

Tests SHOULD mock at established capability boundaries rather than mocking individual internal implementation details.

At minimum, the following boundaries SHOULD be controllable:

- candidate resolution;
- request construction;
- supplier execution;
- response mapping.

R7 tests MUST verify orchestration rather than duplicate the detailed tests already owned by R2-R6.

Test the complete sequence:

    Availability request

### 22.2 No Candidates

- R2 returns no candidates;
- R3 is not invoked;
- supplier execution is not invoked;
- no supplier call occurs;
- canonical unavailable result is returned.

### 22.3 No Supplier Requests

Test that:

- R3 returns zero requests;
- R6/R4 is not invoked;
- canonical unavailable result is returned.

Test that a successful R5 result containing Availability is returned unchanged.

### 22.5 Supplier No Availability

Test that a successful R5 result with `available = false` is returned unchanged.

### 22.6 Candidate Resolution Failure

Test that an R2 failure propagates correctly and no supplier execution occurs.

### 22.7 Request Construction Failure

Test that an R3 failure propagates correctly and no supplier execution occurs.

### 22.8 Supplier Execution Failure

Test that an R6/R4 failure propagates correctly and is not converted into unavailable.

### 22.9 Mapping Failure

Test that an R5 mapping failure propagates correctly.

### 22.10 Context Preservation

Test that the Availability context supplied to R2/R3 remains unchanged through orchestration.

### 22.11 Provider Boundary

Test that the application uses the established accommodation-provider/application boundary rather than directly invoking Hotelbeds transport.
