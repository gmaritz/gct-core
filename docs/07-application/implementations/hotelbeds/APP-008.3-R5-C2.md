# APP-008.3-R5-C2 — Hotelbeds Available Response Mapping

**Document ID:** APP-008.3-R5-C2  
**Status:** Approved for Architect Review  
**Capability:** Accommodation Availability  
**Provider:** Hotelbeds  
**Bounded Context:** Reservations / Accommodation Availability  
**Depends On:** APP-008.3-R3-C1, APP-008.3-R5-C1, APP-008.3-CAN-001  
**Purpose:** Complete and verify mapping of a real Hotelbeds available-availability response into the canonical GCT Core Availability model.

---

## 1. Purpose

APP-008.3-R5-C2 completes the Hotelbeds Availability response-mapping path for the case where Hotelbeds returns one or more available hotels.

APP-008.3-R5-C1 established the verified Hotelbeds response envelope:

    response.hotels.hotels[]

and APP-008.3-CAN-001 established the canonical distinction between:

    kind: "ACCOMMODATION"

and:

    kind: "NO_AVAILABILITY"

R5-C2 must verify that a real Hotelbeds availability response containing hotels, rooms, and rates is correctly transformed into the existing canonical GCT Core Availability model.

The objective is not merely to parse the supplier JSON.

The objective is to prove:

    Hotelbeds available response
        ↓
    R5
        ↓
    R7
        ↓
    canonical ACCOMMODATION result
        ↓
    real accommodation
    + rooms
    + rates
    + availability semantics

## 3. Architectural Objective

R5-C2 shall map the supplier response into the existing canonical GCT Core Availability structures.

The canonical result must be:

    {
      kind: "ACCOMMODATION",
      accommodation: <real Accommodation>,
      available: true,
      metadata: <existing metadata>
    }

when at least one valid bookable accommodation/rate is available.

No fabricated accommodation may be created for a positive result.

---

## 4. Existing R5-C1 Protection

R5-C1 already established:

    response.hotels.hotels[]

as the Hotelbeds hotel collection.

R5-C2 must preserve that behaviour.

The mapper must continue to support:

    response.hotels.hotels[]

for positive availability.

The mapper must continue to recognize:

    response.hotels.total === 0

as:

    NO_AVAILABILITY

The R5-C2 implementation must not regress the zero-result path.

---

## 5. Canonical Result

The positive result must conform to APP-008.3-CAN-001.

The result must use:

    kind: "ACCOMMODATION"

and contain:

    accommodation

    available

    metadata

For a valid bookable Hotelbeds result:

    available: true

The existing canonical result semantics must be preserved.

## 6. Hotel Mapping

Each Hotelbeds hotel entry shall be mapped to the canonical `Accommodation` model using the existing domain/application mapping conventions.

The mapper must use supplier data only where the canonical model has an appropriate field.

### 6.1 Hotel Identity

Hotelbeds:

    code

must remain available as the supplier accommodation identity/reference according to the existing canonical provider-reference conventions.

Do not convert or discard the supplier hotel code unnecessarily.

### 6.2 Hotel Name

Hotelbeds:

    name

shall map to the canonical accommodation name.

### 6.3 Category

Hotelbeds:

    categoryCode

    categoryName

shall be mapped only to the existing canonical category/rating fields where an appropriate mapping already exists.

Do not invent a new category model inside R5-C2.

### 6.4 Destination

Hotelbeds:

    destinationCode

    destinationName

shall map to existing canonical location/destination fields where supported.

### 6.5 Zone

Hotelbeds:

    zoneCode

    zoneName

shall be mapped where the canonical accommodation model already provides a suitable field.

Do not introduce a new domain field solely for R5-C2.

### 6.6 Coordinates

Hotelbeds:

    latitude

    longitude

shall be mapped to existing canonical location/coordinate fields if supported.

String-to-number conversion must follow existing project validation/conversion conventions.

Invalid coordinates must not cause fabricated values to be created.

### 6.7 Hotel Images, Amenities, Contacts and Policies

The verified Availability response does not provide the complete content required for:

- images;
- amenities;
- contacts;
- complete accommodation policies.

R5-C2 must not invent these values.

If the canonical `Accommodation` model requires values that are not present in the Availability response, use the existing established defaults/empty structures only where those defaults are already part of the canonical model.

Do not create new supplier-content behaviour in R5-C2.

Hotel Content API enrichment remains outside this specification.

---

## 7. Room Mapping

Each Hotelbeds:

    hotel.rooms[]

entry represents an available room option.

The mapper must preserve:

    code

and:

    name

where corresponding canonical room fields exist.

Room occupancy information must be mapped from the rate where the canonical model supports it.

The mapper must not collapse multiple rooms into one room.

Room ordering must be preserved.

---

## 8. Rate Mapping

Each Hotelbeds:

    room.rates[]

entry represents a rate option.

The mapper must preserve the existing canonical rate semantics.

The following supplier fields must be reviewed and mapped where corresponding canonical fields exist:

    rateKey

    rateClass

    rateType

    net

    allotment

    paymentType

    packaging

    boardCode

    boardName

    cancellationPolicies

    taxes

    rooms

    adults

    children

    childrenAges

### 8.1 Rate Key

Hotelbeds:

    rateKey

must be preserved as the supplier rate identifier where the canonical model supports a supplier rate/reference field.

Do not expose or log rate keys in normal verification reports.

### 8.2 Rate Type

Hotelbeds:

    rateType

may contain values such as:

    BOOKABLE

    RECHECK

The existing canonical availability semantics must be used.

Do not invent new availability states solely for R5-C2.

### 8.3 Net Rate

Hotelbeds:

    net

shall map to the existing canonical monetary/rate representation.

Currency must be taken from the appropriate supplier response field:

    hotel.currency

The existing `Money` value-object conventions must be respected.

Do not perform an unapproved currency conversion.

### 8.4 Allotment

Hotelbeds:

    allotment

must remain available to the canonical rate model if the existing model supports allotment.

A positive allotment must not be discarded if the canonical model has a suitable field.

### 8.5 Board

Hotelbeds:

    boardCode

    boardName

shall map to existing canonical board/meal-plan fields where available.

Do not create a new board domain model in R5-C2.

### 8.6 Occupancy

Hotelbeds:

    rooms

    adults

    children

    childrenAges

shall be mapped according to the existing canonical occupancy model.

The mapper must preserve the supplier-reported occupancy associated with the returned rate.

The current controlled R8 scenario uses:

    rooms: 1
    adults: 1 or 2
    children: 1
    child age: 7

R5-C2 must not hard-code these values.

## 11. Availability Determination

R5-C2 must preserve the existing availability determination logic unless the actual canonical model requires a correction.

A rate may be considered bookable according to the existing mapper rules, including the existing handling of:

    BOOKABLE

and:

    RECHECK

The implementation must not arbitrarily equate:

    hotel exists

with:

    available === true

Availability must be determined from the existing canonical rate/availability rules.

---

## 12. Multiple Hotels

When Hotelbeds returns:

    hotels.hotels[]

containing multiple hotels:

- preserve supplier order;
- map each hotel independently;
- do not discard valid hotels because another hotel has no valid rate;
- do not collapse all hotels into one result unless the existing canonical contract explicitly requires that behaviour.

The existing application result model and provider orchestration must determine whether the provider returns:

- one result per accommodation;
- an aggregated result;
- or another existing canonical structure.

Do not redesign the result aggregation model as part of R5-C2.

---

## 13. Multiple Rooms

When a hotel contains multiple:

    rooms[]

entries:

- preserve room ordering;
- map each valid room;
- preserve its rates;
- do not collapse rooms;
- do not discard a room solely because another room is invalid.

Invalid individual supplier entries must be handled according to existing mapper validation conventions.

---

## 14. Multiple Rates

When a room contains multiple:

    rates[]

entries:

- preserve rate ordering;
- map all valid supported rates;
- preserve rate keys;
- preserve board information;
- preserve cancellation information;
- preserve monetary information;
- preserve occupancy information.

Do not select only the cheapest rate unless the existing canonical/application contract explicitly requires that behaviour.

---

## 15. Min/Max Rate

Hotelbeds supplies:

    minRate

    maxRate

These fields shall only be mapped where the canonical model has an appropriate aggregate-rate representation.

Do not introduce new canonical fields solely to retain these values.

If the canonical model does not support them, they may remain supplier-response-only data and must not be logged.

---

## 16. Currency

Hotelbeds supplies:

    currency

at hotel level.

Rate monetary values must use the supplier currency according to the existing canonical `Money` representation.

No currency conversion is permitted in R5-C2.

## 17. Audit Data

The Hotelbeds response contains:

Do not expose:

- audit token;
- request identifiers;
- internal supplier identifiers;
- supplier infrastructure information.

No audit data may appear in normal verification reports.

## 18. Error and No-Availability Protection

R5-C2 must preserve the distinctions established by previous specifications.

### Valid availability

    response.hotels.hotels[]

with valid hotel/room/rate data:

    ACCOMMODATION

### Valid no availability

    response.hotels.total === 0

must remain:

    NO_AVAILABILITY

### Supplier error

Supplier error responses remain supplier errors.

They must not become:

    NO_AVAILABILITY

### Malformed response

Unsupported or structurally invalid responses remain malformed responses.

They must not become:

    NO_AVAILABILITY

Clients must ultimately be able to specify:

- number of rooms;
- adults;
- children;
- child ages;
- associated occupancy.

However, room-count configurability is not part of R5-C2.

    rooms: 1

A separate specification shall define:

- configurable room count;
- multiple occupancy groups;
- adults per room;
- children per room;
- child ages per room;
- validation rules;
- R8 environment/configuration representation;
- R3 supplier occupancy construction.

R5-C2 must not hard-code or redesign room-count semantics.
