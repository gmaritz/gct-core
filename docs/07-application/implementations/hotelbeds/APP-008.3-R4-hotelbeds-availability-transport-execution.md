## 2. Purpose

APP-008.3-R4 establishes the Hotelbeds Availability execution path required to execute the Availability requests produced by R3.

The execution flow is:

R3 Availability Request
→ Availability Execution Boundary
→ Hotelbeds Transport
→ `POST /hotel-api/1.0/hotels`
→ Structured Raw Supplier Response

R4 establishes the supplier transport and execution boundary only.

R4 MUST NOT implement canonical Availability response mapping, CheckRate, Booking or Cancellation.

---

## 3. Architectural Baseline

The accepted APP-008.3 sequence is:

R1 — Availability Foundation
→ R2 — Catalogue Candidate Resolution
→ R3 — Availability Request Construction
→ R4 — Availability Transport & Execution

R1-R3 remain accepted contracts.

R4 MUST consume the R3 Availability request contract.

R4 MUST NOT recreate R2 candidate resolution.

R4 MUST NOT recreate R3 request construction.

R4 MUST NOT route Availability through the existing legacy GET search implementation.

The purpose of R4 is to establish the missing execution path between the R3 request contract and Hotelbeds.

---

## 4. Existing Architecture Constraints

The current implementation has the following relevant conditions:

1. R2 candidate resolution exists.
2. R3 Availability request construction exists.
3. The current provider search path still uses the legacy GET search contract.
4. No dedicated Availability execution entrypoint currently exists.
5. The current Hotelbeds operation model does not contain an explicit Availability operation.
6. R3 currently emits the existing `search` operation for its Availability requests.
7. The current integration result does not preserve the complete raw supplier response required by R4.
8. The current client unwraps some supplier failures into thrown errors.
9. The current transport has no explicit mTLS configuration mechanism.
10. The current transport does not provide an explicit GZIP contract.
11. Retry classification exists, but a bounded retry executor does not.
12. R3 currently rejects Availability occupancy groups where `rooms != 1`.

R4 SHALL address only the gaps required for the R4 execution boundary.

The inherited R3 `rooms == 1` restriction is an existing R3 behaviour and MUST NOT be redesigned in R4.

## 6. Availability Operation Semantics

R4 SHALL extend the existing `HotelbedsOperation` model with an explicit `availability` operation.

The existing operation model SHALL remain the single source of operation identity.

No alternative Availability marker or parallel operation-identification mechanism shall be introduced.

The R3 Availability request builder SHALL emit `availability` for Hotelbeds Availability requests instead of the generic `search` operation.

The change is limited to correctly identifying the existing R3 Availability request.

Existing operations SHALL remain unchanged.

The resulting distinction SHALL be:

- `availability` — Hotelbeds Availability API execution;
- existing `search` — existing search functionality;
- existing details/content/images/rates/content-sync operations — unchanged.

The R4 executor SHALL use the explicit Availability operation for execution context, error context, logging and tests.

---

## 7. R3 Request Contract

R3 remains the authoritative producer of Hotelbeds Availability requests.

R4 SHALL accept the existing `HotelbedsAvailabilityRequest` structure.

R4 MUST NOT reconstruct the request.

R4 MUST NOT modify the semantics of:

- check-in;
- check-out;
- source market;
- occupancy;
- adults;
- children;
- child ages;
- hotel codes;
- hotel-code batch boundaries;
- request field names;
- request nesting.

The existing R3 hotel-code batch limit remains authoritative.

R4 MUST NOT introduce another batching rule.

The existing R3 restriction that Availability occupancy groups require `rooms == 1` remains unchanged.

R4 MUST NOT expand or reinterpret that rule.

---

## 8. R3 → R4 Wiring

R4 SHALL establish one explicit Availability execution entrypoint connecting the existing R3 request-building/application path to the dedicated Availability executor.

The wiring SHALL follow:

R3 request builder
→ existing Availability application/provider boundary
→ dedicated Availability executor
→ Hotelbeds transport

The executor SHALL receive the already constructed R3 request list.

R4 MUST NOT reconstruct requests from search criteria.

R4 MUST NOT resolve hotel candidates again.

The existing legacy provider GET-search path MUST be bypassed for R4 Availability execution.

The existing provider implementation for unrelated operations SHALL remain unchanged.

Only the minimum provider/application wiring required to invoke R4 SHALL be modified.

The executor entrypoint SHALL be explicit and testable. Do not rely on implicit routing based solely on operation names.

---

## 9. Availability Execution Boundary

R4 SHALL introduce the smallest appropriate dedicated Availability execution boundary within the existing Hotelbeds architecture.

The boundary SHALL be conceptually equivalent to:

`executeAvailability(requests)`

where `requests` are already constructed R3 `HotelbedsAvailabilityRequest` instances.

The boundary MUST:

1. accept R3 requests;
2. execute them in deterministic order;
3. use the explicit Availability operation;
4. execute `POST /hotel-api/1.0/hotels`;
5. apply Hotelbeds authentication;
6. apply configured secure transport;
7. apply timeout and bounded retry behaviour;
8. return Availability-specific structured raw supplier results.

The boundary MUST NOT:

- resolve catalogue candidates;
- construct Availability requests;
- alter request payloads;
- persist responses;
- perform canonical response mapping.

---

## 10. HTTP Contract

Availability SHALL use:

`POST /hotel-api/1.0/hotels`

The request SHALL:

- use HTTP POST;
- send the R3 Availability request as JSON;
- apply Hotelbeds authentication;
- explicitly advertise compressed-response support;
- use the configured timeout.

The existing single-hotel GET search/rates path MUST NOT be used for R4 Availability execution.

The endpoint SHALL be represented through the existing Hotelbeds transport architecture rather than duplicated across multiple layers.

---

## 11. Authentication

R4 SHALL reuse the established Hotelbeds authentication implementation.

Availability requests MUST include:

- `Api-Key`;
- `X-Signature`.

Authentication MUST remain configuration driven.

R4 MUST NOT:

- hard-code credentials;
- hard-code signatures;
- log credentials;
- log generated signatures;
- replace the established signature algorithm unnecessarily.

Authentication failures MUST remain distinguishable from successful supplier responses.

---

## 12. mTLS Configuration

R4 SHALL extend the existing Hotelbeds integration configuration to support the TLS material required for mutual TLS.

Configuration SHALL support:

- client certificate;
- private key;
- trusted CA material.

TLS configuration MUST use the established configuration/environment mechanism.

Certificate and private-key material MUST NOT be embedded in source code.

Certificate, private-key and trusted-CA contents MUST NOT be logged.

Configuration property names SHALL follow the existing Hotelbeds integration configuration naming convention.

No separate global TLS configuration system shall be introduced.

---

## 13. mTLS Transport

R4 SHALL extend the existing Hotelbeds transport so that the Availability execution path can provide the configured mTLS material to the underlying HTTPS implementation.

TLS-specific objects MUST remain inside the infrastructure/integration boundary.

The transport MUST surface:

- certificate configuration errors;
- private-key configuration errors;
- trusted CA errors;
- TLS handshake failures

as transport/infrastructure failures.

The existing HTTP stack and transport abstraction SHALL be reused.

A second HTTP client stack MUST NOT be introduced unless the existing runtime is technically incapable of supporting the required TLS material.

---

## 14. GZIP

R4 SHALL make GZIP behaviour explicit at the Hotelbeds transport boundary.

The Availability request SHALL explicitly advertise compressed-response support using the appropriate HTTP header.

The transport SHALL correctly process a GZIP-compressed Hotelbeds response.

The implementation MUST NOT rely solely on undocumented runtime-specific automatic decompression.

The decompressed logical response body SHALL be returned to the structured result boundary.

GZIP implementation details MUST remain inside the transport boundary.

---

## 15. Timeout

R4 SHALL reuse the existing Hotelbeds timeout configuration.

Where the current configuration uses:

`HOTELBEDS_TIMEOUT_MS`

that configuration remains the baseline.

A timeout MUST:

- terminate the request;
- produce the appropriate transport failure;
- participate in retry only when classified as retryable;
- never cause an unbounded execution loop.

R4 MUST NOT introduce Booking-specific timeout configuration.

---

## 16. Retry Execution

Existing Hotelbeds retry classification SHALL be reused where applicable.

R4 SHALL add the missing bounded retry executor for Availability.

The retry executor MUST:

- operate only around Availability execution;
- use existing retry classification where possible;
- apply a finite retry limit;
- retry only eligible transient failures;
- immediately fail non-retryable failures;
- return failure after retry exhaustion.

The following MUST NOT be retried automatically:

- malformed requests;
- authentication failures;
- invalid configuration;
- TLS configuration failures;
- deterministic client errors;
- permanent supplier errors.

Retries MUST NOT modify the original R3 request or batch structure.

No general-purpose resilience framework shall be introduced.

---

## 17. Batch Execution

R4 SHALL execute every R3-generated Availability request.

Example:

R3 produces:

- Request 1;
- Request 2;
- Request 3.

R4 executes:

- Request 1;
- Request 2;
- Request 3.

Execution order MUST be deterministic.

R4 MUST preserve the R3 batch boundaries.

R4 MUST NOT:

- merge requests;
- split valid R3 requests;
- create one request per hotel;
- create one request per room;
- apply Content synchronisation batching;
- discard a generated request.

Each R3 request SHALL produce one final execution result.

Retries apply inside the execution of an individual request and MUST NOT alter batch ordering.

---

## 18. Empty Request Set

If R3 produces zero Availability requests:

- R4 MUST NOT call Hotelbeds;
- R4 SHALL return an empty execution result;
- no artificial Availability request shall be created.

This behaviour MUST be covered by a focused test.

---

## 19. Availability Raw Response Contract

R4 SHALL introduce an Availability-specific structured raw-response result type.

The generic summary-oriented `HotelbedsIntegrationResult` SHALL NOT be expanded merely to satisfy R4 unless the existing architecture demonstrates that doing so is the smaller and safer change.

The Availability-specific result SHALL preserve, per request:

- deterministic request/batch index;
- HTTP status;
- relevant response headers;
- decompressed response body;
- supplier error payload, where present;
- transport failure information, where present.

The result SHALL identify whether the execution produced:

- a successful supplier response;
- an HTTP/supplier error response;
- a transport failure.

The raw response MUST remain supplier-specific.

R4 MUST NOT map it into canonical GCT Core Availability structures.

---

## 20. Client Behaviour

The current Hotelbeds client may convert supplier failures into thrown errors.

R4 SHALL provide an Availability-specific structured execution path where necessary to preserve:

- status;
- headers;
- body;
- supplier error payload;
- transport failure.

The implementation MUST NOT globally redesign error handling for unrelated Hotelbeds operations.

If modifying the shared client would alter unrelated behaviour, the Availability-specific path SHALL be preferred.

The required flow is:

HTTP execution
→ Availability structured supplier result
→ Availability execution boundary

The implementation MUST NOT discard a supplier response merely because it contains an error status.

---

## 21. Error Handling

R4 SHALL distinguish transport failure from supplier response failure.

### 21.1 Transport Failure

Examples:

- connection failure;
- network failure;
- timeout;
- TLS failure;
- mTLS failure.

Transport failure information SHALL be preserved in the structured result.

### 21.2 HTTP Failure

A non-success HTTP status SHALL remain available to the caller.

Relevant headers and response body SHALL be preserved where available.

### 21.3 Supplier Error Payload

A valid Hotelbeds supplier error response SHALL remain available as supplier response information.

It MUST NOT automatically become an empty successful Availability result.

### 21.4 Retry Exhaustion

When retryable execution fails after the configured limit, the final failure SHALL be preserved.

R4 MUST NOT hide retry exhaustion.

## 27. Acceptance Criteria

### AC-01 — Explicit Availability Operation

The existing Hotelbeds operation model contains an explicit `availability` operation and R3 Availability requests emit that operation.

### AC-02 — Dedicated Execution Boundary

A dedicated Hotelbeds Availability execution boundary accepts the R3 Availability request DTO.

### AC-03 — Explicit R3 → R4 Wiring

The R3-built request list reaches the dedicated Availability executor through an explicit, testable application/provider entrypoint.

### AC-04 — Legacy Path Bypass

R4 Availability execution does not use the existing legacy GET search path.

### AC-05 — Correct Endpoint

Availability uses:

`POST /hotel-api/1.0/hotels`

### AC-06 — Request Integrity

R3 request payloads are transmitted without semantic modification.

### AC-07 — Authentication

The established API-key and `X-Signature` authentication is applied.

### AC-08 — mTLS

The Availability transport supports configured client certificate, private key and required trusted CA material.

### AC-09 — GZIP

Compressed Hotelbeds responses are explicitly supported and correctly decompressed.

### AC-10 — Timeout

The configured Hotelbeds timeout is enforced.

### AC-11 — Bounded Retry

Eligible transient failures are retried only within the configured finite retry limit.

### AC-12 — Batch Execution

All R3-generated Availability requests execute in deterministic order without rebatching.

### AC-13 — Empty Input

Zero R3 requests produces zero Hotelbeds calls.

### AC-14 — Structured Raw Response

Each R4 execution result preserves the required supplier response information.

### AC-15 — Error Integrity

Transport failures, HTTP failures and supplier error payloads are not silently converted into successful empty Availability results.

### AC-16 — Security

Credentials and TLS private material are configuration driven and are not logged.

### AC-17 — Inherited R3 Occupancy Behaviour

R4 preserves the existing R3 restriction that Availability occupancy groups require `rooms == 1`.

R4 MUST NOT expand or redesign that rule.

### AC-18 — Scope Protection

No response mapping, CheckRate, Booking or Cancellation functionality is implemented.

### AC-19 — Regression

Existing accepted behaviour remains intact.
