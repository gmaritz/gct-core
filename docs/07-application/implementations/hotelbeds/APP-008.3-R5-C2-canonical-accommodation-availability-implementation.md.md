# 1. Purpose

Bring the current accommodation Availability implementation into alignment with the established GCT Core architecture and APP-008.3 requirements.

This iteration replaces the current shallow Hotelbeds-driven Availability result path with the established supplier-neutral Availability structure:

Package/Accommodation Search
→ Candidate Accommodation
→ Supplier Availability
→ Canonical Accommodation Result
→ Room Options
→ Rate Options

The implementation must preserve existing valid APP-008.2 and APP-008.3 infrastructure and must not introduce another supplier-specific canonical model.

---

# 2. Business Requirement

Go Cape Tours sells private multi-day packages.

Each package contains multiple accommodation stops. For each stop, GCT determines the eligible accommodation properties.

The Availability capability must support:

- multiple candidate properties;
- multiple rooms;
- independent occupancy per room;
- adults, children and child ages;
- multiple room types per property;
- multiple rates per room;
- rate pricing and currency;
- board information;
- rate status;
- cancellation information;
- supplier references;
- package-stop association;
- future revalidation and booking continuity.

The client will ultimately select:

Property → Room → Rate

Supplier accommodation pricing is an input to GCT package pricing. Supplier pricing must not become the GCT package price.

APP-005 remains responsible for GCT package pricing.

# 5. Core Architectural Rules

The following rules are mandatory.

### 5.1 Supplier Isolation

Hotelbeds-specific DTOs and concepts remain inside the Hotelbeds adapter.

The following MUST NOT become canonical field names:

- rateKey;
- rateType;
- rateClass;
- Hotelbeds response envelope names;
- Hotelbeds-specific room structures;
- Hotelbeds-specific tax structures;
- Hotelbeds-specific payment codes.

Hotelbeds `rateKey` may populate an opaque canonical supplier reference.

### 5.2 Canonical Hierarchy

Availability SHALL preserve:

Accommodation
→ Availability Options
→ Room Options
→ Rate Options

Rates MUST remain associated with their room.

Rates MUST NOT be flattened into a global accommodation rate collection.

### 5.3 Static vs Dynamic Data

`Accommodation` represents accommodation identity and relatively stable property information.

Room and rate availability are dynamic Availability data.

Do not place dynamic supplier room/rate availability into static accommodation content models.

### 5.4 Pricing Boundary

Availability supplies supplier accommodation pricing.

APP-005 remains responsible for GCT commercial pricing.

No Hotelbeds rate may become the final package price.

### 5.5 No Fabricated Accommodation

A valid supplier no-availability response MUST NOT fabricate an accommodation.

The established canonical `NO_AVAILABILITY` representation remains valid.

# 6. Canonical Request Requirements

The implementation SHALL preserve the existing canonical search intent and support:

- stay/check-in;
- stay/check-out;
- source market;
- ordered room occupancy groups;
- adults per room;
- children per room;
- child ages per room;
- candidate accommodation selection.

The canonical occupancy model MUST NOT require `rooms === 1`.

A request containing:

rooms[0]
- adults
- children
- childAges

rooms[1]
- adults
- children
- childAges

must remain representable.

Do not remove or break existing consumers that still use legacy aggregate occupancy unless required by this iteration.

Where migration is required, provide an adapter rather than duplicating business semantics.

---

# 7. Canonical Availability Result

A positive accommodation result SHALL contain:

- `kind: "ACCOMMODATION"`;
- accommodation;
- requested occupancy;
- availability options;
- availability metadata;
- availability state.

A no-availability result SHALL contain:

- `kind: "NO_AVAILABILITY"`;
- `available: false`;
- metadata;
- no fabricated accommodation.

The existing positive-result semantics SHALL remain intact.

---

# 8. Availability Options

The canonical positive result SHALL expose an availability-options structure containing ordered room options.

Conceptually:

AvailabilityOptions
→ roomOptions[]

The implementation SHALL use the existing canonical models if they already provide an equivalent structure.

If a required structure does not exist, Copilot SHALL implement the smallest supplier-neutral model necessary to satisfy this specification.

Do not introduce Hotelbeds DTOs into the canonical model.

---

# 9. Room Options

Each room option SHALL represent a selectable room type returned by the supplier.

A room option SHALL preserve, where available:

- canonical room reference;
- room name/display name;
- supplier reference required for future continuity;
- ordered rate options.

A room option MUST NOT contain a Hotelbeds-specific DTO.

A positive accommodation result MAY contain multiple room options.

Room options MUST retain their supplier response ordering unless an existing canonical ordering rule requires otherwise.

---

# 10. Rate Options

Each room option SHALL contain zero or more rate options according to the supplier response and established canonical rules.

A rate option SHALL preserve, where supported by the established canonical model:

- supplier-neutral booking reference;
- rate status;
- pricing;
- currency;
- pricing basis;
- occupancy;
- board;
- allotment;
- payment information;
- packaging information;
- cancellation policies;
- taxes/fees;
- supplier reference context.

The implementation MUST NOT discard multiple rates merely because the current legacy model supports only one rate.

---

# 11. Rate Status

Hotelbeds supplier status SHALL be mapped into the existing canonical availability status model.

At minimum:

- BOOKABLE remains bookable;
- RECHECK remains recheck-required.

Do not collapse BOOKABLE and RECHECK into one generic available state.

The implementation MUST preserve sufficient information for the future CheckRate capability.

CheckRate itself remains out of scope.

---

# 12. Supplier References

Supplier references SHALL remain opaque and supplier-neutral.

The canonical model MUST NOT expose `rateKey` as a Hotelbeds-specific property.

The implementation MAY map:

provider + opaque supplier reference

from the Hotelbeds rate reference.

Room-level supplier references SHALL be preserved where required by the supplier response or future booking continuity.

Do not invent additional provider-specific semantics.

---

# 13. Occupancy Mapping

The implementation SHALL preserve:

### Requested Occupancy

The occupancy supplied by the client/search.

### Offered Occupancy

The occupancy associated with the returned rate where the supplier provides it.

The two MUST NOT be silently substituted for one another.

Child ages MUST be preserved.

The implementation MUST support different occupancy groups for different rooms.

The existing R3 one-room implementation restriction MUST NOT be propagated into the canonical Availability contract.

---

# 14. Multiple Accommodation Results

The Availability application path SHALL support multiple accommodation results.

For a candidate set containing properties A through F, the application MUST be able to return multiple independently mapped accommodation results.

Each result retains:

- accommodation identity;
- provider context;
- availability options;
- room options;
- rate options.

Do not select only the first available hotel.

Do not collapse multiple properties into one result.

Do not merge supplier offers merely because accommodation identity is the same.

Provider identity remains part of supplier-reference context.

---

# 15. R5 Responsibility

R5 is responsible for:

Supplier Availability Response
→ Canonical Availability Result

R5 SHALL:

- parse the supplier response;
- identify supplier hotel entries;
- map accommodation data;
- map room options;
- map rate options;
- map supplier status;
- map supplier pricing;
- preserve supplier references;
- map cancellation information;
- map other supported rate information;
- produce canonical results.

R5 SHALL NOT:

- calculate GCT package pricing;
- select the client's preferred room;
- create reservations;
- call CheckRate;
- perform booking;
- persist availability.

---

# 16. R7 Responsibility

R7 owns application orchestration.

R7 SHALL:

- coordinate Availability execution;
- pass canonical search intent into the provider layer;
- aggregate canonical accommodation results;
- preserve candidate/stop context where already defined by the application boundary;
- return canonical application results.

R7 SHALL NOT:

- construct Hotelbeds request DTOs directly;
- contain Hotelbeds response mapping logic;
- calculate package pricing;
- contain supplier-specific business rules.

If the current R7 directly imports Hotelbeds request classes, refactor that dependency as part of this iteration.

---

# 17. Provider Boundary

The provider abstraction SHALL remain supplier-neutral.

The production application flow SHALL be:

Accommodation Application Service
→ Provider Abstraction
→ Supplier Adapter
→ Supplier Transport

The Hotelbeds provider SHALL translate canonical requests into Hotelbeds requests and supplier responses into canonical results.

No application service SHALL directly construct a `HotelbedsAvailabilityRequest`.

# 19. Existing Models

Copilot SHALL inspect existing models before introducing replacements.

### Accommodation

Retain as the canonical static accommodation model where compatible.

### AccommodationRate

Remain a separate rate-query/application contract unless the existing architecture explicitly establishes it as reusable for a required value object.

Do not force Availability room/rate options into it merely for compatibility.

### AccommodationRateResult

Remain a separate rate-query contract.

Do not embed it inside Availability.

### Occupancy

Reuse or extend existing occupancy concepts where semantically correct.

Do not create duplicate occupancy models unnecessarily.

### Money / Currency

Reuse the established pricing model where compatible.

Do not redesign the global pricing architecture in this iteration.

If the current pricing model cannot represent a supplier value required by this specification, isolate the adapter conversion and report the limitation rather than silently redesigning pricing.

# 20. Inventory and Consumer Preservation

Existing consumers that receive Availability results SHALL continue to function.

Where they consume positive results, they must preserve:

- accommodation;
- availability state;
- requested occupancy where applicable;
- availability options;
- room options;
- rate options.

Inventory freezing/cloning SHALL NOT discard the newly mapped room/rate information.

Consumers that do not yet need room/rate details may project the canonical result into their existing view rather than forcing unrelated redesign.

---

# 21. Package Stop Context

Where the current package/journey application boundary already supplies stop context, Availability results SHALL retain that association.

The implementation MUST NOT mix accommodation results between package stops.

The following relationship must remain possible:

Package
→ Stop
→ Accommodation Result
→ Room Option
→ Rate Option

Do not implement full package pricing or client selection in this iteration.

The data structures must preserve the information required by those future capabilities.

---

# 22. No Database Changes

This iteration SHALL NOT introduce Availability persistence.

Do not add Prisma models or database tables for:

- availability responses;
- rooms;
- rates;
- rate keys;
- cancellation policies;
- supplier availability.

Real-time Availability remains transient until a later capability explicitly requires persistence.

# 30. Final Implementation Statement

This iteration does not restart GCT Core and does not redesign the established architecture.

It brings the current Accommodation Availability implementation into alignment with the existing GCT Core contract by replacing the shallow supplier-driven Availability path with the required canonical:

Accommodation
→ Room Options
→ Rate Options

structure while retaining the valid catalogue, provider, transport, authentication, resilience and verification infrastructure already implemented.

Hotelbeds remains an initial supplier adapter.

GCT Core remains the owner of the canonical model and GCT commercial pricing.

The implementation must leave the platform ready for the subsequent package accommodation selection, CheckRate, revalidation and Booking capabilities without implementing those capabilities prematurely.
