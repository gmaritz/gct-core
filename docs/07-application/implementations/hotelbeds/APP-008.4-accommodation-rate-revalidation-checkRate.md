# 1. Purpose

Implement the GCT Core accommodation rate revalidation capability required when an Availability result identifies a rate as requiring supplier recheck.

The capability SHALL:

1. accept a canonical selected accommodation rate;
2. preserve the canonical accommodation/room/rate context;
3. invoke the supplier-specific CheckRate operation through the provider boundary;
4. map the supplier response into the canonical rate representation;
5. determine whether the selected rate remains valid;
6. return the current supplier pricing and booking conditions;
7. preserve supplier-neutral booking continuity;
8. provide the validated result for a future Booking capability.

Hotelbeds `rateKey` and other Hotelbeds-specific concepts SHALL remain inside the Hotelbeds adapter.

---

# 2. Business Context

GCT Core uses accommodation suppliers as part of private multi-day tour packages.

The client may select:

Package Stop
→ Accommodation
→ Room
→ Rate

Availability can identify rates as either:

- `BOOKABLE`; or
- `RECHECK`.

A `BOOKABLE` rate does not require CheckRate before the future Booking operation.

A `RECHECK` rate requires supplier revalidation before Booking.

APP-008.4 implements that revalidation step only.

The capability SHALL NOT implement Booking.

---

# 3. Architectural Position

The canonical flow is:

Availability
→ Client Rate Selection
→ Rate Revalidation
→ Validated Rate
→ Future Booking

For a BOOKABLE rate:

Availability
→ Selection
→ Future Booking

For a RECHECK rate:

Availability
→ Selection
→ APP-008.4 CheckRate
→ Validated Rate
→ Future Booking

The provider boundary remains:

Application
→ Accommodation Provider
→ Hotelbeds Adapter
→ Hotelbeds CheckRate API

The application layer SHALL NOT construct Hotelbeds CheckRate requests directly.

# 5. Canonical Revalidation Request

The application-facing request SHALL be supplier-neutral.

Conceptually it contains:

- selected accommodation;
- selected room;
- selected rate;
- provider reference;
- requested stay;
- selected occupancy;
- selected rate reference;
- package-stop context where already available at the application boundary.

The request MUST contain enough information to identify the selected offer without requiring the application layer to understand Hotelbeds `rateKey`.

The supplier adapter is responsible for translating the opaque supplier reference into the Hotelbeds CheckRate request.

---

# 6. Selected Offer Context

A selected offer SHALL preserve the relationship:

Accommodation
→ Room
→ Rate

The revalidation request MUST NOT contain only an accommodation identifier.

The selected rate MUST remain associated with its selected room and accommodation.

Where package-stop context is available, it MUST remain associated with the selected accommodation offer.

This preserves future package pricing and booking continuity.

---

# 7. Supplier Reference

The canonical supplier reference remains opaque.

The canonical representation SHALL identify:

- provider;
- opaque supplier reference.

For Hotelbeds, the opaque reference SHALL contain the supplier rate reference obtained during Availability.

The canonical model MUST NOT expose a Hotelbeds-specific `rateKey` property.

The Hotelbeds adapter MAY interpret the opaque reference as the Hotelbeds `rateKey`.

No application-layer parsing of the Hotelbeds `rateKey` is permitted.

---

# 8. Provider Contract

The provider abstraction SHALL expose a supplier-neutral revalidation operation.

Conceptually:

Accommodation Provider
→ revalidate selected rate
→ canonical revalidation result

The provider interface MUST NOT expose:

- Hotelbeds request DTOs;
- Hotelbeds response DTOs;
- Hotelbeds `rateKey`;
- Hotelbeds-specific status values.

The Hotelbeds provider SHALL implement the provider contract.

Future suppliers SHALL be able to implement the same contract without modifying the canonical application model.

---

# 9. Revalidation Eligibility

Only rates requiring supplier revalidation SHALL invoke CheckRate.

The canonical rate status established by APP-008.3-R5-C2 remains authoritative for determining the workflow:

- `BOOKABLE` → no CheckRate required;
- `RECHECK` → CheckRate required.

APP-008.4 SHALL NOT automatically invoke CheckRate for BOOKABLE rates.

The capability MAY validate the request and reject an inappropriate BOOKABLE revalidation request rather than silently changing workflow semantics.

---

# 10. Hotelbeds CheckRate Operation

The Hotelbeds adapter SHALL use the Hotelbeds CheckRate operation.

The current Hotelbeds Booking API documentation defines CheckRate as the intermediary operation for rates returned with `RECHECK`, returning updated availability and pricing. :contentReference[oaicite:1]{index=1}

The adapter SHALL use the existing Hotelbeds:

- API key;
- X-Signature;
- mTLS;
- transport;
- timeout;
- error handling;
- GZIP handling where applicable

in accordance with the established Hotelbeds integration infrastructure.

Do not duplicate authentication or transport implementation already established by APP-008.3.

---

# 11. Hotelbeds Adapter Isolation

Hotelbeds-specific structures SHALL remain inside the adapter.

Permitted inside the adapter:

- Hotelbeds CheckRate request DTO;
- Hotelbeds CheckRate response DTO;
- `rateKey`;
- Hotelbeds rate fields;
- Hotelbeds response envelopes;
- Hotelbeds-specific error structures.

Not permitted outside the adapter:

- `rateKey`;
- Hotelbeds DTO imports;
- Hotelbeds status strings;
- Hotelbeds response envelopes.

# 12. Revalidation Result

The canonical revalidation result SHALL clearly distinguish at least:

1. `VALID`
2. `CHANGED`
3. `UNAVAILABLE`
4. `FAILED`

The exact existing canonical result/value-object conventions SHALL be reused where they already exist.

### VALID

The selected rate remains available and its relevant commercial conditions remain valid.

The result contains the current canonical rate information.

### CHANGED

The supplier returned a valid rate, but one or more relevant commercial conditions changed.

Examples include:

- price changed;
- cancellation conditions changed;
- board changed;
- payment condition changed;
- other booking-relevant conditions changed.

The current supplier result SHALL be returned.

The application must not silently treat the old rate as still authoritative.

### UNAVAILABLE

The selected rate can no longer be booked/revalidated.

No booking may proceed using the invalidated offer.

### FAILED

The supplier or integration could not complete revalidation.

The result SHALL distinguish technical failure from genuine supplier unavailability.

---

# 13. Canonical Rate Mapping

A successful CheckRate response SHALL map into the existing canonical `RateOption` structure established by APP-008.3-R5-C2.

Where the supplier returns updated values, preserve:

- supplier-neutral booking reference;
- rate status;
- pricing;
- currency;
- pricing basis;
- occupancy;
- board;
- allotment;
- payment;
- packaging;
- cancellation policies;
- taxes/fees;
- rate comments where the canonical model supports them.

Do not create a second rate model specifically for CheckRate.

---

# 14. Pricing Semantics

The supplier's revalidated accommodation price is authoritative for the supplier offer.

APP-008.4 SHALL NOT calculate GCT package pricing.

The result SHALL provide the updated accommodation pricing input required by APP-005.

The application SHALL preserve the distinction between:

Supplier Accommodation Price
→ GCT Pricing Input
→ GCT Package Pricing

CheckRate does not modify APP-005 pricing rules.

---

# 15. Price Change Handling

If the supplier returns a different price from Availability:

- classify the result as `CHANGED`;
- return the current supplier price;
- preserve the updated canonical rate;
- do not silently overwrite the previous selection without reporting the change.

The previous Availability price remains historical selection information.

The newly returned price is the current supplier value.

No customer/package price calculation occurs in APP-008.4.

---

# 16. Cancellation Changes

If CheckRate returns cancellation conditions that differ from Availability:

- classify the result as `CHANGED`;
- return the current cancellation conditions;
- preserve the updated canonical rate.

Do not retain stale Availability cancellation conditions when CheckRate supplies newer conditions.

---

# 17. Other Commercial Condition Changes

The same `CHANGED` semantics SHALL apply where relevant booking conditions change, including:

- board;
- payment type;
- packaging;
- allotment;
- occupancy;
- supplier status;
- taxes/fees.

The implementation SHALL compare the revalidated offer with the selected offer using the canonical model rather than comparing raw Hotelbeds DTOs outside the adapter.

---

# 18. Occupancy

The selected request SHALL preserve the canonical multi-room occupancy established by APP-008.3-R5-C2.

The implementation MUST support:

- multiple rooms;
- adults per room;
- children per room;
- child ages per room.

If CheckRate returns occupancy information, the canonical result SHALL preserve it.

The implementation MUST NOT revert to the former one-room assumption.

---

# 19. Revalidation and Package Stops

Where the selected rate belongs to a package stop, the revalidation operation SHALL preserve that stop association through the application boundary.

CheckRate operates on the selected accommodation offer for one stop.

APP-008.4 does not orchestrate the complete multi-stop package.

Package-wide revalidation remains a future application orchestration concern.

---

# 20. Failure Semantics

The implementation SHALL distinguish:

### Supplier Unavailability

The selected rate is no longer available.

Result:

`UNAVAILABLE`

### Supplier Business Error

The supplier rejects the revalidation because the selected offer cannot be revalidated.

Map according to the established provider error model.

### Transport Failure

Network, timeout, TLS or equivalent transport failure.

Result:

`FAILED`

### Malformed Supplier Response

The response cannot be safely mapped.

Result:

`FAILED`

The implementation MUST NOT convert technical failures into `UNAVAILABLE` merely to simplify application handling.

---

# 21. Retry Behaviour

Reuse the established supplier protection and retry architecture.

Do not introduce an unrestricted CheckRate retry loop.

Retry behaviour MUST remain bounded and consistent with the existing Hotelbeds transport/protection implementation.

No retry is permitted to change the selected supplier reference.

---

# 22. No Fabricated Data

The implementation MUST NOT fabricate:

- accommodation;
- room;
- rate;
- price;
- booking reference;
- cancellation policy;
- supplier availability.

If the supplier cannot provide a valid revalidated rate, return the appropriate canonical outcome.

---

# 23. Inventory and Existing Consumers

APP-008.3-R5-C2 established the canonical room/rate hierarchy.

APP-008.4 SHALL consume that hierarchy.

Do not revert inventory or application services to the former shallow:

- accommodation;
- available;
- metadata

result.

Where a validated rate is returned, the existing canonical room/rate context SHALL remain available to the caller.

---

# 24. Booking Boundary

APP-008.4 prepares the validated rate for a future Booking capability.

It SHALL NOT:

- create a reservation;
- persist a booking;
- send holder/passenger data;
- confirm a booking;
- generate a voucher;
- perform payment.

The future Booking capability will consume the validated supplier reference and canonical selection.

---

# 25. CheckRate Reference Lifetime

The implementation SHALL treat the supplier reference as a transient offer reference rather than a permanent booking identifier.

Do not assume a supplier rate reference remains valid indefinitely.

The selected offer must be revalidated immediately before a future Booking operation when the business workflow requires it.

Any supplier-specific expiry behaviour SHALL remain inside the supplier adapter unless the canonical architecture explicitly requires exposure.

---

# 26. Supplier-Neutral Revalidation

The application-facing contract MUST remain independent of Hotelbeds.

The architecture SHALL support:

GCT Canonical Selection
→ Provider
→ Supplier CheckRate

A future supplier may implement a different revalidation mechanism without changing the canonical selection model.

If a future supplier does not require a CheckRate equivalent, the provider may return a canonical result indicating that revalidation is not required according to the provider contract.

Do not implement that future supplier in this iteration.

# 37. Final Architectural Statement

APP-008.4 establishes the GCT Core rate-revalidation boundary between Availability and future Booking.

The canonical application flow is:

Availability
→ Client Selection
→ CheckRate
→ Current Validated Rate
→ Future Booking

Hotelbeds remains the initial supplier implementation.

Hotelbeds-specific request/response structures and `rateKey` remain inside the supplier adapter.

GCT Core owns the canonical revalidation result and commercial workflow.

APP-005 remains responsible for GCT package pricing.

APP-004 remains responsible for reservation and future Booking.

APP-008.4 SHALL establish the revalidation capability without implementing any subsequent Booking or Cancellation functionality.
