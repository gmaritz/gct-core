# 1. Purpose

APP-008.3 defines the implementation requirements for real-time accommodation availability and rate retrieval through the Hotelbeds Booking API.

The capability SHALL:

- resolve eligible accommodation candidates from the GCT hotel catalogue;
- support explicit hotel-code selection;
- support catalogue attribute selection;
- enforce the active catalogue boundary;
- construct Hotelbeds Availability requests;
- support multiple hotels in a single Availability request;
- support multiple occupancy configurations and rooms;
- support child ages;
- call the Hotelbeds Availability endpoint;
- map Hotelbeds Availability responses into the canonical accommodation availability model;
- preserve booking-critical supplier information;
- preserve the distinction between `BOOKABLE` and `RECHECK` rates;
- preserve cancellation policies;
- preserve `rateCommentsId`;
- preserve Hotelbeds supplier category information independently from GCT Star Grading;
- satisfy the relevant HBX-001 certification requirements;
- establish the foundation required by later CheckRate and Booking capabilities without implementing those capabilities.

# 3. Architectural Position

The canonical availability flow SHALL be:

```text
Accommodation Search Criteria
        |
        v
Candidate Resolution
        |
        +------------------------------+
        |                              |
        v                              v
Explicit Hotel Codes          Catalogue Attribute Filters
        |                              |
        +---------------+--------------+
                        |
                        v
              Active Catalogue Entries
                        |
                        v
                Candidate Hotel Codes
                        |
                        v
          Hotelbeds Availability Requests
                        |
                        v
              Hotelbeds Availability
                        |
                        v
              Supplier Response Mapping
                        |
                        v
           Canonical Availability / Rates
```

The catalogue is the GCT commercial selection boundary.

Hotelbeds is the real-time availability and rate authority.

Hotelbeds Availability SHALL therefore only be requested for hotel codes resolved from the active GCT catalogue.

Hotelbeds Availability SHALL NOT independently discover hotels outside the GCT catalogue.

# 4. Existing Implementation Baseline

APP-008.2-R5 is complete and SHALL be treated as an existing dependency.

The verified baseline is:

- 340 active catalogue entries;
- 340 unique Hotelbeds hotel codes;
- no duplicate hotel codes;
- no missing destination values;
- no missing zone values;
- no missing GCT Star Grading values;
- 340 successfully synchronized Hotelbeds Content records.

The Content synchronization implementation already provides:

- configurable Content batch size;
- QPS control;
- retry/backoff;
- persisted synchronization state;
- database-backed catalogue enforcement;
- initial synchronization command.

The Content synchronization batch size of 50 hotel codes SHALL NOT be reused as the Availability batch size.

Hotelbeds currently permits up to 2,000 hotel codes in one Availability request. APP-008.3 SHALL therefore use the supplier-supported Availability limit rather than the Content synchronization batch size.

No Hotelbeds Content synchronization SHALL be executed by APP-008.3.

# 5. Current Gaps Being Addressed

- an existing canonical `AccommodationRate`;

However, the current Availability path does not:

- construct `/hotel-api/1.0/hotels` requests;
- resolve catalogue candidates before Availability;
- model per-room occupancy;
- model child ages;
- enforce the Hotelbeds 2,000-hotel Availability limit;
- preserve the complete supplier rate contract;

- preserve `rateCommentsId`;
- carry Hotelbeds supplier category information through Availability;
- use mTLS;
- explicitly handle GZIP;
- provide dedicated Availability tests.

# 6. Domain and Application Requirements

## 6.1 Accommodation Search Criteria

The accommodation search contract SHALL be extended only where necessary to support real Hotelbeds Availability requirements.

The search criteria SHALL support:

- check-in date;
- check-out date;
- source market;
- occupancy configuration;
- explicit hotel codes;
- destination code;
- zone code;
- GCT Star Grading.

Existing accommodation search properties SHALL be retained unless they are proven incompatible with the canonical model.

The implementation SHALL NOT create a parallel accommodation search contract solely for Hotelbeds.

## 6.2 Occupancy Model

The current scalar:

```text
rooms: number
```

is insufficient for Hotelbeds Availability.

APP-008.3 SHALL introduce a canonical occupancy representation supporting multiple occupancy groups.

Each occupancy group SHALL contain:

```text
rooms
adults
children
childAges
```

Conceptually:

```text
occupancies:
[
  {
    rooms: 1,
    adults: 2,
    children: 0,
    childAges: []
  },
  {
    rooms: 1,
    adults: 2,
    children: 1,
    childAges: [7]
  }
]
```

The model SHALL permit multiple rooms with identical occupancy to be represented by `rooms > 1`.

Where rooms have different occupancy configurations, separate occupancy nodes SHALL be used.

Where children have different ages, the occupancy nodes SHALL be separated as necessary to preserve the exact requested occupancy.

## 6.3 Child Ages

If `children > 0`:

- `childAges` SHALL be present;
- the number of child ages SHALL equal the number of children;
- every child age SHALL be valid;
- child ages SHALL be mapped into Hotelbeds child passenger nodes.

The application SHALL NOT send a child count without corresponding ages.

## 6.4 Source Market

The Availability request SHALL carry an explicit `sourceMarket`.

GCT Core SHALL NOT infer source market from:

- IP address;
- destination;
- hotel location;
- traveller nationality;
- browser locale.

The source market SHALL be an explicit application-level value.

The implementation SHALL validate that a source market exists before constructing a Hotelbeds Availability request.

No hard-coded market such as `ZA` SHALL be embedded in the Hotelbeds provider.

The source market SHALL remain configurable and suitable for future commercial channel requirements.

# 7. Candidate Resolution

## 7.1 General Rule

Candidate resolution SHALL occur before Hotelbeds Availability.

The Hotelbeds provider SHALL NOT independently determine the commercial hotel candidate set.

The application SHALL resolve candidates using the GCT hotel catalogue.

## 7.2 Explicit Hotel-Code Selection

When `hotelCodes` are supplied:

1. the supplied codes SHALL be normalised;
2. duplicates SHALL be removed;
3. codes SHALL be validated;
4. codes SHALL be resolved against the active catalogue;
5. inactive or unknown codes SHALL NOT be sent to Hotelbeds.

The resulting candidate set SHALL contain only active catalogue entries.

An explicit hotel code SHALL NOT provide a mechanism to bypass the catalogue.

## 7.3 Catalogue Attribute Selection

When explicit hotel codes are not supplied, candidate resolution SHALL support:

- `destinationCode`;
- `zoneCode`;
- `starGrading`.

The filters SHALL operate against the GCT catalogue.

The catalogue query SHALL return only active entries.

The following conceptual filter is required:

```text
active = true
AND destinationCode = requested destinationCode, when supplied
AND zoneCode = requested zoneCode, when supplied
AND starGrading = requested starGrading, when supplied
```

Additional existing catalogue filters MAY continue to be supported where already part of the canonical application model.

## 7.4 Selection Precedence

Explicit hotel-code selection SHALL take precedence over catalogue attribute selection.

When explicit hotel codes are supplied:

- attribute filters SHALL NOT cause additional hotels to be added;
- only the explicitly selected active catalogue hotels SHALL be eligible.

## 7.5 Empty Candidate Set

If candidate resolution produces zero active hotels:

- Hotelbeds SHALL NOT be called;
- the application SHALL return a deterministic empty-availability result;
- the result SHALL distinguish "no eligible catalogue hotels" from "Hotelbeds returned no availability".

# 8. Availability Request Batching

Hotelbeds Availability supports up to 2,000 hotels per Availability request.

APP-008.3 SHALL:

- use a maximum of 2,000 hotel codes per Availability request;
- not use the existing 50-code Content batch size;
- preserve all requested occupancies within each Availability request;
- minimise the number of Availability calls;
- aggregate the responses into one canonical result.

For the current 340-hotel GCT catalogue, a single Availability request SHALL normally be sufficient from a hotel-count perspective.

The implementation SHALL nevertheless be written against the supplier limit rather than hard-coded for 340 hotels.

If a future catalogue contains more than 2,000 eligible hotels, the candidate list SHALL be partitioned into batches of no more than 2,000 hotels.

# 9. Hotelbeds Availability Integration

## 9.1 Endpoint

The Hotelbeds Availability operation SHALL use:

```text
POST /hotel-api/1.0/hotels
```

The implementation SHALL NOT use the existing:

```text
GET /hotels/{identifier}/rates
```

path as the APP-008.3 Availability implementation.

## 9.2 Availability Request Structure

The request SHALL contain, at minimum:

```json
{
  "sourceMarket": "...",
  "stay": {
    "checkIn": "YYYY-MM-DD",
    "checkOut": "YYYY-MM-DD"
  },
  "occupancies": [
    {
      "rooms": 1,
      "adults": 2,
      "children": 0
    }
  ],
  "hotels": {
    "hotel": [123, 456]
  }
}
```

Where children exist, the occupancy SHALL include the appropriate child passenger nodes:

```json
{
  "rooms": 1,
  "adults": 2,
  "children": 1,
  "paxes": [
    {
      "type": "CH",
      "age": 7
    }
  ]
}
```

The request structure SHALL follow the Hotelbeds Booking API contract.

## 9.3 Hotel Code Source

The `hotels.hotel` array SHALL contain only hotel codes returned by GCT candidate resolution.

The implementation SHALL NOT populate this array from:

- user-supplied raw codes without catalogue validation;
- Hotelbeds Content results;
- Hotelbeds Availability results;
- external hotel searches;
- cached supplier results outside the catalogue.

## 9.4 Multi-Room Availability

All requested rooms SHALL be represented in the same Availability request.

The implementation SHALL NOT issue one Availability request per room.

## 9.5 Multiple Hotel Availability

Multiple eligible hotels SHALL be included in the same Availability request up to the Hotelbeds limit.

The implementation SHALL NOT issue one Availability request per hotel.

# 10. Hotelbeds Transport and Security

## 10.1 Authentication

Existing Hotelbeds API-key and `X-Signature` authentication SHALL be retained.

The authentication implementation SHALL continue to calculate the SHA-256 signature using:

```text
Api Key + Secret + current Unix timestamp in seconds
```

## 10.2 mTLS

Hotelbeds currently requires Mutual TLS for Hotel Availability operations.

APP-008.3 SHALL therefore implement mTLS for the Availability transport.

The mTLS implementation SHALL support:

- client certificate;
- client private key;
- trusted CA configuration where required;
- test endpoint;
- production endpoint;
- secure certificate loading;
- certificate rotation without source-code changes.

The private key SHALL never be logged, persisted in application data, or exposed in diagnostics.

## 10.3 Configuration

The Hotelbeds integration configuration SHALL support separate values for:

- API key;
- API secret;
- environment;
- Availability base URL;
- client certificate;
- private key;
- CA certificate where required;
- Availability timeout;
- QPS limit;
- retry policy.

Secrets SHALL be supplied through the established secure configuration mechanism.

No credential or private key SHALL be hard-coded.

## 10.4 GZIP

The Availability transport SHALL support GZIP compression.

Requests SHALL advertise:

```http
Accept: application/json
Accept-Encoding: gzip
Content-Type: application/json
```

The transport SHALL correctly decode GZIP responses.

## 10.5 Timeout

The current generic 10-second timeout SHALL NOT be assumed to be the final timeout for every Hotelbeds operation.

APP-008.3 SHALL introduce an Availability-specific timeout configuration.

The value SHALL be configurable.

The implementation SHALL NOT introduce the later Booking Confirmation 60-second timeout into APP-008.3.

# 11. Availability Request DTO

A dedicated Availability request contract SHALL be introduced.

It SHALL model the actual Hotelbeds Availability request rather than relying on:

```text
body: unknown
```

The request model SHALL represent:

```text
sourceMarket
stay
occupancies
hotels
```

The occupancy model SHALL represent:

```text
rooms
adults
children
paxes
```

The Hotelbeds supplier DTO SHALL remain isolated from the canonical application domain model.

# 12. Availability Response Model

A dedicated Hotelbeds Availability response model SHALL be introduced.

The supplier response SHALL be mapped through the Hotelbeds Anti-Corruption Layer.

The canonical application model SHALL NOT expose the raw Hotelbeds response structure.

The mapping SHALL preserve all information required by the GCT accommodation search and later booking workflow.

# 13. Hotel Availability Result

Each returned hotel SHALL preserve, where provided:

- Hotelbeds hotel code;
- hotel name;
- Hotelbeds category code;
- Hotelbeds category name;
- destination code;
- destination name;
- zone code;
- zone name;
- coordinates where supplied;
- currency;
- minimum rate where supplied;
- maximum rate where supplied;
- room results;
- availability metadata.

The Hotelbeds category SHALL remain supplier-owned.

# 14. GCT Star Grading

GCT Star Grading SHALL remain a separate commercial classification.

It SHALL NOT be mapped from:

- Hotelbeds `categoryCode`;
- Hotelbeds `categoryName`;
- Hotelbeds `S2C`.

The GCT Star Grading SHALL originate from the GCT catalogue.

Where a Hotelbeds Availability result is mapped back to the canonical hotel result, the implementation SHOULD associate the active catalogue entry's GCT Star Grading with the result.

The model SHALL therefore distinguish:

```text
supplierCategory
```

from:

```text
gctStarGrading
```

These values SHALL never be conflated.

# 15. Room Availability Result

Each room result SHALL preserve:

- supplier room code;
- supplier room name;
- available rates.

Room availability SHALL not be collapsed into a single rate.

The implementation SHALL preserve all supplier rates required by the canonical application contract unless a deliberate existing commercial filter excludes them.

No new commercial filtering of room types or boards SHALL be introduced by APP-008.3.

# 16. Canonical Rate Model

The existing `AccommodationRate` SHALL be extended rather than replaced with a second canonical rate model.

The canonical rate SHALL preserve, where supplied:

- rate identifier;
- `rateKey`;
- `rateType`;
- rate class;
- availability status;
- currency;
- net amount;
- selling amount where supplied;
- board code;
- board name;
- room count;
- adult count;
- child count;
- child ages;
- payment type;
- packaging indicator;
- allotment where supplied;
- hotel mandatory indicator where supplied;
- cancellation policies;
- `rateCommentsId`;
- supplier category context where relevant;
- supplier identity;
- raw supplier metadata only where required by established integration standards.

# 17. Rate Key

`rateKey` is a booking-critical supplier identifier.

The implementation SHALL:

- preserve the exact Hotelbeds `rateKey`;
- never truncate it;
- never transform it;
- never substitute a generated identifier;
- never use `"unknown-rate"` as a fallback.

If Hotelbeds returns a rate without a valid `rateKey`:

- the rate SHALL be rejected from the canonical bookable availability result;
- the condition SHALL be logged as a supplier contract violation;
- the request SHALL not be retried merely because the response is malformed.

# 18. Rate Type

The Hotelbeds `rateType` SHALL be preserved exactly as:

```text
BOOKABLE
RECHECK
```

The implementation SHALL NOT map both values to a generic accommodation rate type.

The canonical model SHALL expose the distinction explicitly.

## 18.1 BOOKABLE

A `BOOKABLE` rate SHALL be classified as:

```text
BOOKABLE
```

and marked as eligible for the future direct Booking workflow.

APP-008.3 SHALL NOT perform Booking.

## 18.2 RECHECK

A `RECHECK` rate SHALL be classified as:

```text
RECHECK
```

and marked as requiring the future CheckRate operation before Booking.

APP-008.3 SHALL NOT perform CheckRate.

## 18.3 Workflow Rule

The implementation SHALL ensure that downstream consumers can determine:

```text
BOOKABLE -> Booking may proceed without CheckRate
RECHECK  -> CheckRate required before Booking
```

# 19. Cancellation Policies

The canonical rate SHALL preserve Hotelbeds cancellation policies.

Each cancellation policy SHALL preserve, where supplied:

- cancellation amount;
- currency;
- effective date/time;
- hotel amount where supplied;
- additional supplier cancellation attributes where required.

The implementation SHALL NOT calculate or reinterpret cancellation fees as part of APP-008.3.

The supplier-provided policy SHALL remain authoritative.

Cancellation policy calculation and booking-time cancellation enforcement belong to later capabilities.

# 20. Rate Comments

The canonical rate SHALL preserve:

```text
rateCommentsId
```

exactly as returned by Hotelbeds.

The identifier SHALL remain available to later rate-comment resolution.

APP-008.3 SHALL NOT implement the full rate-comment resolution workflow.

Where Hotelbeds returns a direct rate comment in the Availability response, it MAY be preserved as supplier metadata, but `rateCommentsId` remains mandatory where supplied.

# 21. Supplier Category

Hotelbeds category information SHALL be preserved separately from GCT Star Grading.

The canonical hotel availability result SHALL support:

```text
supplierCategory.code
supplierCategory.name
```

and:

```text
gctStarGrading
```

as separate values.

Example:

```text
supplierCategory:
  code: "4EST"
  name: "4 STARS"

gctStarGrading:
  4
```

The two values SHALL NOT be assumed equivalent.

# 22. Availability Pagination and Result Completeness

The implementation SHALL preserve the Hotelbeds response metadata required to determine result completeness.

Where the supplier returns:

- total result count;
- returned result count;
- page information;
- pagination metadata;

the canonical result SHALL preserve the information required by the application.

If Hotelbeds Availability returns the complete requested hotel set in one response, no artificial application pagination SHALL be introduced.

The implementation SHALL not silently discard supplier results because of application-side page-size defaults.

# 23. Availability Workflow Integrity

APP-008.3 SHALL establish the Availability stage as a distinct workflow boundary.

The following sequence SHALL be supported:

```text
Availability
    |
    +-- BOOKABLE -> future Booking
    |
    +-- RECHECK  -> future CheckRate -> future Booking
```

APP-008.3 SHALL NOT:

- call Availability again before a future CheckRate;
- call Availability again before a future Booking;
- automatically refresh Availability when a user selects a rate;
- implement a hidden Availability retry that creates duplicate workflow calls.

Retries caused by transport-level failures are separate from business workflow repetition and SHALL follow the retry rules in Section 25.

# 24. Availability Result Aggregation

When multiple Availability requests are required because the candidate set exceeds 2,000 hotels:

1. candidate hotels SHALL be partitioned deterministically;
2. each batch SHALL contain no more than 2,000 hotel codes;
3. each request SHALL contain the same stay and occupancy criteria;
4. each response SHALL be mapped independently;
5. results SHALL be aggregated;
6. duplicate hotel results SHALL be removed;
7. rate keys SHALL remain unchanged;
8. the final result SHALL preserve the requested search context.

The implementation SHALL not modify rate information while aggregating results.

# 25. Error Handling

## 25.1 Supplier HTTP Errors

The existing Hotelbeds error classification SHALL be reused.

At minimum:

| Condition | Behaviour |
|---|---|
| 400 / 422 | Non-retryable validation error |
| 401 | Non-retryable authentication error |
| 403 | Non-retryable authorization/access error |
| 404 | Non-retryable endpoint/resource error |
| 429 | Retryable rate-limit error |
| 5xx | Retryable supplier error |
| Timeout | Retryable transport error |
| Network error | Retryable transport error |
| Malformed response | Non-retryable supplier contract error |

## 25.2 Retry Policy

Availability retries SHALL be bounded.

The implementation SHALL:

- use the established Hotelbeds retry infrastructure where possible;
- respect QPS limits;
- apply bounded exponential backoff for retryable failures;
- not retry validation, authentication or malformed-response errors;
- not create an unbounded retry loop.

Retries SHALL occur at the transport/integration level and SHALL NOT result in multiple successful Availability workflows being exposed to the caller.

## 25.3 429 Handling

A Hotelbeds `429` response SHALL be classified as retryable.

The retry implementation SHALL respect any supplier-provided retry timing where available.

The implementation SHALL remain within the configured supplier QPS limit.

## 25.4 Empty Availability

A successful Hotelbeds response containing no available hotels SHALL be treated as a valid availability result.

It SHALL NOT be interpreted as a supplier failure.

# 26. Security Requirements

The implementation SHALL:

- protect API secrets;
- protect client private keys;
- protect client certificates;
- avoid logging authentication headers;
- avoid logging `X-Signature`;
- avoid logging private key material;
- avoid exposing supplier credentials in application responses;
- use HTTPS only;
- use mTLS for Availability;
- validate the configured Hotelbeds endpoint;
- maintain separate test and production configuration.

The Availability request/response SHALL be treated as supplier integration data.

# 27. Observability

Availability calls SHALL produce structured operational telemetry sufficient to identify:

- operation;
- supplier;
- environment;
- request correlation identifier;
- candidate hotel count;
- number of Availability batches;
- occupancy count;
- response hotel count;
- response rate count;
- duration;
- retry count;
- final outcome.

Sensitive information SHALL NOT be included.

Specifically, logs SHALL NOT contain:

- API secrets;
- X-Signature;
- client private keys.

`rateKey` SHALL be treated as booking-sensitive integration data and SHOULD NOT be written to normal informational logs unless required for controlled debugging.

# 30. No Database Synchronization Changes

APP-008.3 SHALL NOT modify the Hotelbeds Content synchronization workflow.

It SHALL NOT:

- change the Content synchronization batch size;
- trigger Content synchronization;
- modify the existing 340 catalogue entries;
- recreate the catalogue;
- introduce duplicate catalogue records;
- replace the existing catalogue repository.

The catalogue remains an existing dependency.

# 31. Data Persistence

APP-008.3 does not require persistence of Availability responses.

Availability is real-time supplier data.

The implementation SHALL NOT introduce database tables solely to cache:

- Availability responses;
- rates;
- rate keys;
- cancellation policies.

Persistence of booking state and reservation state belongs to subsequent capabilities.

# 32. Application Service Integration

The existing accommodation discovery flow SHALL be integrated with the catalogue resolution and Hotelbeds Availability path.

The implementation SHALL preserve the existing provider abstraction.

The preferred responsibility split is:

```text
Accommodation Discovery
    |
    v
Candidate Resolution
    |
    v
Accommodation Provider
    |
    v
Hotelbeds Availability Gateway
    |
    v
Hotelbeds Transport
```

The Hotelbeds provider SHALL NOT contain direct database access to Prisma.

Catalogue access SHALL remain behind the established catalogue service/repository abstraction.

# 33. Anti-Corruption Layer

Hotelbeds-specific representations SHALL remain isolated within the Hotelbeds integration boundary.

Hotelbeds DTOs SHALL NOT leak into the canonical accommodation domain.

The following SHALL remain supplier-specific:

- Hotelbeds response DTOs;
- Hotelbeds category structures;
- Hotelbeds rate representation;
- Hotelbeds transport configuration;
- Hotelbeds authentication;
- Hotelbeds endpoint paths.

The canonical accommodation model SHALL contain only platform-approved representations.

# 34. Backward Compatibility

Existing accommodation capabilities SHALL remain compilable and testable unless a change is required to establish the canonical Availability model.

Existing APIs SHALL NOT be removed merely because APP-008.3 introduces the dedicated Availability path.
