# APP-008.3 — Accommodation Availability Architecture Review

**Document ID:** APP-008.3-ARCH-001  
**Capability:** Accommodation Availability  
**Status:** Draft — Architecture Review  
**Purpose:** Establish the target GCT Core Accommodation Availability architecture before further implementation  
**Supersedes:** Current incremental APP-008.3 availability design as the implementation baseline  
**Implementation Status:** Not authorized  
**Supplier:** Hotelbeds is an external supplier adapter only

---

## 1. Purpose

This document defines the architecture review required to establish a complete, supplier-neutral Accommodation Availability capability for GCT Core.

The current Hotelbeds implementation is treated as **technical discovery and validated supplier integration knowledge**, not as the canonical architecture.

The objective is to establish the correct GCT Core architecture **before further implementation** and prevent additional incremental patching of the existing Availability implementation.

The architecture must support the actual commercial requirement:

> A client searching a GCT Core tour package must be able to specify the required stay, number of rooms, adults, children and child ages, and receive the available accommodation options including room types and commercially selectable rates.

The architecture must also preserve sufficient information to support a later room/rate selection and booking operation.

---

# 2. Architectural Principle

The canonical model MUST be designed from GCT Core business requirements.

Hotelbeds MUST NOT define the canonical model.

The required architecture is:

    GCT Core Business Requirement
                ↓
    GCT Core Canonical Availability Contract
                ↓
    Supplier Availability Adapter
                ↓
    Hotelbeds Availability API

The inverse architecture is prohibited:

    Hotelbeds JSON
            ↓
    GCT Core Canonical Model

Hotelbeds-specific concepts, field names and structures must remain inside the Hotelbeds adapter boundary.

Examples that MUST NOT become canonical field names include:

- `rateKey`
- `hotelbedsRateKey`
- `hotelbedsRoomCode`
- `rateClass`
- `rateType`
- `paymentType`
- `packaging`

Where supplier-specific information is required for future booking, it must be represented through a supplier-neutral reference abstraction.

---

# 3. Architectural Reset

The existing APP-008.3 implementation has demonstrated the following supplier facts:

- Hotelbeds Availability requires a hotel filter in its Availability request.
- Hotelbeds Availability can return multiple hotels.
- Each hotel can contain multiple room types.
- Each room type can contain multiple rates.
- Rates contain supplier references required for booking continuity.
- Rates contain pricing information.
- Rates contain occupancy information.
- Rates can contain board information.
- Rates can contain cancellation policies.
- Rates can contain taxes.
- Hotelbeds can return a valid zero-result response.
- Hotelbeds uses mTLS authentication.
- The current R3/R4-C1 transport path has been technically validated.
- The current R5 mapper has been technically validated for the observed zero-result response.

These findings are **supplier integration knowledge**.

They do not define the GCT Core canonical model.

The existing R5/R7 implementation MUST therefore not be treated as the architectural source of truth.

---

# 4. Business Requirement

The Accommodation Availability capability must support package-search scenarios in which a client can specify:

- check-in date;
- check-out date;
- one or more rooms;
- adults per room;
- children per room;
- child ages per room;
- source market;
- accommodation candidate selection.

The response must provide sufficient information for the client to select a commercially suitable accommodation option.

The client must be able to understand:

- which accommodation is available;
- which room types are available;
- which rates are available for each room type;
- the price;
- the currency;
- the pricing basis;
- the board/meal plan;
- availability/bookability status;
- cancellation conditions;
- taxes/fees;
- relevant payment conditions;
- the supplier-neutral reference required for later booking.

---

This architecture review does not:

- implement the Availability capability;
- modify the current Hotelbeds adapter;
- modify the database;
- define Hotelbeds DTOs;
- define Hotelbeds transport;
- perform live supplier calls;
- finalize API serialization;
- implement booking;
- implement payment;
- define package pricing.

Those activities follow only after the canonical Availability architecture has been approved.

# 6. Canonical Availability Concept

Availability is a **commercial option discovery capability**, not merely a boolean hotel lookup.

The canonical conceptual relationship is:

    Accommodation
        │
        └── Availability Options
                │
                ├── Room Option
                │       │
                │       ├── Rate Option
                │       ├── Rate Option
                │       └── ...
                │
                └── Room Option
                        │
                        ├── Rate Option
                        └── ...

The architecture MUST preserve the relationship:

    Accommodation
        → Room
            → Rate

It MUST NOT flatten room and rate information into a single accommodation-level collection.

---

# 7. Canonical Availability Request

The canonical Availability request must represent the client's actual search requirement independently of any supplier.

Conceptually:

    AvailabilityRequest
        ├── stay
        │     ├── checkIn
        │     └── checkOut
        │
        ├── occupancy
        │     └── rooms[]
        │           ├── adults
        │           ├── children
        │           └── childAges[]
        │
        ├── sourceMarket
        │
        └── accommodationSelection

The exact names and value-object types must be finalized in the canonical specification.

---

# 8. Multi-Room Requirement

Multi-room support is mandatory.

The canonical request MUST NOT permanently model occupancy as:

    rooms = 1

The canonical representation must support:

    Room 1
        adults
        children
        childAges[]

    Room 2
        adults
        children
        childAges[]

    Room 3
        adults
        children
        childAges[]

Different rooms may have different occupancy.

The canonical model must preserve the relationship between each room occupancy group and the resulting availability options.

A supplier adapter may transform this structure into the supplier's request format.

The supplier's occupancy limitations must not become canonical restrictions unless they represent an actual GCT Core business rule.

---

# 9. Canonical Accommodation

Accommodation represents relatively stable accommodation identity and content.

It may contain:

- accommodation identity;
- name;
- category;
- location;
- coordinates;
- rating;
- images;
- amenities;
- contacts;
- static policies;
- provider reference.

Dynamic Availability MUST NOT be embedded into the static Accommodation entity.

Room and rate availability belong to the Availability result.

---

# 10. Canonical Availability Options

A positive Availability result must contain a supplier-neutral availability-options structure.

Conceptually:

    AvailabilityOptions
        └── roomOptions[]

The architecture must preserve the returned commercial alternatives.

The exact type name, ownership and value-object structure must be finalized by the canonical specification.

---

# 11. Canonical Room Option

A Room Option represents a room type that can be selected as part of an availability result.

A Room Option must be capable of representing:

- canonical room reference;
- room name;
- available rate options;
- relationship to the requested occupancy where applicable;
- supplier-neutral booking continuity information where required.

Conceptually:

    RoomOption
        ├── reference
        ├── name
        └── rateOptions[]

The canonical Room Option MUST NOT expose a Hotelbeds-specific room code as its semantic definition.

The Hotelbeds room code may be retained inside an adapter-specific supplier reference.

---

# 12. Canonical Rate Option

A Rate Option represents a commercially selectable rate associated with a Room Option.

A Rate Option must support, where applicable:

- canonical rate reference;
- supplier-neutral booking reference;
- status;
- pricing;
- occupancy;
- board/meal plan;
- allotment;
- payment information;
- packaging information;
- cancellation policies;
- taxes/fees.

Conceptually:

    RateOption
        ├── bookingReference
        ├── status
        ├── pricing
        ├── occupancy
        ├── board
        ├── allotment
        ├── payment
        ├── packaging
        ├── cancellationPolicies[]
        └── taxes[]

The canonical contract must define which fields are mandatory, optional or conditionally present.

---

# 13. Supplier-Neutral Booking Reference

Booking continuity is mandatory.

A selected rate must be traceable to the supplier offer that produced it.

The canonical model must therefore contain a supplier-neutral reference concept.

Conceptually:

    SupplierReference
        ├── provider
        └── opaqueReference

The canonical model MUST NOT expose the Hotelbeds field name `rateKey`.

The Hotelbeds adapter may populate:

    provider = HOTELBEDS
    opaqueReference = supplier rate reference

The future booking adapter can then translate that opaque reference back into the supplier-specific booking request.

The canonical contract must define:

- provider identity;
- opaque reference;
- immutability;
- serialization rules;
- whether room references also require supplier references;
- relationship between accommodation, room and rate references.

---

# 14. Pricing Architecture

Pricing must be represented as a canonical concept rather than a raw supplier number.

The architecture must resolve:

- amount;
- currency;
- pricing basis;
- total-stay versus per-room semantics;
- whether the amount is net or customer-facing;
- tax inclusion/exclusion;
- applicable fees.

The architecture must avoid ambiguous fields such as:

    price: 863.49

without defining what the amount represents.

A canonical monetary model or deliberately shared pricing value object must be selected.

The existing pricing-domain Money concepts may be evaluated for reuse, but reuse must be intentional and contractually appropriate.

---

# 15. Pricing Basis

Pricing basis must be explicit.

The canonical contract must distinguish, where relevant:

- total stay;
- per room;
- per night;
- per person;
- other supplier-provided pricing semantics.

Hotelbeds-specific pricing semantics must be translated into the canonical pricing model.

---

# 16. Currency

Currency must be associated explicitly with every monetary value.

The canonical contract must define:

- currency representation;
- ISO currency semantics;
- precision;
- rounding expectations;
- relationship to taxes and cancellation amounts.

---

# 17. Occupancy on Availability Results

The request occupancy and returned rate occupancy are related but not necessarily identical concepts.

The architecture must distinguish:

### Requested occupancy

What the client requested.

### Offered occupancy

The occupancy for which the returned rate applies.

This distinction is important because supplier responses can contain rate-level occupancy information.

The canonical rate must therefore be able to retain the applicable occupancy.

---

# 18. Board / Meal Plan

Board information must be canonical and supplier-neutral.

The architecture should support:

- board code;
- board name;
- canonical semantics where appropriate.

Hotelbeds `boardCode` and `boardName` must be mapped into the canonical board representation rather than exposed directly.

---

# 19. Bookability

Rate status must be represented canonically.

The architecture must support supplier states such as:

- directly bookable;
- recheck required;
- unavailable.

Supplier-specific status values must be mapped to canonical semantics.

For example:

    BOOKABLE
    RECHECK_REQUIRED

may be appropriate canonical states.

The final state model must be defined in the canonical specification.

---

# 20. Allotment

Where the supplier provides available room/rate allotment, the architecture must determine whether allotment is:

- exposed to clients;
- used internally;
- used only for booking validation;
- or intentionally discarded.

If exposed, its semantics must be explicitly defined.

No Hotelbeds-specific interpretation may become canonical accidentally.

---

# 21. Payment Information

Payment information must be assessed as part of the rate option.

The architecture must determine whether the canonical contract needs to distinguish concepts such as:

- pay at supplier;
- pay at booking;
- pay later;
- other payment arrangements.

Supplier-specific payment codes must not become canonical.

---

# 22. Packaging

The architecture must determine whether supplier packaging information is commercially meaningful to GCT Core.

If it is meaningful, it must be represented canonically.

If it is not meaningful, the adapter may discard it deliberately.

This decision must be explicit rather than accidental.

---

# 23. Cancellation Policies

Cancellation policies belong to the Rate Option, not merely the Accommodation.

The canonical model must support:

- one or more cancellation rules;
- effective date/time;
- cancellation amount;
- currency;
- cancellation condition;
- ordering.

Accommodation-level static policies must remain separate from dynamic rate cancellation policies.

---

# 24. Taxes and Fees

Taxes and fees must be represented without ambiguity.

The canonical model must support, where supplied:

- amount;
- currency;
- type;
- subtype;
- percentage where applicable;
- included/excluded semantics.

The architecture must prevent double-counting when constructing customer-facing prices.

---

# 25. Hotel-Level Price Aggregates

Hotelbeds may provide:

- `minRate`;
- `maxRate`;
- `currency`.

The canonical architecture must decide whether these are:

1. canonical aggregate values;
2. derived values from Rate Options;
3. supplier metadata;
4. deliberately discarded.

They must not be copied into the canonical model merely because Hotelbeds provides them.

The preferred architecture should derive aggregates from canonical rate options where the semantics are equivalent and reliable.

---

# 26. No Availability

A valid no-availability result must be representable without fabricating:

- accommodation;
- room;
- rate;
- price;
- booking reference.

The canonical result must explicitly distinguish:

    ACCOMMODATION

from:

    NO_AVAILABILITY

A `NO_AVAILABILITY` result must not contain a fabricated `"unavailable"` accommodation.

The existing sentinel used by earlier R2/R3 paths must be treated as legacy behavior and must not define the new canonical semantic.

---

# 27. Static Content and Dynamic Availability

The architecture must maintain a strict distinction.

### Static Accommodation Content

Provides:

- identity;
- descriptive content;
- location;
- category;
- amenities;
- images;
- stable policies.

### Dynamic Availability

Provides:

- available room options;
- rates;
- prices;
- occupancy;
- board;
- cancellation;
- taxes;
- booking references;
- current availability state.

The Availability adapter must not become the accommodation-content master.

---

# 28. Hotelbeds Adapter Boundary

The Hotelbeds integration must contain:

- Hotelbeds request DTOs;
- Hotelbeds response DTOs;
- Hotelbeds field names;
- Hotelbeds authentication;
- Hotelbeds transport;
- Hotelbeds-specific response interpretation;
- translation into canonical GCT Core models.

The canonical domain/application model must contain none of the following supplier-specific structures:

- `hotels.hotel`;
- `hotels.codes`;
- `rateKey`;
- `rateType`;
- `rateClass`;
- Hotelbeds-specific tax structures;
- Hotelbeds-specific cancellation structures.

---

# 29. R2 Responsibility

R2 remains responsible for candidate resolution.

R2 may determine:

- which accommodations are candidates;
- whether explicit hotel codes were supplied;
- catalogue selection;
- catalogue filtering.

R2 must not construct supplier-specific Availability requests.

---

# 30. R3 Responsibility

R3 becomes:

    Canonical Availability Request
            ↓
    Supplier-specific Hotelbeds Request

R3 must translate:

- stay;
- occupancy;
- candidate accommodations;
- source market;

into the Hotelbeds request.

R3 must not alter the canonical business semantics merely to match current supplier DTO limitations.

---

# 31. R4-C1 Responsibility

R4-C1 remains responsible for:

- HTTPS;
- mTLS;
- authentication transport;
- request transmission;
- response reception.

R4-C1 must not interpret canonical room/rate semantics.

---

# 32. R5 Responsibility

R5 becomes:

    Hotelbeds Response
            ↓
    Canonical Availability Result

R5 must:

- map accommodation identity;
- map room options;
- map rate options;
- map pricing;
- map occupancy;
- map board;
- map cancellation;
- map taxes;
- map supplier references;
- map availability/bookability;
- recognize valid no-availability responses.

R5 must not leak Hotelbeds DTOs beyond the adapter boundary.

R5 must reject genuinely malformed responses rather than invent canonical data.

---

# 33. R6 Responsibility

R6 remains responsible for:

- execution protection;
- retry policy;
- retry boundaries;
- failure handling.

R6 must remain independent of the canonical room/rate model.

---

# 34. R7 Responsibility

R7 remains responsible for application orchestration.

R7 must:

- coordinate candidate resolution;
- execute Availability;
- aggregate supplier results;
- expose canonical Availability;
- distinguish positive availability from no availability;
- preserve room/rate options.

R7 must not reconstruct lost supplier data.

---

# 35. R8 Responsibility

R8 remains a controlled verification harness.

R8 must eventually verify:

- canonical request generation;
- multi-room criteria;
- supplier request correctness;
- successful availability;
- multiple room options;
- multiple rates;
- no availability;
- canonical mapping;
- security;
- supplier call count.

R8 must not define the canonical contract.

---

# 36. Consumer Architecture

Consumers must consume the canonical model rather than supplier DTOs.

Expected future flow:

    Availability Result
        ↓
    Accommodation
        ↓
    Room Options
        ↓
    Rate Options
        ↓
    Client Selection
        ↓
    Booking Reference
        ↓
    Booking Capability

Consumers must explicitly handle:

    kind = ACCOMMODATION

and:

    kind = NO_AVAILABILITY

No consumer may assume that `accommodation` is always present.

---

# 37. Inventory

Inventory must preserve:

- accommodation;
- room options;
- rate options;
- booking references;
- pricing;
- relevant availability metadata.

Inventory must not discard the room/rate graph merely because earlier availability results were hotel-level.

---

# 38. Journey and Package Composition

Package composition must be able to consume Availability options when constructing tour packages.

The architecture must support future package selection such as:

    Package
        ↓
    Accommodation
        ↓
    Room Selection
        ↓
    Rate Selection
        ↓
    Package Price

The Availability contract must therefore not be designed as an isolated Hotelbeds integration result.

---

# 39. API / Client Boundary

The eventual client-facing representation must be supplier-neutral.

A client should be able to receive:

    Accommodation
        └── Room Options
              └── Rate Options

and select an option without knowing Hotelbeds field names.

The API contract must not expose:

- Hotelbeds `rateKey`;
- Hotelbeds room codes as semantic identifiers;
- Hotelbeds tax structures;
- Hotelbeds cancellation structures.

---

# 40. Booking Continuity

The architecture must preserve enough information to perform:

    Search
      ↓
    Availability
      ↓
    Room/Rate Selection
      ↓
    Booking

The selected canonical Rate Option must contain or reference sufficient supplier-neutral information to identify the selected offer later.

The canonical model must not require the client to understand or construct supplier-specific booking information.

---

# 41. Existing Model Review

The architecture review must explicitly decide the future of:

### AccommodationRate

Determine whether it:

- becomes the canonical Rate Option;
- is refactored into a reusable value/model;
- remains a separate rate-query contract;
- is replaced.

The decision must be based on semantic compatibility, not field overlap.

### AccommodationRateResult

Determine whether it:

- remains a separate capability;
- is refactored to consume shared rate concepts;
- becomes part of a broader Availability architecture.

It must not be merged implicitly.

### Occupancy Models

Determine whether:

- `AccommodationOccupancy`;
- `AccommodationOccupancyGroup`;
- `AccommodationSearchCriteria`

can be consolidated or reused without preserving the current one-room limitation.

### Money

Determine whether an existing pricing-domain Money model can become the canonical monetary abstraction.

### Cancellation

Determine whether a new shared canonical rate-level cancellation model is required.

### Tax

Determine whether a new shared canonical tax/fee model is required.

# 43. Anti-Patching Rule

This architecture review establishes an explicit prohibition against incremental architectural patching.

The following are prohibited:

- adding a field merely because Hotelbeds returns it;
- adding a canonical field without defining its business semantics;
- adding compatibility aliases;
- retaining supplier-specific field names;
- modifying consumers reactively after implementation failures;
- using compiler errors to discover canonical architecture;
- using Hotelbeds DTOs as canonical models;
- implementing only the fields needed by the current test response;
- deferring essential room/rate decisions until R5 implementation;
- extending the current result model merely because it already exists.

Any fundamental contract change must be resolved at architecture/specification level first.

# 44. Implementation Reset

The existing APP-008.3 Hotelbeds implementation must not be treated as the implementation baseline for the redesigned capability.

Existing work may be retained only where it is architecturally compatible after the new canonical contract is approved.

This includes potentially reusable technical knowledge around:

- Hotelbeds authentication;
- mTLS;
- transport;
- request signing/authentication;
- supplier endpoint configuration;
- R6 protection;
- supplier DTO mapping;
- live verification mechanics.

The existing canonical Availability model and mapper structure must not receive automatic preservation priority.

# 46. Required Outcome

## APPROVED FOR CANONICAL SPECIFICATION

Use this only if the target architecture is sufficiently complete to proceed to a formal canonical specification.

The review must provide:

- target request model;
- target response model;
- room/rate hierarchy;
- occupancy model;
- pricing model;
- booking continuity model;
- no-availability semantics;
- consumer strategy;
- supplier-adapter boundary;
- migration strategy from the current implementation.

## BLOCKED — ARCHITECTURAL GAP

Use this if a fundamental architectural decision remains unresolved.

If blocked:

- do not implement;
- do not modify source;
- do not modify tests;
- do not modify `.env`;
- do not call Hotelbeds;
- identify the unresolved architectural decision;
- recommend the specific next architecture/specification step.
