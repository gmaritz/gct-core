## 2. Purpose

This specification finalizes the canonical Accommodation Availability contract for GCT Core.

It resolves the architectural gaps identified during the APP-008.3-CAN-003-C1 review.

The contract must support the complete commercial accommodation-search lifecycle:

Client Search
→ Multi-Room Occupancy
→ Accommodation Results
→ Room Options
→ Rate Options
→ Price / Board / Cancellation / Tax / Payment Evaluation
→ Client Selection
→ Booking Continuity
→ Provider Booking

The canonical model is owned by GCT Core.

Hotelbeds is a provider implementation only.

No Hotelbeds-specific response structure, field name, identifier semantics, or supplier object may become part of the canonical contract.

---

# 3. Architectural Decisions

## 3.1 Availability Is a Commercial Option Graph

Accommodation Availability is not a boolean capability.

The canonical hierarchy is:

    AvailabilitySearchResult
        results[]
            AccommodationAvailabilityResult
                accommodation
                requestedOccupancy
                availabilityOptions
                    roomOptions[]
                        rateOptions[]

The hierarchy must preserve the relationship:

    Accommodation
        → RoomOption
            → RateOption

A rate cannot exist independently of its room option.

A room option cannot exist independently of its accommodation result.

---

## 3.2 Search-Level Result

The search-level contract is:

    AccommodationAvailabilitySearchResult

        results: AccommodationAvailabilityResult[]

        metadata: AvailabilitySearchMetadata

The result collection is ordered.

Ordering is significant and must be preserved through:

    R2 → R3 → R4 → R5 → R7 → application result

The provider must not arbitrarily reorder returned accommodation results.

---

# 4. Canonical Result Union

## 4.1 Definition

`AccommodationAvailabilityResult` is a discriminated union with exactly two states:

    AccommodationAvailabilityResult
        = AccommodationAvailabilitySuccess
        | AccommodationAvailabilityNoAvailability

The discriminant is:

    kind

Valid values are:

    "ACCOMMODATION"
    "NO_AVAILABILITY"

No third state may be introduced without a separate canonical decision.

---

## 4.2 Accommodation Success

The positive result contains:

    AccommodationAvailabilitySuccess

        kind: "ACCOMMODATION"

        accommodation: Accommodation

        requestedOccupancy: OccupancyRequest

        availabilityOptions: AvailabilityOptions

        available: true

        metadata: AccommodationResultMetadata

Invariants:

- `accommodation` is mandatory;
- `requestedOccupancy` is mandatory;
- `availabilityOptions` is mandatory;
- `available` is always `true`;
- `availabilityOptions.roomOptions` contains the commercially available room options;
- every returned rate belongs to a room option;
- every selectable rate contains a supplier-neutral booking reference.

---

## 4.3 No Availability

The no-availability result contains:

    AccommodationAvailabilityNoAvailability

        kind: "NO_AVAILABILITY"

        available: false

        metadata: AccommodationResultMetadata

The following properties must not exist:

- accommodation;
- requested occupancy;
- availability options;
- room options;
- rate options;
- pricing;
- supplier reference.

No accommodation may be fabricated to represent supplier-confirmed no availability.

---

# 5. Search-Level Empty Result

A search producing no accommodation results is represented by:

    AccommodationAvailabilitySearchResult
        results: []

This is different from an individual `NO_AVAILABILITY` result.

### Empty Search

Means:

    No accommodation result exists.

### NO_AVAILABILITY

Means:

    A valid accommodation availability outcome explicitly indicates no availability.

The provider adapter must not create artificial accommodation results solely to avoid an empty collection.

---

# 6. Canonical Availability Request

The canonical request is:

    AccommodationAvailabilityRequest

        stay: StayPeriod

        occupancy: OccupancyRequest

        sourceMarket: MarketCode

        candidateSelection: CandidateSelection

---

# 7. Stay Period

`StayPeriod` contains:

    checkIn: LocalDate

    checkOut: LocalDate

Invariants:

- check-in must precede check-out;
- both dates are required;
- supplier-specific date formatting is provider-adapter responsibility.

---

# 8. Occupancy Request

## 8.1 Structure

    OccupancyRequest

        rooms: OccupancyRoom[]

Each `OccupancyRoom` contains:

    OccupancyRoom

        adults: number

        children: number

        childAges: number[]

---

## 8.2 Occupancy Invariants

For every room:

- `adults >= 1`;
- `children >= 0`;
- `childAges.length === children`;
- child ages must represent valid child ages;
- room order is preserved.

The number of requested rooms is:

    occupancy.rooms.length

There is no canonical scalar `rooms` property.

---

## 8.3 Multi-Room Requirement

The canonical model must support:

    Room 1
        adults: 2
        children: 1
        childAges: [7]

    Room 2
        adults: 1
        children: 0
        childAges: []

Different rooms may contain different occupancy.

The canonical contract must never assume all rooms have identical occupancy.

---

# 9. Candidate Selection

`CandidateSelection` represents application-owned accommodation selection.

It may contain:

- explicit accommodation identifiers;
- destination selection;
- zone selection;
- another approved application-level selection mechanism.

Candidate selection is not supplier-specific.

R3 is responsible for translating candidate selection into the provider's request format.

---

# 10. Accommodation

The existing `Accommodation` model remains responsible for relatively stable accommodation information.

It may contain:

- identity;
- name;
- category;
- location;
- rating;
- images;
- amenities;
- policies;
- contacts;
- provider reference.

Dynamic room/rate availability must not be added to `Accommodation`.

Dynamic availability belongs under `availabilityOptions`.

---

# 11. Availability Options

The canonical structure is:

    AvailabilityOptions

        roomOptions: RoomOption[]

The collection is ordered.

Ordering received from the provider must be preserved unless an explicit application-level sorting operation is subsequently applied.

`AvailabilityOptions` represents dynamic inventory returned for the requested stay and occupancy.

---

# 12. Room Option

## 12.1 Structure

    RoomOption

        reference: SupplierNeutralReference

        name: string

        rateOptions: RateOption[]

---

## 12.2 Room Reference

The room reference is an opaque supplier-neutral reference.

It is not named after a supplier concept.

The reference must be sufficient to associate the selected room option with the selected provider offer.

A room reference may contain:

    SupplierReference

where provider and opaque reference are explicit.

---

## 12.3 Room Name

`name` is the canonical display name of the room option.

Supplier-specific room terminology may be mapped into this display value.

---

## 12.4 Room-to-Rate Relationship

Every `RateOption` belongs to exactly one `RoomOption`.

The canonical contract must preserve this relationship.

A rate must not be promoted to a global availability-level rate collection.

---

# 13. Rate Option

## 13.1 Structure

    RateOption

        bookingReference: SupplierReference

        status: RateStatus

        pricing: RatePricing

        occupancy: OfferedOccupancy

        board: BoardOption | null

        allotment: number | null

        payment: PaymentOption | null

        packaging: PackagingOption | null

        cancellationPolicies: CancellationPolicy[]

        taxes: TaxOrFee[]

---

## 13.2 Rate Identity

The canonical rate identity is:

    bookingReference

It is represented by:

    SupplierReference

The canonical model does not expose:

- `rateKey`;
- supplier-specific rate identifiers;
- supplier response fragments.

---

# 14. Supplier Reference

## 14.1 Structure

    SupplierReference

        provider: ProviderIdentifier

        opaqueReference: string

---

## 14.2 Provider

`provider` identifies the provider responsible for the reference.

It uses the canonical provider identity convention.

---

## 14.3 Opaque Reference

`opaqueReference` has no canonical internal structure.

The canonical domain must not parse or interpret it.

For Hotelbeds:

    Hotelbeds rateKey
        ↓
    SupplierReference.opaqueReference

The canonical field remains `opaqueReference`.

---

## 14.4 Reference Ownership

The provider owns the meaning of the opaque reference.

The reference must be passed unchanged to the provider adapter when the selected rate is subsequently booked or revalidated.

---

# 15. Rate Status

The canonical rate status is:

    RateStatus

        BOOKABLE
        RECHECK_REQUIRED

### BOOKABLE

The supplier indicates that the rate can proceed through the normal booking flow subject to standard booking validation.

### RECHECK_REQUIRED

The supplier requires the rate to be revalidated before booking.

Provider-specific status values are translated by the adapter.

No Hotelbeds status value may appear in the canonical model.

---

# 16. Rate Pricing

## 16.1 Structure

    RatePricing

        amount: Money

        basis: PricingBasis

        taxesIncluded: boolean

---

## 16.2 Money

`Money` is the shared canonical monetary representation.

It contains:

    amount

    currency

No Availability-specific duplicate Money type may be introduced.

---

## 16.3 Currency

Currency must use a canonical ISO-compatible representation.

The Availability contract must not be limited by the existing restricted accommodation currency enumeration.

If the existing currency implementation cannot represent a legitimate supplier currency, the shared currency abstraction must be extended rather than creating an Availability-specific currency type.

---

# 17. Pricing Basis

The canonical pricing basis is:

    PricingBasis

        TOTAL_STAY
        PER_ROOM
        PER_NIGHT
        PER_ROOM_PER_NIGHT

The provider adapter must map supplier pricing semantics to the correct canonical basis.

The canonical amount must never be exposed without its pricing basis.

---

# 18. Price Semantics

The canonical rate price represents the commercially relevant amount associated with the returned rate.

Supplier terminology such as:

    net

must not automatically become a canonical semantic.

The adapter must establish the meaning of the supplier amount and map it into the canonical pricing contract.

The canonical model must distinguish:

- price amount;
- currency;
- pricing basis;
- tax inclusion.

---

# 19. Hotel-Level Minimum and Maximum Pricing

Hotel-level `minRate` and `maxRate` are not authoritative booking prices.

They are derived summaries.

The canonical result may expose derived pricing summaries only if required by the application presentation contract.

The authoritative commercial price is:

    selected RateOption
        → pricing

The client must never interpret a hotel-level minimum price as independently bookable.

If min/max summaries are exposed, they must be derivable from canonical rate options.

---

# 20. Offered Occupancy

## 20.1 Structure

    OfferedOccupancy

        rooms: OccupancyRoom[]

The structure is intentionally aligned with requested occupancy.

---

## 20.2 Purpose

Offered occupancy describes the occupancy to which the returned rate applies.

It is separate from:

    requestedOccupancy

because the supplier may return rate-specific occupancy information.

---

## 20.3 Multi-Room

An offered rate may contain multiple occupancy groups.

The canonical contract must preserve the relationship between:

    RateOption
        → OfferedOccupancy
            → rooms[]

No aggregate-only adults/children representation is sufficient.

---

# 21. Board Option

## 21.1 Structure

    BoardOption

        code: string

        name: string

`code` and `name` are canonical supplier-neutral representations.

The provider adapter maps supplier board codes/names.

---

## 21.2 Optionality

A rate may have no board information.

In that case:

    board = null

No artificial board value may be created.

---

# 22. Allotment

`allotment` is optional.

If supplied:

- it represents supplier-reported inventory quantity;
- it is informational;
- it does not constitute a booking guarantee.

The canonical domain must not infer booking certainty solely from allotment.

---

# 23. Payment Option

## 23.1 Structure

    PaymentOption

        timing: PaymentTiming

---

## 23.2 Canonical Payment Timing

The canonical payment timing vocabulary is:

    AT_BOOKING
    AT_PROPERTY

Additional payment states require a separate architectural decision.

Supplier-specific payment codes must be translated by the provider adapter.

---

## 23.3 Optionality

Payment may be `null` if the supplier does not provide meaningful payment information.

---

# 24. Packaging

## 24.1 Structure

    PackagingOption

        packaged: boolean

---

## 24.2 Semantics

`packaged = true` means the rate is subject to supplier/package pricing semantics.

The boolean is intentionally limited to the canonical business meaning.

Supplier-specific package metadata is not exposed.

If future package components need to be represented, that is a separate capability/contract decision.

---

# 25. Cancellation Policy

## 25.1 Structure

    CancellationPolicy

        effectiveFrom: ZonedDateTime

        penalty: Money | null

        refundable: boolean

---

## 25.2 Ordering

Policies are ordered chronologically by `effectiveFrom`.

---

## 25.3 Penalty

A penalty is represented using canonical Money.

A raw numeric supplier amount is not permitted in the canonical model.

---

## 25.4 Non-Refundable

A non-refundable rate is represented explicitly through:

    refundable: false

The absence of policies must not automatically imply non-refundable.

---

# 26. Taxes and Fees

## 26.1 Structure

    TaxOrFee

        type: TaxOrFeeType

        subtype: string | null

        amount: Money | null

        percentage: number | null

        included: boolean

---

## 26.2 Type

Minimum canonical values:

    TAX
    FEE

Supplier-specific types are translated by the provider adapter.

---

## 26.3 Amount and Percentage

A supplier may provide:

- monetary amount;
- percentage;
- both;
- neither.

The adapter must preserve meaningful supplier information without inventing unavailable values.

---

## 26.4 Inclusion

`included` indicates whether the charge is already included in the associated rate price.

The canonical model must preserve enough information to prevent consumers from double-counting included taxes or fees.

---

## 26.5 Supplier Aggregate Tax Flags

Supplier aggregate fields such as:

    allIncluded

are adapter-level concepts.

They must be translated into individual canonical tax/fee inclusion semantics.

---

# 27. Requested vs Offered Occupancy

The positive Availability result contains:

    requestedOccupancy

The selected `RateOption` contains:

    occupancy

These are intentionally different contracts.

### Requested Occupancy

What the client asked for.

### Offered Occupancy

What the returned rate applies to.

Consumers must not silently replace one with the other.

---

# 28. Booking Selection Snapshot

## 28.1 Purpose

A selected availability option must retain enough information to continue into booking.

The minimum selection identity is:

    accommodation
    room reference
    rate booking reference
    provider

The selected rate's `SupplierReference` is authoritative for supplier-offer identity.

---

## 28.2 Snapshot Rule

The booking process must retain the selected commercial conditions needed by the booking workflow.

At minimum:

- provider;
- accommodation identity;
- selected room reference;
- selected rate booking reference;
- occupancy;
- pricing;
- board;
- payment;
- packaging;
- cancellation policies;
- taxes.

The snapshot is not a replacement for provider revalidation.

---

## 28.3 Recheck

If:

    status = RECHECK_REQUIRED

the booking workflow must revalidate the offer before committing to booking.

Provider-specific recheck behavior remains outside the canonical model.

---

# 29. Accommodation Rate Separation

The existing:

    AccommodationRate

remains a separate contract.

It must not be aliased to:

    RateOption

The two models may share canonical value objects where semantics are identical.

No implementation may add Availability fields to `AccommodationRate` merely to avoid introducing `RateOption`.

---

# 30. Accommodation Rate Result Separation

The existing:

    AccommodationRateResult

remains a separate application contract.

It must not be embedded inside:

    AccommodationAvailabilityResult

It may reuse:

- Money;
- BoardOption;
- occupancy value objects;
- SupplierReference;

only where semantics are genuinely identical.

---

- AccommodationAvailabilityRequest;

- OccupancyRoom;
- AccommodationAvailabilitySearchResult;
- AccommodationAvailabilityResult;
- AccommodationAvailabilitySuccess;
- AccommodationAvailabilityNoAvailability;

# 32. R5 Mapping Contract

R5 maps a provider response into the canonical search-level result:

    Hotelbeds response
        ↓
    Hotelbeds adapter
        ↓
    AccommodationAvailabilitySearchResult

The provider adapter must be capable of returning multiple accommodation results.

Conceptually:

    mapAvailabilityResponse(response)
        → AccommodationAvailabilitySearchResult

It must not return a single accommodation result when the provider returns multiple accommodations.

---

# 33. R5 Hotelbeds Mapping

For the verified Hotelbeds response:

    response.hotels.hotels[]

maps to:

    AccommodationAvailabilitySearchResult.results[]

Each Hotelbeds hotel maps to one:

    AccommodationAvailabilitySuccess

Its:

    rooms[]

map to:

    availabilityOptions.roomOptions[]

Its:

    rates[]

map to:

    roomOption.rateOptions[]

The adapter must preserve room/rate relationships.

---

# 34. Hotelbeds Field Isolation

The following are adapter-level concepts:

- `rateKey`;
- `rateType`;
- `rateClass`;
- Hotelbeds `hotels.hotels`;
- Hotelbeds `rooms`;
- Hotelbeds `rates`;
- Hotelbeds tax envelope;
- Hotelbeds cancellation structure;
- Hotelbeds payment codes.

They must never appear as canonical property names.

---

# 35. R7 Orchestration Contract

R7 receives the provider's canonical search result.

R7 is responsible for:

- orchestration;
- result aggregation;
- application-level metadata;
- no-result handling;
- preserving result ordering;
- returning the canonical Availability result.

R7 must not reinterpret Hotelbeds response fields.

---

# 36. R7 Collection Semantics

R7 must support:

    zero results;
    one result;
    multiple results.

It must not assume one accommodation.

If the provider returns multiple accommodations, R7 preserves them.

If the provider returns a valid no-availability outcome, R7 preserves the canonical `NO_AVAILABILITY` state according to the final application-level result contract.

---

# 37. R2 Boundary

R2 remains responsible for:

- candidate resolution;
- configured candidate selection;
- candidate validation.

R2 must not construct:

- RoomOption;
- RateOption;
- pricing;
- cancellation;
- taxes;
- booking references.

---

# 38. R3 Boundary

R3 translates:

    AccommodationAvailabilityRequest

into the supplier-specific Availability request.

R3 must consume the canonical multi-room occupancy structure.

R3 must not redefine:

- canonical occupancy;
- canonical room options;
- canonical rate options;
- pricing semantics.

Supplier-specific request structures remain adapter concerns.

---

# 39. R4-C1 Boundary

R4-C1 remains responsible for:

- HTTP;
- TLS;
- mTLS;
- authentication transport;
- response delivery.

It must not map supplier availability structures.

---

# 40. R6 Boundary

R6 remains responsible for:

- execution protection;
- retry policy;
- controlled failure behavior.

It must not reinterpret supplier room/rate semantics.

---

# 41. R8 Boundary

R8 is verification only.

The controlled live verification must eventually demonstrate:

- multi-room request construction;
- correct supplier request;
- successful transport;
- positive Hotelbeds response mapping;
- multiple room options;
- multiple rates;
- canonical pricing;
- occupancy;
- cancellation;
- taxes;
- booking references;
- canonical result preservation.

A zero-availability live test alone is insufficient for final R8 acceptance of the positive Availability path.

# 43. Consumer Migration

Consumers must migrate to the discriminated result.

Positive result consumers narrow:

    kind === "ACCOMMODATION"

before accessing:

- accommodation;
- requested occupancy;
- availability options.

No-availability consumers narrow:

    kind === "NO_AVAILABILITY"

before processing absence.

---

# 44. Inventory

Inventory freezing/cloning must preserve the complete canonical positive result.

It must not reduce the result back to:

    accommodation
    +
    available

The following must survive freezing/cloning:

- requested occupancy;
- room options;
- rate options;
- pricing;
- occupancy;
- board;
- payment;
- packaging;
- cancellation;
- taxes;
- supplier references;
- metadata.

---

# 45. Journey Composition

Journey composition must consume the canonical Availability contract.

It must not reconstruct room/rate information from supplier-specific structures.

If a journey/package requires a room or rate selection, it must use the canonical option graph.

---

# 46. Merchandising

Merchandising may project the canonical Availability model into client-facing representations.

It may select or summarize:

- lowest rate;
- room names;
- board;
- cancellation summary;
- taxes;
- payment conditions.

It must not redefine canonical Availability semantics.

---

# 47. Client Package Search

The eventual client package-search flow must support:

    Search
        rooms[]
            adults
            children
            childAges[]

The returned Availability result must expose enough information for the client to select:

    accommodation
        room
            rate

without receiving Hotelbeds-specific objects.

---

# 48. Supplier Isolation at Client Boundary

The client must never receive:

- Hotelbeds `rateKey` as a named canonical field;
- Hotelbeds response envelopes;
- Hotelbeds internal rate classes;
- supplier-specific response metadata unless explicitly mapped into an approved canonical concept.

The client may receive an opaque booking reference represented by the canonical `SupplierReference`.

---

# 49. Canonical Validation

The canonical constructors/factories must validate:

### Request

- valid stay period;
- at least one room;
- valid adults;
- child count matches child ages;
- valid child ages.

### Positive Result

- accommodation exists;
- requested occupancy exists;
- availability options exist;
- room references are valid;
- rate booking references are valid;
- pricing contains valid Money;
- pricing basis is defined;
- offered occupancy is valid.

### No Availability

- accommodation absent;
- options absent;
- pricing absent;
- booking references absent;
- `available === false`.

Invalid canonical objects must not be constructed.

---

# 50. Immutability

Canonical Availability structures are immutable.

Collections must be protected against external mutation.

This includes:

- result collections;
- room collections;
- rate collections;
- occupancy collections;
- cancellation policies;
- taxes/fees.

Existing project immutability conventions must be followed.

---

# 51. Ordering

The following ordering must be preserved:

1. accommodation result order;
2. room option order;
3. rate option order;
4. occupancy room order;
5. cancellation policy chronological order.

The provider adapter must not introduce arbitrary sorting.

Application-level sorting is a separate presentation concern.

---

# 52. Error Semantics

The following states remain distinct:

### Valid Availability

Canonical `ACCOMMODATION`.

### Valid No Availability

Canonical `NO_AVAILABILITY`.

### Supplier Error

Provider/application error.

### Transport Failure

R4-C1 transport failure.

### Malformed Supplier Response

R5 mapping failure.

### Invalid Canonical Result

Programming/contract validation failure.

No error state may be converted into `NO_AVAILABILITY` merely because it contains no hotel entries.

---

# 53. Legacy Unavailable Sentinel

The existing `"unavailable"` accommodation sentinel may remain temporarily for legacy R2/R3 no-candidate/no-request paths.

It must not be used for supplier-confirmed `NO_AVAILABILITY`.

It is not part of the new positive Availability architecture.

Its future removal is a separate migration.

---

# 54. No Hotelbeds-Shaped Canonical Model

The following pattern is explicitly prohibited:

    HotelbedsAvailabilityResponse
        hotels
            hotels[]
                rooms[]
                    rates[]

being reused as the canonical application model.

The provider adapter may use this structure internally.

The canonical result must remain:

    AccommodationAvailabilitySearchResult
        results[]
            AccommodationAvailabilityResult
                accommodation
                availabilityOptions
                    roomOptions[]
                        rateOptions[]

---

# 55. Implementation Sequence

Implementation must proceed as one coherent canonical migration.

The required sequence is:

1. Implement/finalize shared canonical value objects required by this specification.
2. Implement canonical Availability request types.
3. Implement canonical Availability result types.
4. Implement room/rate option structures.
5. Implement supplier references.
6. Implement pricing, payment, packaging, cancellation, and tax structures.
7. Update R5 mapping interfaces.
8. Update R7 orchestration.
9. Update inventory and downstream consumers.
10. Update serialization.
11. Update all affected tests.
12. Remove obsolete single-result and hotel-only assumptions.
13. Run full regression.
14. Only then implement the complete Hotelbeds R5-C2 positive-response mapping.
15. Execute controlled R8 positive Availability verification.

No step may introduce a temporary supplier-specific substitute for a canonical structure.

---

# 56. Prohibited Implementation Patterns

The following are explicitly prohibited:

- adding Hotelbeds fields to canonical models;
- adding `rateKey` to canonical `RateOption`;
- adding `hotels.hotel` to canonical models;
- embedding Hotelbeds DTOs in Availability results;
- adding compatibility aliases between old and new fields;
- storing room/rate data in untyped metadata;
- storing rate information in arbitrary JSON;
- flattening rooms and rates into a single collection;
- discarding rate references;
- fabricating accommodation for no availability;
- treating supplier errors as no availability;
- creating a second Availability Money model;
- extending `AccommodationRate` merely to avoid `RateOption`;
- forcing all rooms to have identical occupancy;
- assuming one room in the canonical contract;
- implementing R5 directly against Hotelbeds and retrofitting the canonical model later.

---
