# 1. Purpose

Implement the GCT Core accommodation booking capability that converts a validated accommodation selection into a confirmed supplier accommodation booking.

The capability SHALL support the established GCT flow:

Package Stop
→ Accommodation
→ Room
→ Rate
→ Selection
→ Revalidation where required
→ Booking
→ Reservation

Hotelbeds SHALL remain an adapter implementation.

The canonical GCT booking contract MUST NOT reproduce the Hotelbeds Booking API model.

---

# 2. Business Context

Go Cape Tours sells private multi-day packages.

A package may contain multiple accommodation stops. At each stop GCT selects the eligible properties and the client selects:

- accommodation;
- room type;
- rate;
- occupancy.

The accommodation supplier provides the accommodation component of the package.

GCT owns the commercial package price through APP-005.

The supplier booking confirms only the accommodation component.

APP-008.5 therefore creates or updates the accommodation reservation required by the GCT reservation architecture.

---

# 3. Architectural Boundary

The canonical flow SHALL be:

Client Selection
→ Validated Accommodation Offer
→ Accommodation Booking
→ Reservation

For a BOOKABLE rate:

Availability
→ Selection
→ Booking

For a RECHECK rate:

Availability
→ Selection
→ APP-008.4 Revalidation
→ Validated Selection
→ Booking

APP-008.5 MUST NOT repeat Availability as a substitute for CheckRate.

The application flow SHALL remain:

Application
→ Accommodation Provider
→ Supplier Adapter
→ Hotelbeds Booking API

Hotelbeds DTOs MUST remain inside the Hotelbeds adapter.

# 5. Canonical Booking Request

The application-facing booking request SHALL be supplier-neutral.

It MUST contain sufficient information to identify the selected accommodation offer and the guests who will occupy it.

The request SHALL support:

- accommodation identity;
- selected room;
- selected rate;
- supplier/provider context;
- opaque supplier offer reference;
- stay dates;
- occupancy;
- guests/paxes;
- booking holder;
- package-stop context where available.

The request MUST NOT contain Hotelbeds-specific request DTOs.

---

# 6. Selected Offer

The selected accommodation offer MUST preserve:

Accommodation
→ Room
→ Rate

The booking request MUST NOT be reduced to:

- accommodation ID only;
- rate ID only;
- supplier reference only.

The selected room and rate relationship is required for booking continuity.

The selected rate MUST originate from the canonical Availability result or the validated result returned by APP-008.4.

---

# 7. Revalidation Requirement

Before booking:

- `BOOKABLE` offers MAY proceed directly to booking;
- `RECHECK` offers MUST have completed APP-008.4 revalidation.

The booking service SHALL NOT itself implement a second CheckRate implementation.

If a caller attempts to book a `RECHECK` offer without a valid revalidation result, the booking request SHALL be rejected.

The supplier adapter MUST receive the current validated supplier reference.

---

# 8. Supplier Reference

Supplier references remain opaque.

The canonical application layer SHALL use:

- provider;
- opaque supplier reference.

For Hotelbeds, the adapter SHALL translate the opaque reference into the Hotelbeds rate reference required by its Booking API.

The canonical model MUST NOT expose:

- `rateKey`;
- Hotelbeds booking fields;
- Hotelbeds-specific reference structures.

The supplier booking confirmation reference returned by Hotelbeds SHALL be mapped separately from the availability/revalidation offer reference.

---

# 9. Booking Holder

The booking request SHALL contain a canonical booking holder.

At minimum the holder requires the information required by the existing reservation architecture and supplier booking contract, including:

- first name;
- last name;
- contact email;
- contact phone where required.

The Hotelbeds adapter SHALL translate the canonical holder into the supplier-specific holder representation.

Do not duplicate Hotelbeds holder DTOs in the canonical model.

---

# 10. Guests / Paxes

The booking request SHALL preserve the occupancy required by the selected offer.

For each occupant, preserve where required:

- room association;
- adult/child classification;
- first name;
- last name;
- age/date information required by the canonical reservation model;
- child age where applicable.

The implementation MUST support multiple rooms.

Guests MUST remain associated with the correct room occupancy group.

Do not collapse all guests into one global occupancy structure if the existing APP-004 contract supports room-specific association.

---

# 11. Occupancy Integrity

Booking occupancy MUST correspond to the selected and validated offer.

The implementation SHALL validate:

- requested room count;
- guests per room;
- adults per room;
- children per room;
- child ages;
- selected rate occupancy where applicable.

The booking adapter MUST NOT silently change occupancy.

If the supplier requires a different representation, the Hotelbeds adapter performs the translation.

---

# 12. Stay Dates

Booking SHALL use the selected stay:

- check-in;
- check-out.

The dates MUST correspond to the validated offer.

The booking operation MUST NOT retrieve new availability merely to reconstruct stay information.

Date validation SHALL use existing canonical date/value-object conventions.

---

# 13. Package Stop Association

Where booking is performed as part of a package stop, the reservation SHALL preserve the package-stop association already established by the application architecture.

Conceptually:

Package
→ Stop
→ Accommodation Reservation

The accommodation booking itself remains an accommodation reservation.

APP-008.5 does not implement complete multi-stop package booking orchestration.

---

# 14. Pricing Boundary

The supplier booking price SHALL be captured as the supplier accommodation booking value.

APP-008.5 MUST NOT calculate:

- GCT package price;
- GCT markup;
- sliding-scale package price;
- customer package total.

APP-005 remains the owner of GCT commercial pricing.

The booking reservation SHALL preserve the supplier price required by APP-004 and the existing pricing architecture.

If the supplier returns a booking amount different from the validated amount, the difference MUST be represented according to the existing reservation/pricing contract.

Do not silently replace GCT package pricing.

---

# 15. Booking Price Change

If the supplier returns a different booking amount from the validated offer:

- preserve the actual supplier booking amount;
- classify the booking result according to the existing reservation/booking outcome model;
- do not silently alter the GCT package price.

If the existing APP-004 architecture requires explicit commercial approval before confirming a changed supplier price, use that existing contract.

Do not invent a new pricing workflow in APP-008.5.

---

# 16. Hotelbeds Booking Adapter

The Hotelbeds provider SHALL implement the canonical booking operation.

The adapter is responsible for translating:

- accommodation;
- room;
- rate;
- supplier reference;
- holder;
- guests/paxes;
- occupancy;
- stay dates;
- required booking metadata

into the Hotelbeds Booking API request.

Hotelbeds-specific DTOs remain adapter-only.

---

# 17. Hotelbeds Transport

Reuse the existing Hotelbeds transport infrastructure established by previous iterations:

- API credentials;
- signature generation;
- mTLS;
- HTTP client/gateway;
- timeout handling;
- GZIP handling where applicable;
- supplier error mapping;
- bounded retry/protection.

Do not duplicate transport/authentication implementations.

Do not modify established transport behaviour unless a booking-specific defect requires it.

---

# 18. Booking Result

The canonical booking result SHALL distinguish successful confirmation from failure.

A successful result MUST preserve:

- GCT reservation/booking identity;
- supplier/provider identity;
- supplier booking confirmation/reference;
- booked accommodation;
- booked room;
- booked rate;
- occupancy;
- stay dates;
- supplier booking price;
- booking status;
- applicable supplier booking conditions.

The result MUST contain enough information for APP-004 to manage the reservation lifecycle.

---

# 19. Supplier Booking Reference

The supplier booking confirmation reference returned by Hotelbeds SHALL be stored through the existing APP-004 reservation/supplier-reference architecture.

Do not confuse:

Availability Offer Reference
with
Supplier Booking Confirmation Reference

The first identifies the selected offer.

The second identifies the confirmed supplier booking.

Both may be associated with the reservation where the existing APP-004 model supports this distinction.

---

# 20. Reservation Integration

APP-004 remains the owner of:

- reservation identity;
- reservation lifecycle;
- immutable booking snapshot;
- supplier booking reference;
- reservation status;
- downstream reservation operations.

APP-008.5 SHALL integrate with APP-004 rather than create a parallel reservation model.

If an existing APP-004 repository/service is available for booking creation, reuse it.

Do not introduce a second reservation persistence mechanism.

---

# 21. Booking Snapshot

The confirmed accommodation reservation SHALL preserve the information necessary to reproduce the commercial and supplier booking context.

At minimum the snapshot SHALL preserve, through the existing APP-004 model:

- accommodation;
- room;
- rate;
- supplier/provider;
- supplier references;
- stay dates;
- occupancy;
- guests/holder as required;
- confirmed supplier price;
- relevant booking conditions.

The snapshot MUST NOT depend on the availability response remaining available later.

---

# 22. Idempotency / Duplicate Protection

Booking is a state-changing operation.

The implementation MUST use the existing idempotency or duplicate-protection mechanism defined by APP-004 and the canonical integration architecture.

If no suitable mechanism exists, Copilot SHALL use the existing repository architecture to prevent accidental duplicate supplier booking requests where possible and report any genuine architectural limitation.

Do not create a new persistence architecture solely for APP-008.5.

A retry MUST NOT blindly issue a second booking request when the first request may have succeeded.

---

# 23. Failure Semantics

The implementation SHALL distinguish at least:

### Validation Failure

The canonical booking request is invalid.

No supplier call is made.

### Offer Invalid

The selected offer is no longer valid or the required revalidation is missing.

No booking call is made.

### Supplier Rejection

Hotelbeds rejects the booking as a business operation.

Map to the existing canonical booking failure model.

### Transport Failure

The supplier call cannot be completed.

Map to the existing infrastructure/booking failure model.

Do not automatically classify transport failure as booking failure if the supplier may have processed the request.

### Unknown Booking Outcome

Where the request may have reached the supplier but the client cannot establish whether the booking succeeded, the result MUST be distinguishable from a confirmed failure.

Do not automatically retry an unknown booking outcome.

---

# 24. Retry Safety

Booking retries MUST be strictly controlled.

The implementation MUST NOT use the unrestricted Availability retry behaviour for Booking.

A booking request may create an external commercial transaction.

Any retry MUST use the established idempotency/duplicate-protection architecture.

If supplier semantics prevent safe automatic retry, return the appropriate unknown/outcome state instead.

---

# 25. Booking Status

Use the existing canonical reservation/booking status model where available.

At minimum the implementation must distinguish:

- confirmed;
- failed;
- pending/unknown where required by the existing reservation architecture.

Do not introduce a parallel booking-status enum if APP-004 already defines the required concept.

---

# 26. Multiple Suppliers

The canonical booking service SHALL remain supplier-neutral.

The flow is:

Canonical Booking Request
→ Provider Selection
→ Supplier Adapter
→ Supplier Booking

Hotelbeds is the first implementation.

A future supplier MUST be able to implement the same provider booking contract without changing the canonical booking request or APP-004 reservation model.

---

# 27. No Hotelbeds Canonical Model

The following MUST remain Hotelbeds-specific:

- Hotelbeds request DTO;
- Hotelbeds response DTO;
- Hotelbeds rateKey interpretation;
- Hotelbeds booking fields;
- Hotelbeds pax representation;
- Hotelbeds error payloads.

The canonical model SHALL contain business concepts only.

---

# 28. Persistence

Booking differs from Availability and CheckRate because a successful booking is a persistent business transaction.

APP-008.5 SHALL use the existing APP-004 reservation persistence architecture.

Do not create new Prisma entities unless the existing APP-004 contract explicitly requires a missing booking persistence field.

If an existing APP-004 persistence model cannot store information required by this specification, stop at that concrete conflict and report it rather than introducing an unrelated schema redesign.

---

# 29. Security

Booking operations contain personal and commercially sensitive information.

The implementation MUST NOT log:

- credentials;
- private keys;
- API signatures;
- full guest personal data;
- payment credentials;
- supplier secrets.

Logs MAY contain safe operational identifiers such as:

- internal reservation ID;
- provider;
- supplier booking reference where the existing security policy permits it;
- booking outcome.

Follow the existing security and logging standards.

# 37. Final Architectural Statement

APP-008.5 establishes the accommodation Booking boundary:

Availability
→ Selection
→ Revalidation where required
→ Booking
→ APP-004 Reservation

The canonical booking contract belongs to GCT Core.

Hotelbeds is an adapter implementation and MUST NOT become the canonical booking model.

APP-005 remains responsible for GCT package pricing.

APP-004 remains responsible for reservation identity, persistence, immutable booking snapshots and reservation lifecycle.

APP-008.5 establishes accommodation booking only. Cancellation, modification and other post-booking operations are subsequent capabilities.
