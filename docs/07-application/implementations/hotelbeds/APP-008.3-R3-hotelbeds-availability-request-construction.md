2. Purpose

Implement the deterministic construction of Hotelbeds Availability requests from the canonical accommodation search criteria and the R2 catalogue candidate set.

R3 establishes the request-building boundary:

AccommodationSearchCriteria
        +
R2 resolved catalogue candidates
        ↓
Hotelbeds Availability Request Builder
        ↓
Hotelbeds Availability request DTO(s)
        ↓
R4 transport

R3 MUST construct requests only.

It MUST NOT execute an HTTP request.

3. Governing Iteration Principle

R3 is intentionally limited to request construction.

Do not implement:

HTTP transport;

mTLS;

GZIP response handling;

retries;

QPS pacing;

timeout execution;

response mapping;

rate mapping;

provider execution;

persistence.

Those belong to later iterations.

The objective is to produce a complete, deterministic, supplier-compatible request representation that R4 can execute without changing its shape.

The builder MUST be deterministic and side-effect free.

6. Inputs

R3 consumes two logical inputs:

6.1 Search criteria

The existing AccommodationSearchCriteria established through R1.

Required Availability information:

check-in;

check-out;

source market;

occupancy groups.

Legacy scalar occupancy fields MUST NOT override the canonical occupancy groups when the R1 criteria contains explicit occupancy groups.

Do not remove the existing compatibility fields.

6.2 Resolved catalogue candidates

R2 provides the eligible hotel candidates.

Only candidates returned by the R2 catalogue boundary may be passed to the request builder.

Raw explicit hotel codes MUST NOT be accepted as a bypass around R2.

7. Hotelbeds Request Shape

R3 MUST model the Hotelbeds Availability request corresponding to:

POST /hotel-api/1.0/hotels

The request construction model MUST represent the fields required to express:

stay dates;

source market;

hotel codes;

rooms/occupancy.

The builder MUST use the exact Hotelbeds field names and nesting required by the existing integration contract.

Do not introduce fields that are not required by the Availability request contract.

Do not model response-only fields in the request DTO.

8. Date Mapping

Map:

checkIn
checkOut

to the Hotelbeds Availability request date fields.

Dates MUST preserve the canonical application date values.

The builder MUST NOT:

shift dates because of timezone conversion;

convert dates into timestamps;

infer missing dates;

silently substitute default dates.

R1 date validation remains authoritative.

If invalid date criteria reach the builder, the builder MUST fail deterministically rather than constructing an invalid supplier request.

9. Source Market

Map the canonical:

sourceMarket

to the Hotelbeds Availability request.

The value MUST be preserved exactly after R1 validation.

Do not:

infer source market from destination;

substitute a default country;

normalize it differently in R3;

read it from environment configuration.

10. Occupancy Mapping

R1 introduced the canonical occupancy-group model.

Each occupancy group represents one requested room.

For each room:

rooms = occupancyGroups.length

Each Hotelbeds room request MUST preserve:

adult count;

child count;

child ages.

Conceptually:

AccommodationOccupancyGroup
        ↓
Hotelbeds room

Example:

Room 1
Adults: 2
Children: 1
Child age: 7

Room 2
Adults: 1
Children: 2
Child ages: 4, 11

MUST produce two Hotelbeds room entries with the corresponding occupancy values.

11. Child Ages

Child ages are part of the canonical occupancy contract and MUST be mapped exactly.

Rules:

number of child ages MUST equal child count;

each age MUST remain associated with the same room;

age ordering MUST be deterministic;

no age may be dropped;

no age may be duplicated;

no age may be invented;

no age normalization beyond existing R1 validation is permitted.

R3 MUST NOT convert child ages into a different age representation.

12. Occupancy Compatibility

The R1 compatibility fields:

adults
children
rooms

remain supported for existing callers.

However, when canonical occupancy groups are present, the request builder MUST use:

occupancies

as the authoritative occupancy representation.

Do not construct contradictory requests by combining scalar and grouped occupancy values.

Do not change the R1 compatibility behaviour outside the R3 request-building boundary.

13. Hotel Code Mapping

Each R2 resolved candidate MUST contribute its canonical hotel code to the Hotelbeds request.

The builder MUST NOT:

revalidate raw caller-supplied codes independently of R2;

add unknown codes;

add inactive codes;

add duplicates;

add hotels that were not returned by R2.

The candidate list is authoritative.

Example:

R2 candidates:
1001
1002
1007

R3 request:
hotels.codes = [1001, 1002, 1007]

No other codes may be introduced.

14. Hotel Code Deduplication

R2 already guarantees deterministic candidate uniqueness.

R3 MUST preserve that uniqueness.

As a defensive construction rule, the builder MAY assert uniqueness before constructing the request.

It MUST NOT silently create duplicate supplier hotel codes.

If duplicate candidates are detected despite the R2 contract, fail deterministically rather than sending an invalid or redundant request.

15. Maximum Request Size

Hotelbeds Availability requests MUST contain no more than:

2,000 hotel codes

per request.

This is a request-construction constraint.

R3 MUST implement deterministic batching when the R2 candidate set exceeds 2,000 hotels.

Example:

4,500 candidates
        ↓
Request 1: 2,000
Request 2: 2,000
Request 3:   500

No hotel may be lost or duplicated across batches.

16. Deterministic Batching

Batching MUST preserve candidate order.

Given:

[1001, 1002, 1003, ...]

the resulting batches MUST contain contiguous segments of that sequence.

For example:

Batch 1:
[1001 ... 3000]

Batch 2:
[3001 ... 5000]

Do not sort candidates during batching.

Do not randomize.

Do not deduplicate across batches in a way that changes R2 ordering.

17. Empty Candidate Set

An empty R2 candidate set is a valid result.

If:

candidates.length = 0

R3 MUST return:

[]

No empty Hotelbeds request may be constructed.

This ensures:

0 candidates
    ↓
0 supplier requests

R3 MUST NOT invoke any supplier transport.

18. Request Builder Result

The builder should return an ordered collection:

HotelbedsAvailabilityRequest[]

rather than a single request, because batching is part of R3 construction.

For:

0 candidates

return:

[]

For:

1–2,000 candidates

return:

[one request]

For:

>2,000 candidates

return:

[multiple deterministic requests]

19. Request Immutability

The request builder MUST NOT mutate:

the original search criteria;

the R2 candidate collection;

occupancy groups;

child-age arrays.

Construct new request objects.

Tests SHOULD verify that source inputs remain unchanged where practical.

20. Validation

R3 MUST reuse existing R1/R2 validation mechanisms wherever possible.

The builder MUST reject construction when required inputs are structurally invalid.

At minimum, construction MUST reject:

missing search criteria;

invalid check-in/check-out range;

blank source market;

invalid occupancy groups;

mismatched child counts/ages;

invalid candidate hotel codes;

duplicate candidate codes if the R2 invariant has been violated.

Do not create a second general-purpose accommodation validation framework.

21. Supplier-Specific Validation

Supplier-specific request constraints may be enforced at the request-builder boundary where they are necessary to produce a valid Hotelbeds request.

However:

do not duplicate R1 validation unnecessarily;

do not introduce transport concerns;

do not validate response fields;

do not call Hotelbeds to validate a request.

All validation must be local and deterministic.

22. Error Handling

Request-construction failures MUST be deterministic and descriptive.

Use the existing application/integration error conventions where available.

Do not silently:

drop invalid rooms;

drop invalid children;

drop invalid candidates;

substitute defaults;

truncate hotel codes;

truncate occupancy;

create partial requests.

If a request cannot be constructed correctly, fail rather than producing an ambiguous supplier request.

23. No Transport

imports Node HTTP/HTTPS transport for execution;

calls fetch;

creates an HTTP agent;

opens sockets;

loads certificates;

sends requests;

parses HTTP responses.

The output of R3 is a data structure only.
