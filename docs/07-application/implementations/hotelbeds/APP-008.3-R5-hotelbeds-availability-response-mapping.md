## 2. Purpose

APP-008.3-R5 consumes the structured raw Hotelbeds Availability execution results produced by R4 and maps them into the **existing accepted canonical Accommodation Availability result contract**.

The R5 flow is:

R3 Availability Request  
→ R4 Hotelbeds Transport & Execution  
→ Structured Raw Hotelbeds Response  
→ R5 Canonical Result Mapping  
→ Existing Canonical Accommodation Availability Result

The existing canonical Availability contract is authoritative.

R5 MUST NOT expand or redesign that contract.

---

## 3. Architectural Baseline

The accepted APP-008.3 sequence is:

R1 — Availability Foundation  
→ R2 — Catalogue Candidate Resolution  
→ R3 — Availability Request Construction  
→ R4 — Availability Transport & Execution  
→ R5 — Availability Canonical Result Mapping

R1-R4 are accepted contracts.

R5 SHALL consume the structured raw response produced by R4.

The current canonical Availability result is the authoritative output contract.

R5 MUST NOT introduce a richer room/rate inventory model.

---

## 4. Existing Canonical Contract

The accepted canonical Accommodation Availability result currently consists of:

- `accommodation`;
- `available`;
- `metadata`.

The existing application contract explicitly does not introduce room/rate pricing structures at this stage.

R5 SHALL map Hotelbeds Availability into this existing contract only.

R5 MUST NOT add canonical fields for:

- rooms;
- rates;
- rate pricing;
- rate currency;
- `rateKey`;
- BOOKABLE rate state;
- RECHECK rate state;
- cancellation policy;
- rate comments.

These belong to a future canonical Availability model expansion and are outside R5.

## 6. R4 Contract

R4 is the authoritative Hotelbeds supplier execution boundary.

R5 SHALL consume the R4 Availability-specific structured raw result containing, where available:

- deterministic request/batch index;
- HTTP status;
- relevant response headers;
- decompressed response body;
- supplier error payload;
- transport failure information.

R5 MUST NOT perform:

- HTTP decompression;
- authentication;
- TLS handling;
- retry execution;
- HTTP requests.

The R4 response body is already the logical decompressed Hotelbeds response.

---

## 7. Canonical Mapping Boundary

R5 SHALL introduce the smallest appropriate response-mapping boundary.

The boundary SHALL be conceptually equivalent to:

`mapAvailabilityResponse(rawResponses)`

It SHALL receive the R4 structured execution results and produce the existing canonical Accommodation Availability result.

The mapper MUST:

1. inspect valid Hotelbeds Availability responses;
2. identify the relevant supplier hotel result;
3. associate the supplier hotel with the established canonical accommodation identity;
4. determine whether Availability exists;
5. populate the existing canonical `available` value;
6. populate only metadata supported by the existing canonical contract;
7. aggregate multiple R4 batch results deterministically.

The mapper MUST NOT:

- create new canonical domain structures;
- create room/rate models;
- perform HTTP requests;
- retry requests;
- access Prisma;
- modify catalogue records;
- construct new Hotelbeds requests.

---

## 8. Hotel Identity Mapping

For each relevant Hotelbeds hotel result, R5 SHALL map the supplier hotel identifier to the established canonical accommodation identity.

The mapping MUST use existing GCT Core catalogue/application mechanisms where such a mapping already exists.

R5 MUST NOT:

- create new accommodation records;
- modify accommodation records;
- perform catalogue synchronisation;
- invent a new hotel-resolution mechanism.

If the existing canonical/application contract already provides the necessary accommodation identity through the R3/R4 request context, R5 SHALL use that established identity.

If a supplier hotel cannot be associated with an existing canonical accommodation identity, R5 SHALL follow the existing canonical handling for an unknown/unmapped supplier entity.

R5 MUST NOT create a new catalogue entity to resolve the condition.

---

## 9. Availability Determination

R5 SHALL determine the canonical `available` value from the successful Hotelbeds response.

A successful response containing qualifying supplier Availability SHALL map to:

`available = true`

A successful response containing no qualifying Availability SHALL map to:

`available = false`

The exact qualifying condition SHALL follow the existing Hotelbeds Availability response structure and the established application semantics.

R5 MUST NOT infer Availability from:

- transport success alone;
- HTTP success alone;
- presence of an arbitrary response object.

There must be a valid supplier Availability result.

---

## 10. Room and Rate Data

R5 SHALL inspect the Hotelbeds response sufficiently to determine whether qualifying Availability exists.

R5 MUST NOT map room or rate structures into the canonical result.

Supplier room and rate data MAY be used internally to determine whether a qualifying Availability result exists, but MUST NOT be exposed through the canonical R5 result.

R5 MUST NOT create canonical structures for:

- room;
- rate;
- price;
- currency;
- `rateKey`;
- BOOKABLE;
- RECHECK;
- cancellation policy.

The future richer canonical Availability model remains outside R5.

---

## 11. Metadata

R5 SHALL populate `metadata` only with information for which an existing canonical metadata contract already provides an explicit destination.

R5 MUST NOT invent metadata fields solely to retain Hotelbeds supplier information.

Supplier fields without an established canonical destination SHALL remain outside the canonical result.

In particular, R5 MUST NOT add metadata solely for:

- `rateKey`;
- rate pricing;
- currency;
- rate comments;
- cancellation policy;
- room structures.

---

## 12. Supplier Response Handling

R5 SHALL distinguish:

1. successful supplier response;
2. successful empty Availability response;
3. supplier error response;
4. HTTP failure;
5. transport failure;
6. malformed supplier response.

### 12.1 Successful Response

A valid successful Hotelbeds response SHALL be evaluated and mapped to the canonical Availability result.

### 12.2 Successful Empty Response

A valid successful response containing no qualifying Availability SHALL produce:

`available = false`

This MUST remain distinguishable from an execution failure.

### 12.3 Supplier Error

A supplier error SHALL remain distinguishable from a successful empty Availability result.

R5 MUST NOT silently convert a supplier error into:

`available = false`

unless the existing application contract explicitly defines that behaviour.

### 12.4 HTTP Failure

A non-success HTTP result SHALL remain an execution/integration failure.

R5 MUST NOT interpret an HTTP error as successful Availability.

### 12.5 Transport Failure

A transport failure received from R4 SHALL remain a transport/integration failure.

R5 MUST NOT attempt supplier-response parsing when no valid response body exists.

### 12.6 Malformed Response

A response that cannot be safely interpreted SHALL produce a controlled mapping/integration failure.

R5 MUST NOT silently convert malformed content into:

`available = false`

---

## 13. Multi-Batch Aggregation

R4 may return multiple execution results when R3 created multiple hotel-code batches.

R5 SHALL aggregate the results deterministically.

If any valid successful batch contains qualifying Availability for a canonical accommodation, the resulting canonical Availability SHALL reflect:

`available = true`

If all successfully evaluated batches contain no qualifying Availability, the result SHALL reflect:

`available = false`

Execution failures MUST NOT be silently converted into successful empty results.

The aggregation MUST preserve the distinction between:

- successful availability;
- successful no availability;
- execution failure.

R5 MUST NOT introduce speculative room/rate deduplication.

R5 MUST NOT modify R3 batch boundaries.

---

## 14. Request Context

R3 remains the authoritative source for Availability request context.

R5 MUST NOT reconstruct:

- check-in;
- check-out;
- source market;
- occupancy;
- child ages.

Where the existing R4 result/request context is available to R5, it SHALL be used.

The existing R3 restriction that Availability occupancy groups require `rooms == 1` remains unchanged.

R5 MUST NOT expand or reinterpret occupancy semantics.

---

## 15. Error Model

R5 SHALL distinguish mapping failures from supplier execution failures.

### Supplier Execution Failure

Already represented by R4 structured execution results.

### Supplier Response Error

A valid supplier error response remains an integration/supplier failure.

### Mapping Failure

A response that is returned but cannot be safely interpreted SHALL produce an appropriate Availability mapping/integration error.

The error SHOULD identify the affected request/batch where appropriate.

Errors MUST NOT expose:

- API keys;
- generated signatures;
- private keys;
- client certificate material;
- complete authenticated request headers.

---

## 16. Testing Requirements

Automated tests MUST NOT call the real Hotelbeds API.

R5 tests SHALL operate on controlled Hotelbeds response fixtures or mocked R4 structured results.

### 16.1 Successful Availability

Tests SHALL verify:

- valid Hotelbeds Availability response is accepted;
- canonical accommodation identity is populated;
- `available = true`;
- supported metadata is populated only where an existing destination exists.

### 16.2 No Availability

Tests SHALL verify:

- valid successful response containing no qualifying Availability;
- `available = false`;
- no error is produced.

### 16.3 Supplier Error

Tests SHALL verify:

- supplier error remains an error;
- supplier error is not converted to `available = false`.

### 16.4 HTTP Failure

Tests SHALL verify:

- HTTP failure remains an execution/integration failure;
- no successful Availability result is produced.

### 16.5 Transport Failure

Tests SHALL verify:

- transport failure remains distinguishable;
- no response parsing is attempted.

### 16.6 Malformed Response

Tests SHALL verify:

- malformed supplier response produces a controlled mapping failure;
- malformed content is not treated as successful empty Availability.

### 16.7 Multi-Batch Aggregation

Tests SHALL cover:

- multiple successful batches with Availability;
- multiple successful batches with no Availability;
- mixed batch results;
- deterministic aggregation;
- failure preservation.

### 16.8 Unknown Accommodation

Tests SHALL verify the existing handling when a supplier hotel cannot be associated with an established canonical accommodation.

R5 MUST NOT create a catalogue record.

### 16.9 Contract Protection

Tests MUST verify that the R5 canonical result remains limited to the accepted existing contract.

R5 tests MUST NOT introduce assertions requiring:

- rooms;
- rates;
- pricing;
- currency;
- `rateKey`;
- BOOKABLE;
- RECHECK;
- cancellation policy.

### 16.10 Regression

Existing Availability request construction, transport, provider and application-result tests MUST remain passing.

The full Jest regression suite MUST be executed.

## 20. Acceptance Criteria

### AC-01 — R4 Consumption

R5 consumes the structured Availability results produced by R4.

### AC-02 — Existing Canonical Contract

R5 returns the existing canonical Accommodation Availability result without expanding its structure.

### AC-03 — Accommodation Identity

The supplier hotel result is associated with the established canonical accommodation identity using existing application/catalogue mechanisms.

### AC-04 — Availability True

A valid qualifying Hotelbeds Availability response produces:

`available = true`

### AC-05 — Availability False

A valid successful Hotelbeds response containing no qualifying Availability produces:

`available = false`

### AC-06 — Error Integrity

Supplier errors, HTTP failures, transport failures and malformed responses remain distinguishable from successful empty Availability.

### AC-07 — Multi-Batch Aggregation

Multiple R4 batch results are aggregated deterministically.

### AC-08 — Metadata Protection

Only metadata supported by the existing canonical metadata contract is mapped.

### AC-09 — No Room/Rate Expansion

R5 does not add canonical room, rate, pricing, currency, `rateKey`, BOOKABLE, RECHECK or cancellation structures.

### AC-10 — No Persistence

R5 performs no database writes or schema changes.

### AC-11 — No Downstream Execution

R5 performs no CheckRate, Booking or Cancellation execution.

### AC-12 — No Transport Changes

R5 does not modify R4 transport, authentication, mTLS, GZIP or retry behaviour.

### AC-13 — Regression

Existing accepted R1-R4 behaviour remains intact.
