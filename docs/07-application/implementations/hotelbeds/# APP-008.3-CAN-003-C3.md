# 2. Purpose

This specification is the final canonical contract decision for APP-008.3 Accommodation Availability.

It resolves the remaining architectural decisions identified during the CAN-003-C2 review.

The resulting contract must support the complete commercial workflow:

Client Search  
→ Multi-Room Occupancy  
→ Accommodation Results  
→ Room Options  
→ Rate Options  
→ Price Evaluation  
→ Client Selection  
→ Booking Selection  
→ Provider Revalidation  
→ Booking

The canonical contract is owned by GCT Core.

Hotelbeds remains a provider implementation.

No Hotelbeds response structure, field name, identifier format, or supplier DTO may become part of the canonical model.

---

# 3. Architectural Principles

The following principles are mandatory.

## 3.1 Supplier Neutrality

Canonical models represent business meaning.

They must not reproduce supplier terminology or structures.

Hotelbeds concepts such as:

- `rateKey`
- `rateType`
- `rateClass`
- `hotels.hotels`
- supplier tax envelopes
- supplier cancellation structures
- supplier payment codes

remain adapter-level concepts.

## 3.2 Commercial Completeness

Availability must expose sufficient information for a client to choose:

- accommodation;
- room;
- rate.

The model must preserve the commercial conditions associated with that selection.

## 3.3 Booking Continuity

A selected availability option must retain sufficient information to continue into booking and provider revalidation.

## 3.4 No Fabrication

The system must never fabricate an accommodation, room, rate, price, or booking reference.

## 3.5 Multi-Room First

The canonical model must support multiple rooms with independent occupancy.

The canonical model must not inherit the current R3/R8 one-room implementation limitation.

# 4. Canonical Type System

The following types are the normative canonical contracts.

TypeScript notation is used to define the contract.

Existing project naming and shared value-object conventions may be applied where they are semantically identical, but the resulting implementation must conform to these contracts.

---

# 5. Accommodation Availability Request

The canonical request is:

    AccommodationAvailabilityRequest {
        stay: StayPeriod
        occupancy: OccupancyRequest
        sourceMarket: MarketCode
        candidateSelection: CandidateSelection
    }

All properties are required.

---

# 6. StayPeriod

    StayPeriod {
        checkIn: LocalDate
        checkOut: LocalDate
    }

Invariants:

- `checkIn` is required.
- `checkOut` is required.
- `checkIn < checkOut`.
- Both dates represent accommodation-local calendar dates.
- Supplier date formatting remains an adapter responsibility.

---

# 7. OccupancyRequest

    OccupancyRequest {
        rooms: OccupancyRoom[]
    }

Invariants:

- `rooms.length >= 1`.
- Room ordering is significant.
- Each room represents one requested accommodation room.

---

# 8. OccupancyRoom

    OccupancyRoom {
        adults: PositiveInteger
        children: NonNegativeInteger
        childAges: ChildAge[]
    }

Invariants:

- `adults >= 1`.
- `children >= 0`.
- `childAges.length === children`.
- Every child age is valid according to the canonical child-age rules.
- No aggregate-only room count replaces the ordered room collection.

Example:

    rooms: [
        {
            adults: 2,
            children: 1,
            childAges: [7]
        },
        {
            adults: 1,
            children: 0,
            childAges: []
        }
    ]

This represents two rooms with different occupancy.

---

# 9. CandidateSelection

    CandidateSelection {
        mode: CandidateSelectionMode
        hotelCodes: AccommodationIdentifier[]
    }

The canonical contract may support future selection modes, but provider-specific filtering remains outside the canonical model.

R2 owns candidate resolution.

R3 translates resolved candidates into the supplier request.

---

# 10. Search-Level Availability Result

The provider and application boundary uses:

    AccommodationAvailabilitySearchResult {
        results: AccommodationAvailabilityResult[]
        metadata: AvailabilitySearchMetadata
    }

`results` is ordered.

Valid cardinality:

- zero;
- one;
- many.

No single-result compatibility contract is permitted.

---

# 11. AccommodationAvailabilityResult

    AccommodationAvailabilityResult =
        AccommodationAvailabilitySuccess
        | AccommodationAvailabilityNoAvailability

The union is discriminated by `kind`.

---

# 12. Positive Result

    AccommodationAvailabilitySuccess {
        kind: "ACCOMMODATION"
        accommodation: Accommodation
        requestedOccupancy: OccupancyRequest
        availabilityOptions: AvailabilityOptions
        available: true
        metadata: AccommodationResultMetadata
    }

All properties are mandatory.

Invariants:

- accommodation exists;
- requested occupancy exists;
- at least one `RoomOption` exists;
- every room option has at least one `RateOption`;
- every rate option has a booking reference;
- every rate option has pricing;
- every rate option has offered occupancy;
- `available === true`.

A positive accommodation result with no room options is invalid.

A room option with no rate options is invalid.

---

# 13. No-Availability Result

    AccommodationAvailabilityNoAvailability {
        kind: "NO_AVAILABILITY"
        available: false
        metadata: AccommodationResultMetadata
    }

The following properties are prohibited:

- accommodation;
- requested occupancy;
- availability options;
- room options;
- rate options;
- pricing;
- supplier references.

No supplier-confirmed no-availability response may create a fabricated accommodation.

---

# 14. Search-Level Empty Result

An empty search result is:

    {
        results: []
    }

This means no accommodation result exists.

It is distinct from an individual `NO_AVAILABILITY` result.

A provider must not manufacture a `NO_AVAILABILITY` result merely because its response contains zero accommodations.

---

# 15. AvailabilityOptions

    AvailabilityOptions {
        roomOptions: RoomOption[]
    }

Invariants:

- positive results require at least one room option;
- ordering is preserved;
- room options represent selectable room configurations for the accommodation.

---

# 16. RoomOption

    RoomOption {
        reference: SupplierReference
        name: string
        rateOptions: RateOption[]
    }

All properties are required.

Invariants:

- `reference.provider` identifies the provider;
- `reference.opaqueReference` is non-empty;
- `name` is non-empty;
- at least one rate option exists;
- all rate options belong to this room option.

The room reference is provider-scoped through `SupplierReference`.

The canonical model does not expose a Hotelbeds room code.

---

# 17. Room Option Semantics

A `RoomOption` represents one selectable room configuration returned for an accommodation.

It is not merely descriptive static room content.

It is part of the dynamic availability offer.

A client may therefore select:

    Accommodation
        → RoomOption
            → RateOption

The selected room reference must be preserved into the booking selection.

---

# 18. RateOption

    RateOption {
        bookingReference: SupplierReference
        status: RateStatus
        pricing: RatePricing
        occupancy: OfferedOccupancy
        board: BoardOption | null
        allotment: NonNegativeInteger | null
        payment: PaymentOption | null
        packaging: PackagingOption | null
        cancellationPolicies: CancellationPolicy[]
        taxes: TaxOrFee[]
    }

The following are mandatory:

- bookingReference;
- status;
- pricing;
- occupancy;
- cancellationPolicies;
- taxes.

The remaining properties are nullable where the supplier does not provide meaningful information.

---

# 19. Rate Identity

The authoritative identity of a returned commercial rate is:

    bookingReference

The reference is:

    SupplierReference {
        provider: ProviderIdentifier
        opaqueReference: string
    }

The canonical model does not expose supplier-specific reference names.

For Hotelbeds:

    Hotelbeds rateKey
        ↓
    SupplierReference.opaqueReference

The opaque value must not be parsed by canonical domain code.

---

# 20. SupplierReference

    SupplierReference {
        provider: ProviderIdentifier
        opaqueReference: string
    }

Invariants:

- provider is required;
- opaque reference is required;
- opaque reference must not be empty;
- canonical code must not interpret supplier-specific structure.

A supplier reference identifies an externally owned object or offer.

---

# 21. Room Reference vs Rate Reference

Both room and rate references are retained.

The room reference identifies the selected room option.

The rate reference identifies the selected commercial offer.

The rate reference alone must not be assumed to be sufficient to reconstruct room identity.

A booking selection therefore retains both:

    accommodation
    selectedRoomReference
    selectedRateBookingReference

This avoids implicit dependency on supplier-specific reference composition.

---

# 22. RateStatus

    RateStatus =
        "BOOKABLE"
        | "RECHECK_REQUIRED"

`BOOKABLE` means the supplier has returned the offer as normally bookable subject to standard booking validation.

`RECHECK_REQUIRED` means the provider requires offer revalidation before booking.

Supplier-specific status values are translated by the provider adapter.

---

# 23. RatePricing

    RatePricing {
        amount: Money
        basis: PricingBasis
        taxesIncluded: boolean
    }

All properties are required.

---

# 24. Money

Availability uses the shared canonical `Money` concept.

    Money {
        amount: Decimal
        currency: CurrencyCode
    }

`amount` must not use binary floating-point semantics for canonical monetary storage.

The implementation must use the repository's established decimal/money representation or an equivalent exact representation.

No Availability-specific Money type may be created if the existing shared Money abstraction can be extended safely.

---

# 25. Currency

`CurrencyCode` is a canonical ISO-compatible currency code.

The existing restricted accommodation currency enum must not constrain Availability.

The implementation must support legitimate supplier currencies without creating supplier-specific currency types.

Canonical currency values are represented by their ISO-compatible code.

---

# 26. PricingBasis

    PricingBasis =
        "TOTAL_STAY"
        | "PER_ROOM"
        | "PER_NIGHT"
        | "PER_ROOM_PER_NIGHT"

The basis describes the semantic unit represented by `RatePricing.amount`.

The provider adapter is responsible for translating supplier pricing semantics.

A price without a defined basis is invalid.

---

# 27. Pricing Semantics

The canonical rate price is the commercial amount represented by the supplier offer after supplier-specific interpretation.

The adapter must establish whether the returned supplier amount represents:

- net;
- gross;
- tax-inclusive;
- tax-exclusive;

before mapping it into the canonical representation.

The canonical contract does not use the supplier term `net` as a semantic definition.

`taxesIncluded` explicitly identifies whether included taxes/fees are already incorporated into the rate amount.

---

# 28. Tax Double-Counting Rule

Consumers must not add a tax/fee amount to the rate price when:

    tax.included === true

An excluded tax/fee may be added separately where required for client-facing total calculations.

The canonical model preserves the information required to perform this calculation correctly.

---

# 29. Hotel-Level Minimum and Maximum Rates

Hotel-level supplier summaries such as:

- `minRate`;
- `maxRate`;

are not authoritative rate objects.

They must not replace `RateOption.pricing`.

If the application requires hotel-level minimum/maximum pricing, it is derived from the canonical rate options.

No independently supplied hotel-level summary may be treated as a selectable booking price.

---

# 30. OfferedOccupancy

    OfferedOccupancy {
        rooms: OccupancyRoom[]
    }

It uses the same canonical room occupancy structure as the request.

The purpose is to describe the occupancy to which the returned rate applies.

---

# 31. Requested vs Offered Occupancy

The positive result contains:

    requestedOccupancy

The rate contains:

    occupancy

The requested occupancy is what the client asked for.

The offered occupancy is what the supplier rate applies to.

They must not be silently substituted for one another.

---

# 32. Offered Occupancy Invariants

For a selectable rate:

- `occupancy.rooms.length >= 1`;
- each room has at least one adult;
- child counts match child-age collections;
- room order is preserved.

The offered room count must match the room allocation represented by the rate.

If the supplier response does not provide sufficient occupancy information to establish the applicable room allocation, the adapter must not invent it.

The rate must either:

- use a valid provider-derived occupancy representation; or
- be rejected as unmappable.

---

# 33. BoardOption

    BoardOption {
        code: string
        name: string
    }

Board information is optional.

When unavailable:

    board = null

The adapter maps supplier board terminology into this canonical representation.

Supplier-specific board codes remain provider concerns.

---

# 34. PaymentOption

    PaymentOption {
        timing: PaymentTiming
    }

    PaymentTiming =
        "AT_BOOKING"
        | "AT_PROPERTY"

The canonical contract deliberately represents payment timing rather than supplier payment codes.

If a supplier returns payment information that cannot be safely mapped to one of the approved canonical values, the adapter must not invent a value.

The rate remains valid only if the unmapped payment information is non-essential to the canonical commercial decision. Otherwise mapping must fail and return a provider mapping error.

---

# 35. PackagingOption

    PackagingOption {
        packaged: boolean
    }

`packaged` describes whether the returned rate is subject to packaged supplier pricing semantics.

Supplier-specific package composition is not part of Availability.

A future requirement to expose included package components requires a separate canonical capability decision.

---

# 36. Allotment

`allotment` is:

    NonNegativeInteger | null

It is informational supplier inventory data.

Allotment:

- does not guarantee booking;
- does not replace `RateStatus`;
- must not be interpreted as a booking reservation;
- must not be used to fabricate availability.

---

# 37. CancellationPolicy

    CancellationPolicy {
        effectiveFrom: ZonedDateTime
        penalty: Money | null
        refundable: boolean
    }

Policies are ordered chronologically.

`effectiveFrom` represents the point at which the cancellation condition becomes effective.

The provider adapter must preserve the supplier's applicable timezone.

The canonical model must not silently convert cancellation times to an incorrect local timezone.

---

# 38. Cancellation Semantics

A cancellation policy with:

    refundable = false

represents a non-refundable condition from the effective point represented by the policy.

A monetary penalty is optional because a supplier may express a non-monetary or full-refund condition.

The absence of cancellation policies does not automatically mean non-refundable.

---

# 39. TaxOrFee

    TaxOrFee {
        type: TaxOrFeeType
        subtype: string | null
        amount: Money | null
        percentage: Decimal | null
        included: boolean
    }

    TaxOrFeeType =
        "TAX"
        | "FEE"

A tax/fee may contain:

- amount;
- percentage;
- both;
- neither where the supplier provides only a classification/inclusion condition.

The adapter must not invent monetary values.

---

# 40. Tax/Fee Semantics

`included` means the charge is included in the associated rate pricing.

`included = true` prevents the charge from being added again when calculating the client-facing payable amount.

`included = false` means the charge is additional to the rate amount unless another canonical pricing rule explicitly states otherwise.

Supplier aggregate flags such as Hotelbeds `allIncluded` must be translated into individual canonical tax/fee semantics.

---

# 41. Availability Metadata

`AccommodationResultMetadata` remains application/provider metadata.

Supplier diagnostic information must not be placed in metadata merely because no canonical destination exists.

Metadata is not a compatibility container for supplier response data.

---

# 42. Booking Selection Snapshot

The selected commercial offer is represented by an application-level selection snapshot.

Conceptually:

    AvailabilitySelection {
        provider: ProviderIdentifier
        accommodationReference: AccommodationIdentifier
        roomReference: SupplierReference
        rateReference: SupplierReference
        occupancy: OfferedOccupancy
        pricing: RatePricing
        board: BoardOption | null
        payment: PaymentOption | null
        packaging: PackagingOption | null
        cancellationPolicies: CancellationPolicy[]
        taxes: TaxOrFee[]
    }

This snapshot is application-owned.

It is not a Hotelbeds DTO.

---

# 43. Booking Selection Purpose

The snapshot ensures that the booking workflow retains the commercial offer that the client selected.

It must not require the system to reconstruct the selection from supplier response JSON.

The supplier reference remains authoritative for provider-side revalidation.

---

# 44. Booking Revalidation

Before final booking:

- `BOOKABLE` offers may proceed through the normal booking path;
- `RECHECK_REQUIRED` offers must be revalidated.

Revalidation may change:

- availability;
- price;
- cancellation conditions;
- taxes;
- payment conditions.

The booking workflow must not assume that the original Availability response remains permanently valid.

---

# 45. R5 Mapping Contract

The R5 provider mapping boundary is:

    Provider Availability Response
        ↓
    Provider Adapter
        ↓
    AccommodationAvailabilitySearchResult

The canonical method contract is conceptually:

    mapAvailabilityResponse(response): AccommodationAvailabilitySearchResult

The provider adapter is responsible for translating every supplier result into the canonical hierarchy.

---

# 46. R5 Collection Semantics

R5 must return a search-level result.

It must not return only the first hotel.

For a supplier response containing:

    hotels[]

every valid supplier hotel must become an ordered canonical result.

For each hotel:

    hotel
        → AccommodationAvailabilitySuccess

For each room:

    room
        → RoomOption

For each rate:

    rate
        → RateOption

---

# 47. Hotelbeds Mapping

The verified Hotelbeds response structure:

    response
        hotels
            hotels[]
                rooms[]
                    rates[]

maps to:

    AccommodationAvailabilitySearchResult
        results[]
            AccommodationAvailabilitySuccess
                accommodation
                requestedOccupancy
                availabilityOptions
                    roomOptions[]
                        rateOptions[]

The adapter must preserve:

- accommodation ordering;
- room ordering;
- rate ordering;
- room-to-rate relationship;
- supplier booking references;
- commercial conditions.

---

# 48. R7 Contract

R7 consumes:

    AccommodationAvailabilitySearchResult

R7 must:

- preserve result cardinality;
- preserve ordering;
- attach application-level metadata;
- preserve positive room/rate options;
- preserve no-availability semantics;
- return the canonical result.

R7 must not reinterpret provider-specific structures.

---

# 49. R7 No-Availability

R7 must not convert:

- supplier errors;
- malformed responses;
- mapping failures;
- transport failures

into `NO_AVAILABILITY`.

Only an explicit provider-level no-availability outcome may become:

    kind: "NO_AVAILABILITY"

---

# 50. R2 Boundary

R2 remains responsible for candidate resolution.

R2 does not create:

# 51. R3 Boundary

R3 translates the canonical request into supplier-specific request syntax.

The current R3 one-room implementation constraint must be removed or revised during implementation where required to support the canonical contract.

---

# 52. R4-C1 Boundary

R4-C1 remains responsible for:

- HTTP;

- mTLS;

- response delivery.

---

# 53. R6 Boundary

R6 remains responsible for:

- execution protection;

It does not alter canonical room/rate semantics.

# 54. R8 Boundary

# 55. Static Accommodation vs Dynamic Availability

`Accommodation` contains stable property information.

`AvailabilityOptions` contains dynamic inventory and commercial offer information.

The following must not be added to `Accommodation`:

- rooms available;
- rates;
- supplier rate keys;
- dynamic pricing;
- cancellation conditions for a specific rate;
- rate taxes;
- rate payment conditions.

---

# 56. Existing AccommodationRate

The existing `AccommodationRate` remains a separate contract.

It must not become an alias for `RateOption`.

Shared value objects may be reused when their semantics are identical.

If its current fields are insufficient, it must be extended independently according to its own contract rather than becoming the Availability model.

---

# 57. Existing AccommodationRateResult

`AccommodationRateResult` remains a separate rate-query contract.

It is not the Availability response.

It may share:

- Money;
- currency;
- BoardOption;
- occupancy concepts;
- SupplierReference

where semantics are identical.

It must not be embedded into `AccommodationAvailabilitySearchResult`.

---

# 58. Existing Occupancy Models

Existing occupancy models may be reused or refactored only where they can represent:

    rooms[]
        adults
        children
        childAges[]

The current R3 restriction that each occupancy group represents one room is an implementation constraint, not a canonical restriction.

The canonical model must not contain a `rooms = 1` assumption.

---

# 59. Inventory Migration

Inventory must preserve the complete positive canonical result.

When freezing/cloning an availability result, it must preserve:

- accommodation;
- requested occupancy;
- availability options;
- room options;
- rate options;
- pricing;
- offered occupancy;
- board;
- allotment;
- payment;
- packaging;
- cancellation;
- taxes;
- supplier references;
- metadata.

Inventory must narrow the discriminated union before accessing accommodation.

---

# 60. Journey Composition

Journey composition must consume canonical Availability results.

It must not depend on Hotelbeds response objects.

Package composition must be able to carry a selected:

    Accommodation
        → RoomOption
            → RateOption

into the next booking stage.

# 61. Merchandising

Merchandising may project the canonical model into client-facing views.

It may derive:

- lowest available rate;
- room display name;
- board;
- cancellation summary;
- tax summary;
- payment conditions.

It must not modify canonical semantics.

---

# 63. Consumer Narrowing

Consumers must use:

    kind === "ACCOMMODATION"

before accessing:

- accommodation;
- requested occupancy;
- availability options;
- room options;
- rate options.

Consumers must use:

    kind === "NO_AVAILABILITY"

for explicit absence.

No consumer may rely on:

    result.accommodation

being universally present.

---

# 64. Positive Result Invariants

A valid positive result must satisfy:

1. `kind === "ACCOMMODATION"`.
2. `available === true`.
3. accommodation exists.
4. requested occupancy exists.
5. at least one room option exists.
6. every room option has a valid reference.
7. every room option has at least one rate.
8. every rate has a booking reference.
9. every rate has a valid status.
10. every rate has pricing.
11. every rate has offered occupancy.
12. every rate belongs to exactly one room option.

---

# 65. No-Availability Invariants

A valid no-availability result must satisfy:

1. `kind === "NO_AVAILABILITY"`.
2. `available === false`.
3. accommodation does not exist.
4. room options do not exist.
5. rate options do not exist.
6. pricing does not exist.
7. booking references do not exist.

---

# 66. Supplier Mapping Failure

If a supplier returns commercially required information that cannot be represented by the canonical contract:

- do not discard it silently;
- do not place it in metadata;
- do not add a supplier-specific field;
- do not fabricate a value.

The provider mapping must fail and the architecture must be reviewed if the information is materially required by the business capability.

---

# 67. Malformed Response Semantics

A response with no recognized availability structure is malformed unless the provider contract explicitly identifies it as a valid no-availability response.

The mapper must not use:

    missing hotels = no availability

as a generic rule.

Only an explicitly recognized supplier no-availability structure may become `NO_AVAILABILITY`.

---

# 68. Hotelbeds Isolation

The following Hotelbeds structure remains entirely inside the adapter:

    hotels
        hotels[]
            rooms[]
                rates[]

The adapter translates it into the canonical structure.

The canonical model never exposes:

- `hotels.hotels`;
- `rateKey`;
- `rateType`;
- `rateClass`;
- Hotelbeds-specific payment codes;
- Hotelbeds tax objects;
- Hotelbeds cancellation objects.

---

# 69. Result Ordering

The following ordering is preserved:

1. accommodation result order;
2. room option order;
3. rate option order;
4. occupancy room order;
5. cancellation policy chronological order.

No implicit sorting is permitted in R5.

Presentation-level sorting occurs outside the canonical mapping boundary.

---

# 70. Immutability

Canonical result structures are immutable.

Collections must not be externally mutable.

This includes:

- search results;
- room options;
- rate options;
- occupancy;
- cancellation policies;
- taxes.

Existing project freezing/deep-cloning conventions must be applied consistently.

---

# 71. API and Client Contract

The canonical Availability model is intended to support future client search responses.

The client must be able to:

1. submit multiple room occupancy groups;
2. receive multiple accommodations;
3. inspect room options;
4. inspect rates for each room;
5. compare pricing;
6. inspect board;
7. inspect cancellation;
8. inspect taxes/fees;
9. inspect payment conditions;
10. select a room/rate combination;
11. carry the selection into booking.

No supplier-specific knowledge is required by the client.

---

# 72. Canonical-to-Booking Boundary

The client selects:

    accommodation
        room
            rate

The application creates:

    AvailabilitySelection

The booking provider adapter translates that selection into the supplier booking request.

The canonical model does not contain supplier-specific booking request structures.

---

# 73. Selection Freshness

Availability results are time-sensitive.

A `SupplierReference` does not guarantee that an offer remains available.

The booking workflow must therefore treat the Availability response as an offer snapshot subject to provider validation.

`RECHECK_REQUIRED` explicitly requires revalidation.

Even `BOOKABLE` offers remain subject to normal provider booking validation.

---

# 74. No Canonical Hotelbeds DTO

Hotelbeds response DTOs may exist under the provider adapter.

They must not be returned from:

- domain services;
- canonical application contracts;
- R7;
- client-facing application services.

---

4. Implement AvailabilityOptions.
