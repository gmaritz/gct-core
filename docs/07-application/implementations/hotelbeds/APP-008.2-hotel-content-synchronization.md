# 1. Objective

Implement the Hotelbeds **Hotel Content synchronization capability**.

The capability shall retrieve static hotel content from the Hotelbeds Content API, transform it into the canonical GCT Core accommodation content model, and persist it locally for application use.

Hotelbeds explicitly recommends periodic batch retrieval and local storage of Content API data rather than retrieving static content in real time. Subsequent synchronization should use `lastUpdateTime` to retrieve differential changes.

---

# 2. Scope

Implement:

* Hotelbeds Content API Hotels retrieval
* initial/full content synchronization
* incremental content synchronization
* pagination
* content mapping
* canonical hotel content model
* required supporting reference data
* local persistence
* synchronization state
* synchronization result
* failure handling
* tests
* implementation report

---

# 3. Exclusions

Do not implement:

* live hotel availability
* pricing
* CheckRate
* hotel booking
* booking cancellation
* post-booking
* frontend hotel search
* package-tour presentation
* dynamic rates
* supplier selection rules

These belong to later milestones.

---

# 4. Architectural Position

```text
Hotelbeds Content API
        ↓
APP-008.1 Integration Foundation
        ↓
APP-008.2 Content Synchronization
        ↓
Canonical Hotel Content
        ↓
Local Persistence
        ↓
APP-008.3 Availability & Search
```

Static content and dynamic booking information must remain separate. Hotelbeds identifies descriptions, images, addresses and similar information as static content, while prices, availability and cancellation policies are dynamic.

---

# 5. Existing Architecture

Before implementation Copilot shall inspect the current repository for:

* accommodation/hotel domain models
* persistence conventions
* repository patterns
* batch/import workflows
* synchronization patterns
* Hotelbeds gateway established by APP-008.1
* configuration conventions

Reuse existing architecture.

Do not introduce a second persistence or synchronization framework.

---

# 6. Hotel Content Source

Use the Hotelbeds Content API Hotels operation as the primary hotel-content source.

Hotelbeds supports paged hotel retrieval using `from` and `to`, with up to 1000 hotels per request.

The implementation shall support pagination until the requested synchronization scope is complete.

---

# 7. Initial Synchronization

Support a full/initial synchronization capable of populating the local hotel-content store.

The synchronization shall:

1. request a page
2. validate the response
3. map the content
4. persist the content
5. continue until all pages are processed
6. record successful synchronization state

A failed page must not be reported as successfully synchronized.

---

# 8. Incremental Synchronization

Support differential synchronization using Hotelbeds `lastUpdateTime`.

The synchronization state shall retain the last successfully processed synchronization point.

A subsequent synchronization shall request only changes since that point.

Hotelbeds recommends this approach for ongoing content updates.

Do not advance the synchronization checkpoint until the applicable changes have been successfully processed.

---

# 9. Synchronization State

Implement the minimum state required to safely resume synchronization.

At minimum:

* synchronization type
* last successful update timestamp/checkpoint
* execution status
* processed count
* failed count
* execution metadata

The state must distinguish successful and unsuccessful synchronization.

---

# 10. Pagination

Pagination shall be deterministic.

The synchronizer shall:

* use the configured page size
* process pages sequentially unless an established batch pattern safely supports parallelism
* avoid skipping pages
* avoid duplicate processing caused by incorrect offsets
* record the final successful checkpoint only after processing succeeds

---

# 11. Hotel Content Model

Implement or extend the canonical GCT Core hotel-content model required by the current architecture.

At minimum, preserve the Hotelbeds information required for:

* Hotelbeds hotel code
* name
* description
* category/star classification
* accommodation type
* address
* country
* destination
* coordinates
* facilities
* images
* contact information where supplied
* last-update information

The exact model shall follow the existing GCT Core domain/entity model rather than reproducing the Hotelbeds response structure.

---

# 12. Supporting Reference Data

Hotelbeds hotel content references supporting datasets such as:

* countries
* destinations
* facilities
* categories
* accommodation types
* chains
* room types
* board types

Hotelbeds documents these as complementary Content API operations used to describe codes returned by the Hotels operation.

Copilot shall determine which reference datasets are actually required by the existing GCT Core model.

Do not implement every Content API operation merely because it exists.

---

# 13. Images

Hotel images shall be stored as canonical image metadata/references.

Do not download binary image files as part of APP-008.2 unless the existing architecture explicitly requires local image storage.

Preserve the information required to retrieve/display the images later.

---

# 14. Languages

The synchronization shall support the language strategy already established by GCT Core.

Do not hard-code multilingual behaviour into the Hotelbeds adapter.

If only one language is currently required, implement that language cleanly while keeping the model extensible for later languages.

---

# 15. Mapping Boundary

Hotelbeds responses shall be mapped:

```text
Hotelbeds Content DTO
        ↓
Hotel Content Mapper
        ↓
Canonical GCT Core Hotel Content
```

Hotelbeds DTOs must not become canonical GCT Core models.

---

# 16. Upsert Behaviour

Hotel content synchronization shall be idempotent.

If a hotel already exists:

```text
Existing Hotel
      ↓
Updated Content
      ↓
Canonical Update
```

If it does not exist:

```text
New Content
      ↓
Canonical Hotel
```

Repeated processing of the same content must not create duplicate hotels.

---

# 17. Hotel Identity

The Hotelbeds hotel code shall be treated as the external provider identity.

The canonical GCT Core hotel identity shall follow the existing domain model.

Do not use hotel name as identity.

Hotel name changes must not create a second hotel.

---

# 18. Removed/Inactive Hotels

If Hotelbeds indicates that content has been removed or is no longer available, follow the established GCT Core lifecycle convention.

Do not physically delete a hotel merely because it disappears from one response unless the canonical architecture explicitly requires deletion.

Prefer an inactive/unavailable state where supported.

If the current model does not define this behaviour, report the gap rather than inventing a destructive rule.

---

# 19. Persistence

Use the existing repository/persistence architecture.

APP-008.2 may introduce the required hotel-content persistence structures if they do not yet exist.

Do not bypass repositories with direct database calls from the synchronizer.

---

# 20. Transaction Safety

A synchronization page must not be marked successfully processed before its content has been persisted successfully.

If a page fails:

```text
Page Processing
      ↓
Failure
      ↓
No successful checkpoint advance
```

Avoid partial state where the existing persistence architecture supports transactional processing.

---

# 21. Error Handling

Classify failures using the APP-008.1 integration error model where applicable.

The synchronizer shall distinguish:

* provider failure
* transport failure
* malformed content
* mapping failure
* persistence failure
* configuration failure

A synchronization failure must be observable and retryable where appropriate.

---

# 22. Retry

Reuse existing retry infrastructure.

Do not introduce a new retry scheduler.

A failed synchronization may be rerun safely because content processing is idempotent.

---

# 23. Concurrency

The synchronization mechanism shall prevent overlapping full/incremental synchronization jobs unless the existing infrastructure explicitly supports safe concurrency.

Two simultaneous synchronizations must not corrupt:

* synchronization checkpoints
* hotel records
* reference data

---

# 24. Dynamic Data Boundary

APP-008.2 must not store dynamic booking information as if it were static content.

Do not synchronize:

* live availability
* booking rates
* cancellation rules for a specific booking
* live fees

Those will come from the Booking API in later milestones.

---
