# 1. Purpose

Implement supplier-neutral modification of an existing confirmed accommodation booking.

The capability SHALL support modification of accommodation booking data where the original supplier and booking support the requested change.

The canonical flow SHALL be:

Confirmed Accommodation Booking
→ Modification Request
→ Supplier Modification
→ Modified Accommodation Booking
→ APP-004 Reservation Lifecycle

Hotelbeds SHALL remain an adapter implementation.

The canonical GCT model MUST NOT reproduce the Hotelbeds modification request or response model.

---

# 2. Business Context

Go Cape Tours sells private multi-day packages containing accommodation at individual package stops.

An accommodation booking may need to be changed after confirmation.

Examples include:

- changing stay dates;
- changing room occupancy;
- changing guests;
- changing the selected room;
- changing the selected rate;
- changing the booking holder where the supplier permits it.

A modification changes the accommodation component of the reservation.

It does NOT automatically modify:

- the entire GCT package;
- other accommodation stops;
- GCT package pricing;
- tour services;
- transport;
- the complete customer itinerary.

Package-level consequences belong to the appropriate higher-level application capability.

# 4. Architectural Boundary

The canonical application flow SHALL be:

Application
→ Accommodation Modification Service
→ Original Accommodation Provider
→ Supplier Adapter
→ Supplier Modification API

The provider MUST be determined from the existing confirmed booking.

The modification operation MUST NOT search for a different provider.

Hotelbeds-specific request and response DTOs SHALL remain inside the Hotelbeds adapter.

APP-004 remains responsible for reservation ownership and persistence.

---

# 5. Existing Booking Requirement

A modification SHALL operate only against an existing confirmed accommodation booking.

The canonical request MUST identify the existing reservation/booking through the established APP-004 contract.

The request MUST contain sufficient information to identify:

- internal reservation;
- provider;
- supplier booking reference.

The supplier booking reference is the confirmed reference returned by APP-008.5.

The availability offer reference MUST NOT be used as the booking identifier.

---

# 6. Provider Continuity

The provider associated with the original confirmed booking is authoritative.

The application MUST NOT:

- select the first registered provider;
- perform provider discovery;
- move a booking between suppliers;
- replace the original supplier automatically.

For example:

Existing Booking
→ Hotelbeds

Modification
→ Hotelbeds

A future booking from Supplier B remains a separate booking and is not an APP-008.7 modification.

---

# 7. Canonical Modification Request

The canonical modification request SHALL be supplier-neutral.

It SHALL contain:

- reservation identity;
- provider;
- supplier booking reference;
- requested changes;
- request correlation/idempotency information where required;
- caller context where already supported by APP-004.

The requested changes SHALL be explicit rather than represented as arbitrary JSON.

---

# 8. Modification Types

The canonical contract SHALL support the following business-level modification categories where the provider supports them:

- stay dates;
- occupancy;
- guests/paxes;
- room selection;
- rate selection;
- booking holder;
- accommodation-specific booking information already represented by the canonical reservation model.

A modification request MAY contain more than one change.

The canonical model MUST preserve the distinction between:

- unchanged booking data;
- requested changes;
- resulting confirmed booking data.

Do not force every modification into a generic key/value structure.

---

# 9. Stay-Date Modification

The modification contract SHALL support:

- new check-in date;
- new check-out date.

The dates SHALL be represented using the existing canonical date/value-object conventions.

The modification service MUST validate:

- check-out is after check-in;
- dates are valid;
- required booking constraints are satisfied.

The Hotelbeds adapter SHALL translate the canonical dates into the supplier-specific request.

The adapter MUST NOT expose Hotelbeds date field names to the canonical layer.

---

# 10. Occupancy Modification

The modification contract SHALL support the established multi-room occupancy model.

It MUST support:

- multiple rooms;
- adults per room;
- children per room;
- child ages.

The canonical structure SHALL remain compatible with the multi-room model established by APP-008.3.

The modification service SHALL validate that the requested occupancy is internally consistent.

The provider MAY reject an occupancy change if the supplier does not support it for the existing booking.

---

# 11. Guest Modification

The modification contract SHALL support modification of guest information where the supplier permits it.

Guest information MAY include:

- first name;
- last name;
- adult/child classification;
- child age where required;
- room association.

The canonical service MUST preserve room-to-guest association.

The implementation MUST NOT silently change guest identities or occupancy to make a supplier request valid.

---

# 12. Booking Holder Modification

The canonical modification contract MAY support changing:

- holder first name;
- holder surname;
- holder email;
- holder phone.

The provider determines whether the supplier allows the requested change.

If the supplier does not support holder modification, return a canonical unsupported/failed outcome.

Do not silently convert the request into a cancellation and new booking.

---

# 13. Room Modification

A room modification SHALL represent the desired canonical room selection.

The canonical request MUST NOT use Hotelbeds-specific room DTOs.

Where the supplier requires a new supplier offer/reference to modify the room, that translation SHALL occur inside the adapter.

If a new rate or supplier reference is required, the implementation MUST NOT fabricate one.

The supplier adapter SHALL use the appropriate supplier workflow to obtain or validate the required modification data.

---

# 14. Rate Modification

A rate modification SHALL identify the desired canonical rate selection.

A supplier-specific rate reference MAY be required.

The canonical model SHALL continue to represent supplier references as opaque values.

If a rate modification requires revalidation before modification, the implementation SHALL use APP-008.4 rather than implementing another CheckRate mechanism.

The modification service MUST NOT assume that an old availability rate remains valid.

---

# 15. Revalidation

Where the requested modification changes the selected room, rate, occupancy, or dates in a way that requires current supplier availability/pricing:

Modification
→ Revalidation
→ Modification

APP-008.4 remains the canonical revalidation capability.

The modification service MUST NOT duplicate CheckRate behaviour.

If the supplier's modification API itself performs the required validation, Copilot MAY use the supplier operation directly where appropriate.

The implementation MUST follow the existing provider capability contract and avoid redundant supplier calls.

---

# 16. Supplier Modification Capability

The existing provider capability architecture SHALL be extended with a supplier-neutral modification capability.

Conceptually:

AccommodationProvider

- availability
- revalidation
- booking
- cancellation
- modification

A provider MAY support modification independently of other capabilities.

The application MUST check provider capability before attempting modification.

If the original provider does not support modification, return a canonical unsupported outcome without making a supplier call.

---

# 17. Hotelbeds Modification Adapter

Hotelbeds SHALL implement the canonical modification capability through its Booking API.

Hotelbeds documents the `/bookings` operation as supporting booking modification in addition to booking confirmation, booking details and cancellation. :contentReference[oaicite:1]{index=1}

The adapter SHALL translate the canonical modification request into the Hotelbeds-specific modification request.

The exact Hotelbeds:

- HTTP method;
- endpoint/path;
- request structure;
- modification fields;
- response structure;
- status values;
- error codes

MUST remain adapter-specific.

The canonical service MUST NOT contain these supplier details.

---

# 18. Hotelbeds Transport

Reuse the existing Hotelbeds infrastructure:

- authentication;
- signature generation;
- mTLS;
- HTTP gateway;
- transport;
- timeout handling;
- error handling;
- logging;
- existing supplier capability registration.

Hotelbeds identifies booking change as an mTLS-protected Hotels API operation. :contentReference[oaicite:2]{index=2}

Do not create a second Hotelbeds transport stack.

---

# 19. Modification Result

The canonical result SHALL distinguish successful modification from unsuccessful modification.

A successful result MUST preserve:

- internal reservation identity;
- provider;
- supplier booking reference;
- resulting booking status;
- resulting accommodation;
- resulting room;
- resulting rate where returned;
- resulting stay dates;
- resulting occupancy;
- resulting guests/holder where returned;
- resulting supplier price;
- modification charges where supplied;
- relevant booking conditions.

The raw Hotelbeds response MUST NOT cross the canonical boundary.

---

# 20. Modification Outcome

The canonical result SHALL support at least:

- `MODIFIED`;
- `FAILED`;
- `UNKNOWN`;
- `UNSUPPORTED`.

`MODIFIED` means the supplier confirmed the requested modification.

`FAILED` means the supplier definitively rejected or failed the modification without an ambiguous state.

`UNKNOWN` means the modification request may have been processed but the application cannot establish the final supplier state.

`UNSUPPORTED` means the provider does not support the requested modification capability.

---

# 21. Unknown Modification Outcome

Modification is a state-changing supplier operation.

If the supplier request may have succeeded but the response cannot be established:

- return `UNKNOWN`;
- do not automatically issue a second modification request;
- do not mark the reservation as modified;
- preserve the information required for later resolution.

A future booking-detail/reconciliation capability may resolve the state.

APP-008.7 SHALL NOT implement a new reconciliation capability.

---

# 22. Retry Safety

Modification requests MUST NOT use unrestricted automatic retries.

A retry is permitted only where the implementation can establish that:

- the original request did not reach the supplier; or
- the operation is explicitly idempotent under the supplier contract; or
- the existing idempotency architecture guarantees duplicate protection.

If safe retry cannot be established, return `UNKNOWN` where appropriate.

Do not blindly resend a modification request.

---

# 23. Idempotency

The modification operation SHALL use the existing idempotency/duplicate-protection architecture where available.

The implementation MUST NOT introduce a separate idempotency database solely for APP-008.7.

If the current APP-004 architecture cannot persist an idempotency key, Copilot SHALL preserve the existing architecture and report the limitation rather than creating an unrelated persistence model.

---

# 24. Supplier Price

A successful modification MAY change the supplier accommodation price.

The canonical result SHALL preserve the supplier-confirmed price returned by the supplier.

The implementation MUST distinguish:

- previous supplier booking price;
- new supplier booking price;
- modification charge where supplied.

The application MUST NOT silently overwrite GCT package pricing.

---

# 25. GCT Package Pricing Boundary

APP-008.7 MUST NOT calculate the new GCT customer package price.

The accommodation modification result becomes an input to the established GCT pricing/application workflow.

APP-005 remains responsible for:

- package price;
- sliding-scale pricing;
- package adjustments;
- customer-facing price.

If a future package-level modification workflow is required, it SHALL consume APP-008.7 results.

---

# 26. Modification Charges

Where the supplier returns a modification charge, preserve:

- amount;
- currency;
- applicable description/reference where supplied.

A modification charge is supplier accommodation information.

It is not automatically:

- a GCT cancellation fee;
- a GCT package adjustment;
- a customer refund;
- a package repricing calculation.

Do not invent a financial settlement workflow.

---

# 27. Reservation Update

After confirmed modification:

APP-008.7 SHALL update the reservation through the existing APP-004 boundary.

The reservation SHALL reflect the confirmed supplier state.

Where supported by the existing reservation model, preserve:

- new stay dates;
- new room;
- new rate;
- new occupancy;
- new guests;
- new holder;
- supplier price;
- modification timestamp;
- supplier booking reference;
- modification status.

The supplier response MUST NOT remain only in transient memory when APP-004 has an established persistence mechanism for the relevant data.

---

# 28. Reservation Snapshot

The modification operation SHALL preserve the resulting confirmed booking state.

The previous state MUST NOT be silently destroyed if the existing APP-004 reservation architecture supports history/versioning.

If APP-004 currently supports only a current snapshot, update that snapshot according to its established semantics.

Do not invent a new reservation-versioning architecture inside APP-008.7.

---

# 29. Atomicity Boundary

Supplier modification and local reservation persistence are separate systems.

The implementation MUST NOT assume a distributed transaction.

If:

1. supplier modification succeeds; and
2. local persistence fails;

the result MUST NOT be represented as a normal supplier modification failure.

The implementation SHALL preserve enough information to identify that the supplier may already have modified the booking.

Do not falsely report the supplier state.

---

# 30. Modification of Cancelled Bookings

A cancelled accommodation booking MUST NOT be modified.

The canonical service SHALL reject the request before making a supplier call when the existing reservation state is already cancelled.

If the supplier reports the booking as cancelled, map the supplier result to the canonical reservation state.

Do not attempt to recreate the booking automatically.

---

# 31. Modification of Unknown Bookings

If the existing reservation state is `UNKNOWN` because of an earlier booking or cancellation operation:

- modification SHALL be rejected;
- no supplier modification call SHALL be made;
- the unknown state must first be resolved by the appropriate future/current booking-detail or reconciliation capability.

Do not modify an uncertain booking state.

---

# 32. Multi-Room Modification

The canonical contract SHALL support modifications affecting multiple rooms.

A modification MAY:

- modify one room;
- modify several rooms;
- replace the room/rate selection for the booking;
- change occupancy across multiple rooms.

The implementation MUST preserve room identity/association when applying changes.

A partial modification MUST NOT be represented as a complete successful booking modification unless the supplier confirms the complete requested operation.

If the supplier supports only certain partial modifications, the provider adapter SHALL enforce that supplier capability.

---

# 33. Partial Modification

The canonical model SHALL distinguish:

- full booking modification;
- partial modification where explicitly supported.

The implementation MUST NOT assume that changing one room automatically modifies every room.

If Hotelbeds returns a supplier-specific partial modification structure, it remains adapter-specific.

The canonical result SHALL describe the resulting confirmed reservation state.

---

# 34. Modification Eligibility

The canonical service SHALL validate:

- reservation exists;
- reservation is an accommodation reservation;
- provider matches the original booking;
- supplier booking reference exists;
- reservation is confirmed;
- reservation is not cancelled;
- reservation is not already in an unknown state;
- requested changes are valid.

Supplier-side eligibility remains authoritative for supplier-specific restrictions.

---

# 35. Unsupported Modification

If a provider does not support modification:

- return `UNSUPPORTED`;
- do not issue a supplier call;
- do not automatically cancel and rebook.

Cancellation followed by new booking is a separate business decision and MUST NOT be silently performed by APP-008.7.

---

# 36. Multiple Suppliers

The canonical modification capability SHALL remain supplier-neutral.

The provider is selected from the original confirmed reservation.

A future supplier SHALL be able to implement the same canonical modification contract.

Supplier-specific modification limitations belong to the provider capability.

No Hotelbeds-specific field names may be introduced into the canonical modification contract.

---

# 37. Security

Modification requests contain personal and commercially sensitive information.

The implementation MUST NOT log:

- API credentials;
- private keys;
- signatures;
- authentication headers;
- unnecessary guest personal data.

Logs MAY contain safe operational identifiers such as:

- internal reservation ID;
- provider;
- supplier booking reference where permitted;
- modification outcome;
- correlation ID.

Use the established security and logging architecture.

# 45. Final Architectural Statement

APP-008.7 establishes the accommodation modification boundary:

Confirmed Accommodation Booking
→ Modification Request
→ Revalidation where required
→ Supplier Modification
→ Canonical Modified Booking
→ APP-004 Reservation Lifecycle

The canonical GCT Core model owns the modification business operation.

The original supplier/provider remains authoritative for the existing booking.

Hotelbeds remains an adapter and MUST NOT become the canonical modification model.

APP-004 remains responsible for reservation lifecycle and persistence.

APP-005 remains responsible for GCT package pricing.

APP-008.7 does not cancel and rebook when modification is unsupported.

Future package-level modification, refund calculation, reconciliation and booking-history capabilities remain separate concerns.
