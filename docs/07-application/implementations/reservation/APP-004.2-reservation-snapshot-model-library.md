# Objective

Implement the canonical Reservation Snapshot Model Library.

The library defines immutable commercial records that preserve the state of a reservation at specific points in time.

Snapshot models are historical records.

They are not live business aggregates.

# Snapshot Contract

Create

```typescript
ReservationSnapshot
```

Every snapshot shall implement this contract.

Minimum properties

```typescript
snapshotId

capturedAt

version
```

All properties are immutable.

---

# Journey Snapshot

Represents the booked journey exactly as sold.

Typical properties

- journey identifier
- title
- destination
- duration
- accommodation summary
- experience summary

This snapshot shall never reference the live Journey aggregate.

---

# Traveller Snapshot

Represents a traveller at the time of booking.

Typical properties

- traveller identifier
- full name
- contact details
- nationality
- traveller type

Remain immutable.

---

# Accommodation Snapshot

Represents booked accommodation.

Typical properties

- accommodation identifier
- property name
- room type
- meal basis
- check-in
- check-out
- the selected canonical rate's cancellation-policy collection
- the selected canonical rate's supplier payment type

Preserve the complete existing cancellation-policy values, including applicable deadlines and penalties, and the supplier payment type with the selected rate exactly as supplied. Do not infer missing supplier terms. These are supplier terms, not customer collection amounts.

Remain immutable.

---

# Pricing Snapshot

Represents the commercial pricing agreed with the customer.

Typical properties

- currency
- total price
- taxes
- discounts
- fees

No live pricing calculations.

---

# Payment Snapshot

Represents Reservation-owned historical commercial payment terms and payment state. It does not contain a Payment Aggregate or provider payload.

The snapshot SHALL preserve an immutable `initialRequirement`:

```typescript
InitialPaymentRequirement {
  classification: "PARTIAL_PAYMENT" | "FULL_PAYMENT";
  amountPayableAtBooking: Money;
  contractualFutureBalance?: {
    amount: Money;
    dueDate: string; // calendar date, YYYY-MM-DD
  };
  pricingSnapshotId: string;
  commercialPolicy: {
    policyId: string;
    version: string;
    appliedRate: string; // exact decimal representation
  };
  calculationBasis: {
    bookingDate: string; // calendar date, YYYY-MM-DD
    departureDate: string; // calendar date, YYYY-MM-DD
    leadTimeDays: number;
    commercialTimeZone: "Africa/Johannesburg";
    gctComponent: {
      sourcePricingLineIdentifier: string;
      amount: Money;
      costingSourceId: string;
      costingSourceVersion: string;
      costingSourceEffectiveDate: string; // calendar date, YYYY-MM-DD
    };
    accommodationComponents: ReadonlyArray<{
      packageStopId: string;
      sourcePricingLineIdentifier: string;
      amount: Money;
    }>;
  };
}
```

The `Money` values use the existing canonical amount/currency contract. Reservation total and currency remain authoritative in PricingSnapshot and SHALL NOT be duplicated as independently mutable values in `initialRequirement`.

The physical JSONB mapping is defined by [SPEC-027 v2.1](../../../06-specifications/engineering/SPEC-027-physical-data-model%20v2.1.md) and [SPEC-028 v2.1](../../../06-specifications/engineering/SPEC-028-prisma-data-model%20v2.1.md), using the existing Reservation `paymentSnapshot` field.

Typical properties

- payment status
- payment method
- amount received
- balance outstanding
- initial requirement

`amountReceived` reflects verified received funds only. `balanceOutstanding` is Reservation total less verified amount received; it is not the initial amount payable and does not replace the contractual future balance. These facts and an individual Payment outcome remain distinct.

No payment processing logic.

The requirement is immutable historical commercial agreement. A changed requirement requires explicit customer re-agreement and a new Reservation snapshot version. If required source/costing or quote context is missing or inconsistent, do not create the requirement.

# Versioning

Every snapshot shall support versioning.

Future reservation amendments shall create new snapshots without modifying historical records.

# Milestone Outcome

Upon successful completion, GCT Core shall expose a canonical Reservation Snapshot Model Library providing immutable, versionable commercial records for journeys, travellers, accommodation, pricing, payments and supplier references.

The library establishes the foundation for preserving historical booking integrity while remaining independent of live business aggregates and future domain evolution.
