# 1. Objective

Implement the canonical **Invoice Model Library** for APP-007.

The model library establishes the reusable, immutable business language used by the Invoice capability.

It shall extract the supporting Invoice concepts currently defined locally within the Invoice Aggregate and establish them as canonical application models.

The library shall provide immutable shared contracts for:

* invoice identity
* invoice references
* reservation references
* customer/traveller references
* quotation references
* pricing snapshots
* financial obligations
* deposit requirements
* payment allocations
* financial adjustments
* cancellation financial snapshots
* external financial references
* invoice lifecycle status
* invoice metadata

The Invoice Aggregate shall be refactored to consume these canonical models.

The model library shall remain:

* immutable
* provider-independent
* accounting-system independent
* presentation-independent
* calculation-independent
* policy-independent
* validation-pipeline independent

---

# 2. Architectural Purpose

APP-007.1 established the Invoice Aggregate.

APP-007.2 extracts the reusable supporting concepts from that aggregate and establishes the canonical Invoice model language.

The architectural relationship is:

```text
APP-007.1
Invoice Aggregate
       │
       ▼
APP-007.2
Invoice Model Library
       │
       ├── Identity
       ├── References
       ├── Pricing
       ├── Financial
       ├── Deposit
       ├── Payments
       ├── Adjustments
       ├── Cancellation
       ├── Lifecycle
       └── Metadata
```

The Invoice Aggregate shall own the aggregate boundary.

The Model Library shall own the reusable business concepts.

The model library shall not own aggregate behaviour.

# 4. Architectural Principles

The Invoice Model Library shall follow these principles.

## 4.1 Single Canonical Language

Each Invoice business concept shall have one canonical model.

The platform shall not create competing representations of the same Invoice concept.

---

## 4.2 Immutable Models

All models shall be immutable.

Use:

* `readonly` properties
* defensive copying
* cloned dates
* immutable collections
* frozen nested objects

---

## 4.3 Aggregate Independence

The models belong to the Invoice capability but do not own the Invoice Aggregate lifecycle.

Models shall not contain:

* aggregate methods
* state transitions
* orchestration
* external calls
* business workflows

---

## 4.4 Provider Independence

No Invoice model shall directly depend upon:

* QuickBooks
* Stripe
* PayGate
* PayPal
* Adyen
* Ozow
* Peach Payments
* Hotelbeds
* any other external provider

Provider-specific references shall remain represented through generic external-reference contracts.

---

## 4.5 Accounting Independence

The Invoice model represents the application's commercial financial obligation.

It does not assert that the model is the authoritative accounting document.

The model must therefore support:

```text
GCT Core
   ↓
Commercial Financial Obligation
   ↓
External Accounting
```

without introducing accounting-system dependencies.

---

## 4.6 Historical Snapshot Principle

Pricing, quotation and cancellation information used by an Invoice must be represented as historical snapshots or references.

The Invoice models shall not reference mutable live Pricing, Quotation or policy objects.

# 7. Identity Models

Implement:

```typescript
export interface InvoiceIdentity {
  readonly id: string;
}

export function createInvoiceIdentity(
  identity: InvoiceIdentity,
): InvoiceIdentity;
```

The factory shall:

* preserve the supplied ID
* return an immutable object
* not generate a new ID
* not mutate the input

The aggregate remains responsible for validating whether the identity is acceptable in its construction context.

The model factory provides structural immutability.

# 20. Model Factory Pattern

All object-based Invoice models shall use the established GCT Core model factory pattern where required.

For example:

```typescript
export function createInvoicePricingSnapshot(
  snapshot: InvoicePricingSnapshot,
): InvoicePricingSnapshot {
  return Object.freeze({
    snapshotId: snapshot.snapshotId,
    pricingId: snapshot.pricingId,
    capturedAt: new Date(snapshot.capturedAt.getTime()),
    version: snapshot.version,
    currency: snapshot.currency,
    totalAmount: snapshot.totalAmount,
  });
}
```

Factories shall:

* return new immutable objects
* never mutate caller input
* clone mutable values
* preserve scalar values
* preserve optional values
* avoid business calculation

---

# 21. Structural Validation vs Business Validation

The Model Library must remain distinct from the Validation Pipeline.

APP-007.2 may protect models against unsafe construction where required by the established model pattern.

However, it shall not implement application-level business validation.

For example, the model library may preserve:

```text
readonly type
readonly amount
readonly currency
```

but APP-007.3 determines whether an Invoice request satisfies the complete Invoice validation contract.

APP-007.2 shall not implement:

```text
InvoiceValidationPipeline
InvoiceValidator
InvoiceValidationResult
InvoiceValidationError
```

---

# 22. Immutability

Every object-based Invoice model shall be immutable.

Requirements:

* all properties `readonly`
* returned objects frozen
* nested objects independently frozen
* dates defensively copied
* arrays defensively copied
* collections exposed as `ReadonlyArray`

No model shall expose a mutable internal reference.

---

# 23. Date Handling

Every model containing a `Date` shall clone the supplied date.

Use:

```typescript
new Date(value.getTime())
```

Never retain the caller's original Date object.

Example:

```typescript
const capturedAt = new Date(snapshot.capturedAt.getTime());
```

The factory shall return the cloned value.

If a model is subsequently exposed by the aggregate, the aggregate shall preserve the established defensive-copying convention.

---

# 24. Collection Handling

APP-007.2 does not introduce collection models unless required.

Where the Invoice Aggregate stores collections such as:

```text
paymentAllocations
adjustments
externalReferences
```

the aggregate shall continue to expose:

```typescript
ReadonlyArray<T>
```

The model library shall provide immutable item models.

The aggregate remains responsible for freezing the collection itself.

Do not introduce unnecessary collection wrapper classes.
