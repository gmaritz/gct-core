# 1. Objective

Implement the canonical **Invoice Integration boundary** for the APP-007 Invoice Capability.

APP-007.7 is responsible for communicating Invoice outcomes to external systems and coordinating external Invoice-related actions without placing external-system concerns inside the Invoice Aggregate, Validation Pipeline, Policy Framework, Engine, or Presentation Pipeline.

The Integration layer shall establish the contracts and orchestration required for:

* external Invoice synchronisation
* accounting integration
* external Invoice references
* integration status
* integration errors
* external action requests
* integration results
* retry-safe execution
* provider-independent integration boundaries

Provider-specific adapters shall be implemented only where an established GCT Core integration requires them.

---

# 2. Scope

APP-007.7 includes:

* Invoice integration contracts
* external Invoice representation
* integration request/result models
* integration status
* integration error model
* integration orchestration
* accounting integration boundary
* external Invoice reference handling
* provider adapter boundary
* synchronisation operations
* retry/idempotency contract
* integration result handling
* immutable integration results
* integration tests
* capability exports
* implementation report

---

# 3. Explicit Exclusions

APP-007.7 shall not implement:

* Invoice business rules
* Invoice calculations
* Invoice validation
* Invoice policy evaluation
* Invoice Aggregate mutation
* Invoice presentation
* frontend implementation
* Hotelbeds integration
* accommodation supplier integration
* payment gateway implementation unless already defined as an Invoice integration dependency
* database persistence implementation
* Prisma schema changes unless an existing canonical persistence model explicitly requires them
* PDF generation
* email rendering
* email delivery
* arbitrary provider-specific behaviour without an established integration contract

APP-007.7 is the Invoice **integration boundary**, not a general external-integration framework for the entire platform.

# 5. Core Responsibility

The Invoice Integration layer shall answer:

> How does GCT Core communicate an Invoice outcome to an approved external system while preserving the canonical Invoice model and integration boundaries?

The Integration layer shall:

1. receive canonical Invoice information
2. construct the required integration request
3. invoke the appropriate external adapter
4. process the external response
5. map external references into canonical integration results
6. report success or failure
7. preserve retry/idempotency information
8. avoid mutating the Invoice Aggregate

---

# 6. Architectural Principles

The Integration layer shall be:

* provider-independent at its contract boundary
* adapter-based
* deterministic where possible
* side-effect aware
* retry-safe
* idempotent where the external provider supports it
* immutable at the result boundary
* isolated from domain logic

External-system behaviour must not leak into the Invoice Aggregate.

---

# 9. Integration Contract

Implement the repository-equivalent Invoice integration contract.

Conceptually:

```text
InvoiceIntegrationRequest
        ↓
InvoiceIntegrationResult
```

The request shall provide sufficient information to perform an external Invoice operation without requiring the adapter to access internal application state.

---

# 10. Integration Operations

The initial integration operation set shall support the operations required by the established Invoice lifecycle.

At minimum, the architecture shall support:

* create/synchronise Invoice
* update/synchronise Invoice
* cancel synchronisation where externally required
* void synchronisation where externally required

If an external system requires additional operations, they shall be introduced through the integration contract rather than through the Invoice Aggregate.

---

# 11. Accounting Integration

APP-007.7 shall establish the accounting integration boundary.

The architecture shall allow an Invoice to be synchronised to an external accounting system.

The integration may communicate:

* Invoice reference
* Invoice date
* due date
* customer information
* reservation reference
* line/financial information
* tax information where already canonically available
* currency
* total
* payment state
* cancellation state
* external references

The integration shall not calculate these values independently.

---

# 12. Accounting Provider Independence

The Invoice Capability shall not become structurally dependent on a specific accounting provider.

The canonical architecture shall be:

```text
Invoice Integration
        ↓
Accounting Port
        ↓
Accounting Adapter
        ↓
Provider
```

A provider such as QuickBooks may be implemented through the adapter boundary if and when that integration is enabled.

Provider-specific models shall remain inside the adapter boundary.

---

# 13. Provider Adapter

A provider adapter shall:

* translate canonical integration requests into provider requests
* invoke the provider
* translate provider responses into canonical integration results
* map provider errors
* return provider references
* preserve idempotency information where supported

Provider-specific DTOs must not escape the adapter boundary.

---

# 14. External Invoice Representation

Where required, define a canonical integration representation of an Invoice.

It shall be derived from the canonical Invoice state.

It must not become a second source of truth.

Conceptually:

```text
Invoice Aggregate
       ↓
Integration Mapping
       ↓
External Invoice Request
```

---

# 15. External Reference

The canonical Invoice External Reference model established by APP-007.2 shall be used to represent references returned by external systems.

Examples include:

* external Invoice ID
* accounting document number
* provider reference
* synchronisation reference

Do not introduce a duplicate external-reference model.

---

# 16. External Reference Ownership

External references belong to the integration boundary.

The integration layer may produce an external reference as part of its result.

Persistence of that reference belongs to the established application/persistence orchestration.

The adapter shall not directly mutate the Invoice Aggregate.

---

# 17. Integration Result

The Integration Result shall provide, at minimum:

* success/failure
* operation
* provider/system identifier
* external reference where available
* integration status
* error information
* retry information where applicable
* provider metadata where appropriate

The result shall be immutable.

---

# 18. Integration Status

The canonical integration status shall distinguish at least:

```text
SUCCESS
FAILED
RETRYABLE_FAILURE
REJECTED
PENDING
```

Only statuses required by the established repository architecture need to be implemented.

Do not introduce unnecessary state variants.

---

# 19. Integration Errors

Integration errors shall be mapped into canonical error categories.

At minimum, distinguish:

```text
CONFIGURATION_ERROR
AUTHENTICATION_ERROR
VALIDATION_ERROR
PROVIDER_REJECTION
NETWORK_ERROR
TIMEOUT
RATE_LIMITED
DUPLICATE_REQUEST
UNKNOWN_EXTERNAL_ERROR
```

Use existing application error conventions where available.

Provider-specific error classes must not leak outside the adapter.

---

# 20. Retry Behaviour

The Integration layer shall distinguish retryable from non-retryable failures.

Typical retryable failures include:

* network failure
* timeout
* temporary provider unavailability
* rate limiting

Typical non-retryable failures include:

* invalid credentials
* invalid Invoice data
* provider business rejection
* unsupported operation

The exact retry classification shall follow the provider contract and established application conventions.

---

# 21. Retry Boundary

APP-007.7 shall identify whether an integration result is retryable.

It shall not introduce an autonomous background retry scheduler unless an established platform infrastructure already provides one.

Conceptually:

```text
Integration Result
       ↓
retryable?
       ↓
Application / Infrastructure Retry Mechanism
```

The Invoice Integration layer provides the information required for retry.

---

# 22. Idempotency

Invoice integration operations shall be designed for idempotent execution where the external system supports idempotency.

The request shall use a stable idempotency key where appropriate.

The key should be derived from canonical operation identity rather than random values.

The same logical Invoice operation must not unintentionally create duplicate external Invoices.

---

# 23. Duplicate Handling

If the provider reports that an Invoice already exists, the adapter shall map the response into the canonical integration result.

The system must not blindly create another external Invoice.

Where the provider supports lookup by external/idempotency reference, the adapter may use the provider's canonical mechanism.

---

# 24. External State

External system state shall not replace canonical GCT Core Invoice state.

The relationship remains:

```text
GCT Core Invoice
       ↓
External Representation
```

The external system is a consumer/representation of Invoice state.

It is not the authority for:

* Invoice lifecycle
* GCT Core pricing
* cancellation rules
* payment rules
* business policy

---

# 25. Synchronisation

Invoice synchronisation shall use canonical Invoice state.

The synchronisation process must not recalculate:

* totals
* balances
* cancellation charges
* refunds
* deposits

If an external system requires a different representation, mapping occurs at the adapter boundary.

---

# 26. Payment Synchronisation

If accounting integration requires payment information, APP-007.7 may communicate canonical payment state.

It shall not execute payment transactions.

The distinction remains:

```text
Payment Execution
    ↓
APP-006

Invoice Financial Consequence
    ↓
APP-007.5

External Accounting Synchronisation
    ↓
APP-007.7
```

---

# 27. Cancellation Synchronisation

If an Invoice is cancelled, the integration layer may communicate the canonical cancellation state to an external accounting system.

It shall not calculate the cancellation consequence.

The Engine remains authoritative.

---

# 28. Void Synchronisation

If an Invoice is voided, the integration layer may communicate the canonical void state.

The external system must receive sufficient information to represent the state without requiring the adapter to make a business decision.

---

# 29. Presentation Independence

APP-007.7 may consume canonical Invoice state directly or an appropriate canonical integration model.

It shall not require:

* HTML
* PDF
* email templates
* frontend models

Presentation output from APP-007.6 is not a substitute for integration contracts.

---

# 30. Integration Mapping

Mapping shall be explicit.

Conceptually:

```text
Invoice
  ↓
Invoice Integration Mapper
  ↓
Canonical Integration Request
  ↓
Provider Adapter
  ↓
Provider Request
```

Provider mapping must remain inside the adapter.

---

# 31. No Domain Mutation

The Integration layer shall never mutate:

* Invoice Aggregate
* Invoice models
* Engine Result
* Presentation Result

If an external reference needs to become part of canonical Invoice state, the integration result shall return it to the appropriate application orchestration layer.

---

# 32. Persistence Boundary

APP-007.7 shall not directly write to persistence unless an established integration infrastructure explicitly defines that responsibility.

The preferred flow is:

```text
Invoice Integration
       ↓
Integration Result
       ↓
Application Orchestration
       ↓
Repository
```

---

# 33. Configuration

Provider configuration shall be externalised.

Do not hard-code:

* API keys
* credentials
* account identifiers
* provider URLs
* secrets
* environment-specific values

Use the established GCT Core configuration mechanism.

---

# 34. Security

External integration shall:

* protect credentials
* avoid logging secrets
* avoid logging access tokens
* avoid exposing provider credentials in errors
* use the established secure HTTP/client mechanism
* preserve appropriate request correlation information

Do not introduce a new secrets-management mechanism.

---

# 35. Observability

Integration operations should expose sufficient diagnostic information to identify:

* Invoice
* operation
* provider/system
* success/failure
* correlation/reference
* retryability

Sensitive information must not be logged.

Follow established logging and observability conventions.

---

# 36. Timeout and Failure Isolation

Provider calls shall use the established external-client timeout mechanism.

A provider failure must not corrupt canonical Invoice state.

External integration failure must be represented as an integration result or established application exception according to repository conventions.

---

# 37. Provider Availability

The Invoice Capability must remain structurally independent from provider availability.

A temporary accounting provider outage shall not invalidate the canonical Invoice Aggregate.

The external integration state may indicate:

```text
RETRYABLE_FAILURE
```

while the Invoice itself remains valid.

---

# 38. Integration Ordering

Where multiple external operations are required, ordering shall be explicit.

Do not rely on implicit execution order.

If an operation requires a previously created external reference, the integration contract shall make that dependency explicit.

---

# 39. Transaction Boundary

Do not attempt to create a distributed database/provider transaction unless an established infrastructure capability explicitly supports it.

The expected model is:

```text
Local Invoice State
       ↓
External Integration
       ↓
Integration Result
```

Failures are handled through explicit result/error/retry semantics.

---

# 57. Expected Outcome

APP-007.7 shall establish a stable and provider-independent external integration boundary for the Invoice Capability.

The fundamental responsibility is:

> **Communicate canonical Invoice outcomes to approved external systems without allowing external-system concerns to contaminate the Invoice domain or application execution model.**

The completed Invoice Capability shall therefore have a clear separation between:

```text
Business State
    ↓
Execution
    ↓
Presentation
    ↓
Integration
    ↓
External Systems
```

No provider-specific integration, business rule, persistence mechanism, Hotelbeds dependency, or frontend concern shall be introduced outside its appropriate architectural boundary.
