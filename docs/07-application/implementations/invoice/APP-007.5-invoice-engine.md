# 1. Objective

Implement the canonical **Invoice Engine** for the APP-007 Invoice Capability.

The Invoice Engine is responsible for executing permitted Invoice operations and producing the resulting Invoice Aggregate and canonical execution result.

The Engine is the execution boundary between:

```text
Validation
    ↓
Policy
    ↓
Invoice Engine
    ↓
Invoice Result
```

The Engine shall execute business operations and calculate their Invoice-side financial consequences without taking ownership of validation, policy definition, persistence, external payment execution, accounting integration, or presentation.

---

# 2. Scope

APP-007.5 includes:

* Invoice Engine
* operation dispatch
* Invoice creation execution
* Invoice issue execution
* Invoice payment application
* Invoice cancellation execution
* Invoice void execution
* Invoice financial calculations required by those operations
* Invoice balance calculation
* deposit calculation where required
* adjustment calculation
* cancellation financial calculation
* refund calculation where required by the established Invoice model
* Invoice Aggregate reconstruction
* canonical Engine result
* Engine errors
* immutable Engine results
* unit and integration-level application tests
* capability exports
* implementation report

---

# 3. Explicit Exclusions

APP-007.5 shall not implement:

* Invoice presentation
* PDF generation
* email generation
* frontend behaviour
* HTTP controllers
* HTTP routes
* database persistence
* Prisma changes
* database migrations
* payment gateway communication
* payment capture
* payment settlement
* external refund execution
* accounting integration
* QuickBooks integration
* Hotelbeds integration
* supplier communication

These responsibilities remain outside APP-007.5.

# 5. Core Responsibility

The Invoice Engine shall answer:

> Given a valid Invoice operation that has been permitted by the Invoice Policy Framework, what resulting Invoice state and financial outcome should be produced?

The Engine shall therefore:

1. accept the validated execution context
2. verify that validation succeeded
3. verify that policy permits execution
4. dispatch the operation
5. perform the required calculation
6. construct the resulting Invoice Aggregate
7. return a canonical Engine result

---

# 6. Architectural Principles

The Engine shall be:

* deterministic
* stateless
* immutable at its result boundary
* provider-independent
* persistence-independent
* testable
* operation-oriented

The Engine shall not duplicate:

* Aggregate invariants
* validation rules
* policy rules
* persistence logic
* external integration logic

Before implementation Copilot shall inspect the existing repository patterns for:

The implementation shall not introduce a competing architectural pattern merely because an alternative structure is possible.

# 9. Validation Dependency

APP-007.5 consumes the result of APP-007.3.

The Engine shall not execute an operation when validation has failed.

Conceptually:

```text
validation.success === false
        ↓
Engine Result
        ↓
No operation execution
```

The Engine shall return the established canonical validation failure representation.

The Engine shall not reimplement the Invoice Validation Pipeline.

---

# 10. Policy Dependency

APP-007.5 consumes the result of APP-007.4.

The Engine shall not execute an operation when policy evaluation results in:

* DENY
* REQUIRE_ACTION

Only a permitted operation may execute.

The Engine shall not reimplement individual policy rules.

---

# 11. Engine Contract

Implement the repository-equivalent canonical Engine contract.

The public execution boundary shall provide:

```text
Invoice Engine Request
        ↓
Invoice Engine Result
```

The request shall contain sufficient information to identify:

* operation
* Invoice where applicable
* validated execution context
* policy evaluation
* operation-specific input

The implementation shall use the repository's established request/result contract conventions where available.

---

# 12. Engine Result

The Engine Result shall provide, at minimum:

* success/failure
* executed operation
* resulting Invoice where successful
* operation outcome
* financial impact where applicable
* errors
* warnings where applicable
* execution metadata

The result shall be immutable.

Nested objects and collections shall also be protected from mutation.

Dates shall be defensively copied according to established repository conventions.

---

# 13. Engine Errors

Engine errors shall use deterministic, typed error codes.

The Engine shall distinguish at least:

```text
VALIDATION_FAILED
POLICY_DENIED
POLICY_ACTION_REQUIRED
MISSING_INVOICE
INVALID_OPERATION
INVALID_OPERATION_INPUT
CALCULATION_ERROR
```

Operation-specific financial errors shall be added where required by the existing domain/application model.

Do not create overlapping error codes where an established canonical error already exists.

---

# 14. Operation Model

The Engine shall dispatch operations using the canonical Invoice operation model.

The initial operation set shall support the operations already established by APP-007.4:

* Create
* Issue
* Payment
* Cancellation
* Void

If the existing Invoice model explicitly defines Refund as an Invoice operation, the Engine shall support it.

Copilot shall not introduce a new Invoice operation solely to support an implementation convenience.

---

# 15. Operation Isolation

Each operation shall have a focused execution responsibility.

The Engine coordinates operation execution.

Operation-specific logic shall not be placed into one large conditional service.

The implementation should preserve a structure equivalent to:

```text
InvoiceEngine
    ↓
Operation
    ↓
Calculation
    ↓
Invoice Aggregate
```

The exact class/file structure shall follow established repository conventions.

---

# 16. Create Operation

The Create operation shall:

* construct the canonical Invoice Aggregate
* use APP-007.2 models
* preserve supplied commercial references
* preserve the accepted pricing snapshot
* establish the canonical initial Invoice state
* apply canonical financial defaults
* return the resulting Invoice Aggregate

Aggregate construction shall use the existing `Invoice.create()` contract.

The Engine shall not duplicate Aggregate construction rules.

---

# 17. Create Financial Defaults

The Engine shall preserve the defaults established by APP-007.1.

Where not explicitly supplied:

```text
amountPaid = 0
balanceDue = totalAmount
refundableAmount = 0
```

The Engine shall not introduce different defaults.

---

# 18. Issue Operation

The Issue operation shall:

* operate only on a permitted Invoice
* transition the Invoice to the canonical issued state
* preserve the Invoice's commercial and financial state
* return the resulting Invoice Aggregate

Issue shall not independently modify financial values unless an established Invoice rule requires it.

The operation shall use the canonical Aggregate reconstruction mechanism.

---

# 19. Payment Operation

The Payment operation shall apply a payment allocation to the Invoice.

It shall:

* validate execution-specific payment input
* verify currency compatibility
* verify the payment amount
* create the canonical payment allocation
* preserve existing payment allocations
* calculate the resulting amount paid
* calculate the resulting balance
* determine the resulting canonical lifecycle state
* reconstruct the Invoice Aggregate

The Engine records the **Invoice-side consequence** of the payment.

It does not execute the payment.

---

# 20. Payment Constraints

The Engine shall reject invalid payment input according to established financial rules.

At minimum:

* payment amount must be positive
* payment currency must match Invoice currency
* payment must not create an invalid financial state
* duplicate payment allocation must not be silently created where the canonical payment identifier already exists

The exact duplicate-payment behaviour shall follow the established Payment/Invoice architecture.

---

# 21. Payment Financial Calculation

The Engine shall calculate the resulting financial state from the canonical Invoice financial state.

The fundamental relationship remains:

```text
amountPaid
    +
remaining balance
    =
total obligation
```

Subject to the established monetary model and adjustment rules.

The calculation must use the repository's canonical monetary representation and precision rules.

Do not introduce a second Money implementation.

---

# 22. Payment Status

The resulting Invoice lifecycle state shall follow the canonical Invoice status model.

Where the established model supports these states:

```text
ISSUED
    ↓
PARTIALLY_PAID
    ↓
PAID
```

the Engine shall apply the appropriate state based on the resulting financial position.

The Engine shall not invent additional lifecycle states.

---

# 23. Cancellation Operation

The Cancellation operation shall:

* operate only when policy permits cancellation
* validate execution-specific cancellation input
* calculate the cancellation financial consequence
* create the canonical cancellation snapshot
* create any required adjustment
* calculate the resulting refundable amount
* reconstruct the Invoice Aggregate
* transition the Invoice to the canonical cancelled state

The operation shall preserve existing financial history.

---

# 24. Cancellation Financial Calculation

Cancellation calculations shall use explicit supplied cancellation information.

The Engine shall not retrieve cancellation rules from:

* suppliers
* Hotelbeds
* databases
* external APIs

Supplier-specific cancellation information may be supplied to the Engine by a higher application layer once established by the architecture.

The Engine shall calculate the Invoice-side result from that supplied information.

---

# 25. Cancellation Business Rules

APP-007.5 shall implement only cancellation rules already established by the GCT Core business/domain model.

If required cancellation rules are not yet defined, Copilot shall report a:

```text
Business Rule Gap
```

and shall not invent commercial rules merely to complete the implementation.

---

# 26. Cancellation Snapshot

The resulting Invoice shall contain the canonical cancellation snapshot defined by APP-007.2.

The snapshot shall preserve the accepted cancellation financial outcome.

It shall not depend on future changes to external policy data.

---

# 27. Cancellation Adjustments

Where cancellation requires a financial adjustment, the Engine shall create the canonical Invoice Adjustment model.

Existing adjustments must remain preserved.

The original pricing snapshot must not be rewritten to represent the cancellation.

---

# 28. Void Operation

The Void operation shall:

* execute only when permitted
* transition the Invoice to the canonical void state
* preserve financial history
* preserve payment allocations
* preserve adjustments
* preserve cancellation information where applicable
* return the resulting Invoice Aggregate

Void shall not silently delete or reset historical financial information.

---

# 29. Refund Handling

If the established Invoice operation model includes refund execution at the Invoice level, APP-007.5 shall calculate the Invoice-side refund consequence.

The Engine shall not execute an external refund.

It may return a canonical required external action for later integration.

Actual refund execution remains outside APP-007.5.

---

# 30. Balance Calculation

Implement the Invoice balance calculation required by the Engine.

The calculation shall use the canonical Invoice financial model.

At minimum, the Engine shall be capable of determining:

```text
total obligation
amount paid
balance due
```

The calculation shall be deterministic and shall not mutate the Invoice.

---

# 31. Deposit Calculation

Where the canonical Invoice Deposit Requirement requires calculation, the Engine shall calculate the resulting deposit amount.

The calculation shall use the established deposit model and monetary conventions.

Do not introduce new deposit business rules.

If the existing model does not define a required deposit calculation sufficiently, report a Business Rule Gap.

---

# 32. Adjustment Calculation

The Engine shall calculate the financial impact of canonical Invoice adjustments.

Adjustment history must remain preserved.

The Engine shall use the existing Invoice Adjustment model rather than creating a parallel representation.

---

# 33. Refund Calculation

Where refund calculation is required by the canonical Invoice model, the Engine shall:

* validate the requested refund
* determine the refundable amount
* prevent an invalid negative result
* produce the resulting Invoice-side financial state

The Engine shall not perform external refund execution.

---

# 34. Monetary Rules

All monetary calculations shall use the established GCT Core monetary representation.

Copilot shall first identify the canonical Money/monetary arithmetic implementation.

The Engine shall not introduce:

* a second Money value object
* arbitrary floating-point financial arithmetic
* inconsistent rounding
* operation-specific precision rules

If the repository lacks a sufficient canonical monetary calculation mechanism, report the architecture gap before introducing one.

---

# 35. Currency Rules

The Engine shall not perform currency conversion.

Where an operation supplies a monetary value, its currency must be compatible with the Invoice currency according to the established model.

Currency conversion belongs outside APP-007.5.

---

# 36. Aggregate Reconstruction

The Engine shall never directly mutate an existing Invoice Aggregate.

For an existing Invoice:

```text
Existing Invoice
       ↓
Calculate resulting state
       ↓
Canonical Aggregate reconstruction
       ↓
New Invoice Aggregate
```

Use the existing `Invoice.restore()` or equivalent canonical reconstruction mechanism.

---

# 37. Aggregate Invariants

Invoice invariants remain owned by the Invoice Aggregate.

The Engine shall not duplicate invariant enforcement.

The Engine shall use:

```text
Invoice.create()
Invoice.restore()
```

or their established equivalents.

---

# 38. State Preservation

Operations shall preserve unchanged Invoice state.

Unless explicitly affected by the operation, preserve:

* Invoice identity
* Reservation reference
* Customer reference
* Quote reference
* Pricing snapshot
* financial obligation
* payment history
* adjustment history
* external references
* metadata

---

# 39. Immutability

The Engine shall preserve the immutability guarantees established by APP-007.1 and APP-007.2.

The implementation shall not mutate:

* input Invoice
* canonical model instances
* validation results
* policy results
* operation input

Results shall be immutable.

---

# 40. Determinism

Given identical:

* Invoice state
* operation
* validated context
* policy result
* operation input

the Engine shall produce the same logical outcome.

Execution timestamps may vary according to the established metadata convention.

No random or environment-dependent financial behaviour is permitted.

---

# 41. External Side Effects

APP-007.5 shall not perform external side effects.

Specifically, the Engine shall not:

* write to the database
* call payment providers
* call accounting systems
* call Hotelbeds
* send email
* generate documents
* call HTTP endpoints

The Engine produces the resulting application state.

Persistence and integration occur elsewhere.

---

# 42. Persistence Boundary

The expected application flow is:

```text
Application Orchestration
        ↓
Invoice Engine
        ↓
Invoice Aggregate
        ↓
Repository / Persistence
```

The Engine shall not own repository interaction.

---

# 43. Payment Boundary

The distinction between APP-006 and APP-007.5 remains:

```text
APP-006 Payments
Payment execution

APP-007.5 Invoice Engine
Invoice-side financial consequence
```

The Invoice Engine must not absorb payment-provider responsibilities.

---

# 44. Accounting Boundary

The Engine may identify that an accounting action is required.

It shall not perform accounting synchronisation.

Accounting integration belongs to APP-007.7.

---

# 45. Presentation Boundary

The Engine shall return canonical application results.

It shall not produce:

* HTML
* PDF
* email content
* UI DTOs
* presentation-specific formatting

APP-007.6 owns presentation.

---

# 46. Error Behaviour

Normal business failures shall be represented by the canonical Engine Result rather than thrown as unexpected exceptions.

Examples include:

* validation failure
* policy denial
* missing Invoice
* invalid operation
* invalid payment
* invalid financial input
* calculation failure

Unexpected programming/infrastructure failures shall follow the established application exception strategy.
