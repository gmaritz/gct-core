# 1. Objective

Implement the canonical **Invoice Validation Pipeline** for APP-007.

The pipeline validates Invoice requests and Invoice financial state before they proceed to Invoice policy evaluation or the Invoice Engine.

Validation shall determine whether the supplied Invoice context is:

* structurally complete
* referentially coherent
* commercially consistent
* financially internally consistent
* sufficiently complete for the requested Invoice operation

Validation shall remain:

* deterministic
* stateless
* immutable
* provider-independent
* accounting-independent
* presentation-independent

Validation shall never perform:

* financial calculation
* lifecycle policy evaluation
* payment execution
* accounting communication
* provider communication

# 5. Validation Responsibility

Validation answers:

> Can this Invoice request or Invoice state safely proceed to the next application stage?

Validation may identify invalid commercial or financial state.

Validation must not determine whether an operation is **permitted by policy**.

For example:

```text
Validation:
"Invoice status is CANCELLED."

Policy:
"Can a CANCELLED invoice be changed?"
```

The first belongs to APP-007.3.

The second belongs to APP-007.4.

# 12. Validation Request

Implement the canonical validation request:

```typescript
export interface InvoiceReservationContext {
  readonly exists?: boolean;
  readonly status?: string;
}

export interface InvoiceValidationRequest {
  readonly invoice?: Invoice | null;

  readonly reservationReference?: InvoiceReservationReference | null;

  readonly customerReference?: InvoiceCustomerReference | null;

  readonly quoteReference?: InvoiceQuoteReference | null;

  readonly pricingSnapshot?: InvoicePricingSnapshot | null;

  readonly financialObligation?: InvoiceFinancialObligation | null;

  readonly reservationContext?: InvoiceReservationContext | null;
}
```

The request shall be extended only where required by the established application architecture.

The request represents the context required for Invoice validation.

It does not represent an HTTP DTO.

It does not represent a persistence record.

The validation request must allow validation of:

* a new Invoice construction context
* an existing Invoice Aggregate
* an Invoice before engine execution
* an Invoice before a later policy operation

The pipeline must not require a live external system.

Context required from other capabilities shall be supplied explicitly.

# 14. Invoice Request Validator

Implement:

```typescript
InvoiceRequestValidator
```

The validator shall validate request completeness and structural correctness.

Responsibilities:

* request exists
* Invoice identifier available when validating an existing Invoice
* reservation reference supplied
* customer/traveller reference supplied
* quote reference supplied
* pricing snapshot supplied
* financial obligation supplied

The validator shall not validate:

* reservation state
* pricing commercial consistency
* financial calculations
* lifecycle policy

---

# 15. Request Validation Rules

The Invoice Request Validator shall identify:

### Missing Request

```text
MISSING_REQUEST
```

when the request is null or undefined.

### Missing Invoice Identifier

```text
MISSING_INVOICE_IDENTIFIER
```

when an existing Invoice is expected but the Invoice identity is missing or blank.

### Missing Reservation Reference

```text
MISSING_RESERVATION_REFERENCE
```

when the reservation reference is absent.

### Missing Customer Reference

```text
MISSING_CUSTOMER_REFERENCE
```

when both customer and traveller references are absent.

### Missing Quote Reference

```text
MISSING_QUOTE_REFERENCE
```

when the quote reference is absent.

### Missing Pricing Snapshot

```text
MISSING_PRICING_SNAPSHOT
```

when the pricing snapshot is absent.

### Missing Financial Obligation

```text
MISSING_FINANCIAL_OBLIGATION
```

when the financial obligation is absent.

All such failures are:

```text
CRITICAL
```

---

# 16. Blank Value Handling

Use the established blank-string convention.

For example:

```typescript
function isBlank(value: unknown): boolean {
  return typeof value !== "string" || value.trim().length === 0;
}
```

The validator shall not silently trim and replace supplied values.

A blank required value is invalid.

```typescript
ReservationValidator
```

Responsibilities:

* validate Reservation existence context
* validate Reservation lifecycle state relevant to Invoice creation
* validate that a cancelled Reservation cannot create a new financial obligation
* validate Reservation reference consistency

The validator shall not:

* retrieve a Reservation

* call an API
* modify a Reservation
* determine Invoice lifecycle policy

---

# 18. Reservation Validation Rules

If the reservation context indicates:

```text
exists = false
```

return:

```text
MISSING_RESERVATION
```

as a critical error.

If the reservation status is:

```text
CANCELLED
```

return:

```text
RESERVATION_CANCELLED
```

as a critical error for creation/readiness validation.

If the Reservation exists but is not in a state suitable for financial obligation creation, return:

```text
RESERVATION_NOT_CONFIRMED
```

as a critical error.

The exact supported Reservation status values shall follow the existing Reservation capability model.

Do not introduce a duplicate Reservation lifecycle enumeration.

---

# 19. Reservation Reference Consistency

Where both are available:

```text
InvoiceReservationReference.reservationId
```

and:

```text
InvoiceReservationContext
```

must refer to the same Reservation.

The validator must not attempt to resolve the reference externally.

CommercialValidator

Responsibilities:

* validate relationship between accepted quotation and Invoice
* validate pricing snapshot identity
* validate pricing currency consistency
* validate commercial snapshot completeness
* validate that the Invoice's commercial references are coherent

The validator shall not calculate pricing.

---

# 21. Quote Validation

The Commercial Validator shall verify:

* quote reference exists
* quote ID is non-blank
* quote version is non-blank
* Invoice references an accepted quote context where supplied
* quote reference is internally consistent

The validator shall not:

* retrieve the quotation
* recalculate the quotation
* change the quotation
* evaluate quotation policy

---

# 22. Pricing Validation

The Commercial Validator shall verify:

* pricing snapshot exists
* pricing ID is present
* pricing snapshot ID is present
* pricing version is present
* pricing currency is present
* pricing total is finite
* pricing total is non-negative
* pricing currency agrees with the financial obligation currency

The validator shall not calculate the pricing total.

---

# 23. Pricing Total Consistency

Where the Invoice Aggregate contains both:

```text
financialObligation.totalAmount
```

and:

```text
pricingSnapshot.totalAmount
```

the Commercial Validator shall verify that they are consistent.

If they differ, return:

```text
PRICING_TOTAL_MISMATCH
```

as a critical error.

This is an integrity check.

It is not a pricing calculation.

---

# 24. Pricing Currency Consistency

The following must agree:

```text
pricingSnapshot.currency
financialObligation.currency
```

If they differ, return:

```text
PRICING_CURRENCY_MISMATCH
```

as a critical error.

The validator shall not perform currency conversion.

---

# 25. Quote Reference Consistency

Where the validation context supplies a canonical quotation reference, compare:

```text
InvoiceQuoteReference.quoteId
InvoiceQuoteReference.quoteVersion
```

with the expected context.

If inconsistent, return:

```text
QUOTE_REFERENCE_INCONSISTENT
```

as a critical error.

Do not retrieve the quote.

# 27. Financial Value Validation

Validate:

```text
totalAmount
amountPaid
balanceDue
refundableAmount
```

Each must be:

* numeric
* finite
* non-negative

Return:

```text
INVALID_TOTAL_AMOUNT
INVALID_AMOUNT_PAID
INVALID_BALANCE_DUE
INVALID_REFUNDABLE_AMOUNT
```

as appropriate.

---

# 28. Balance Validation Boundary

The validator shall **not** calculate:

```text
balanceDue =
totalAmount
- payments
+ adjustments
- refunds
```

That calculation belongs to APP-007.5.

However, the validator may identify structurally impossible state.

For example:

```text
balanceDue < 0
```

is invalid.

Similarly:

```text
amountPaid < 0
```

is invalid.

This distinction is mandatory.

---

# 29. Payment Allocation Validation

For each:

```text
InvoicePaymentAllocation
```

validate:

* payment ID exists
* allocated amount is numeric
* allocated amount is finite
* allocated amount is greater than zero
* allocatedAt is valid
* optional external reference is non-blank when supplied

Return:

```text
INVALID_PAYMENT_ALLOCATION
```

for invalid allocation structure.

The validator shall not:

* retrieve Payment Aggregates
* execute payments
* allocate payment amounts
* recalculate amount paid

---

# 30. Payment Allocation Total Consistency

The validator may verify that the aggregate's supplied:

```text
amountPaid
```

is not structurally inconsistent with its payment allocation state.

If payment allocations exist and their supplied total cannot be reconciled with the authoritative `amountPaid`, return:

```text
PAYMENT_ALLOCATION_TOTAL_MISMATCH
```

as a critical error.

This validation must **not** become a financial calculation engine.

The validator may sum supplied allocations solely to detect an internal inconsistency.

It shall not derive or replace the authoritative financial state.

---

# 31. Deposit Requirement Validation

If a deposit requirement exists:

### Fixed

Validate:

```text
value >= 0
value is finite
```

### Percentage

Validate:

```text
0 <= value <= 100
value is finite
```

If invalid, return:

```text
INVALID_DEPOSIT_REQUIREMENT
```

The validator shall not calculate the actual deposit amount.

---

# 32. Adjustment Validation

* ID exists
* type exists
* amount is finite
* reason exists
* appliedAt is valid

Invalid adjustment state returns:

```text
INVALID_ADJUSTMENT
```

* cancellation charge is non-negative

* refundable amount is non-negative

INVALID_CANCELLATION_SNAPSHOT

INVALID_EXTERNAL_REFERENCE

# 37. Lifecycle Readiness Validator

Implement:

```typescript
LifecycleReadinessValidator
```

Responsibilities:

* validate Invoice status is recognised
* identify structurally invalid lifecycle state
* validate that the Invoice is not already terminal where the requested validation context requires further processing

The validator shall **not** decide whether a lifecycle transition is allowed.

---

# 38. Lifecycle Policy Boundary

The distinction is:

```text
APP-007.3
LifecycleReadinessValidator

"Is the current Invoice lifecycle state structurally valid
for continued processing?"
```

versus:

```text
APP-007.4
Invoice Policy Framework

"Is this requested lifecycle transition permitted?"
```

APP-007.3 must not implement transition rules.

---

# 39. Lifecycle Validation

Validate that:

```text
Invoice.status
```

is one of:

```text
DRAFT
ISSUED
PARTIALLY_PAID
PAID
OVERDUE
CANCELLED
VOID
```

An unsupported state returns:

```text
INVALID_INVOICE_STATUS
```

as a critical error.

---

# 40. Terminal State Readiness

Where the validation request represents an operation requiring a mutable/readiness state, a terminal Invoice may produce:

```text
INVOICE_ALREADY_VOID
```

or:

```text
INVOICE_ALREADY_CANCELLED
```

as appropriate.

The validator must not determine whether the requested operation is legally or commercially permitted.

That remains APP-007.4.

---

# 41. No Policy Evaluation

The following logic is explicitly prohibited in APP-007.3:

```text
if status === ISSUED
    allow payment

if status === PAID
    reject cancellation

if status === CANCELLED
    allow refund

if status === DRAFT
    allow issue
```

These are policy decisions.

APP-007.4 owns them.

# 42. Validation Pipeline

Create:

```typescript
InvoiceValidationPipeline
```

Responsibilities:

* execute validators in deterministic order
* aggregate validation results
* stop on critical failures
* return immutable `InvoiceValidationResult`

Validators shall be constructor injected.

---

# 43. Constructor Injection

The pipeline constructor shall receive:

```typescript
InvoiceRequestValidator
ReservationValidator
CommercialValidator
FinancialIntegrityValidator
LifecycleReadinessValidator
```

Example:

```typescript
export class InvoiceValidationPipeline {
  public constructor(
    private readonly requestValidator: InvoiceRequestValidator,
    private readonly reservationValidator: ReservationValidator,
    private readonly commercialValidator: CommercialValidator,
    private readonly financialIntegrityValidator: FinancialIntegrityValidator,
    private readonly lifecycleReadinessValidator: LifecycleReadinessValidator,
  ) {}
}
```

The exact syntax may follow the repository's established implementation convention.

No validator may instantiate another validator.

---

# 44. Pipeline Execution Order

The pipeline shall execute:

```text
1. REQUEST

2. RESERVATION

3. COMMERCIAL

4. FINANCIAL_INTEGRITY

5. LIFECYCLE_READINESS
```

This order is mandatory.

---

# 45. Pipeline Execution

Conceptually:

```typescript
const requestResult =
  requestValidator.validate(request);

if (hasCriticalErrors(requestResult.errors)) {
  return aggregateResult(
    InvoiceValidationStage.REQUEST,
    [requestResult],
  );
}

const reservationResult =
  reservationValidator.validate(request);

if (hasCriticalErrors(reservationResult.errors)) {
  return aggregateResult(
    InvoiceValidationStage.RESERVATION,
    [requestResult, reservationResult],
  );
}

const commercialResult =
  commercialValidator.validate(request);

if (hasCriticalErrors(commercialResult.errors)) {
  return aggregateResult(
    InvoiceValidationStage.COMMERCIAL,
    [
      requestResult,
      reservationResult,
      commercialResult,
    ],
  );
}

const financialResult =
  financialIntegrityValidator.validate(request);

if (hasCriticalErrors(financialResult.errors)) {
  return aggregateResult(
    InvoiceValidationStage.FINANCIAL_INTEGRITY,
    [
      requestResult,
      reservationResult,
      commercialResult,
      financialResult,
    ],
  );
}

const lifecycleResult =
  lifecycleReadinessValidator.validate(request);

return aggregateResult(
  InvoiceValidationStage.LIFECYCLE_READINESS,
  [
    requestResult,
    reservationResult,
    commercialResult,
    financialResult,
    lifecycleResult,
  ],
);
```

The exact implementation may differ while preserving the same behaviour.

---

# 46. Critical Fail-Fast

The pipeline shall stop when a validator returns one or more:

```text
CRITICAL
```

errors.

Subsequent validators shall not execute.

Warnings do not cause short-circuiting.

For example:

```text
REQUEST
   │
   └── CRITICAL
          ↓
       STOP
```

No Reservation, Commercial, Financial or Lifecycle validators should execute after that failure.

---

# 47. Warning Behaviour

Warnings may be returned where the state is usable but deserves attention.

Warnings must not cause the pipeline to fail.

Warnings shall be immutable.

Warnings must not replace critical errors.

Do not invent warning rules without a concrete architectural requirement.

The initial APP-007.3 implementation should prefer deterministic critical validation over speculative warnings.

---

# 48. Aggregated Result

The pipeline shall aggregate:

* errors from executed stages
* warnings from executed stages

The returned result shall use the stage at which execution stopped, or:

```text
LIFECYCLE_READINESS
```

when all stages execute.

Example:

```typescript
createInvoiceValidationResult({
  stage,
  errors: stageResults.flatMap(
    result => result.errors,
  ),
  warnings: stageResults.flatMap(
    result => result.warnings,
  ),
  metadata: {
    validatedAt: new Date(),
    version: "1.0.0",
    source: "InvoiceValidationPipeline",
  },
});
```

---

# 49. Validation Result Immutability

The result must be immutable.

The following must be frozen:

* result
* errors array
* error objects
* warnings array
* metadata object

Dates must be defensively cloned.

The caller must not be able to mutate the validation result.

---

# 50. Validator Statelessness

All Invoice validators shall be stateless.

Validators must not retain:

* Invoice state
* Reservation state
* Payment state
* mutable request state
* previous validation results

Validators may receive all required context through `validate()`.

---

# 51. Provider Independence

Validators shall not call:

* Hotelbeds
* payment gateways
* QuickBooks
* accounting systems
* external APIs
* supplier APIs

If external information is required, it must be supplied as explicit validation context.

---

# 52. Persistence Independence

Validators shall not access:

* Prisma
* repositories
* database clients
* persistence adapters

Validation is performed against supplied application context.

Persistence orchestration belongs elsewhere.

---

* execute Payments
* refund Payments

InvoiceExternalReference

# 56. Aggregate Validation Boundary

The Invoice Aggregate already enforces construction invariants.

APP-007.3 is the application-level validation layer.

Therefore:

```text
Aggregate
    ↓
Protects its own invariants

Validation Pipeline
    ↓
Determines whether application input/context
is sufficiently valid to proceed
```

Do not duplicate every aggregate invariant unnecessarily.

Where an aggregate cannot exist because construction already rejects invalid state, the validation pipeline should focus on application-level readiness and cross-model consistency.
