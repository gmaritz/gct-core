# 1. Objective

Implement the canonical **Invoice Aggregate** for APP-007.

The Invoice Aggregate represents the immutable commercial financial obligation created for a reservation.

It establishes the aggregate root for the Invoice Capability and owns the financial obligation state required throughout the invoice lifecycle.

The aggregate shall preserve the commercial state required to determine:

* what the client owes
* why the client owes it
* the reservation to which the obligation belongs
* the accepted commercial pricing basis
* the invoice lifecycle state
* the payment allocation state
* the outstanding balance
* applicable due dates
* deposit requirements
* financial adjustments
* cancellation financial consequences
* refundable amounts
* external financial references

The aggregate shall remain independent of:

* payment gateway providers
* accounting systems
* QuickBooks
* presentation
* persistence
* validation pipelines
* policy evaluation
* invoice calculation engines
* external APIs

# 3. Architectural Position

APP-007 sits between Reservation/Pricing and Payments.

The canonical commercial relationship is:

```text
APP-005 Pricing
       │
       ▼
Accepted Quote
       │
       ▼
APP-004 Reservation
       │
       ▼
APP-007 Invoice
       │
       ├────────────────┐
       │                │
       ▼                ▼
APP-006 Payments    Accounting
```

The Invoice Aggregate represents the **financial obligation**.

The Payment capability represents **actual money movement**.

Therefore:

```text
Invoice
"What does the client owe?"

        ↓

Payment
"What did the client actually pay?"
```

The Invoice Aggregate must not execute payment operations.

# 7. Invoice Identity

Introduce an aggregate-local identity contract:

```typescript
export interface InvoiceIdentity {
  readonly id: string;
}
```

The identity shall be immutable.

The identity must not be regenerated during restoration.

The identity shall never change during the invoice lifecycle.

The Invoice Model Library introduced by APP-007.2 may replace this local contract with the canonical shared model.

---

# 8. Invoice Status

Introduce the initial canonical invoice lifecycle status:

```typescript
export enum InvoiceStatus {
  DRAFT = "DRAFT",
  ISSUED = "ISSUED",
  PARTIALLY_PAID = "PARTIALLY_PAID",
  PAID = "PAID",
  OVERDUE = "OVERDUE",
  CANCELLED = "CANCELLED",
  VOID = "VOID",
}
```

The aggregate shall expose the invoice status concept only.

The aggregate shall **not** implement lifecycle transition rules.

Lifecycle transition rules belong to:

```text
APP-007.4 Invoice Policy Framework
```

The aggregate must therefore permit construction/restoration of valid persisted statuses without embedding lifecycle policy logic.

---

# 9. Financial Obligation

Introduce an aggregate-local immutable financial obligation contract:

```typescript
export interface InvoiceFinancialObligation {
  readonly totalAmount: number;
  readonly currency: string;
}
```

The financial obligation represents the total commercial amount owed.

Requirements:

* `totalAmount` must be finite
* `totalAmount` must not be negative
* `currency` must be non-blank

The aggregate shall not perform currency conversion.

The aggregate shall not calculate the total.

The amount supplied to the aggregate is authoritative for that aggregate instance.

APP-007.2 may replace this local contract with the canonical Invoice Model Library.

# 10. Pricing Snapshot

The Invoice Aggregate must preserve the accepted commercial pricing basis.

Introduce a minimal immutable snapshot contract:

```typescript
export interface InvoicePricingSnapshot {
  readonly snapshotId: string;
  readonly pricingId: string;
  readonly capturedAt: Date;
  readonly version: string;
  readonly currency: string;
  readonly totalAmount: number;
}
```

The snapshot must preserve the accepted pricing identity and commercial total.

Requirements:

* snapshot ID required
* pricing ID required
* captured timestamp required
* version required
* currency required
* total amount finite
* total amount non-negative

The aggregate must defensively clone `capturedAt`.

The aggregate must not retain a mutable reference supplied by the caller.

The aggregate must not reference the live Pricing Aggregate.

The invoice is based on a historical pricing snapshot.

---

# 11. Reservation Reference

The aggregate must retain the Reservation to which the obligation belongs.

Introduce:

```typescript
export interface InvoiceReservationReference {
  readonly reservationId: string;
}
```

The reservation reference is immutable.

The aggregate must not hold a live Reservation Aggregate reference.

The relationship is historical and referential.

# 12. Customer / Traveller Reference

The aggregate must identify the commercial customer/traveller associated with the obligation.

Introduce:

```typescript
export interface InvoiceCustomerReference {
  readonly customerId?: string;
  readonly travellerId?: string;
}
```

At least one identifier must be supplied.

This deliberately supports the current GCT Core model while allowing future customer/account structures.

The aggregate shall not create a new Customer or Traveller model.

The aggregate shall not depend upon a Customer capability.

---

# 13. Accepted Quote Reference

The financial obligation originates from an accepted quotation.

Introduce:

```typescript
export interface InvoiceQuoteReference {
  readonly quoteId: string;
  readonly quoteVersion: string;
}
```

Both values are required.

The reference must identify the exact accepted commercial quotation version used as the basis of the reservation.

The aggregate shall not reference a live quotation.

---

# 14. Deposit Requirement

The aggregate must support a deposit requirement.

Introduce:

```typescript
export interface InvoiceDepositRequirement {
  readonly type: "FIXED" | "PERCENTAGE";
  readonly value: number;
}
```

Rules:

* `type` is required
* `value` must be finite
* `value` must not be negative
* for `FIXED`, value represents an amount in the invoice currency
* for `PERCENTAGE`, value represents a percentage from `0` to `100`

The aggregate shall preserve the supplied requirement.

The aggregate shall not calculate the deposit amount.

Deposit calculation belongs to:

```text
APP-007.5 Invoice Engine
```

---

# 15. Payment Allocation Snapshot

The Invoice Aggregate must preserve the financial relationship between the obligation and payments without owning payment execution.

Introduce:

```typescript
export interface InvoicePaymentAllocation {
  readonly paymentId: string;
  readonly allocatedAmount: number;
  readonly allocatedAt: Date;
  readonly externalReference?: string;
}
```

Rules:

* payment ID required
* allocated amount must be finite
* allocated amount must be greater than zero
* allocated timestamp required
* external reference optional
* timestamp must be defensively cloned

The allocation is a snapshot/reference to payment activity.

APP-006 remains the owner of actual payment transactions.

APP-007 owns the allocation of payment value against the invoice obligation.

The aggregate shall not execute or modify a Payment Aggregate.

---

# 17. Cancellation Financial Snapshot

The aggregate must preserve cancellation-related financial consequences.

Introduce:

```typescript
export interface InvoiceCancellationSnapshot {
  readonly policyReference: string;
  readonly policyVersion?: string;
  readonly effectiveFrom?: Date;
  readonly effectiveTo?: Date;
  readonly cancellationDate: Date;
  readonly cancellationCharge: number;
  readonly refundableAmount: number;
}
```

Requirements:

* policy reference required
* cancellation date required
* cancellation charge finite and non-negative
* refundable amount finite and non-negative
* optional dates defensively cloned

This is a historical snapshot.

The aggregate must not evaluate the cancellation policy.

The aggregate must not call a supplier or policy service.

APP-007.4 determines cancellation policy outcomes.

APP-007.5 determines resulting financial calculations.

APP-006 executes an eventual refund.

# 21. Financial State Defaults

The aggregate may expose:

```typescript
public readonly amountPaid: number;
public readonly balanceDue: number;
public readonly refundableAmount: number;
```

Defaults:

```text
amountPaid = 0
balanceDue = financialObligation.totalAmount
refundableAmount = 0
```

However, these values are snapshots supplied to the aggregate.

The aggregate shall not perform financial calculation.

The purpose of these fields is to preserve authoritative aggregate state.

APP-007.5 Invoice Engine will later calculate these values.

---

# 22. Due Date

The aggregate may contain:

```typescript
readonly dueDate?: Date;
```

If supplied:

* the value must represent a valid date
* the date must be defensively copied
* the exposed value must not allow mutation of aggregate state

The aggregate shall not determine whether an invoice is overdue.

Overdue determination belongs to the Invoice Policy Framework.

---

# 23. Balance Constraint

The aggregate must reject invalid negative financial state.

Construction shall fail if:

```text
amountPaid < 0
```

or:

```text
balanceDue < 0
```

or:

```text
refundableAmount < 0
```

The aggregate must also reject non-finite monetary values.

The aggregate must not silently clamp values.

Invalid financial state must fail fast.

---

# 24. Financial Consistency

The aggregate shall enforce only structural financial consistency.

It shall not introduce calculation logic.

The following must hold:

```text
totalAmount >= 0
amountPaid >= 0
balanceDue >= 0
refundableAmount >= 0
```

The aggregate shall **not** enforce:

```text
balanceDue = totalAmount - amountPaid
```

because the eventual relationship may include:

* payment allocations
* financial adjustments
* refunds
* cancellation outcomes
* policy effects

Those calculations belong to the Invoice Engine.

---

# 25. Payment Allocation Consistency

The aggregate shall ensure:

* every payment allocation has a valid payment ID
* every allocated amount is positive
* every allocation timestamp is valid

It shall not calculate the sum of allocations.

It shall not automatically derive `amountPaid`.

The supplied `amountPaid` represents the current aggregate state.

---

# 26. Immutability

The Invoice Aggregate must be immutable by design.

Requirements:

* `readonly` public properties
* frozen aggregate instance
* frozen collections
* defensive copying
* cloned `Date` instances
* frozen nested objects
* no mutable references escaping the aggregate

The implementation must follow the established patterns already used by:

* Reservation
* Pricing
* Payment

---

# 27. Defensive Copying

All nested objects must be copied before exposure.

Dates must be cloned:

```typescript
new Date(value.getTime())
```

Collections must be copied and frozen.

For example:

```typescript
Object.freeze(items.map(item => ...))
```

Nested objects must be frozen.

The caller must not be able to mutate aggregate state through an original input reference.

The caller must not be able to mutate aggregate state through an exposed reference.

---

# 28. Aggregate Construction

Provide:

```typescript
Invoice.create(composition)
```

The method shall:

1. validate construction invariants
2. create immutable internal state
3. defensively copy nested objects
4. freeze collections
5. freeze the aggregate
6. return the Invoice Aggregate

The constructor shall remain private.

---

# 29. Aggregate Restoration

Provide:

```typescript
Invoice.restore(composition)
```

The method shall:

1. validate structural invariants
2. recreate the immutable aggregate
3. preserve supplied lifecycle state
4. preserve supplied financial state
5. avoid recalculation
6. avoid policy evaluation
7. avoid external communication

Restoration must not mutate or reinterpret persisted values.

# 33. Relationship With APP-005 Pricing

The Invoice Aggregate must preserve the accepted Pricing outcome through:

```text
InvoicePricingSnapshot
```

It must not reference the live Pricing Aggregate.

The relationship is:

```text
APP-005 Pricing
       │
       ▼
Accepted Pricing
       │
       ▼
Pricing Snapshot
       │
       ▼
APP-007 Invoice
```

The snapshot represents historical commercial truth for the invoice.

The Invoice Aggregate must therefore remain valid even if the original Pricing Aggregate subsequently changes.

---

# 34. Relationship With APP-004 Reservation

The Invoice Aggregate must retain:

```text

```

The relationship is:

```text
APP-004 Reservation
       │
       ▼
Reservation Reference
       │
       ▼
APP-007 Invoice
```

The invoice is associated with the reservation but owns its own financial state.

---

# 35. Relationship With APP-006 Payments

APP-007 Invoice

       │

* payment execution

* capture

* refunds

APP-007 remains responsible for:

* amount owed
* payment allocation
* balance state
* cancellation financial consequence

# 49. Error Handling

Invalid aggregate construction must fail deterministically.

Use the existing GCT Core domain/application exception convention.

Do not introduce a new exception hierarchy for Invoice unless an existing approved convention requires a capability-specific exception.

Errors shall identify the violated invariant sufficiently for unit tests and implementation diagnostics.

Do not silently:

* coerce invalid values
* clamp negative amounts
* replace invalid dates
* generate missing identifiers
* infer missing references
* recalculate supplied financial state

Invalid input must fail fast.

---

# 50. Date Handling

All date values shall be treated as immutable snapshots.

For every supplied `Date`:

1. validate that it represents a valid date
2. create a defensive copy
3. never retain the caller's original reference
4. never expose the internal reference directly

For example:

```typescript
const copiedDate = new Date(sourceDate.getTime());
```

When exposing the date, return another defensive copy if required by the established aggregate pattern.

---

# 51. Collection Handling

All supplied arrays shall be copied.

For example:

```typescript
const copiedItems = sourceItems.map(item => cloneItem(item));
```

The resulting collection shall be immutable.

The aggregate shall not retain a caller-owned array.

The aggregate shall not expose a mutable internal array.

Empty optional collections shall use an immutable empty collection.

---
