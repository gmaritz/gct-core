# 1. Objective

Implement the canonical **Invoice Presentation Pipeline** for the APP-007 Invoice Capability.

The Presentation Pipeline converts canonical Invoice application results into stable, presentation-ready models for consumers such as:

* invoice screens
* invoice detail views
* invoice summaries
* customer-facing invoice documents
* email presentation
* PDF generation
* future frontend clients

The Presentation Pipeline shall contain presentation transformation only.

It shall not own:

* Invoice business rules
* financial calculations
* Invoice lifecycle decisions
* policy evaluation
* persistence
* payment execution
* accounting integration
* Hotelbeds integration

---

# 2. Scope

APP-007.6 includes:

* Invoice presentation pipeline
* presentation context
* presentation result
* Invoice presentation model
* Invoice summary model
* Invoice line/presentation item model where required by the canonical Invoice model
* payment presentation model
* adjustment presentation model
* cancellation presentation model
* presentation metadata
* deterministic mapping from canonical Invoice state
* presentation formatting rules
* immutable presentation results
* tests
* public exports
* implementation report

---

# 3. Explicit Exclusions

APP-007.6 shall not implement:

* Invoice business calculations
* tax calculation
* payment calculation
* cancellation calculation
* refund calculation
* policy evaluation
* validation
* Invoice Aggregate mutation
* database queries
* Prisma
* payment gateway communication
* accounting integration
* QuickBooks integration
* Hotelbeds integration
* email delivery
* PDF generation engine
* frontend components
* HTTP routes

Presentation adapters may consume the output of APP-007.6, but those concerns remain outside this milestone.

# 5. Core Responsibility

The Presentation Pipeline shall answer:

> How should the canonical Invoice result be represented for presentation without changing its meaning?

The Pipeline shall:

1. receive canonical Invoice state or Engine result
2. map canonical data into presentation models
3. apply presentation-only formatting
4. preserve financial meaning
5. preserve lifecycle meaning
6. return immutable presentation output

---

# 6. Architectural Principles

The Presentation Pipeline shall be:

* deterministic
* read-only
* immutable
* provider-independent
* persistence-independent
* presentation-oriented
* reusable by multiple consumers

It shall not mutate the Invoice Aggregate or Engine Result.

---

Before implementation Copilot shall inspect existing GCT Core patterns for:

* View Models
* DTOs
* presentation/application mappers
* response models
* formatting utilities
* date/number formatting
* frontend-facing contracts
* document presentation structures

APP-007.6 shall follow established conventions wherever they exist.

Do not introduce a competing presentation architecture.

# 8. Input Boundary

The Presentation Pipeline shall consume canonical application/domain output.

Primary inputs shall be:

```text
Invoice Aggregate
```

and, where appropriate:

```text
InvoiceEngineResult
```

The Pipeline shall not retrieve Invoice data directly from repositories.

It shall not perform its own persistence lookup.

---

# 9. Presentation Pipeline Contract

Implement the repository-equivalent presentation contract.

Conceptually:

```text
InvoicePresentationRequest
        ↓
InvoicePresentationResult
```

The request shall identify the canonical Invoice/application result being presented and any explicitly supported presentation context.

The implementation shall follow existing application presentation conventions.

---

# 10. Presentation Result

The presentation result shall provide:

* success/failure
* canonical presentation model where successful
* presentation errors where applicable
* presentation metadata where required

The result shall be immutable.

---

# 11. Invoice Presentation Model

Implement the canonical presentation model required to represent an Invoice.

It shall expose presentation-ready representations of the established Invoice information, including where applicable:

* Invoice identity/reference
* Invoice status
* reservation reference
* customer information
* invoice dates
* due date
* pricing information
* financial totals
* amount paid
* balance due
* deposit information
* adjustments
* cancellation information
* payment allocations
* external references where appropriate

The model must not expose internal implementation details unnecessarily.

---

# 12. Presentation Model Boundary

The Presentation Model is not a replacement for the Invoice Aggregate.

The distinction is:

```text
Invoice Aggregate
Business state and invariants

Presentation Model
Representation of business state
for a presentation consumer
```

The Presentation Model must never become the source of truth for Invoice state.

---

# 13. Financial Representation

The Presentation Pipeline may format canonical financial values for display.

It shall not calculate new financial outcomes.

For example, it may transform:

```text
Money
```

into:

```text
"R 10,000.00"
```

where the presentation context requires it.

It shall not independently calculate:

```text
total - paid = balance
```

The Engine remains authoritative for financial calculations.

---

# 14. Monetary Formatting

All monetary formatting shall use the established GCT Core monetary conventions.

The Pipeline shall preserve:

* amount
* currency
* precision
* sign

The Pipeline must not introduce a new financial arithmetic implementation.

---

# 15. Currency Display

Presentation output may include:

* currency code
* currency symbol
* formatted amount

The mapping must be deterministic.

Currency conversion is explicitly prohibited.

---

# 16. Invoice Status Presentation

The Pipeline may map canonical Invoice statuses to presentation labels.

For example:

```text
DRAFT
ISSUED
PARTIALLY_PAID
PAID
CANCELLED
VOID
```

The canonical status remains authoritative.

Presentation labels must not introduce new lifecycle states.

---

# 17. Status Formatting

Presentation labels may be human-readable.

For example:

```text
PARTIALLY_PAID
```

may become:

```text
Partially Paid
```

This is presentation formatting only.

The underlying canonical status must remain available where required by the consumer contract.

---

# 18. Date Presentation

The Pipeline may format canonical dates for presentation.

It shall use the established GCT Core date/time conventions.

It must not change the semantic date/time value.

Dates shall be defensively copied where mutable date objects are used.

---

# 19. Customer Presentation

The Pipeline may map canonical Customer reference information into an Invoice presentation structure.

It shall not:

* query Customer repositories
* enrich from external services
* modify Customer data

Only information already available through the canonical input may be presented.

---

# 20. Reservation Presentation

The Pipeline may expose the canonical Reservation reference and presentation information available from the Invoice.

It shall not retrieve additional Reservation data from persistence.

Reservation enrichment belongs to the appropriate application orchestration boundary.

---

# 21. Pricing Presentation

The Pipeline shall present the accepted Invoice pricing snapshot.

It must not:

* recalculate pricing
* retrieve current prices
* apply discounts
* change the accepted commercial price
* query the Pricing capability

The Invoice's accepted commercial pricing remains authoritative.

---

# 22. Payment Presentation

The Pipeline may present payment allocation information including:

* payment reference
* payment date
* amount
* currency
* external reference where appropriate

It shall not execute or recalculate payments.

---

# 23. Adjustment Presentation

The Pipeline may present canonical Invoice adjustments.

It shall preserve:

* adjustment identity
* type
* amount
* reason
* relevant date/context

It shall not calculate or reinterpret adjustment amounts.

---

# 24. Cancellation Presentation

Where an Invoice contains a cancellation snapshot, the Pipeline may present:

* cancellation date
* cancellation reason
* cancellation charge
* refundable amount
* policy reference/version where appropriate

The Pipeline shall not recalculate cancellation consequences.

---

# 25. Deposit Presentation

Where a deposit requirement exists, the Pipeline may present:

* deposit type
* required amount
* percentage where applicable
* deposit status where canonically available

The Pipeline shall not independently calculate the deposit.

---

# 26. Invoice Summary

Implement a concise Invoice Summary presentation model where required by established application conventions.

The summary should contain only the information needed for list/overview presentation, such as:

* Invoice reference
* customer display information
* reservation reference
* status
* issue date
* due date
* total
* amount paid
* balance due
* currency

The summary must derive from canonical Invoice state.

---

# 27. Detailed Invoice Presentation

The detailed presentation model may contain the complete presentation information required by an Invoice screen or document adapter.

It should include the canonical information necessary to represent:

* Invoice identity
* customer
* reservation
* accepted pricing
* financial totals
* payments
* adjustments
* cancellation
* deposit
* metadata

Do not add information that requires external retrieval.

---

# 28. Presentation Context

If the repository's established presentation architecture supports multiple presentation targets, APP-007.6 may define an explicit context such as:

```text
INVOICE_DETAIL
INVOICE_SUMMARY
CUSTOMER_VIEW
DOCUMENT_VIEW
```

Only introduce target-specific contexts where they provide an actual architectural benefit.

Do not create separate models for every possible frontend component.

---

# 29. Presentation Mapping

Mapping shall be explicit and deterministic.

Conceptually:

```text
Invoice Aggregate
        ↓
Invoice Presentation Mapper
        ↓
Invoice Presentation Model
```

Where Engine results are consumed:

```text
InvoiceEngineResult
        ↓
Presentation Mapper
        ↓
Invoice Presentation Result
```

---

# 30. No Business Logic

Presentation mapping must not contain business decisions.

Do not implement logic such as:

```text
if amountPaid === totalAmount
    status = PAID
```

The status already belongs to the canonical Invoice state.

Presentation may format that status.

---

# 31. No Financial Logic

Presentation must not calculate:

* balances
* totals
* taxes
* deposits
* cancellation charges
* refunds
* adjustments

All financial outcomes come from canonical application/domain state.

---

# 32. No Policy Logic

Presentation shall not determine:

* whether an Invoice can be issued
* whether payment is allowed
* whether cancellation is allowed
* whether refund is allowed
* whether an Invoice is valid

Those decisions belong to APP-007.3 and APP-007.4.

---

# 33. No Persistence

The Pipeline shall not depend on:

* Prisma
* repositories
* database clients
* persistence services

All required information must be supplied through the presentation input.

---

# 34. No External Enrichment

APP-007.6 shall not call:

* Hotelbeds
* accounting providers
* payment providers
* Customer services
* Reservation repositories
* external APIs

If enrichment is required, it must be performed before the presentation pipeline receives its canonical input.

---

# 35. Engine Result Presentation

When an Invoice Engine operation has just executed, the Presentation Pipeline shall be able to represent the resulting:

* Invoice
* operation
* resulting status
* financial impact
* warnings
* required external actions where appropriate

The Pipeline shall not alter the Engine Result.

---

# 36. Error Presentation

Presentation errors shall be distinct from business execution errors.

For example:

```text
InvoiceEngineResult
    success = false
```

must not be transformed into a successful Invoice presentation.

The Pipeline shall preserve meaningful failure information for the consuming layer.

---

# 37. Missing Data

If required presentation data is missing from the canonical input, the Pipeline shall return an explicit presentation error according to established application conventions.

It must not:

* query the database
* invent values
* silently substitute unrelated values

---

# 38. Optional Data

Optional Invoice information shall remain optional in the presentation model.

Do not manufacture:

```text
null
```

or empty placeholder values where the established model supports absence.

Follow existing repository conventions for optional fields.

---

# 39. Immutability

Presentation output shall be immutable.

This includes:

* root presentation model
* nested objects
* arrays
* collections
* metadata

Inputs must not be mutated.

---

# 40. Determinism

Identical canonical Invoice input and presentation context shall produce identical presentation output, apart from explicitly dynamic metadata if the established convention requires it.

No presentation output shall depend on:

* current database state
* external services
* random values
* environment-specific business logic

---

# 41. Presentation Metadata

Where required, presentation metadata may contain:

* presentation version
* presentation target
* generated timestamp
* source

Metadata must describe presentation generation rather than business state.

---

# 42. Versioning

The presentation contract shall be versionable independently from the Invoice Aggregate.

Do not modify the canonical Invoice model merely to satisfy a presentation requirement.

Presentation models provide the compatibility boundary for consumers.

---

# 43. Consumer Independence

The Pipeline should support multiple consumers without coupling the Invoice Aggregate to them.

Conceptually:

```text
                   ┌── Frontend
                   │
Invoice Aggregate ─┼── PDF Adapter
       ↓           │
Presentation       └── Email Adapter
Pipeline
```

The presentation model is the shared application boundary.

---

# 44. Frontend Boundary

APP-007.6 prepares the canonical presentation model for future frontend consumption.

It shall not implement:

* React/Vue/Angular components
* templates
* browser state
* client-side routing
* frontend-specific data fetching

Those belong to the frontend implementation phase.

---

# 45. Document Boundary

APP-007.6 may provide the data structure required for document generation.

It shall not implement:

* PDF rendering
* HTML templates
* document files
* printer-specific formatting

Those are consumer/adapter responsibilities.

---

# 46. Email Boundary

APP-007.6 may provide presentation data required by email templates.

It shall not:

* send email
* communicate with an email provider
* implement email delivery

---

# 47. Export Boundary

The Invoice capability root shall expose the public Presentation Pipeline contracts.

Private mapper/helper implementations shall not be exported unnecessarily.

Follow established barrel conventions.

```text

      ↓
Canonical Invoice Result
      ↓
APP-007.6
Presentation Pipeline
      ↓

      ↓
```

The fundamental responsibility is:

> **Represent canonical Invoice state for presentation without changing its business meaning.**
