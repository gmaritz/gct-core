# 1. Objective

Implement the canonical **Invoice Policy Framework** for APP-007.

The policy framework determines whether requested Invoice operations are permitted based on validated Invoice state and explicit business policy context.

It shall establish:

* Invoice policy contracts
* policy context
* policy outcomes
* policy priorities
* policy results
* required actions
* policy registry
* policy pipeline
* lifecycle policies
* commercial policies
* payment-related Invoice policies
* cancellation policies
* issue/void policies
* policy evaluation tests

The policy framework shall remain:

* deterministic
* stateless
* immutable
* explicitly ordered
* provider-independent
* persistence-independent
* presentation-independent
* calculation-independent

# 5. Policy Responsibility

A policy answers:

> Is a requested operation permitted under the current validated business context?

Examples:

```text
Can this Invoice be issued?

Can this Invoice accept payment?

Can this Invoice be cancelled?

Can this Invoice be voided?

Can this Invoice proceed to a refund workflow?
```

The policy determines permission.

The policy does not perform the operation.

---

# 6. Policy vs Validation

The distinction is mandatory.

```text
APP-007.3 Validation

"Is the Invoice state valid?"
```

versus:

```text
APP-007.4 Policy

"Given valid state, is this requested operation permitted?"
```

For example:

```text
Validation:
Invoice status is CANCELLED.

Policy:
A CANCELLED Invoice cannot be issued.
```

Validation identifies state.

Policy interprets state against a business rule.

---

# 7. Policy vs Engine

The distinction is:

```text
APP-007.4 Policy

Determines:
ALLOW / DENY / REQUIRE_ACTION
```

while:

```text
APP-007.5 Engine

Executes:
the permitted business operation
```

Policies shall never:

* mutate the Invoice Aggregate
* calculate financial outcomes
* execute payments
* issue refunds
* persist changes
* call external systems

# 10. Invoice Policy Outcome

Implement:

```typescript
export enum InvoicePolicyOutcome {
  ALLOW = "ALLOW",
  DENY = "DENY",
  REQUIRE_ACTION = "REQUIRE_ACTION",
  WARNING = "WARNING",
  IGNORE = "IGNORE",
}
```

Interpretation:

### ALLOW

The policy permits the requested operation.

### DENY

The policy prohibits the requested operation.

### REQUIRE_ACTION

The operation may proceed only after a required action has been satisfied.

### WARNING

The policy identifies a non-blocking business concern.

### IGNORE

The policy does not apply to the current context.

# 18. Validation Dependency

Policies must not execute if validation has failed critically.

The expected flow is:

```text
InvoiceValidationPipeline
        │
        ├── success = false
        │
        └── Policy evaluation must not proceed
```

The Policy Framework assumes that validation has been performed.

The policy pipeline may defensively reject a context whose validation result is unsuccessful.

# 24. Policy Pipeline Ordering

The pipeline shall use registry ordering.

The default conceptual order shall therefore be:

```text
CRITICAL policies
      ↓
HIGH policies
      ↓
NORMAL policies
      ↓
LOW policies
```

Do not hard-code policy execution order into the pipeline.

Priority belongs to the registry.

---

# 25. Critical Denial

The pipeline shall stop evaluation when:

```text
outcome = DENY
priority = CRITICAL
```

Example:

```text
Critical policy
     ↓
DENY
     ↓
STOP
```

Lower-priority policies shall not execute after a critical denial.

---

# 26. Non-Critical Denial

A non-critical denial shall be recorded.

The pipeline may continue evaluating subsequent policies.

This preserves the established GCT Core policy pattern and allows all applicable business observations to be returned.

The final result remains:

```text
permitted = false
```

if any policy denies the operation.

---

# 27. Require Action

If one or more policies return:

```text
REQUIRE_ACTION
```

the final evaluation shall contain the combined required actions.

Unless a policy explicitly denies the operation, `REQUIRE_ACTION` shall result in:

```text
permitted = false
```

The engine may later use the required actions to determine what must happen before proceeding.

The policy framework does not execute the required actions.

---

# 28. Warning

Warnings do not automatically deny the operation.

If the only policy outcome is:

```text
WARNING
```

the final result may remain:

```text
permitted = true
```

Warnings must be included in the final evaluation.

---

# 29. Ignore

An ignored policy contributes no permission decision.

If all applicable policies return:

```text
IGNORE
```

the pipeline shall return:

```text
permitted = true
outcome = IGNORE
```

unless another policy produces a stronger outcome.

---

# 30. Outcome Aggregation

The final outcome precedence is:

```text
DENY
   ↓
REQUIRE_ACTION
   ↓
WARNING
   ↓
ALLOW
   ↓
IGNORE
```

Therefore:

```text
if any DENY
    outcome = DENY

else if any REQUIRE_ACTION
    outcome = REQUIRE_ACTION

else if any WARNING
    outcome = WARNING

else if any ALLOW
    outcome = ALLOW

else
    outcome = IGNORE
```

---

# 31. Permission Aggregation

The final `permitted` value shall be:

```text
false
```

when:

* any policy denies
* any policy requires an action

Otherwise:

```text
true
```

This means:

```text
DENY → false
REQUIRE_ACTION → false
WARNING → true
ALLOW → true
IGNORE → true
```

---

# 32. Priority Aggregation

The final priority shall represent the highest priority encountered.

Precedence:

```text
CRITICAL
HIGH
NORMAL
LOW
```

If no policies are evaluated, use:

```text
LOW
```

consistent with the existing policy framework.

---

# 33. Result Aggregation

The pipeline shall aggregate:

```text
requiredActions
errors
warnings
observations
policyResults
```

using immutable collections.

No duplicate removal is required unless the established policy framework already performs it.

Preserve policy output.

# 36. Issue Policy

Implement:

```text
InvoiceIssuePolicy
```

The Issue Policy determines whether an Invoice may transition into the issued state.

It shall evaluate:

* requested operation is `ISSUE`
* Invoice exists
* Invoice validation succeeded
* current status
* required commercial references exist
* Invoice is not already terminal
* Invoice is not already issued/paid

The policy shall not mutate status.

---

# 37. Issue Policy Rules

For operation:

```text
ISSUE
```

the following shall apply.

### DRAFT

```text
ALLOW
```

provided validation succeeded.

### ISSUED

```text
DENY
```

because the Invoice is already issued.

### PARTIALLY_PAID

```text
DENY
```

because an issued financial obligation already exists.

### PAID

```text
DENY
```

because the Invoice is already fully paid.

### OVERDUE

```text
DENY
```

because the Invoice has already passed issue lifecycle.

### CANCELLED

```text
DENY
```

because a cancelled Invoice cannot be issued.

### VOID

```text
DENY
```

because a void Invoice cannot be issued.

The policy shall not calculate anything.

---

# 38. Issue Policy Priority

The Issue Policy shall use:

```text
NORMAL
```

for a valid `DRAFT → ISSUE` decision.

Invalid terminal-state denial shall use:

```text
HIGH
```

unless the existing repository policy conventions require `CRITICAL`.

Do not use `CRITICAL` merely because the operation is denied.

`CRITICAL` is reserved for conditions requiring immediate pipeline termination.

---

# 39. Payment Policy

Implement:

```text
InvoicePaymentPolicy
```

This policy determines whether the Invoice may accept a payment operation.

The operation is:

```text
ACCEPT_PAYMENT
```

The policy shall evaluate:

* Invoice status
* outstanding balance state
* cancellation state
* void state
* validation result

It shall not calculate the outstanding balance.

It uses the authoritative Invoice state supplied by the aggregate.

---

# 40. Payment Policy Rules

### DRAFT

```text
DENY
```

A draft Invoice is not payable.

### ISSUED

```text
ALLOW
```

### PARTIALLY_PAID

```text
ALLOW
```

provided the Invoice is not otherwise terminal.

### PAID

```text
DENY
```

No further payment is accepted by policy.

### OVERDUE

```text
ALLOW
```

An overdue Invoice may still be payable.

The policy may emit a warning:

```text
"Invoice is overdue."
```

### CANCELLED

```text
DENY
```

### VOID

```text
DENY
```

The policy shall not execute payment.

---

```text
PAYMENT_REVIEW
```

only where the supplied Invoice context explicitly indicates that payment review is required.

Do not invent risk scoring or payment-provider rules.

# 47. Commercial Policy

Implement:

```text
InvoiceCommercialPolicy
```

The policy determines whether the Invoice has sufficient commercial integrity to proceed with operations requiring a valid commercial basis.

It shall evaluate:

* accepted quote reference
* pricing snapshot
* financial obligation
* currency consistency
* validation result

It shall not recalculate pricing.

---

# 48. Commercial Policy Rules

The Commercial Policy shall:

### Allow

when:

* validation succeeded
* quote reference is present
* pricing snapshot is present
* financial obligation is present
* commercial state is consistent

### Deny

when the validation context reports a critical commercial failure.

The policy must not duplicate the entire validation pipeline.

It consumes the validation result.

---

# 49. Validation Result Dependency

Policies should consume:

```text
InvoiceValidationResult
```

rather than reimplementing validation logic.

For example:

```text
Validation:
PRICING_CURRENCY_MISMATCH

Commercial Policy:
DENY
```

The policy interprets the validation result.

It does not recreate the validation rule.

---

# 50. Policy-Specific Context

If a policy requires information beyond the base `InvoicePolicyContext`, introduce a policy-specific immutable context only where necessary.

Do not create a large universal context containing every possible future field.

For example:

```typescript
export interface InvoiceCancellationPolicyContext
  extends InvoicePolicyContext {
  readonly cancellationRequestedAt: Date;
}
```

should only be introduced if the actual repository implementation requires it.

Prefer the base context where sufficient.

---

# 51. Policy Statelessness

All policies shall be stateless.

Policies must not retain:

* Invoice instances
* previous evaluation results
* request state
* mutable collections
* external state

Each evaluation must depend only on the supplied context.

---

# 52. No Policy Mutation

Policies shall never:

```text
issue Invoice
cancel Invoice
void Invoice
record payment
apply adjustment
change status
modify balance
```

Policies return decisions.

The Engine performs operations later.

---

# 53. No Policy Calculation

Policies shall not calculate:

```text
invoice total
balance
deposit
cancellation charge
refund
tax
discount
payment amount
```

Policies may compare supplied state.

They must not create new authoritative financial state.

---

# 54. No External Communication

Policies shall not call:

* QuickBooks
* Hotelbeds
* payment gateways
* repositories
* databases
* external APIs

All required context must be supplied explicitly.

---

# 116. Default Behaviour




```text

permitted = true
```

# 117. Policy Priority Semantics

Priority is not the same as outcome.

For example:

```text
HIGH + ALLOW
```

does not override:

```text
CRITICAL + DENY
```

The pipeline must aggregate:

1. outcome
2. priority
3. required actions
4. errors
5. warnings
6. observations

independently.

---

# 118. Critical Policy Semantics

A critical policy represents a condition that makes further evaluation unnecessary or unsafe.

Therefore:

```text
CRITICAL + DENY
```

shall stop the pipeline.

However:

```text
CRITICAL + ALLOW
```

does not automatically stop the pipeline.

Only critical denial causes fail-fast.
