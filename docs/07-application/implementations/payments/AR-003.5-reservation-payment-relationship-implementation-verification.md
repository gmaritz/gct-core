## 2. Scope, method and classification

Read the governing process, decision records, application and infrastructure source, Prisma schema and relevant migration and test source. Traced the customer-journey Reservation creation and frontend payment paths, including ITN identity checks. Searched repository TypeScript for `Payment.restore`, `PaymentRepository` and Prisma Payment CRUD patterns, and repository filenames for payment repositories. These searches support the scoped negative findings below, not proof about arbitrary dynamic access or other deployed systems. No tests were run.

Classifications describe the source path, not proof that a particular record exists or a migration is deployed:

1. **Implemented and persisted** — implemented with a persistence path in source.
2. **Implemented in domain only** — domain capability without demonstrated physical persistence.
3. **Partially implemented** — present in some layers but incomplete or inconsistent.
4. **Not implemented** — no supporting implementation found in the inspected scope.
5. **Unable to verify** — source cannot establish the fact.

## 3. Reservation identity

- **Implemented and persisted:** In this customer-journey flow, `createReservationRequestId` hashes a fingerprint of the Journey and selected reservation inputs, returning `reservation-${journeyId}-${digest}`. This is passed as `query.requestId`, and `ReservationBuilder.createComposition` assigns it to the Aggregate's `identity.id`. The service calls `executeIfAbsent`; the Prisma repository upserts `Reservation` with that exact ID. The Prisma UUID default is therefore not used for this explicit creation ID. See evidence E1–E4.
- **Implemented and persisted:** `findById` reconstructs a canonical `Reservation` with `identity.id` from the row's `id`. The separate generated `reservationNumber` is a business-facing reference, not the Aggregate ID. See E3–E5.
- **Partially implemented:** The request ID is not a temporary ID replaced at persistence in this path: it becomes the canonical ID. Journey ID selects context; `reservationNumber`, the Reservation's historical `PaymentSnapshot.snapshotId`, the derived Payment ID and the provider-facing attempt reference have distinct roles. The initial snapshot ID happens to use `payment-${reservationRequestId}`, the same text later derived as Payment ID; that coincidence does not make it a persisted Payment or the attempt reference. See E1, E6 and E7.
- **Partially implemented:** The Reservation repository has legacy Booking fallback reconstruction using the Booking row's ID as the reconstructed Reservation identity. `findByJourneyId` checks whether *any* canonical Reservation rows exist before filtering for the requested Journey; legacy fallback occurs only if that unfiltered result is empty. Source inspection cannot establish which branch supplies a particular existing Reservation. A legacy-only identity does not by itself establish that a corresponding `reservation` row exists for the attempt FK. See E5 and E8.

## 4. Payment initiation

- **Implemented and persisted:** The frontend POST identifies a Journey, resolves an existing Reservation through the repository, and passes the resulting context to `DefaultPaymentInitiationService`. The resolver selects the first returned non-cancelled candidate, requires usable pricing, and supplies its `identity.id` in the request, Payment reference and Payment Reservation snapshot. Selection has no explicit ordering in the inspected repository query. See E8–E10.
- **Partially implemented:** The resolver already derives `payment-${reservation.identity.id}` as the in-memory `Payment.reference.paymentId` and request idempotency key. This matches the scoped D01 identity convention, but does not demonstrate creation of a Prisma `Payment.id` or its separate `Payment.paymentReference`. D01's collision, legacy-reference and consumer compatibility checks remain outstanding. See E9, E11 and E13.
- **Partially implemented:** The engine builds a fresh Payment via `Payment.create` before `PaymentAttempt.createOrFind`; the service is supplied an attempt repository, not a Payment repository. No canonical Payment save or lookup precedes the attempt in this path. On a repeated eligible request, the engine creates another in-memory object with the derived identity; `createOrFind` may reuse the same persisted attempt by idempotency key. It does not retrieve the same persisted Payment. The claim and status gates determine whether initiation proceeds. See E10–E12.
- **Partially implemented:** Initiation checks that the request Reservation ID is nonblank and matches the snapshot ID; it does not independently compare `Payment.reference.reservationId` with either. The standard resolver supplies matching values, but the service accepts a constructed request rather than loading the Reservation itself. See E9–E10, E14–E15.

## 5. Canonical Payment domain

- **Implemented in domain only:** `PaymentReference.reservationId` and `PaymentComposition.reservationSnapshot` are required TypeScript members. The snapshot contains its own `reservationId`. `Payment.create` and `Payment.restore` construct the same composition and copy these values. See E14–E16.
- **Partially implemented:** Required TypeScript fields do not establish nonblank runtime validation of the reference's Reservation ID or equality with the snapshot ID. The Aggregate's composition validation checks Payment identity and snapshot object presence, while the reference/snapshot copy functions do not compare the two. The standard resolver builds matching values; that is not an Aggregate invariant. See E9, E14–E16.
- **Implemented in domain only:** `Payment.restore` can preserve the supplied reference and snapshot in memory. The inspected production source does not demonstrate obtaining those values from a persisted Payment row; the located `Payment.restore` call is a test. Therefore a persisted Payment round trip with its Reservation reference is **not demonstrated**. See E14, E16 and E19.

## 6. Prisma schema and repositories

- **Not implemented:** The checked-in Prisma `Payment` model has no direct `reservationId`, Reservation relation or direct Payment–Reservation FK. Consequently there is no nullable/mandatory direct Payment–Reservation relation in this schema to assess. Its `bookingId` and Booking relation remain mandatory. `Payment.id` and the unique `Payment.paymentReference` are separate columns. See E13.
- **Not implemented:** No canonical Payment repository contract, concrete repository, reconstruction mapper or production `Payment.restore`/Prisma Payment CRUD path was found in the scoped source searches. Reservation persistence writes its own snapshot, not a Payment Aggregate. Thus Payment persistence cannot currently be shown to write, read or reconstruct the canonical Reservation association. The existence of the Prisma Payment model or an in-memory Payment does not establish such a path. See E4, E11, E13 and E19.
- **Unable to verify:** The actual deployed database schema, existing Payment and Reservation rows, Booking links, migration state, historical identity collisions and consumer compatibility were not examined. Checked-in schema and migration definitions are not evidence of deployment or actual data.

## 7. PaymentAttempt relationship

- **Implemented and persisted:** `PaymentAttempt.reservationId` is mandatory in the checked-in Prisma model, with a declared restrictive Reservation relation. The checked-in creation migration also declares the corresponding FK. This is schema/migration evidence, not verification of the deployed constraint. See E17–E18.
- **Partially implemented:** `PaymentAttempt.paymentId` is a mandatory indexed string, not a Prisma relation or FK to Payment. Initiation populates it from the in-memory Payment reference and populates `reservationId` from the request; `createOrFind` persists both. An attempt can therefore carry a Payment ID without a demonstrated Payment row. See E10, E12 and E17.
- **Partially implemented:** For an existing idempotency key, `createOrFind` compares Payment ID, Reservation ID, provider, environment, numeric amount and currency against the input, but not payment method or a persisted Payment. It does not verify the in-memory Payment's Reservation reference against the attempt's Reservation ID. On verified ITN processing, the processor loads the attempt and Reservation and checks `attempt.paymentId === payment-${reservation.identity.id}`; it does not load a Payment row or compare its Reservation reference. See E12, E20 and E21.
- **Unable to verify:** Whether any existing attempts refer to actual Payment rows, whether their references match historical records, and whether the deployed FK is present require separate authorised investigation. No database was accessed.

## 10. Gaps, inconsistencies and unverified assumptions

- **Partially implemented:** Required domain Reservation reference and snapshot coexist without a demonstrated equality invariant. The normal resolver sets both to the same ID; arbitrary service input is not equivalently checked. E9–E10, E14–E16.
- **Not implemented:** The physical Payment model does not directly represent that domain association, and the inspected path lacks a Payment persistence/reconstruction implementation. The mandatory Booking link remains a separate physical requirement. E11, E13, E19.
- **Partially implemented:** Attempt Reservation linkage exists in checked-in schema and migration, but its Payment link is only a string. ITN-derived identity checking is not Payment existence or relationship verification. E17–E18, E20–E21.
- **Partially implemented:** Legacy Booking fallback and the global canonical-row check in Journey lookup complicate claims that every returned Reservation is backed by the row required by the attempt FK. No data conclusions follow from source alone. E5, E8, E18.
- **Unable to verify:** D01 collision, legacy-reference and consumer compatibility conditions; real data, actual migration deployment, runtime traffic and operational outcomes. No live database, provider or external service was accessed.

## 11. D02 implications

- **Already implemented:** Domain Payment reference and immutable Reservation snapshot fields; matching construction in the standard resolver; Reservation persistence; and a Reservation-linked PaymentAttempt. E4, E9, E14–E18.
- **Genuinely missing:** A demonstrated canonical Payment persistence/round-trip path, direct physical Payment–Reservation association and enforcement that its reference agrees with its snapshot. A PaymentAttempt-to-Payment FK and Payment-row comparison are also absent, but are addressed separately by D06. E12–E18, E20.
- **Duplication:** A decision merely to introduce a domain Reservation reference or snapshot would duplicate existing typed capabilities. D02's proposed explicit restrictive *physical* association and agreement check are not demonstrated by those capabilities; neither is already approved by their existence.
- **Still requiring decision:** D02's proposed relationship representation and constraint, snapshot/reference consistency, Booking and legacy compatibility and any required specification-owner and governance confirmations remain for the authorised reviewers. No one-to-one relationship or attempt cardinality is inferred. D01 does not authorise implementation.

## 12. Conclusion

**Partially implemented:** The existing flow preserves the canonical Reservation ID through Reservation persistence, payment context and PaymentAttempt, and constructs an in-memory Payment with that reference. It does not demonstrate persistence or reconstruction of a Payment Aggregate associated directly with that Reservation. D02 remains a Project Owner decision; the findings do not choose its outcome.
