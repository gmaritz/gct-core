# Payment Persistence and PayFast ITN Implementation-Readiness Review

## 1. Executive conclusion

**Readiness: blocked for implementation and payment execution.** The Project Owner has approved specific AR-003.4 directions, with conditions; that decision record is not an implementation specification or implementation authorisation. The proposed Payment and persistence revisions are drafts. Required specification-owner and architecture-governance confirmations, the detailed exact-money, persistence, lifecycle and recovery contracts, and relevant owner decisions are outstanding. In particular, do not implement a PayFast `COMPLETE` to canonical Payment transition or automatically confirm a Reservation from it while D05 remains unresolved.

The code creates an in-memory Payment and a separately persisted PaymentAttempt. A verified ITN currently atomically updates the attempt and Reservation payment snapshot; it neither persists the Payment Aggregate nor confirms the canonical Reservation. It does not provide the approved D07 sequence or D08 durable recovery. An individual completed attempt is not evidence that the full Reservation is settled. A historical partial initial payment may ultimately support confirmation under D09, but only after its approved Payment outcome and all confirmation conditions exist.

This is a source and document review, not a database-state assertion. Findings below use the requested classifications. **Implemented and verified** means verified in the reviewed source and, where stated, focused tests; it does not assert production deployment, live-provider correctness or authority to use the behavior.

## 6. ITN verification, acknowledgements and recovery

- **Implemented and verified:** [`PayFastItnProcessor.process`](../../src/infrastructure/payments/payfast/payfast-itn-processor.ts) parses unique fields, checks a configured source allowlist and signature, then invokes environment-specific server validation before persistence. [`payfast-itn-security.ts`](../../src/infrastructure/payments/payfast/payfast-itn-security.ts) uses ordered form fields, passphrase and MD5 signature comparison, rejects malformed/duplicate fields, and posts the original body to the selected HTTPS validation endpoint with timeout. [`receivePayFastItn`](../../src/interfaces/http/controllers/payfast-itn.controller.ts) uses the direct peer unless the immediate proxy is explicitly trusted, and accepts only form-encoded raw body; [`express.ts`](../../src/bootstrap/express.ts) sets a 16 KB limit. Current allowlist and deployment/proxy configuration are not independently validated against the live provider.
- **Partially implemented:** After provider validation, the processor requires merchant ID matching configuration, numeric provider transaction ID, bounded merchant payment reference, `COMPLETE`/`CANCELLED`, and gross amount equal to the attempt under two-decimal comparison. It checks attempt provider, environment and ZAR, Reservation identity, Pricing/Payment snapshots and derived Payment ID. It does not look up a persisted Payment, verify its Reservation association or persist independent verified provider evidence. The provider transaction ID is globally unique on attempts.
- **Partially implemented:** Exact duplicate means matching mapped attempt status, provider transaction ID and raw-body SHA-256 hash; differing hash or transaction ID is a conflict, even if semantically equivalent. `applyVerifiedPayFastNotification` conditionally changes attempt state and JSON snapshot within one database transaction; stale snapshot, unique provider ID collision and concurrent attempt changes produce conflicts or an exact duplicate. This guards the current coupled operation, not the required separate A1/P1/A2/R1 boundaries.
- **Specification conflict:** [`transitionReservationFromVerifiedPayFastNotification`](../../src/application/payments/verified-payfast-notification-transition.ts) restores a Reservation with updated snapshot directly from provider `COMPLETE`, including a new snapshot `capturedAt`, cumulative received/outstanding and `PARTIAL` or `COMPLETED`, while leaving Reservation lifecycle unchanged. The attempt repository writes that snapshot directly in the same transaction. D07 requires durable A1, Payment evidence/checkpoint P1, attempt outcome A2, then Reservation R1; D09 calls for approved canonical Reservation operations and provenance, and D05 prohibits automatic confirmation before an approved Payment transition. The existing snapshot write is not an approved Payment outcome or D07/D09 coordinator.
- **Partially implemented:** The controller returns 200 `OK` for applied and exact duplicate, 400/403 for validation failures, 404 for unmatched attempt, 409 for conflicting state and 503 for validation unavailability or unexpected errors; it logs categories. An HTTP response is not a durable reconciliation checkpoint. Whether these acknowledgement semantics should change is a specification/operations question, not decided here.

## 7. Reservation confirmation and partial payment

- **Missing:** [`application Reservation`](../../src/application/reservations/aggregate/reservation.ts) has `create`/`restore`, not a canonical outcome-application or confirmation method. [`DefaultReservationConfirmationService.resolve`](../../src/application/reservations/confirmation/reservation-confirmation-service.ts) is a read-only view: it requires a snapshot payment status in `COMPLETED`, `PAID`, `SETTLED` or `CAPTURED`, a Reservation already `CONFIRMED` or `COMPLETED`, and confirmed fulfilment. It does not perform confirmation and does not treat snapshot `PARTIAL` as sufficient. A supplier failure currently yields pending after the payment/reservation checks, rather than independently establishing confirmation.
- **Specification conflict:** The separate legacy [`domain Reservation.confirm`](../../src/domain/aggregates/reservation.aggregate.ts) only accepts `PENDING` and the separate [`ConfirmReservationService.execute`](../../src/application/services/reservation/confirm-reservation.service.ts) uses that domain repository. It is not the canonical PayFast path; do not reuse it without approved lifecycle reconciliation.
- **Partially implemented:** The existing context resolver uses accepted `amountPayableAtBooking` if the preserved requirement matches Pricing; without a requirement it falls back to full total. The ITN transition can keep the full total, increment received, reduce outstanding and spread/preserve the original future-balance terms. These calculations are not an approved Payment outcome, exact persistence guarantee or confirmation policy. The accepted requirement and contractual future balance/due date must not be overwritten as if a completed initial transaction settled the whole Reservation.
- **Specification-owner/governance approval required:** D09 permits a verified initial partial payment to support confirmation only when it satisfies the historically agreed requirement and all approved conditions. Owners must specify canonical predecessor states, Payment-outcome evidence and provenance, fulfillment/operational prerequisites, discrepancy and cancellation handling, conditional persistence and multiple/conflicting outcomes. Implement a provider-neutral application coordinator only after approval; persist each Aggregate separately and preserve a successfully persisted Payment outcome if Reservation processing fails. No cross-Aggregate transaction is authorised.
