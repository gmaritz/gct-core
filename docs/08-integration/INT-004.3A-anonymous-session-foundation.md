## 1. Purpose

Establish a trusted, server-managed anonymous session mechanism for customers using the GCT Core frontend without requiring account registration or login.

The session mechanism must provide a validated server-derived owner identity that subsequent journey-state isolation can use.

The repository assessment established that the application currently has no trusted anonymous session identity, session middleware, session record store, or cookie-based ownership contract.

This iteration establishes that missing foundation. It does not implement journey-state isolation itself.

## 2. Governing Development Process

Follow `docs/09-governance/GOV-DEV-001-DEVELOPMENT-PROCESS.md` as the single source of truth for the development workflow.

The required sequence is:

Specification → Copilot Implementation → Focused Tests + Regression → Copilot Implementation Report → Architect Acceptance → User Commit.

Implement only this specification. Do not introduce an additional approval stage before implementation, implement future iterations, or perform unrelated refactoring.

## 3. Architectural Decisions

### 3.1 Anonymous session identity

1. Anonymous sessions are supported without login.
2. The server is authoritative for session identity and validity.
3. The browser receives only an opaque, cryptographically unpredictable session identifier.
4. The session cookie is not itself a trusted owner identity until the identifier has been validated against the server-side session record.
5. Request IDs, public journey IDs, URL parameters, form fields, and other client-supplied values must never establish session ownership.
6. A client-supplied unknown or expired session identifier must not be adopted as an owner identity.

### 3.2 Session record persistence

Use the existing PostgreSQL and Prisma infrastructure for server-side session records.

Do not introduce Redis, a new external session service, or a new database server as part of this iteration.

Add the minimum persistence model and repository implementation necessary to create, validate, expire, renew where applicable, and invalidate anonymous sessions.

Keep Prisma-specific implementation within the existing infrastructure and persistence boundaries. Do not expose Prisma models or types through domain interfaces.

Before implementation, inspect the current canonical persistence specifications, Prisma schema, migrations, repository conventions, and session-related security configuration. Follow the established schema and migration conventions. Do not overwrite existing models, relationships, or persistence semantics.

If this design conflicts with an approved canonical specification or cannot be implemented without an unresolved architectural decision, stop and report the exact conflict. Do not silently change the canonical model.

### 3.3 Ownership context

Establish a typed, server-derived anonymous session owner context through Express middleware.

Downstream application code must obtain ownership from this validated context, not reconstruct it from request data.

The implementation must provide a clear distinction between:

- A valid session resolved from a presented cookie.
- A newly issued anonymous session.
- An invalid, expired, or missing session identifier.
- A request that has no valid owner context.

An invalid presented identifier must not grant access to an existing session. Where appropriate, the server may issue a new independent session, but it must not transfer the old session's ownership or state.

### 3.4 Session storage and deployment

Session records must be stored in PostgreSQL so session identity validation does not depend on a process-local session map.

This does not make the existing journey-selection and guest-information maps durable or shared across instances. Those stores remain outside this iteration.

Do not claim that complete customer journey continuity or multi-instance journey-state consistency has been achieved by this session foundation alone.

## 4. Scope

### 4.1 Included

- Anonymous session identifier generation using a cryptographically secure source.
- Server-side session record persistence through the existing Prisma architecture.
- Session creation, validation, expiry, and invalidation.
- Express middleware to resolve and expose validated owner context.
- Secure session-cookie issuance and handling.
- Explicit session configuration with safe defaults.
- CSRF protection appropriate to the cookie-based frontend.
- Focused unit and integration tests.
- Required build, regression, Prisma validation, and lint verification.
- Documentation of any remaining deployment or persistence constraints.

### 4.2 Excluded

- JourneySelectionStore or GuestInformationStore ownership changes.
- Journey-state persistence or distributed-cache implementation.
- Reservation, payment, or confirmation authorization changes.
- Customer registration, login, or account authentication.
- Changes to public journey URLs or journey identifiers.
- Hotelbeds integration changes.
- New external infrastructure.
- Unrelated schema, architecture, or frontend refactoring.

These exclusions must not be interpreted as proof that the excluded areas are already secure. They remain explicit follow-on work.

## 5. Session Contract

### 5.1 Session identifier

The session identifier must:

- Be generated using a cryptographically secure random source.
- Have sufficient entropy to resist guessing.
- Be opaque and contain no customer details, guest information, journey data, or other business state.
- Be validated against a server-side session record.
- Never be accepted as proof of ownership merely because it is syntactically valid.

Do not log the raw session identifier or include it in application error messages.

### 5.2 Session record

The server-side record must contain only the minimum fields required to manage session lifecycle and ownership.

At minimum, the persistence design must support:

- A unique session identifier or a securely stored representation of it.
- Creation time.
- Expiry time.
- Last activity or equivalent lifecycle information, if sliding expiry is implemented.
- Revocation or invalidation state, if required by the chosen lifecycle design.

Use existing project conventions for identifiers, timestamps, repository interfaces, error handling, migrations, and database access.

Avoid persisting guest details or journey-selection state in the session record. The session record establishes identity; the corresponding application stores remain responsible for their own data.

### 5.3 Expiry and invalidation

Implement an explicit session lifetime policy.

The implementation must:

- Reject expired or revoked sessions.
- Never reactivate an expired session simply because its cookie is presented again.
- Provide a server-side invalidation operation.
- Ensure session validation and invalidation behave consistently under concurrent requests.
- Avoid relying exclusively on periodic cleanup for access control; expiry must be checked during validation.
- Use the existing project scheduling and infrastructure conventions for cleanup if a cleanup process is needed. Do not add an unrelated scheduling framework.

Use configurable expiry values where required by the existing configuration conventions. Do not introduce unbounded sessions.

If the repository does not establish an appropriate idle and absolute lifetime, implement a documented, conservative default and keep the values configurable. Report the chosen values in the implementation report.

### 5.4 Cookie policy

Use a host-only cookie carrying the opaque session identifier.

The cookie must:

- Be `HttpOnly`.
- Use `Secure` in HTTPS production deployments.
- Use an explicitly configured and restrictive `SameSite` policy compatible with the actual frontend and payment flow.
- Omit the `Domain` attribute unless an approved deployment requirement demonstrates that it is necessary.
- Have a deliberately chosen `Path` and lifetime.
- Be cleared or expired when the associated session is invalidated where the relevant response is available.

Do not weaken production cookie security to make local HTTP tests pass. Test configuration must not silently become production configuration.

Inspect the existing Express proxy configuration before determining how HTTPS is detected. The assessment identified a discrepancy between `security.config.ts` and the Express `trust proxy` setting. Do not make broad proxy changes in this iteration. If correct secure-cookie behavior cannot be established without resolving that discrepancy, report the precise blocker rather than trusting arbitrary forwarded headers.

### 5.5 Session renewal

Define and implement the minimum renewal behavior required by the chosen lifecycle policy.

Where the session identifier is rotated, the previous identifier must cease to authorize the session after successful rotation, subject only to any explicitly documented and security-reviewed concurrency behavior.

Do not introduce an undocumented grace period that permits indefinite use of previous identifiers.

## 6. Express Integration

Integrate session resolution into the existing Express application and middleware pipeline.

The implementation must:

1. Preserve existing request-ID behavior without using request IDs as owner identity.
2. Resolve the presented session cookie through the server-side session service.
3. Validate expiry and revocation before exposing an owner context.
4. Establish a typed owner context for downstream request processing.
5. Prevent controllers and application services from accepting client-supplied owner identifiers as authoritative.
6. Fail closed when a protected operation requires an owner context and none exists.
7. Preserve existing non-frontend routes and application behavior unless session integration is required for correctness.

Do not create a second Express application, replace the frontend routing architecture, or introduce a new frontend framework.

Use existing dependency-injection and application composition conventions where available.

## 7. CSRF Protection

Cookie-based sessions introduce ambient browser credentials. CORS alone is not sufficient CSRF protection.

Inspect the existing frontend forms, POST routes, middleware order, payment flow, and test conventions.

Implement a CSRF strategy appropriate to the existing architecture. It must:

- Protect state-changing frontend requests that rely on the anonymous session cookie.
- Validate tokens or other approved request-origin protections on the server.
- Reject invalid or missing CSRF protection where required.
- Avoid treating the session cookie itself as a CSRF token.
- Avoid accepting a client-provided owner ID as a substitute for CSRF protection.
- Preserve legitimate same-origin form submissions.
- Include focused tests for accepted and rejected requests.

If an existing approved security specification defines the CSRF contract, follow it. Do not introduce a competing mechanism without identifying the conflict.

## 8. Persistence and Error Handling

Implement session persistence through the established repository architecture.

Requirements:

- Keep database access out of domain logic.
- Keep Prisma types within infrastructure.
- Use migrations for schema changes in accordance with existing repository conventions.
- Do not edit or remove existing migration history.
- Handle missing, expired, and revoked sessions as normal invalid-session outcomes rather than exposing internal errors.
- Handle persistence failures without silently treating an unvalidated identifier as a valid session.
- Avoid returning session identifiers, internal database details, or sensitive configuration in error responses.
- Ensure concurrent validation, expiry, and invalidation cannot produce unauthorized session reuse.

Do not change the canonical Reservation persistence model or existing Reservation lifecycle semantics.

## 9. Acceptance Tests

Add focused tests covering the following behaviors.

### 9.1 Session lifecycle

- A new anonymous session receives an unpredictable opaque identifier.
- A valid issued identifier resolves to the correct server-side session.
- An unknown identifier cannot access another session.
- An expired session is rejected.
- A revoked session is rejected.
- A previously invalidated or rotated identifier cannot authorize the active session.
- Session invalidation clears the browser cookie where a response is available.
- Database errors do not grant access.

### 9.2 Ownership context

- A valid session produces a server-derived owner context.
- A client-supplied request ID does not influence session ownership.
- A public journey ID does not influence session ownership.
- A client cannot choose an arbitrary owner by supplying a request field, query parameter, header, or URL value.
- A protected operation without the required owner context fails closed.
- Middleware ordering ensures protected controllers cannot run before required session validation.

### 9.3 Cookie security

- Cookie attributes match the configured security policy.
- Production configuration uses secure-cookie behavior.
- Local test configuration does not weaken production defaults.
- Cookie parsing and validation handle malformed or missing cookies safely.
- Raw session identifiers are not exposed through application error responses.

### 9.4 CSRF

- A legitimate protected same-origin request succeeds with valid CSRF protection.
- A state-changing request with a missing or invalid CSRF token is rejected where required.
- CSRF failure does not mutate application state.
- Existing frontend form tests are updated to provide valid protection where appropriate.

### 9.5 Persistence

- Session records can be created, read, expired, and invalidated through the repository boundary.
- Expiry is enforced by validation even when cleanup has not run.
- Concurrent invalidation and validation do not authorize an invalid session.
- Tests use the established database-testing conventions and do not depend on production credentials.

Do not use tests that merely assert the existence of middleware or a session cookie. Verify the actual lifecycle and authorization behavior.

## 11. Definition of Done

This iteration is complete when:

1. A server-managed anonymous session can be issued, validated, expired, and invalidated.
2. Session records use the approved PostgreSQL/Prisma persistence boundary.
3. The Express application exposes a trusted, typed owner context only after validation.
4. Cookie and CSRF behavior is implemented and tested.
5. Missing, invalid, expired, revoked, and untrusted client-supplied identifiers fail closed.
6. Focused tests pass.
7. Build, Prisma validation, regression tests, and lint results are reported accurately.
8. No canonical persistence or Reservation semantics have been changed outside this specification.
9. Remaining deployment or security constraints are explicitly reported.
10. No commit or push is performed by Copilot.

## 12. Downstream Requirements

INT-004.3 — Customer Journey State Isolation must consume the trusted session owner context established here.

The downstream iteration must scope every relevant read, write, and clear operation in `JourneySelectionStore` and `GuestInformationStore` to both the validated owner and the public journey ID.

It must also address the process-local nature of the existing journey stores. Session records in PostgreSQL do not make those stores shared or durable. Before claiming multi-instance journey continuity, an approved shared or persistent journey-state design is required.

Reservation, payment, and confirmation ownership remains a separate security concern and must not be assumed solved by this session foundation.
