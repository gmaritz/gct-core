## 1. Purpose

Correct the confirmed customer-state isolation defect identified in the INT-004 functional assessment.

The current implementation uses process-global `JourneySelectionStore` and `GuestInformationStore` maps keyed only by a public journey ID. Consequently, separate customers using the same public journey identifier may overwrite or access one another's booking context, accommodation selections and guest information.

This specification establishes customer-scoped ownership of mutable journey state while preserving the existing GCT Core architecture and application contracts.

## 3. Scope

### 3.1 Included

- `JourneySelectionStore` ownership and isolation.
- `GuestInformationStore` ownership and isolation.
- The booking context and selected accommodation data associated with a customer journey.
- Express route/controller integration required to resolve the correct customer's state.
- Review and guest-information guard integration.
- Regression tests proving concurrent customer isolation.
- Cleanup or expiry behaviour only where compatible with existing established infrastructure.

### 3.2 Excluded

- Reservation aggregate redesign or persistence implementation.
- Prisma schema changes or database migrations.
- Introduction of a new database, session framework, authentication system or distributed state infrastructure.
- Changes to Hotelbeds request or response semantics.
- Multi-room availability and allotment corrections.
- Group pricing changes.
- Currency conversion or supplier account configuration.
- Reservation snapshot redesign.
- Unrelated frontend or operational changes.

## 4. Architectural Constraints

1. Preserve the existing Express and server-rendered EJS architecture.
2. Preserve existing `/ui` routes and their established request/response contracts unless a minimal change is essential for isolation.
3. Preserve the current application/domain separation and dependency direction.
4. Do not change the canonical Prisma schema, migrations, Reservation aggregate or persistence contracts.
5. Do not use the public journey ID alone as the owner of mutable customer state.
6. Do not trust a customer/session identifier supplied freely by the request body, query string or URL.
7. Do not expose guest information, selected accommodation or booking context through a public identifier without verifying ownership.
8. Do not introduce new persistence or infrastructure without an existing approved architectural basis.
9. Preserve the existing dynamic availability, pricing and currency-mismatch behaviour.
10. Preserve unrelated working-tree changes and untracked files.

## 5. Required Implementation Behaviour

### 5.1 Customer-scoped state ownership

Every mutable booking journey state entry SHALL be associated with a customer-scoped owner boundary established by the existing application architecture.

The owner boundary SHALL be resolved by trusted server-side request/session infrastructure already present in the repository.

The public journey ID SHALL remain a journey identifier, not proof of customer ownership.

If an existing suitable session or equivalent ownership mechanism is available, reuse it. Do not introduce a competing mechanism.

If no suitable ownership mechanism exists, or the existing mechanism cannot safely support this requirement without an unapproved architectural decision, STOP implementation and report the precise decision gap. Do not invent an authentication, session or persistence design.

### 5.2 Journey selection state

The journey selection state SHALL be isolated by customer ownership.

This includes all mutable state managed by `JourneySelectionStore`, including, where present:

- booking context and dates;
- party and room occupancy inputs;
- resolved journey offers;
- selected properties, rooms and rates;
- selection-derived quote inputs;
- cached availability or offer data associated with the journey.

A state lookup or mutation SHALL use the established customer owner boundary together with the appropriate journey identifier.

One customer's selection or booking-context change SHALL NOT alter another customer's state, even where both use the same public journey ID.

### 5.3 Guest information state

`GuestInformationStore` SHALL enforce the same customer ownership boundary.

Guest information submitted by one customer SHALL NOT replace, expose or be returned as another customer's guest information.

All reads, writes, updates and removals SHALL be scoped consistently. An implementation that isolates writes but leaves unscoped reads is not acceptable.

### 5.4 Route and service integration

Trace all existing route/controller/service paths that read or mutate either store.

Ensure that:

- journey configuration and selection use the current request's trusted owner boundary;
- guest-information submission and retrieval use the same boundary;
- quote and review retrieve only the current customer's selections and guest information;
- missing or mismatched ownership cannot silently fall back to another customer's state;
- existing guards continue to reject missing or invalid prerequisites;
- ownership failures use a controlled response consistent with existing route conventions and do not reveal another customer's data.

Do not add new public endpoints unless essential to satisfy the existing flow.

### 5.5 State lifecycle

Inspect existing state cleanup and expiry behaviour.

Preserve established behaviour where safe. If owner-scoped state introduces a demonstrable cleanup requirement, implement only a minimal solution supported by existing infrastructure and conventions.

Do not introduce timers, background workers, new persistence or speculative lifecycle policies.

If safe cleanup cannot be established without a separate architectural decision, document the gap rather than expanding this task.

## 6. Required Regression Tests

Add focused tests using the existing Jest and Supertest conventions.

### 6.1 Same journey, two customers

Create two independent customer/session contexts using the same public journey ID.

Verify that:

1. Customer A can configure and select accommodation.
2. Customer B can configure and select different accommodation independently.
3. Customer B's operations do not overwrite Customer A's booking context or selections.
4. Each customer receives only their own selected state.
5. Results remain isolated regardless of operation order.

### 6.2 Guest-information isolation

Using the same public journey ID:

1. Submit distinct guest information as Customer A and Customer B.
2. Retrieve guest information in each customer's context.
3. Assert that each receives only their own submitted information.
4. Assert that updating or clearing one customer's information does not alter the other's data.

Use synthetic test data. Do not use real personal information.

### 6.3 Cross-customer access attempts

Attempt to access another customer's selection or guest information by reusing the public journey ID from the other customer's request context.

Verify that no protected data is returned and no cross-customer mutation occurs.

Test the existing controlled failure behaviour without requiring a particular HTTP status if repository conventions establish a different appropriate response.

### 6.4 Journey guards

Verify that Customer B cannot reach a valid review state by relying on Customer A's guest information or accommodation selection.

Verify that existing missing-selection and missing-guest-information guards still operate correctly.

### 6.5 Same-customer continuity

Verify that a single customer can still complete the existing progression through journey configuration, accommodation selection, guest information, quote and review using the established ownership boundary.

### 6.6 Regression compatibility

Retain and run existing tests for:

- `JourneySelectionStore`;
- `GuestInformationStore`;
- accommodation selection;
- guest-information validation;
- journey quote;
- reservation review;
- relevant frontend routes and controllers.

Update existing tests only where the approved ownership contract necessarily changes their setup. Do not weaken existing assertions to obtain passing tests.

## 7. Security and Data Handling

- Never use the public journey ID as the sole authorization or ownership mechanism.
- Never trust an arbitrary client-provided owner identifier.
- Do not log guest information or sensitive session material.
- Do not include guest data in errors or diagnostics.
- Do not introduce new credentials, secrets, cookies or authentication mechanisms without an approved architectural basis.
- Preserve existing security settings and session behaviour.
- Do not claim that the change establishes full authentication or authorization beyond the customer-state isolation actually implemented.

## 10. Acceptance Criteria

The implementation is eligible for architect acceptance only when:

- Mutable journey state is scoped to a trusted customer ownership boundary.
- Selection state cannot be overwritten or read across customers sharing a public journey ID.
- Guest information cannot be overwritten or read across those customers.
- Quote and review operate only on the current customer's state.
- Cross-customer access attempts do not disclose protected data.
- Same-customer journey continuity remains functional.
- Required focused and regression tests pass, with any baseline failures explicitly documented.
- Existing application architecture and persistence boundaries remain intact.
- No unrelated working-tree changes have been lost.
- The Copilot implementation report contains sufficient evidence to assess every acceptance criterion.
