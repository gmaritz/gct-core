# INT-004.4 — Multi-Room Availability and Occupancy Allocation Correctness

**Status:** Multi-room Availability allocation implemented and architecturally accepted (section 5.2.2). The combined multi-room booking lifecycle is not implemented.  
**Supplier evidence:** Multi-room Availability and a combined two-room booking (reference `241-749700`) demonstrated through Postman on 3 November 2026 (section 5.2.1). Remaining supplier questions are listed in section 5.2.1 and recorded in `HBX-AV-009`.  
**Type:** Integration and application functional correction  
**Governing workflow:** `docs/09-governance/GOV-DEV-001-DEVELOPMENT-PROCESS.md`  
**Related specifications:** `INT-004`, `INT-004.1`, `INT-004.2`, `INT-004.3`, `APP-003`, `APP-005`, `APP-004`, `APP-008.3-R7`, `INT-001`, `INT-002`

## 1. Objective

Correct accommodation availability and room allocation so that the application:

1. Evaluates the complete requested room allocation for each accommodation stop, rather than combining independent single-room searches into an apparently valid result.
2. Rejects invalid or duplicate room/rate selections that do not represent distinct, valid room allocations.
3. Supports adults and children, including individual child ages, as first-class occupancy data.
4. Allows different room allocations at different package stops.
5. Preserves the complete occupancy and selected supplier information through selection, pricing, review, and the existing reservation handoff.
6. Enforces journey-specific occupancy policies without imposing the Cape Winelands adults-only rule on other packages.

This iteration corrects the allocation capability and its application flow. It does not introduce supplier booking, payment, cancellation, or new persistence infrastructure.

## 4. Occupancy and allocation contract

### 4.1 Occupancy is a per-room value

The allocation model must represent each room independently. Conceptually, each room has:

- An explicit room-slot identity within the request.
- A positive integer number of adults.
- Zero or more children.
- The individual age of every child.
- The selected room and rate references once a valid supplier offer is selected.

The implementation must reuse existing canonical types where they correctly express these values. Introduce or refine a type only where the current model cannot represent the required contract.

A journey-level party count may be derived from room allocations. It must not replace the per-room allocation.

### 4.2 Children and child ages

For every package that permits children:

- The user can specify whether children are travelling.
- The number of children must be represented by the number of individual child-age entries, not by a count alone.
- Every child must have an age valid under the established application and supplier contract.
- The ages must be sent to the existing Hotelbeds availability request builder in the format its current contract requires.
- The exact ages must remain associated with the correct room throughout selection, pricing, review, and reservation handoff.

Inspect the current Hotelbeds request builder, DTOs, mapper, validation, and approved supplier documentation before defining age boundaries or transformations. Do not invent Hotelbeds-specific age rules.

Reject missing ages, malformed values, and values outside the verified supported range. Return the established validation or unavailable result through the existing application error-handling conventions; do not silently discard ages or convert invalid input to adults-only occupancy.

### 4.3 Journey-specific occupancy policy

Adults-only is a journey-specific restriction, not a platform-wide rule.

The Cape Winelands journey must continue to enforce its currently approved adults-only allocation.

Other package journeys must be capable of accepting children and their individual ages, subject to the applicable journey policy and supplier rules.

Use the smallest compatible extension of the existing journey configuration or policy contract. Do not scatter hard-coded Cape Winelands checks throughout shared services.

The backend must enforce the policy even when requests are submitted directly without using the browser interface.

### 4.4 Different allocations at different stops

Each package stop must have its own allocation.

For example, Stop 1 may have two rooms containing two adults in one room and one adult with two children in the other. Stop 2 may have a different room count and different occupants.

This is an illustration of the required model, not a new business rule or a guarantee that a particular supplier will accept that allocation.

Do not reuse a single journey-wide `roomAdults` list as the allocation for every stop. Replace or adapt the existing contract so each stop's occupancy is independently represented and validated.

Every availability request, selected room set, pricing input, and reservation snapshot must use the allocation belonging to its own stop.

## 5. Complete-allocation availability

### 5.1 Eliminate merged single-room evidence

Inspect `CapeWinelandsJourneyResolver`, the availability service, and `HotelbedsAvailabilityRequestBuilder`.

The current defect is that separate searches for different adult counts can be merged to produce an apparent set of room options without demonstrating that the supplier can fulfil the complete requested allocation together.

Change the flow to evaluate the complete requested room occupancy for each stop through the existing multi-occupancy availability capability.

Do not treat several independent single-room search results as proof of simultaneous availability.

### 5.2 Verify supplier semantics

Before implementing assumptions about the request or response, inspect:

- The existing Hotelbeds request builder and its tests.
- The canonical request and response DTOs.
- The availability response mapper.
- Approved supplier documentation or existing contract fixtures available in the repository.

Establish how multiple requested occupancies are represented and how the returned results identify the rooms and rates applicable to those occupancies.

If the existing contract or available documentation cannot establish whether the returned result satisfies the complete allocation, do not invent a guarantee. Stop that part of the implementation and report the precise unresolved contract question.

### 5.2.1 Demonstrated supplier evidence (3 November 2026)

The following tests were conducted through Postman against the Hotelbeds test services on 3 November 2026. The authoritative evidence record is `HBX-AV-009` in `docs/08-integration/hotelbeds/HBX-001-certification-readiness.md` (sections 12 and 12.1).

#### MR-01 — One room, two adults

- One occupancy entry: one room, two adults.
- Hotelbeds returned individual room types and rate options with `rateKey` values.
- Some identical rate objects were repeated in the response with identical `rateKey` values and prices.

#### MR-02 — Two rooms, two adults per room

- Two separate occupancy entries, each requesting one room and two adults.
- Hotelbeds returned rates with `rooms: 1`, `adults: 2`, `children: 0`.
- The response did not provide an explicit GCT room-slot identifier.
- Identical rate objects and `rateKey` values were repeated.
- `allotment` values were returned. Their inventory scope and concurrency semantics remain undocumented.

#### MR-03 — Two rooms with different occupancy

- Room 1: two adults, no children. Room 2: two adults, one child aged seven.
- The initial request, which supplied child ages through `childrenAges`, was rejected by Hotelbeds with `INVALID_DATA: If children >= 1 it is mandatory that you specify a paxes element per child.`
- The corrected request used `paxes: [{ "type": "CH", "age": 7 }]` and succeeded.
- Hotelbeds returned occupancy-specific rate variants, including `rooms: 1`, `adults: 2`, `children: 0` and `rooms: 1`, `adults: 2`, `children: 1`, `childrenAges: "7"`.
- For The Whale Coast All Suite Hotel, the adult-only and child-occupancy offers had different `rateKey` values despite matching property, room type, dates and net amount.
- The response also demonstrated that not every room type supports every requested occupancy.

#### Successful combined booking — booking reference 241-749700

Hotelbeds confirmed one booking containing two different room types at The Whale Coast All Suite Hotel.

- Check-in: 18 November 2026. Check-out: 19 November 2026.
- The booking request contained two separate entries in `rooms`.
- The first entry used the Availability `rateKey` for `APT.B2` (opaque identifier `917288786`). The second used the Availability `rateKey` for `APT.B3-C6` (opaque identifier `705047521`).
- Each entry contained its own passenger list with two adults.
- Both `rateKey` values were submitted unchanged from the matching Availability response, timestamped `2026-11-03 14:54:19.942`. The exact Availability-to-Booking `rateKey` match was verified.
- The booking response returned overall status `CONFIRMED`, booking reference `241-749700`, and two room objects, each with `status: CONFIRMED`.
  - Room 1: `APT.B2`, two adults, net EUR 272.24.
  - Room 2: `APT.B3-C6`, two adults, net EUR 281.34.
  - Total net: EUR 553.58.

This is direct transaction evidence that Hotelbeds accepted two different room offers, selected from one Availability response, in one combined booking request and confirmed both rooms.

#### Supplier pricing reconciliation (unresolved)

The booking returned higher net amounts than the matching Availability response.

| Room | Availability | Booking | Difference |
|---|---|---|---|
| `APT.B2` | EUR 266.91 | EUR 272.24 | +EUR 5.33 |
| `APT.B3-C6` | EUR 275.83 | EUR 281.34 | +EUR 5.51 |
| Total | EUR 542.74 | EUR 553.58 | +EUR 10.84 |

This is recorded as an unresolved supplier pricing reconciliation question. No explanation is asserted. It must not be assumed to be tax, commission, repricing or a currency issue. The CUR-001 currency integrity requirements are unchanged: no currency conversion or substitution is introduced.

#### Passenger `roomId` observation

The booking request assigned `roomId: 1` to passengers in both room entries. The response returned two room objects with IDs 1 and 2, but the passengers in both room objects still had `roomId: 1`. This is an observed supplier request/response behaviour that requires clarification. The request convention must not be changed silently, and the supplier response must not be asserted to be defective.

#### Behaviour established by the evidence

1. Hotelbeds accepts multiple occupancy entries in one Availability request.
2. Each requested room can be represented by a separate occupancy entry with `rooms: 1`.
3. Hotelbeds can return rate offers describing different occupancy combinations.
4. Returned occupancy attributes (`rooms`, `adults`, `children`, `childrenAges`) can distinguish adult-only and child-occupancy offers.
5. Different room types can be selected in one booking.
6. Multiple selected room `rateKey` values can be submitted together in one booking request.
7. Hotelbeds confirmed both rooms in the demonstrated combined booking.
8. `rateKey` values must be preserved unchanged as opaque supplier references.
9. GCT room-slot identity remains an application-owned identity. No supplier room-slot identifier exists or may be invented.
10. Passenger allocations must remain associated with the correct GCT room selection through the booking handoff.
11. When children are supplied, Hotelbeds requires one `paxes` element per child carrying its age. This corroborates the existing request contract and does not establish any age limit.

The order of rates in a supplier response does not identify the requested room slot. Duplicate identical rate objects must not be treated as additional inventory or additional room offers.

#### Questions that remain unresolved

- The exact semantics and inventory scope of `allotment`, including whether it is shared across rate variants or occupancy groups.
- General guarantees of simultaneous availability beyond the successful demonstrated transaction.
- Formal rate-to-requested-occupancy mapping rules across all possible supplier responses.
- The meaning of `rate.rooms > 1`.
- The semantics of duplicate response entries.
- The formal meaning and scope of the passenger `roomId`.
- The explanation for the price difference between Availability and Booking.
- Whether any supplier-specific booking or CheckRate conditions change these conclusions.

### 5.2.2 Accepted allocation principle and implementation

The multi-room Availability allocation described in this section is implemented and architecturally accepted. It is the allocation capability that was previously held back pending supplier evidence; the evidence in section 5.2.1 and the accepted architectural decision below replace that restriction.

#### Allocation principle

- A Hotelbeds `rateKey` identifies one supplier offer.
- Each requested room slot receives exactly one matching offer.
- One `rateKey` cannot be allocated to more than one GCT Core room slot. Separate room allocations require distinct `rateKey` values.
- An offer must match the requested room's occupancy: adults, children and each individual child age.
- Offers must originate from the same successful Availability response for the relevant accommodation stop and stay dates.
- A rate that describes more than one room (`rate.rooms > 1`) is not accepted as an offer for a single room slot, because its semantics are unresolved.
- Duplicate identical response entries are one offer and do not count as additional offers or inventory.
- Entries that share a `rateKey` but are described inconsistently (different room, occupancy, amount, currency or status) are ambiguous and the property is rejected.
- A complete allocation, with a distinct matching offer for every requested room slot of the stop, is required before the property is presented to the customer. An incomplete, duplicate or ambiguous allocation is not presented. Because every stop must have an offer, the journey is then unavailable.
- Response order does not identify the requested room slot, and the allocation does not assume one response entry per requested slot.
- The allocation does not rely on the unverified semantics of `allotment`.
- Fail-closed behaviour remains required for incomplete, ambiguous or inconsistent supplier responses.

#### Separate identifiers

GCT Core room-slot identity (for example `stop-1-room-2`) and the Hotelbeds `rateKey` are separate identifiers. The slot is application-owned and is never sent to or derived from the supplier. The `rateKey` is an opaque supplier reference and is preserved unchanged through selection, pricing, reservation handoff and persistence. Each selected room keeps its own occupancy, room type, rate, amount and currency.

#### Implementation record

- The previous production restriction that rejected every stop requesting more than one room (`isSuitableResult` in `src/application/merchandising/homepage/showcase/cape-winelands-journey-resolver.ts`) has been removed and replaced by the allocation rules above. The rules are enforced in that function; selection (`DefaultAccommodationSelectionService`), quote, reservation handoff and persistence already enforced distinct rate references, slot identity and occupancy per room.
- The Reservation persistence round-trip restores each occupancy room's `slotId` (INT-004.4-A1), consistent with `selectedRooms[].roomSlotId`.
- CUR-001 currency integrity is unchanged, and the Cape Winelands adults-only policy is unchanged.

#### Verification evidence

The accepted implementation was verified with the full regression suite: 129 test suites and 878 tests passed. Type-check, lint (no errors), Prisma validation and a build to a temporary output directory also succeeded. Focused tests cover two rooms of different room types with different `rateKey` values, two rooms of the same room type with different `rateKey` values, different occupancies including a child and its age, duplicate and inconsistent `rateKey` rejection, missing offers, occupancy mismatch, `rate.rooms > 1`, single-room behaviour, selection, and the preservation of `rateKey` and slot identity through persistence. The fixtures are modelled on the Postman reference transaction (booking `241-749700`) with synthetic `rateKey` values. They are not live supplier responses and do not constitute certification.

#### Scope boundary: allocation accepted, combined booking lifecycle not implemented

What is accepted is Availability allocation: complete, distinct-`rateKey` allocation of requested rooms, presented only when complete.

The combined multi-room booking lifecycle is not implemented. The downstream contract is that the selected rooms are submitted together in one booking request, passenger assignments stay with the correct GCT room selection, and the actual supplier booking response is authoritative evidence of the confirmed transaction. The combined booking requirement describes the intended downstream supplier handoff contract. It does not authorise implementation of supplier booking or confirmation in the current INT-004.4 iteration. Any such implementation remains subject to its own approved specification and scope. The existing booking, CheckRate, cancellation and payment behaviour is unchanged.

### 5.3 Result validation

A property must not be presented as satisfying an allocation unless the returned availability evidence supports every requested room slot for that stop.

The application must verify:

- Every requested room slot has a corresponding valid selection candidate.
- Each candidate's occupancy is compatible with that room slot.
- Adult counts and child ages are consistent with the requested occupancy and supplier response.
- Room and rate references belong to the returned property and offer.
- The full requested allocation can be represented without reusing an incompatible or non-distinct supplier room/rate reference.
- Every required room has valid pricing and currency metadata under the existing contract.

Do not assume that room identifiers must always be globally unique across different supplier result shapes. Determine the identity semantics from the existing canonical contract and enforce uniqueness at the correct scope.

If a supplier result does not prove a valid complete allocation, mark the offer unavailable or invalid using the existing result conventions. Never fabricate missing rooms, rates, occupancy, or prices.

### 5.4 Duplicate selection protection

`DefaultAccommodationSelectionService` must reject attempts to use the same room/rate selection repeatedly across multiple requested room slots when the supplier contract does not permit that reuse.

Validate the selection server-side against the original owner-scoped offered result. Client-provided room IDs, rates, occupancy, or room-slot labels are not authoritative.

A rejected allocation must not be stored as a successful selection or passed into pricing.

## 7. Selection state, pricing, and reservation continuity

### 7.1 Selection state

Store the complete per-stop allocation and selected room/rate references through the existing INT-004.3 owner-scoped selection store.

Every read, mutation, and clear operation must retain the existing session-owner and journey-ID requirements.

Changing a stop's dates or occupancy must invalidate affected selections and cached offers through the existing lifecycle. Do not leave a quote or selection valid against an allocation that has changed.

Do not add unscoped store methods or restore journey-ID-only ownership.

### 7.2 Pricing

Preserve the existing APP-005 boundary.

The selected accommodation pricing input for each stop must include the correct:

- Package-stop identity and order.
- Property identity.
- Room and rate references.
- Per-room occupancy and child ages.
- Supplier amount, currency, and pricing basis.
- Room count and stay period.

The existing GCT pricing engine remains responsible for the authoritative customer-facing package price. Do not add supplier costs more than once, replace the GCT package price with supplier cost, or invent currency conversions.

Verify how the existing supplier amount and `pricingBasis` apply to each returned room/rate. Do not multiply or aggregate amounts using assumptions that are not established by the existing contract.

If the allocation contains incompatible or unconfirmed currencies, use the established currency-safety behavior. Do not misclassify a currency mismatch as an ordinary stale selection if the existing error contract can represent it accurately.

### 7.3 Review and reservation handoff

Preserve the complete selected occupancy and room allocation through the existing review and reservation handoff.

At the handoff boundary, verify that every selected stop and room retains the correct:

- Stop identity and order.
- Stay dates.
- Property, room, and rate references.
- Adult counts and individual child ages.
- Supplier amounts and currencies.
- Provider identity and existing opaque supplier references.
- Authoritative final GCT package price.

Reuse the existing reservation snapshot and booking-request mapping. Extend the mapping only where required data is demonstrably lost.

This iteration does not authorize supplier booking, payment, confirmation, cancellation, or unrelated Reservation persistence changes.
