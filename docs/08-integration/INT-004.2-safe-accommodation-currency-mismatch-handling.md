# INT-004.2 — Safe Accommodation Currency Mismatch Handling

**Status:** Architect Approved for Implementation
**Type:** Focused implementation specification
**Scope:** GCT Core — Cape Winelands dynamic availability and pricing
**Dependencies:** Approved INT-004 and INT-004.1

## 1. Objective

Prevent an accommodation supplier currency mismatch from producing an unhandled error or an apparently valid but mathematically invalid package total.

The current GCT group component is denominated in ZAR. Hotelbeds accommodation offers must retain their actual returned supplier currency until the account’s currency configuration is confirmed.

## 2. Mandatory Business Rules

1. Never add amounts denominated in different currencies.
2. Do not invent or apply a currency conversion rate.
3. Do not force a currency in the Hotelbeds request unless explicitly supported and approved.
4. Do not change the existing Hotelbeds endpoint, authentication, TLS adapter, signature generation, or Availability request contract.
5. Preserve the supplier amount and currency in the canonical accommodation offer and relevant diagnostics.
6. If the accommodation currency cannot be safely combined with the ZAR group component, do not present a combined package total.
7. A missing or unknown accommodation currency must not be treated as ZAR.
8. A currency mismatch must result in a controlled application outcome, not an unhandled exception.
9. Do not weaken validation or silently discard currency information to make pricing succeed.
10. Do not perform CheckRate, booking, cancellation, or payment operations.

## 3. Implementation Requirements

### 3.1 Quote service

Inspect the existing accommodation pricing input, quote service, controller, and view-model path.

Handle the existing currency validation failure explicitly. Use the existing application result and error conventions where possible.

The outcome must distinguish between:

- A valid quote where all required amounts are compatible.
- A quote that cannot be finalised because accommodation currency is incompatible or unknown.
- Existing genuine availability or validation failures.

Do not introduce a second pricing engine or duplicate currency rules across layers.

### 3.2 User-facing experience

When a quote cannot be safely finalised:

- Display the Go Cape Tours group component in ZAR if the existing journey already has a valid group quote.
- Display accommodation supplier prices only with their actual currency.
- Explain that a final combined package price is temporarily unavailable because the accommodation currency requires confirmation.
- Do not display a combined total, misleading zero total, or stale total.
- Do not allow the journey to proceed as though a final quote were valid.
- Preserve the existing selected journey and accommodation state where appropriate so the guest does not have to restart unnecessarily.

Follow the existing Express/EJS server-rendered architecture. Do not introduce SPA behaviour or redesign unrelated pages.

### 3.3 State invalidation

Ensure a previously valid quote cannot remain visible or usable after a change that makes its pricing invalid, including accommodation currency or selection changes.

Reuse existing quote and selection invalidation mechanisms where possible. Do not introduce unrelated persistence or session redesign.

## 4. Tests

Add focused tests covering at least:

1. Compatible ZAR pricing continues to produce the existing valid quote.
2. EUR accommodation amounts are not added to the ZAR group component.
3. Unknown or missing supplier currency cannot be treated as ZAR.
4. Currency mismatch produces a controlled result rather than an unhandled exception.
5. The rendered journey does not show a combined total when pricing is invalid.
6. A previous valid total cannot survive a change to incompatible accommodation pricing.
7. Existing valid pricing, accommodation selection, and reservation handoff behaviour remain unaffected.

Use deterministic unit and integration tests. Do not make live supplier requests.

## 5. Constraints

- Do not modify approved business prices or the group pricing schedule.
- Do not implement currency conversion.
- Do not change Hotelbeds configuration or credentials.
- Do not modify Prisma schema or introduce new persistence.
- Do not expand into other journeys, payments, or booking operations.
- Keep changes limited to the currency failure path and directly necessary tests.
- Preserve all unrelated tracked and untracked work.
