# INT-004.4-A1 — Reservation Occupancy Slot Identity Restoration

**Status:** Implementation specification  
**Type:** Focused persistence mapping correction  
**Parent:** INT-004.4 — Multi-Room Availability and Occupancy Allocation Correctness  
**Governing process:** `docs/09-governance/GOV-DEV-001-DEVELOPMENT-PROCESS.md`

## 1. Objective

Correct the canonical Reservation Prisma repository mapping so that application-owned room-slot identity is preserved when a Reservation is reconstructed from persistence.

The identified gap is in:

`src/infrastructure/persistence/repositories/canonical-reservation-prisma.repository.ts`

The `toDomain` mapping restores `occupancy.rooms[]` without restoring each room's `slotId`, although the Reservation domain model and reservation handoff carry that identity.

The correction must preserve the existing canonical Reservation contract without introducing new persistence infrastructure.

## 3. Scope

Included:

- Inspect the Reservation domain occupancy structure.
- Inspect the Prisma repository's persistence mapping in both directions.
- Identify how room-slot identity is represented in the persisted Reservation snapshot.
- Restore `slotId` for every reconstructed `occupancy.rooms[]` entry.
- Preserve consistency with the corresponding `selectedRooms[].roomSlotId`.
- Add focused repository tests covering the complete round-trip.

Excluded:

- Prisma schema changes.
- Database migrations.
- Changes to the canonical Reservation aggregate.
- Changes to accommodation selection or availability matching.
- Changes to Hotelbeds request or response mapping.
- Changes to pricing or currency behaviour.
- Changes to reservation handoff semantics.
- Supplier booking, payment or confirmation implementation.
- Any modification to the production multi-room fail-closed guard.

## 4. Required behaviour

### 4.1 Persistence round-trip

When a Reservation containing multiple occupancy rooms is persisted and reconstructed:

- Every room must retain its original `slotId`.
- Adult counts must remain unchanged.
- Child counts must remain unchanged.
- Individual child ages must remain unchanged and associated with the correct room.
- Room ordering must remain unchanged.
- The associated selected room's `roomSlotId` must remain consistent with the occupancy room's `slotId`.

Do not generate new slot IDs during reconstruction.

Do not infer slot identity from array position when the persisted representation already contains the identity.

### 4.2 Mapping authority

Inspect the existing write mapping before changing `toDomain`.

Use the existing persisted representation as the source of truth. Do not introduce a second representation or modify the schema merely to work around a mapping omission.

If the persisted Reservation representation does not contain enough information to restore the original slot identity, stop and report the precise gap. Do not invent an identity or silently substitute another value.

### 4.3 Backward compatibility

Inspect existing Reservation records and repository conventions before defining behaviour for missing or legacy slot IDs.

Do not invent a fallback identity.

If legacy records require a compatibility rule, document the evidence and implement only a rule supported by the existing canonical contract. Otherwise report the limitation.

## 5. Required tests

Extend the existing canonical Reservation Prisma repository tests.

At minimum, verify:

1. A single-room occupancy retains its slot ID after persistence and reconstruction.
2. A multi-room occupancy retains every distinct slot ID.
3. Room ordering is preserved.
4. Adult counts and child ages are preserved for each room.
5. `occupancy.rooms[].slotId` agrees with the corresponding `selectedRooms[].roomSlotId`.
6. Existing Reservation persistence tests continue to pass.
7. Existing records without a slot ID follow only the verified compatibility behaviour.

Tests must use deterministic fixtures and must not require live supplier calls.
