## 2. Purpose

APP-008.3-R8 verifies the complete accepted Hotelbeds Accommodation Availability flow against the real Hotelbeds supplier.

R1-R7 are accepted and SHALL remain architecturally unchanged.

R8 SHALL validate the complete application path:

    R8 Test-Only Composition Root
            ↓
    Test-Only In-Memory Catalogue
            ↓
    R7 Application Availability Service
            ↓
    R2 Candidate Resolution
            ↓
    R3 Availability Request Construction
            ↓
    R6 Supplier Protection
            ↓
    R4 Hotelbeds Transport & Execution
            ↓
    Hotelbeds
            ↓
    R5 Response Mapping
            ↓
    Canonical Accommodation Availability Result

R8 is a controlled supplier-verification iteration.

R8 is NOT Hotelbeds certification.

Certification remains a later, single process after the required Hotelbeds integration capabilities are complete.

## 3. Architectural Decisions

The following decisions are authoritative for R8.

### 3.1 Test-Only Composition

R8 SHALL use a dedicated test-only composition root.

It SHALL assemble the existing R1-R7 production classes for verification.

It MUST NOT alter production application bootstrap.

### 3.2 Test-Only Catalogue

R8 SHALL use an isolated in-memory catalogue repository seeded with exactly one configured Hotelbeds hotel.

This is test-local memory only.

It is NOT a production catalogue modification.

It MUST NOT persist data.

R2 SHALL still perform the actual candidate resolution.

R8 MUST NOT inject a resolved candidate directly into R3.

### 3.3 R7 Remains the Application Entry Point

The live verification harness SHALL invoke the accepted R7 Availability Service.

R8 MUST NOT directly invoke:

- R4 transport;
- R4 gateway;
- authentication;
- R6 executor;
- R5 mapper;
- Hotelbeds provider internals.

### 3.4 No Alternative Supplier Path

R8 SHALL use the existing provider and execution path.

No second HTTP client, retry mechanism, rate limiter, concurrency mechanism, or response-mapping path may be introduced.

### 3.5 Daily Supplier Allowance

The known Hotelbeds testing allowance of 50,000 requests/day is an external supplier allowance.

R8 SHALL NOT implement application-level daily quota accounting.

R8 SHALL use the minimum practical number of live requests and rely on the accepted R6 protection.

### 3.6 mTLS

R8 SHALL use the accepted R4 transport unchanged.

R8 MUST NOT implement an mTLS workaround.

If the configured Hotelbeds test environment requires mTLS that the accepted R4 transport cannot provide, live verification SHALL be reported as blocked by an R4 prerequisite.

### 3.7 R6 Configuration

R8 MUST NOT work around the identified R6 QPS/concurrency configuration-precedence issue.

If the issue remains present, it SHALL be reported as an R6 issue.

R8 SHALL use the effective accepted R6 protection.

## 5. Test-Only Composition Root

Create a dedicated test-only live verification entrypoint.

Recommended location:

    src/scripts/hotelbeds/availability-live-verification.ts

The exact repository location may follow the existing script/test organisation if an equivalent test-only location already exists.

The entrypoint MUST NOT be imported by production application code.

It MUST NOT execute as part of the normal Jest test suite.

It SHALL compose the existing production components.

The composition SHALL include:

- `InMemoryHotelCatalogueRepository`;
- existing Hotel Catalogue Service;
- `InMemoryProviderRegistry`;
- existing Hotelbeds Provider;
- existing Hotelbeds Availability Request Builder;
- existing R7 Availability Service;
- existing Hotelbeds integration configuration;
- existing provider dependencies.

Where existing constructor defaults are appropriate, the harness SHOULD reuse them rather than duplicating lower-level configuration.

The composition root is not a second application flow.

It is only a test composition of the accepted application flow.

## 6. Test Catalogue Fixture

The harness SHALL create a new isolated:

    InMemoryHotelCatalogueRepository

The repository SHALL contain exactly one `HotelCatalogueEntry`.

The entry SHALL use the existing catalogue model.

It SHALL contain:

- configured Hotelbeds hotel code;
- valid star grading;
- non-empty destination code;
- non-empty zone code;
- non-empty zone name;
- active status.

The exact valid values SHALL use the existing catalogue model constraints.

The Hotelbeds hotel code SHALL come from:

    HOTELBEDS_AVAILABILITY_LIVE_HOTEL_CODE

The fixture SHALL be created only inside the R8 verification process.

It MUST NOT:

- modify production catalogue records;
- write to Prisma;
- create migrations;
- persist state;
- modify production repository configuration.

R2 SHALL resolve the hotel through:

    HotelCatalogueService.select(...)

The harness MUST NOT pass a manually constructed candidate into R3.

If R2 cannot resolve the configured hotel from the fixture, the verification SHALL stop before supplier execution.

## 8. Explicit Live Enablement

Live verification SHALL be controlled by:

    HOTELBEDS_AVAILABILITY_LIVE_VERIFY

The parser SHALL implement exactly:

| Value | Behaviour |
|---|---|
| absent | disabled |
| empty | disabled |
| `false` | disabled |
| `0` | disabled |
| `true` | enabled |
| `1` | enabled |
| any other non-empty value | fail closed |

Live verification MUST be disabled by default.

The flag SHALL be evaluated by the R8 test-only harness.

It MUST NOT be added to the general Hotelbeds integration configuration.

Credentials being present MUST NOT enable live execution.

Normal application execution MUST NOT enable live execution.

## 11. Configuration Validation

When live verification is enabled, the harness MUST validate all required configuration before constructing or invoking the supplier execution path.

Validation SHALL include:

- live verification flag;
- Hotelbeds hotel code;
- check-in;
- check-out;
- valid date range;
- adult occupancy;
- child occupancy where applicable;
- child ages where applicable;
- source market;
- required Hotelbeds credentials/configuration.

Invalid configuration MUST result in:

- no R7 invocation;
- no R2 invocation;
- no R3 invocation;
- no R6 invocation;
- no R4 invocation;
- no supplier call.

Configuration validation MUST NOT make network calls.

## 12. Fail-Closed Safety

The following conditions SHALL produce zero supplier calls:

- live flag absent;
- live flag disabled;
- invalid live flag;
- missing hotel code;
- invalid hotel code;
- missing check-in;
- missing check-out;
- invalid date range;
- invalid occupancy;
- missing required child ages;
- missing source market;
- missing required Hotelbeds configuration.

The harness MUST NOT substitute defaults for required live test values.

The harness MUST NOT automatically select another hotel.

## 19. mTLS Handling

The current R4 transport passes TLS configuration through its existing transport abstraction.

The current repository does not establish that native Node `fetch` uses the configured custom TLS object to create a client certificate connection.

Therefore R8 SHALL treat mTLS as an environment-dependent R4 prerequisite.

If the Hotelbeds test environment does NOT require mTLS:

- use R4 unchanged;
- proceed with R8.

If the Hotelbeds test environment DOES require mTLS and the accepted R4 transport cannot establish it:

- do not modify R4 in R8;
- do not create an alternate transport;
- report the R4 prerequisite;
- do not claim successful live verification.

R8 MUST NOT make an architectural decision about mTLS implementation itself.

## 22. Live Verification Success Criteria

A live verification is successful when:

1. live verification was explicitly enabled;
2. all required configuration passed validation;
3. the test-only catalogue fixture was created;
4. R2 resolved the configured hotel;
5. R3 created the request;
6. R6 protection executed;
7. R4 contacted Hotelbeds;
8. Hotelbeds returned a response;
9. R5 mapped the response;
10. R7 returned the canonical Availability result.

The final canonical result SHALL be reported without exposing supplier secrets or unnecessary raw supplier data.

---

## 23. Live No-Availability Result
