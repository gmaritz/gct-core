# APP-008.3-CAN-001 — Canonical Availability No-Result Contract

**Document ID:** APP-008.3-CAN-001  
**Status:** Approved for Implementation  
**Capability:** Accommodation Availability  
**Provider:** Hotelbeds  
**Scope:** Canonical Availability result contract and zero-result handling  
**Depends On:** Existing canonical Availability model, R2-R7, APP-008.3-R5-C1 investigation  
**Implementation Type:** Cross-boundary canonical contract correction

---

## 1. Purpose

APP-008.3-CAN-001 establishes the canonical representation of a valid Availability search that returns no accommodation results.

Hotelbeds has been verified to return the following valid Availability response:

    {
      "hotels": {
        "total": 0
      }
    }

This response contains no hotel, room, rate, or accommodation identity.

The current canonical `AccommodationAvailabilityResult` requires:

    accommodation: Accommodation

This prevents R5 from representing a valid supplier zero-result response without fabricating accommodation data.

This specification introduces an explicit canonical `NO_AVAILABILITY` result state and defines the R5-to-R7 mapping contract required to produce it.

---

## 2. Architectural Decision

`AccommodationAvailabilityResult` shall become a discriminated union.

The canonical result shall distinguish:

1. a result containing a real accommodation;
2. a valid result where no accommodation is available.

The discriminant shall be:

    kind

The two canonical states are:

    kind: "ACCOMMODATION"

and:

    kind: "NO_AVAILABILITY"

This prevents the presence or absence of `accommodation` from being inferred indirectly from `available`.

---

## 3. Canonical Result Contract

The canonical result shall be represented conceptually as:

    type AccommodationAvailabilityResult =
      | {
          readonly kind: "ACCOMMODATION";
          readonly accommodation: Accommodation;
          readonly available: boolean;
          readonly metadata: AccommodationResultMetadata;
        }
      | {
          readonly kind: "NO_AVAILABILITY";
          readonly accommodation?: never;
          readonly available: false;
          readonly metadata: AccommodationResultMetadata;
        };

The exact formatting shall follow existing project TypeScript conventions.

### 3.1 ACCOMMODATION

`kind: "ACCOMMODATION"` requires:

- a real `Accommodation`;
- existing `available` semantics;
- existing metadata.

Existing positive-availability behaviour must remain unchanged.

The `available` property remains boolean because an accommodation result may legitimately exist while its availability state is false under existing application semantics.

### 3.2 NO_AVAILABILITY

`kind: "NO_AVAILABILITY"` requires:

- `available: false`;
- valid `metadata`;
- no `Accommodation`.

The result must not fabricate accommodation information.

The `accommodation?: never` constraint is intended to prevent accidental construction of an accommodation-bearing no-availability result.

---

## 4. No-Availability Semantics

`NO_AVAILABILITY` means:

> The Availability search was successfully processed, but no accommodation was returned for the requested criteria.

It does not mean:

- malformed response;
- transport failure;
- TLS failure;
- authentication failure;
- supplier error;
- R2 candidate-resolution failure;
- R3 request-construction failure.

The canonical result must preserve this distinction.

---

## 5. Verified Hotelbeds Zero-Result Response

The following supplier response is authoritative for this capability:

    {
      "hotels": {
        "total": 0
      }
    }

R5 shall classify this response as:

    NO_AVAILABILITY

R5 shall not:

- throw a malformed-response error;
- fabricate an `Accommodation`;
- create a fake hotel;
- create a fake room;
- create a fake rate;
- invent supplier metadata.

---

## 6. R5 Mapping Contract

R5 shall no longer require every valid supplier response to immediately produce `AccommodationAvailabilityResult`.

R5 shall return an intermediate discriminated mapping outcome.

The contract shall be:

    type HotelbedsAvailabilityMappingResult =
      | {
          readonly kind: "ACCOMMODATION";
          readonly result: AccommodationAvailabilityResult;
        }
      | {
          readonly kind: "NO_AVAILABILITY";
        };

The exact type location shall follow the existing provider/mapping architecture.

### 6.1 ACCOMMODATION Mapping

When the supplier response contains:

    response.hotels.hotels[]

R5 shall perform the existing accommodation, room, and rate mapping.

The result shall be:

    {
      kind: "ACCOMMODATION",
      result: <existing canonical accommodation result>
    }

Existing positive mapping behaviour shall remain unchanged.

### 6.2 NO_AVAILABILITY Mapping

When the supplier response contains:

    response.hotels.total === 0

R5 shall return:

    {
      kind: "NO_AVAILABILITY"
    }

R5 shall not construct a canonical result for this branch because it does not possess valid accommodation data.

---

## 7. Supplier Response Classification

R5 shall recognize the verified Hotelbeds response forms.

### 7.1 Availability

Recognize:

    response.hotels.hotels[]

as the supplier hotel collection.

### 7.2 No Availability

Recognize:

    response.hotels.total === 0

as valid no availability.

### 7.3 Malformed Response

Responses that do not match a supported structure shall remain rejected.

Examples include:

- missing `hotels`;
- unsupported `hotels` structure;
- non-array `hotels.hotels`;
- missing collection where `total` does not establish valid zero availability;
- arbitrary supplier JSON that cannot safely be interpreted.

Do not classify arbitrary missing hotel collections as `NO_AVAILABILITY`.

---

## 8. Supplier Error Distinction

A supplier error or warning response must remain distinct from `NO_AVAILABILITY`.

R5 shall not convert:

- supplier error envelopes;
- authentication errors;
- malformed responses;
- unsupported response variants;

into `NO_AVAILABILITY` unless the verified supplier contract explicitly establishes the response as a valid zero-result response.

The only newly authorized zero-result condition is:

    response.hotels.total === 0

---

## 9. R7 Orchestration Contract

R7 shall consume the R5 mapping outcome.

The flow shall be:

    Hotelbeds response
          ↓
    R5 mapper
          ↓
    HotelbedsAvailabilityMappingResult
          ↓
       ┌──┴──┐
       ↓     ↓
    ACCOMMODATION
       ↓
    existing canonical result

    NO_AVAILABILITY
       ↓
    R7 canonical result construction
       ↓
    canonical NO_AVAILABILITY result

R7 is responsible for converting the R5 `NO_AVAILABILITY` outcome into:

    {
      kind: "NO_AVAILABILITY",
      available: false,
      accommodation: undefined,
      metadata: <valid application metadata>
    }

The exact TypeScript construction shall follow the canonical type.

---

## 10. R7 Metadata

R7 shall construct valid `AccommodationResultMetadata` for the `NO_AVAILABILITY` result using metadata already available to the application.

R7 must not fabricate supplier accommodation data.

R7 must not add:

- audit tokens;
- supplier credentials;
- rate keys;
- raw supplier responses;
- certificates;
- private keys;
- passphrases.

If an existing metadata factory or construction pattern exists, it should be reused.

---

## 11. Existing Unavailable Sentinel

The existing `createUnavailableResult(provider)` behaviour shall remain temporarily unchanged.

It currently creates a sentinel accommodation with values such as:

    identity: "unavailable"

and is used for existing upstream scenarios including:

- R2 resolving no candidates;
- R3 producing no requests.

This sentinel shall **not** be reused for the new supplier `NO_AVAILABILITY` state.

Therefore:

    R2 no candidates
        ≠
    supplier NO_AVAILABILITY

and:

    R3 no requests
        ≠
    supplier NO_AVAILABILITY

The sentinel remains a temporary compatibility mechanism for those existing paths.

A future migration/deprecation specification may replace it with the new canonical no-accommodation representation.

---

## 12. Positive Availability Compatibility

The positive accommodation path must remain semantically unchanged.

Existing results shall continue to contain:

- real `Accommodation`;
- existing `available` semantics;
- existing metadata;
- mapped rooms;
- mapped rates;
- existing supplier information that is already part of the canonical result.

The only required structural addition is:

    kind: "ACCOMMODATION"

Consumers shall use `kind` to safely distinguish canonical result states.

## 13. Consumer Migration

All production consumers of `AccommodationAvailabilityResult` must be identified and updated where required.

At minimum inspect:

- `accommodation-availability.result.ts`;
- `DefaultAccommodationAvailabilityService`;
- provider interfaces;
- `accommodation-inventory-service.ts`;
- `accommodation-composition-adapter.ts`;
- homepage/journey services;
- API/application serializers;
- merchandising consumers;
- availability consumers;
- journey composition;
- related tests.

### 13.1 Consumer Rule

Consumers must not assume:

    result.accommodation

is always present.

Consumers must narrow on:

    result.kind

before accessing:

    result.accommodation

### 13.2 ACCOMMODATION Branch

For:

    result.kind === "ACCOMMODATION"

the consumer may safely access:

    result.accommodation

### 13.3 NO_AVAILABILITY Branch

For:

    result.kind === "NO_AVAILABILITY"

the consumer must not attempt to access accommodation properties.

The consumer must apply the appropriate existing no-availability behaviour.

Do not fabricate accommodation data at consumer level.

## 14. Inventory Service

`accommodation-inventory-service.ts` currently contains logic that unconditionally clones or accesses:

    result.accommodation

This must be updated to narrow the canonical result before accommodation access.

For:

    NO_AVAILABILITY

the inventory layer must preserve the no-accommodation semantics.

It must not construct a fabricated accommodation solely to satisfy existing cloning logic.

The existing inventory result contract must be reviewed and adjusted only as necessary to support the canonical union.

## 28. Final Architecture

The completed flow shall be:

    Hotelbeds
        ↓
    R4-C1 transport
        ↓
    R5 response mapper
        ↓
    ┌───────────────────────────────┐
    │ HotelbedsAvailabilityMapping  │
    │ Result                        │
    └───────────────────────────────┘
          ↓                  ↓
    ACCOMMODATION      NO_AVAILABILITY
          ↓                  ↓
    R7 canonical       R7 canonical
    result             result
          ↓                  ↓
    real               no accommodation
    accommodation      available
                           ↓
                    available = false

The critical invariant is:

    A valid supplier zero-result response must never require or create a fabricated Accommodation.

---

## 29. Architectural Principle

Availability and no availability are both valid outcomes of an Availability search.

A successful search that returns zero accommodations is not:

- an error;
- malformed data;
- an accommodation;
- or a fabricated sentinel accommodation.

The canonical model must represent that state explicitly.

APP-008.3-CAN-001 therefore establishes the canonical contract required for R5 and R7 to handle verified Hotelbeds zero availability correctly.
