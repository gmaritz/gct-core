# APP-008.3-CAN-002 — Canonical Accommodation Availability Options

**Document ID:** APP-008.3-CAN-002  
**Status:** Approved for Architect Review  
**Capability:** Accommodation Availability  
**Bounded Context:** Reservations  
**Depends On:** APP-008.3-CAN-001, APP-008.3-R3-C1, APP-008.3-R5-C1  
**Purpose:** Define the canonical GCT Core representation of accommodation availability options returned by suppliers, including rooms, rates, occupancy, pricing, board, cancellation policies, taxes, and supplier booking references.

---

## 1. Purpose

APP-008.3-CAN-002 extends the canonical Accommodation Availability contract so that GCT Core can represent the commercially meaningful accommodation choices returned by suppliers.

The canonical availability result must not stop at:

- accommodation identity;
- accommodation metadata;
- available/unavailable status.

It must also expose the accommodation options required by a client searching a tour package.

The canonical model must therefore be capable of representing:

- available rooms;
- room types;
- rates;
- rate identifiers;
- occupancy;
- pricing;
- currency;
- board/meal plan;
- bookability;
- allotment;
- cancellation policies;
- taxes;
- supplier references required for subsequent booking operations.

The model must remain supplier-neutral.

Hotelbeds is the first implementation provider, but Hotelbeds-specific JSON structures must not become the canonical domain contract.

---

## 2. Business Requirement

A client searching a Go Cape Tours package must ultimately be able to specify and receive accommodation availability based on requirements such as:

- number of rooms;
- adults per room;
- children per room;
- child ages.

The availability response must allow the client/application to evaluate the available accommodation options and select an appropriate room/rate combination.

Therefore the canonical Availability model must preserve enough information to support a later selection and booking workflow.

The canonical model must not discard supplier room/rate information after merely determining whether an accommodation is available.

---

## 3. Architectural Principle

The canonical Availability result represents two distinct concepts:

### Accommodation identity

The property being offered.

### Availability options

The commercially selectable room/rate combinations available for the requested search.

These concepts must be modelled separately.

The accommodation itself must not become a container for transient supplier availability data.

---

## 4. Canonical Result

The existing APP-008.3-CAN-001 discriminated result remains authoritative.

Positive result:

    kind: "ACCOMMODATION"

    accommodation: Accommodation

    available: true

    metadata: AccommodationResultMetadata

For positive availability, the result must additionally expose availability options.

Conceptually:

    AccommodationAvailabilityResult
        |
        +-- kind: "ACCOMMODATION"
        +-- accommodation
        +-- available
        +-- metadata
        +-- availabilityOptions
              |
              +-- room options
                    |
                    +-- rate options

The exact TypeScript structure must be confirmed during architect review against the existing canonical model.

Do not implement an unapproved structure before architect acceptance.

---

## 5. Availability Options

Introduce a canonical supplier-neutral representation for the commercially selectable availability returned for an accommodation.

The model should distinguish:

    Availability Option
        |
        +-- Room
        |
        +-- Rate

An availability option must represent a valid combination of:

- accommodation;
- room type;
- occupancy;
- rate;
- pricing;
- booking conditions.

The model must not assume that one accommodation has only one room or one rate.

---

## 6. Room Option

A canonical room option must represent a distinct room type returned by the supplier.

At minimum it must be capable of representing:

- room identifier/code;
- room name;
- one or more rate options;
- applicable occupancy information where required;
- supplier reference where required.

Example conceptual structure:

    AvailabilityRoomOption
        roomCode
        name
        rates[]

The exact field names are subject to architect review.

---

## 7. Rate Option

A canonical rate option represents a commercially selectable rate associated with a room.

It must be capable of representing:

- supplier rate identifier;
- rate classification;
- bookability/status;
- price;
- currency;
- board/meal plan;
- allotment;
- payment type;
- packaging status where commercially relevant;
- occupancy;
- cancellation policies;
- taxes;
- supplier references required for subsequent booking.

The canonical model must preserve the supplier rate identity required to perform a later booking operation.

---

## 8. Rate Identity

A rate must have a stable identifier within the availability result.

For Hotelbeds this is currently:

    rateKey

The canonical field must be supplier-neutral, for example conceptually:

    supplierRateReference

or another architect-approved equivalent.

The Hotelbeds `rateKey` must not be exposed as a domain-specific field name in the canonical model.

The original supplier reference must remain recoverable for downstream provider operations.

---

## 9. Supplier Identity

The availability option must remain associated with its provider.

The existing provider identity conventions must be preserved.

The canonical model must support downstream operations such as:

    Availability
        ↓
    Client selects room/rate
        ↓
    Booking
        ↓
    Provider-specific booking request

The selected canonical option must therefore retain the supplier reference information necessary to reconstruct the provider booking request.

---

## 10. Pricing

The canonical availability option must represent the price returned by the supplier.

At minimum:

- amount;
- currency.

The existing canonical `Money` value object must be used where appropriate.

No provider-specific numeric representation must become the canonical pricing model.

Do not perform currency conversion in the Availability mapper.

The supplier currency must be preserved.

---

## 11. Price Semantics

The architect must establish whether the canonical availability price represents:

- total stay price;
- per-room price;
- per-night price;
- another supplier-defined pricing basis.

The canonical model must not silently assume a pricing basis that is not supported by the supplier contract.

For Hotelbeds, the verified response provides:

    net

at rate level and:

    currency

at hotel level.

R5 must preserve the supplier pricing semantics accurately.

If the existing canonical model lacks an explicit pricing-basis representation and that distinction is necessary for correct client display or booking, the architect must resolve it before implementation.

---

## 12. Occupancy

Occupancy is a first-class part of availability.

The canonical availability option must support:

- rooms;
- adults;
- children;
- child ages.

The model must support future multi-room searches.

A single global occupancy value is insufficient for the long-term booking requirement.

Conceptually:

    AvailabilitySearch
        |
        +-- Occupancy Group 1
        |     +-- rooms
        |     +-- adults
        |     +-- children
        |     +-- child ages
        |
        +-- Occupancy Group 2
              ...

The exact relationship between search occupancy and returned rate occupancy must be defined during architect review.

---

## 13. Multi-Room Requirement

The canonical model must not assume:

    rooms = 1

as a permanent business rule.

The current R8 controlled verification uses one room, but production package searching must support client-selected room quantities.

The model must therefore support multiple rooms without requiring a future breaking redesign.

The implementation of configurable room input is a separate capability and is not part of CAN-002 implementation unless the architect determines that the canonical contract cannot support it without defining the structure now.

---

## 14. Children and Child Ages

Children are part of occupancy.

The canonical model must preserve:

- number of children;
- age of each child.

The model must not collapse children into an undifferentiated count when age-specific supplier pricing or availability may depend on those ages.

For the verified Hotelbeds response:

    children: 1

    childrenAges: "7"

must remain representable canonically as a child count and age information.

---

## 15. Board / Meal Plan

Hotelbeds provides:

    boardCode

    boardName

The canonical rate option must represent the applicable board/meal-plan information where commercially relevant.

The canonical field must be supplier-neutral.

Do not create:

    hotelbedsBoardCode

or equivalent supplier-specific canonical fields.

---

## 16. Bookability

The canonical rate option must represent whether the rate is:

- bookable;
- recheck-required;
- another architect-approved supported state.

Hotelbeds currently provides:

    rateType

including:

    BOOKABLE

    RECHECK

The canonical model must not lose this distinction.

A rate that requires recheck must not be presented as equivalent to a directly bookable rate if the booking workflow requires different handling.

---

## 17. Allotment

Hotelbeds provides:

    allotment

The canonical rate option must preserve allotment where it has commercial significance.

Allotment must not be used as the sole definition of availability unless the canonical availability rules explicitly require it.

---

## 18. Payment Type

Hotelbeds provides:

    paymentType

The architect must determine whether payment type is required by the canonical booking workflow.

If required, it must be represented in the canonical rate option using a supplier-neutral concept.

If not required for Availability but required for downstream booking, the supplier reference must remain available through an approved provider-reference structure.

Do not discard information required to execute a later booking.

---

## 19. Packaging

Hotelbeds provides:

    packaging

The architect must determine whether this is:

- canonical availability information;
- booking metadata;
- provider-specific booking information.

It must not be blindly added to the domain model.

If required for booking, it must remain available through an approved provider-specific reference mechanism.

---

## 20. Cancellation Policies

Cancellation policies belong to the rate option rather than the accommodation itself.

The canonical rate model must therefore support rate-specific cancellation conditions.

At minimum, the model must be capable of representing:

- effective date/time;
- cancellation amount;
- currency where applicable;
- applicable policy sequence/order.

For Hotelbeds:

    cancellationPolicies[]

contains:

    amount

    from

The canonical representation must preserve these semantics.

---

## 21. Taxes

Taxes belong to the applicable rate/price.

The canonical availability option must be capable of representing tax information when the supplier provides it and when the booking/client presentation requires it.

Hotelbeds currently provides:

    included
    percent
    amount
    currency
    type
    clientAmount
    clientCurrency
    subType

and:

    allIncluded

The architect must determine the minimum canonical tax representation required by the commercial and booking workflows.

Do not introduce a supplier-specific tax model.

---

## 22. Hotel-Level Min/Max Rates

Hotelbeds provides:

    minRate
    maxRate

These values are aggregate supplier response values.

They must not replace the actual room/rate pricing structure.

If useful for search-result summaries, the canonical model may expose approved aggregate pricing information.

However:

- min/max must remain derived from actual options where possible;
- the canonical model must not treat minRate/maxRate as the selected booking price;
- the selected rate must retain its own price.

---

## 23. Accommodation vs Availability Options

The canonical Accommodation represents relatively stable property information.

Availability options represent search-specific information.

Therefore:

### Accommodation

May contain:

- identity;
- name;
- category;
- location;
- rating;
- images;
- amenities;
- contacts;
- stable policies;
- provider identity.

### Availability Options

May contain:

- room;
- rate;
- price;
- currency;
- occupancy;
- board;
- cancellation;
- taxes;
- allotment;
- bookability;
- supplier rate reference;
- search-specific conditions.

Do not place transient supplier rate information into `Accommodation`.

---

## 24. Provider Neutrality

The canonical model must not contain Hotelbeds-specific structures.

Forbidden canonical examples:

    hotelbedsRateKey

    hotelbedsBoardCode

    hotelbedsRoomCode

    hotelbedsCancellationPolicy

    hotelbedsTaxes

Supplier-specific values may exist inside provider adapters or approved provider-reference structures.

---

## 25. R5 Contract

R5 must be able to transform:

    response.hotels.hotels[]

into the canonical availability representation.

R5 must preserve:

- hotel identity;
- room options;
- rate options;
- occupancy;
- pricing;
- board;
- bookability;
- cancellation;
- taxes;
- supplier references.

R5 must not:

- perform booking;
- perform rate recheck;
- perform payment;
- perform room selection;
- perform package composition;
- modify R2 candidate resolution;
- modify R3 request construction.

---

## 26. R7 Contract

R7 remains responsible for application-level orchestration.

R7 must expose the canonical availability result produced by R5 without losing the detailed availability options.

The selected option must remain capable of being passed into a later booking workflow.

R7 must not collapse:

    accommodation
    + rooms
    + rates

into only:

    available: true

---

## 27. Inventory and Consumer Compatibility

Existing consumers must be reviewed.

Particular attention is required for:

- `accommodation-inventory-service.ts`;
- `accommodation-composition-adapter.ts`;
- journey composition;
- merchandising;
- package search;
- API/application serializers;
- availability result freezing/cloning;
- tests assuming availability results contain only accommodation-level data.

Consumers must be updated to preserve the new options without breaking existing positive availability semantics.

No consumer may silently discard room/rate options.

---

## 28. Selection and Booking Boundary

CAN-002 does not implement booking.

It establishes the canonical information required to allow a later selection:

    Accommodation
        ↓
    Room Option
        ↓
    Rate Option
        ↓
    Client selection
        ↓
    Booking capability

The canonical rate reference must therefore be sufficient for the provider integration to identify the selected supplier rate.

The actual booking contract remains outside APP-008.3.

---

## 29. No-Availability Contract

APP-008.3-CAN-001 remains authoritative.

For:

    hotels.total === 0

the canonical result remains:

    kind: "NO_AVAILABILITY"

    available: false

    accommodation: absent

    availabilityOptions: absent or empty

The exact representation must be consistent across all canonical results.

No room/rate option may exist in a `NO_AVAILABILITY` result.

---

## 30. Positive Availability Contract

A valid positive result must contain:

    kind: "ACCOMMODATION"

    accommodation

    available: true

    availabilityOptions

The availability options must contain one or more valid commercially selectable options when Hotelbeds has returned bookable availability.

The model must not report:

    available: true

while discarding all available room/rate information.

---

---

## 32. Existing Models

The existing `AccommodationRate` and `AccommodationRateResult` models must be reviewed.

They must not be reused implicitly merely because they contain some overlapping fields.

The architect must determine whether:

1. they are suitable to become part of the canonical Availability contract;
2. they should be extended;
3. a new canonical Availability Options model is required;
4. an existing model can be composed into Availability through an explicit contract.

The decision must preserve bounded-context ownership and avoid duplicate representations of the same business concept.

---

## 33. Backward Compatibility

Existing valid accommodation results must remain semantically valid.

The extension must not break:

- accommodation identity;
- availability state;
- metadata;
- existing positive result consumers.

Where possible, existing consumers should continue to function while being extended to consume availability options.

Any breaking change must be explicitly identified and approved.

## 36. Room-Count Product Requirement

The canonical model must support future client-configurable room searches.

The production search experience must eventually allow a client to specify:

- room count;
- adults;
- children;
- child ages;
- occupancy per room.

CAN-002 must not hard-code a one-room limitation into the canonical model.

The implementation of client input and R8 configuration is a separate capability, but CAN-002 must establish a canonical structure that does not require redesign when that capability is implemented.

---

## 37. Separation of Concerns

CAN-002 defines the canonical data contract.

It does not implement:

- search UI;
- package configuration;
- room selection UI;
- booking;
- payment;
- rate recheck;
- cancellation;
- supplier booking.

Those capabilities will consume the canonical availability options.

- stop;
