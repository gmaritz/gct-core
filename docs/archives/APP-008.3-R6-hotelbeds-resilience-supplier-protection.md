## 2. Purpose

APP-008.3-R6 establishes the resilience and supplier-protection controls around the accepted Hotelbeds Availability execution path.

The objective is to ensure that GCT Core can execute Availability requests without exceeding configured Hotelbeds request-rate constraints and without allowing transient supplier instability to create uncontrolled request pressure.

R6 builds on the accepted R4 execution boundary and the R5 canonical mapping boundary.

R6 SHALL protect the supplier execution boundary.

R6 MUST NOT redesign R4 or R5.

---

## 3. Architectural Baseline

The accepted APP-008.3 sequence is:

R1 — Availability Foundation  
→ R2 — Catalogue Candidate Resolution  
→ R3 — Availability Request Construction  
→ R4 — Hotelbeds Transport & Execution  
→ R5 — Availability Canonical Result Mapping  
→ R6 — Resilience & Supplier Protection

R1-R5 are accepted contracts.

R6 SHALL operate around the existing Hotelbeds Availability execution path.

R6 MUST preserve:

- R3 request construction;
- R4 transport behaviour;
- R4 bounded retry behaviour;
- R5 canonical result mapping.

R6 MUST NOT change the meaning of an Availability result.

---

## 4. Supplier Constraints

Hotelbeds testing access is currently configured for:

- 20 requests per second (QPS);
- 50,000 requests per day.

These limits SHALL be treated as the current supplier-protection configuration baseline.

The implementation MUST NOT hard-code these values into domain logic.

Supplier protection SHALL be configuration driven.

The design MUST allow the configured limits to be changed without modifying application/domain code.

---

## 5. Scope

### 5.1 In Scope

R6 SHALL implement:

- bounded Hotelbeds Availability request-rate protection;
- configurable requests-per-second limit;
- controlled concurrency for supplier execution;
- protection against burst submission;
- supplier execution throttling at the Hotelbeds integration boundary;
- integration of rate limiting with the existing Availability execution path;
- protection against retry amplification;
- configuration-driven resilience settings;
- focused resilience tests;
- deterministic behaviour under controlled test conditions.

### 5.2 Out of Scope

R6 MUST NOT implement:

- new Availability response mapping;
- canonical model changes;
- CheckRate;
- Booking;
- Cancellation;
- database persistence;
- daily quota persistence or accounting;
- supplier certification;
- supplier-specific business rules unrelated to request protection;
- replacement of the existing HTTP transport;
- replacement of the existing authentication mechanism;
- new retry semantics unless required specifically to prevent retry amplification;
- unrelated provider refactoring;
- unrelated lint cleanup.

---

## 6. Resilience Boundary

R6 SHALL establish resilience controls at the Hotelbeds Availability execution boundary.

The conceptual flow SHALL be:

R3 Requests
→ R6 Supplier Protection
→ R4 Availability Execution
→ Hotelbeds

and:

Hotelbeds response
→ R4 Execution Result
→ R5 Mapping

R6 MUST NOT sit inside the canonical response-mapping layer.

R6 MUST NOT modify the R5 canonical result contract.

---

## 7. Rate Limiting

R6 SHALL enforce a configurable maximum Hotelbeds request rate.

The rate limiter SHALL ensure that execution does not intentionally exceed the configured requests-per-second limit.

The initial configured baseline SHALL support:

`20 requests / second`

The value MUST be configuration driven.

The implementation MUST prevent bursts from immediately exceeding the configured supplier rate.

A request that cannot execute immediately because the rate limit has been reached SHALL wait according to the configured rate-limiting policy.

R6 MUST NOT silently discard requests because the rate limit is temporarily reached.

---

## 8. Concurrency Control

R6 SHALL provide bounded concurrency for Hotelbeds Availability execution.

The concurrency limit MUST be configuration driven.

The implementation MUST prevent an unrestricted number of simultaneous Hotelbeds requests.

Concurrency control MUST work together with the request-rate limiter.

The implementation MUST NOT assume that a QPS limit alone is sufficient to control concurrent network activity.

R6 MUST preserve the deterministic ordering semantics already established for the R4 Availability request list where the existing execution contract requires ordered result association.

---

## 9. Retry Amplification Protection

R4 already provides bounded retry behaviour.

R6 MUST NOT introduce a second independent retry mechanism.

Instead, R6 SHALL ensure that retries remain subject to the same supplier-protection controls as initial requests.

A retry is a supplier request and MUST therefore:

- pass through the rate limiter;
- count toward concurrency;
- not bypass supplier-protection controls.

The implementation MUST prevent a transient supplier failure from producing an uncontrolled retry burst.

R6 MUST preserve the existing R4 retry classification and finite retry limit unless a change is strictly required to prevent supplier-protection failure.

---

## 10. Request Ordering

R6 MUST preserve the association between each R3 request and its eventual R4 execution result.

Rate limiting or concurrency scheduling MUST NOT cause result misassociation.

Each request SHALL retain its existing request/batch index.

R6 MUST NOT:

- merge requests;
- split requests;
- reconstruct requests;
- reorder request semantics;
- alter hotel-code batches.

Scheduling order MAY differ internally where bounded concurrency requires it, but result identity and batch association MUST remain deterministic.

If the existing R4 contract requires strict sequential execution, R6 MUST preserve that contract rather than introducing concurrency that changes accepted behaviour.

---

## 11. Burst Protection

R6 SHALL prevent an incoming batch of Availability requests from immediately generating an uncontrolled burst against Hotelbeds.

The protection mechanism MUST apply equally to:

- initial requests;
- retries.

The implementation MUST NOT simply insert a fixed delay between requests if that would fail to enforce the configured rate under concurrent execution.

Use the smallest appropriate rate-limiting mechanism compatible with the existing architecture.

Do not introduce a general-purpose distributed rate-limiting platform.

---

## 12. Configuration

Supplier-protection settings MUST be configuration driven.

The configuration SHALL support at minimum:

- maximum requests per second;
- maximum concurrent supplier requests.

Configuration names SHALL follow the existing Hotelbeds integration configuration conventions.

The default configuration SHALL be suitable for the current Hotelbeds testing limit.

The implementation MUST allow lower values for controlled testing.

Configuration values MUST be validated.

Invalid resilience configuration MUST fail predictably rather than silently disabling supplier protection.

---

## 13. Configuration Validation

The following conditions MUST be rejected:

- requests-per-second less than 1;
- concurrency less than 1;
- non-numeric values;
- invalid numeric values;
- values that cannot be safely represented by the implementation.

Configuration validation MUST occur before supplier execution begins.

R6 MUST NOT silently replace invalid values with unlimited execution.

---

## 14. Supplier Protection Semantics

The supplier-protection layer SHALL be integration infrastructure.

It MUST NOT become part of:

- the canonical Accommodation domain model;
- Availability business rules;
- booking rules;
- pricing rules.

The rate limiter and concurrency controller MUST remain inside the Hotelbeds integration/infrastructure boundary.

---

## 15. Timeout Interaction

R6 SHALL preserve the existing R4 timeout configuration.

Waiting for rate-limit permission and executing the HTTP request are distinct activities.

The implementation MUST define the interaction clearly:

- supplier protection MUST NOT disable the existing HTTP timeout;
- waiting for a rate-limit slot MUST NOT create an unbounded wait;
- a request already admitted to transport remains subject to the R4 timeout.

R6 MUST NOT introduce a second conflicting timeout mechanism.

---

## 16. Failure Handling

R6 MUST NOT convert supplier-protection failures into successful Availability results.

If resilience configuration is invalid, execution MUST fail before supplier calls occur.

If the resilience mechanism itself encounters an infrastructure failure, the failure MUST be surfaced through the existing integration error boundary.

R6 MUST NOT silently bypass rate limiting when the protection mechanism fails.

Fail-safe supplier protection is preferred over uncontrolled supplier execution.

---

## 17. Daily Quota

The current Hotelbeds daily limit of 50,000 requests SHALL be treated as an operational supplier constraint.

R6 MUST NOT introduce persistent daily quota accounting in this iteration.

The system MUST NOT claim to enforce the 50,000-request daily quota unless an authoritative persistent accounting mechanism exists.

Daily quota monitoring, accounting and enforcement remain outside R6.

The implementation MUST avoid creating the false impression that QPS protection is equivalent to daily quota protection.

---

## 18. Retry and Daily Quota

Every retry remains a supplier request.

R6 SHALL therefore ensure retries pass through the same QPS and concurrency controls.

R6 MUST NOT introduce persistent daily quota counting for retries.

No request counter or quota database model shall be introduced.

---

## 19. Interaction with R4

R4 remains responsible for:

- HTTP execution;
- authentication;
- mTLS;
- GZIP;
- timeout;
- retry classification;
- bounded retry execution;
- structured raw supplier response.

R6 remains responsible for:

- request-rate protection;
- concurrency protection;
- retry amplification protection;
- resilience configuration.

R6 MUST NOT duplicate R4 responsibilities.

---

## 20. Interaction with R5

R5 remains responsible for:

- interpretation of successful supplier responses;
- canonical Accommodation Availability mapping.

R6 MUST NOT modify:

- canonical result structures;
- availability semantics;
- response-mapping behaviour.

R6 MUST remain transparent to R5 except for execution timing and controlled failure propagation.

---

## 21. Testability

The resilience mechanism MUST be testable without real time delays where practical.

Focused tests SHOULD use controllable clocks/timers or equivalent deterministic test mechanisms.

Tests MUST NOT depend on:

- real Hotelbeds access;
- real 20 QPS timing;
- real daily quota consumption;
- unpredictable network timing.

---

## 22. Testing Requirements

Automated tests MUST NOT call Hotelbeds.

### 22.1 Rate Limit

Tests SHALL verify:

- configured QPS limit is respected;
- requests do not bypass the limiter;
- bursts are controlled;
- lower configured limits work deterministically.

### 22.2 Concurrency

Tests SHALL verify:

- maximum concurrent requests are bounded;
- concurrency cannot exceed configuration;
- requests are eventually released after completion.

### 22.3 Retry Protection

Tests SHALL verify:

- initial requests pass through supplier protection;
- retries also pass through supplier protection;
- retries do not bypass the QPS limit;
- retries do not exceed concurrency;
- existing finite retry behaviour remains intact.

### 22.4 Configuration

Tests SHALL verify:

- valid configuration is accepted;
- invalid QPS configuration is rejected;
- invalid concurrency configuration is rejected;
- zero/negative values are rejected;
- configuration can be reduced for controlled testing.

### 22.5 Failure Safety

Tests SHALL verify:

- invalid resilience configuration prevents supplier execution;
- resilience infrastructure failure does not silently bypass protection;
- supplier-protection failures remain integration failures.

### 22.6 Request Association

Tests SHALL verify:

- every R3 request remains associated with the correct result;
- batch/request indexes are preserved;
- concurrent scheduling cannot misassociate results.

### 22.7 Empty Input

Tests SHALL verify:

- zero requests cause zero supplier calls;
- no rate-limit or concurrency activity is unnecessarily created.

### 22.8 Regression

Existing R4 and R5 tests MUST remain passing.

The full Jest regression suite MUST be executed.

---

## 26. Acceptance Criteria

### AC-01 — Configurable QPS Protection

Hotelbeds Availability requests are subject to a configurable maximum requests-per-second limit.

### AC-02 — Current Supplier Baseline

The configuration supports the current Hotelbeds baseline of 20 QPS without hard-coding that value into application/domain logic.

### AC-03 — Burst Protection

A batch of requests cannot intentionally bypass the configured rate limit through immediate burst submission.

### AC-04 — Configurable Concurrency

Concurrent Hotelbeds requests are bounded by configuration.

### AC-05 — Retry Protection

R4 retries are subject to the same R6 supplier-protection controls as initial requests.

### AC-06 — Retry Semantics

Existing bounded R4 retry classification and finite retry behaviour remain intact unless a narrowly justified change is required for supplier protection.

### AC-07 — Configuration Validation

Invalid QPS or concurrency configuration prevents supplier execution.

### AC-08 — Request Association

R3 request/batch identity remains correctly associated with the resulting R4 execution result.

### AC-09 — Empty Input

An empty request set produces zero supplier calls.

### AC-10 — Failure Safety

Supplier-protection failure never silently bypasses the protection mechanism.

### AC-11 — Daily Quota Boundary

R6 does not falsely claim to enforce the 50,000-request daily quota and introduces no persistent daily quota accounting.

### AC-12 — R4 Preservation

R4 HTTP, authentication, mTLS, GZIP, timeout and retry responsibilities remain intact.

### AC-13 — R5 Preservation

R5 canonical Availability mapping remains unchanged.

### AC-14 — No Persistence

R6 introduces no database writes or schema changes.

### AC-15 — Regression

Existing accepted R1-R5 behaviour remains intact.
