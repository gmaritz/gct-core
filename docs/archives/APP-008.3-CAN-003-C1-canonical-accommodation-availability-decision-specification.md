## 2. Purpose

This specification resolves the remaining canonical architecture decisions identified during the APP-008.3-CAN-003 architect review.

The objective is to establish a stable, supplier-neutral Accommodation Availability contract that can support the complete commercial lifecycle:

Client search
→ multi-room occupancy
→ accommodation availability
→ room selection
→ rate selection
→ pricing/cancellation/tax evaluation
→ supplier-neutral selection
→ future booking

The contract must support detailed accommodation availability without making Hotelbeds the canonical model.

Hotelbeds remains a provider adapter.

No R5-C2 implementation shall begin until this specification is architect-approved.

---

## 3. Architectural Principles

### 3.1 Canonical Ownership

GCT Core owns the canonical Availability model.

Provider adapters translate supplier-specific structures into the canonical model.

The canonical model must never expose supplier-specific field names.

### 3.2 Commercial Completeness

Availability is not a boolean.

A positive Availability result must preserve the commercial option graph required for client selection:

Accommodation
→ Room Options
→ Rate Options

### 3.3 Booking Continuity

A selected availability option must retain sufficient supplier-neutral information to allow a later booking operation to resolve the selected supplier offer.

### 3.4 Multi-Room First

The canonical contract must support multiple rooms with independently defined occupancy.

No canonical contract may assume one room.

### 3.5 Dynamic vs Static Data

`Accommodation` represents relatively stable accommodation information.

Availability-specific room, rate, pricing, cancellation, tax, and booking information belongs to the Availability model.

### 3.6 Explicit Absence

No availability must be represented explicitly.

A valid supplier no-availability response must never require fabrication of an accommodation.

### 3.7 No Supplier Leakage

Supplier-specific concepts such as Hotelbeds `rateKey`, `rateType`, `rateClass`, or supplier response envelopes must remain inside the provider adapter.

## 4. Canonical Result Cardinality

### 4.1 Decision

One `AccommodationAvailabilityResult` represents one accommodation.

A search may return multiple accommodation results.

The canonical search-level result is therefore an ordered collection:

    AccommodationAvailabilityResults
        results: AccommodationAvailabilityResult[]

The individual result remains discriminated:

    AccommodationAvailabilityResult
        ├── ACCOMMODATION
        └── NO_AVAILABILITY

### 4.2 Positive Result

A positive result represents one accommodation and contains:

- accommodation;
- requested occupancy;
- availability options;
- metadata.

### 4.3 No Availability

`NO_AVAILABILITY` represents the search outcome where the supplier confirms that no accommodation options are available for the requested search.

It contains:

- `kind`;
- `available: false`;
- metadata.

It does not contain:

- accommodation;
- room options;
- rate options;
- pricing;
- cancellation policies;
- taxes;
- supplier references.

### 4.4 Search-Level Empty Result

A search returning zero accommodation candidates is represented by:

    AccommodationAvailabilityResults
        results: []

This is distinct from an individual accommodation returning no availability.

The distinction is:

- empty result collection = no accommodation result exists;
- `NO_AVAILABILITY` = a specific accommodation/search outcome is explicitly unavailable.

The provider adapter must not invent accommodation results solely to represent supplier absence.

## 5. Canonical Availability Request

### 5.1 Request

The canonical request is:

    AccommodationAvailabilityRequest

        stay
            checkIn
            checkOut

        occupancy
            rooms[]

                adults
                children
                childAges[]

        sourceMarket

        candidateSelection

### 5.2 Stay

`checkIn` and `checkOut` represent the requested stay period.

Invariants:

- check-in is before check-out;
- dates are represented using the established canonical date representation;
- supplier-specific date formatting is adapter responsibility.

### 5.3 Occupancy

The request contains an ordered list of room occupancy groups.

Each room group contains:

- `adults`;
- `children`;
- `childAges`.

Invariants:

- at least one room;
- each room contains at least one adult;
- `children` equals the number of child ages;
- child ages are non-negative valid ages;
- room order is significant and must be preserved.

The canonical request does not contain a scalar `rooms` field.

The number of rooms is derived from `occupancy.rooms.length`.

### 5.4 Source Market

Source market is represented as a canonical ISO-style market/country identifier.

Provider-specific validation or transformation is adapter responsibility.

### 5.5 Candidate Selection

Candidate selection is application-owned.

It may represent:

- explicit accommodation identifiers;
- destination selection;
- zone selection;
- other approved catalogue selection mechanisms.

Provider-specific filtering rules are not part of the canonical request.

## 6. Requested Occupancy vs Offered Occupancy

### 6.1 Decision

The canonical model distinguishes:

1. requested occupancy;
2. rate-offered occupancy.

Requested occupancy belongs to the Availability search.

Offered occupancy belongs to a `RateOption`.

### 6.2 Requested Occupancy

The requested occupancy is preserved on the positive Availability result.

It represents what the client asked for.

### 6.3 Offered Occupancy

Each `RateOption` contains the occupancy to which that rate applies.

This allows the supplier response to be represented accurately where a returned rate has occupancy information differing from the original request representation.

### 6.4 Multi-Room

Offered occupancy is represented as an ordered collection of room occupancy groups.

A rate must not silently collapse multi-room occupancy into aggregate adults/children counts.

---

## 7. Availability Options

### 7.1 Structure

A positive result contains:

    AvailabilityOptions

        roomOptions[]

### 7.2 Purpose

`AvailabilityOptions` represents dynamic accommodation inventory returned for the requested search.

It is not part of the static `Accommodation` entity.

### 7.3 Invariants

- room options preserve supplier-independent ordering;
- each room option belongs to the accommodation result;
- each room option contains zero or more rate options;
- only commercially meaningful room options should be returned;
- provider-specific response metadata is not exposed.

---

## 8. Room Option

### 8.1 Structure

    RoomOption

        reference
        name
        rateOptions[]

### 8.2 Reference

The room reference is a supplier-neutral opaque reference.

It is not a Hotelbeds-specific field.

Where the supplier does not provide a distinct room reference sufficient for booking continuity, the provider adapter may derive a stable provider-scoped opaque reference.

### 8.3 Name

`name` is the canonical display name of the room option.

It is presentation-oriented and supplier-neutral.

### 8.4 Rate Relationship

Rates belong to the room option:

    RoomOption
        rateOptions[]

A rate must not be detached from its room context.

### 8.5 Multi-Room

A returned room option represents a room type/option.

A client selecting multiple rooms may select a room option independently for each requested room, subject to the availability and booking rules of the provider.

The canonical model must not assume that all requested rooms use the same room option.

---

## 9. Rate Option

### 9.1 Structure

    RateOption

        bookingReference
        status
        pricing
        occupancy
        board
        allotment
        payment
        packaging
        cancellationPolicies[]
        taxes[]

### 9.2 Purpose

`RateOption` represents one commercially selectable rate for a specific room option.

### 9.3 Rate Identity

Every bookable or recheckable rate must contain a supplier-neutral `bookingReference`.

The reference is opaque to the canonical domain.

---

## 10. Supplier Reference

### 10.1 Structure

    SupplierReference

        provider
        opaqueReference

### 10.2 Provider

`provider` identifies the provider responsible for the reference.

It is represented using the existing canonical provider identity convention where available.

### 10.3 Opaque Reference

`opaqueReference` is an opaque provider-issued or provider-derived reference.

The canonical model must not interpret its internal structure.

For Hotelbeds, the adapter may place the supplier `rateKey` into `opaqueReference`.

The canonical model must never expose a field named `rateKey`.

### 10.4 Booking Continuity

The selected rate's `SupplierReference` must be sufficient for the provider adapter to resolve the selected supplier offer during booking.

The provider adapter remains responsible for interpreting the opaque reference.

---

## 11. Rate Status

### 11.1 Canonical Status

Rate status is supplier-neutral.

The minimum canonical states are:

    BOOKABLE
    RECHECK_REQUIRED

Additional states may only be introduced when they represent a genuine business distinction.

### 11.2 Supplier Mapping

Provider-specific status values are mapped by the adapter.

For example, a supplier's `BOOKABLE` value may map to canonical `BOOKABLE`.

A supplier response requiring a live revalidation step maps to `RECHECK_REQUIRED`.

Supplier-specific status names must not appear in the canonical contract.

---

## 12. Pricing

### 12.1 Decision

Pricing is represented using the established canonical `Money` abstraction where compatible with Availability semantics.

No new duplicate Money model is introduced solely for Availability.

If the existing Money implementation requires extension for Availability currency coverage or precision, the extension must be made to the shared canonical Money contract rather than creating a parallel Availability Money type.

### 12.2 Rate Pricing

A rate contains:

    pricing
        amount
        currency
        basis

The implementation must use the established Money representation for `amount + currency`.

### 12.3 Pricing Basis

The canonical pricing basis must explicitly identify how the amount applies.

Minimum supported basis:

    TOTAL_STAY

Additional bases may include:

    PER_ROOM
    PER_NIGHT
    PER_ROOM_PER_NIGHT

Only bases actually required by provider contracts or business use may be introduced.

### 12.4 Net vs Customer Price

The canonical Availability price represents the amount available for commercial client selection.

Provider-specific `net` terminology must not automatically become the canonical semantic name.

The provider adapter must determine whether the supplier amount represents:

- customer-facing price;
- supplier net;
- another defined commercial amount.

The canonical pricing specification must identify the semantic meaning of the mapped amount.

### 12.5 Tax Inclusion

Pricing must explicitly identify whether taxes/fees are included in the displayed amount.

A raw numeric price without defined tax semantics is invalid.

---

## 13. Hotel-Level Min/Max Rates

### 13.1 Decision

Hotel-level `minRate` and `maxRate` are derived presentation summaries, not authoritative booking prices.

They are not required in the canonical `Accommodation` entity.

If exposed by the Availability result, they must be represented as derived pricing summaries from the canonical rate options.

### 13.2 Source Independence

The canonical model must not depend on a supplier's `minRate` or `maxRate` fields.

A provider may supply those values, but the adapter may instead derive them from mapped canonical rates.

### 13.3 Invariant

`minRate` must never imply that a client can book the minimum amount without selecting the corresponding room/rate option.

The authoritative commercial price is always the selected `RateOption.pricing`.

---

## 14. Board / Meal Plan

### 14.1 Structure

Board is represented as a supplier-neutral concept:

    BoardOption

        code
        name

### 14.2 Supplier Mapping

Provider-specific board codes are mapped into canonical board codes.

The canonical model does not use supplier-specific board terminology.

### 14.3 Optionality

Board may be absent where the supplier does not provide a meaningful meal-plan concept.

---

## 15. Allotment

### 15.1 Decision

Allotment may be represented on `RateOption` when supplied and commercially meaningful.

It represents the supplier's available inventory quantity for the rate.

### 15.2 Semantics

Allotment is informational availability data.

It must not be interpreted by the canonical domain as an unconditional booking guarantee.

The provider remains authoritative at booking time.

---

## 16. Payment

### 16.1 Decision

Payment information is represented as canonical booking-relevant information.

The minimum distinction is:

    AT_PROPERTY
    AT_BOOKING

or the equivalent established canonical payment vocabulary where the repository already provides one.

### 16.2 Supplier Independence

Provider-specific payment codes must be translated by the adapter.

The canonical model must describe the commercial payment behavior rather than the supplier's field names.

### 16.3 Optionality

Payment information is optional where the supplier does not provide a meaningful distinction.

---

## 17. Packaging

### 17.1 Decision

Packaging is retained as a canonical rate attribute because it may affect commercial interpretation and booking behavior.

Minimum representation:

    packaged: boolean

### 17.2 Semantics

`packaged` indicates whether the rate is subject to package pricing/packaging semantics.

The canonical model must not expose supplier-specific packaging flags or terminology beyond the business meaning.

---

## 18. Cancellation Policies

### 18.1 Structure

Each `RateOption` may contain ordered cancellation policies:

    CancellationPolicy[]

        effectiveFrom
        penalty
        refundable

### 18.2 Effective Time

`effectiveFrom` represents the canonical point at which the stated cancellation consequence becomes effective.

It must preserve timezone-aware date/time information.

### 18.3 Penalty

`penalty` uses canonical Money.

A cancellation policy must not contain an unqualified numeric amount.

### 18.4 Refundability

The canonical model explicitly represents whether the rate remains refundable under the policy.

### 18.5 Ordering

Cancellation policies are ordered chronologically by effective time.

### 18.6 Non-Refundable Rates

A non-refundable rate is represented explicitly through the cancellation policy semantics.

The absence of a cancellation policy must not automatically mean non-refundable.

---

## 19. Taxes and Fees

### 19.1 Decision

Availability requires a supplier-neutral tax/fee representation.

The existing pricing tax concepts may be reused where their semantics are compatible.

A duplicate Availability-specific tax model must not be created without architectural justification.

### 19.2 Minimum Structure

Each tax/fee item must support:

    TaxOrFee

        type
        subtype
        amount
        percentage
        included

`amount` uses canonical Money.

### 19.3 Tax vs Fee

The canonical model must distinguish:

- tax;
- fee.

They must not be collapsed into an undifferentiated amount.

### 19.4 Inclusion

`included` identifies whether the item is included in the associated rate price.

### 19.5 Aggregate Inclusion

A supplier-level aggregate such as `allIncluded` may be translated into the canonical individual tax/fee inclusion semantics.

The canonical model must not depend on the supplier aggregate field.

### 19.6 Double Counting

The adapter must not produce duplicate tax/fee items representing the same commercial charge.

The canonical result must preserve the relationship between:

- rate price;
- included taxes/fees;
- excluded taxes/fees.

---

## 20. Payment, Tax and Cancellation Currency

All monetary values must use canonical Money.

This includes:

- rate price;
- cancellation penalties;
- taxes;
- fees;
- derived price summaries.

No monetary field may use an independent numeric amount plus supplier-specific currency string.

---

## 21. Offered Occupancy

### 21.1 Structure

Rate occupancy is represented as:

    Occupancy

        rooms[]

            adults
            children
            childAges[]

### 21.2 Relationship

The occupancy belongs to the rate option because the supplier may return rate-specific occupancy information.

### 21.3 Validation

The adapter must validate supplier-provided occupancy before constructing the canonical object.

Invalid supplier occupancy must not be silently normalized into a different search.

---

## 22. Requested Occupancy Preservation

The positive Availability result preserves the original requested occupancy.

This allows consumers to distinguish:

    requested occupancy

from:

    rate offered occupancy

This distinction is required for multi-room package search and future booking selection.

---

## 23. Selection and Booking Continuity

### 23.1 Selection

A client selects:

1. accommodation;
2. room option;
3. rate option.

### 23.2 Selection Identity

The selected rate contains its `SupplierReference`.

The selected room contains its canonical room reference and, where required, its supplier-neutral opaque reference.

### 23.3 Booking Snapshot

The selected availability option must retain the information required to reconstruct the provider-specific booking request.

The canonical booking process must not need to rediscover a rate by searching again merely because the original supplier reference was discarded.

### 23.4 Provider Translation

The provider adapter translates:

    SupplierReference
    +
    selected room/rate context
    +
    booking request

into the provider-specific booking request.

Hotelbeds `rateKey` interpretation remains entirely inside the Hotelbeds adapter.

---

## 24. Existing AccommodationRate

`AccommodationRate` is not the canonical Availability `RateOption`.

It may remain as a separate contract where existing application behavior depends upon it.

Common value objects may be shared where semantically identical.

No automatic aliasing between:

    AccommodationRate

and:

    RateOption

is permitted.

If future consolidation is desirable, it requires a separate architectural decision.

---

## 25. Existing AccommodationRateResult

`AccommodationRateResult` remains a separate rate-query result.

It must not be embedded inside Availability.

Shared lower-level concepts such as:

- Money;
- Board;
- occupancy;
- supplier reference;

may be reused where their semantics are identical.

The two result contracts remain distinct.

---

## 26. Existing Occupancy Models

The canonical Availability occupancy contract must support per-room occupancy.

Existing aggregate occupancy models may remain for legacy contracts.

`AccommodationOccupancyGroup` may be reused or refactored only if its invariants can support the canonical multi-room requirement.

The existing R3 rule requiring one room per occupancy group must not be copied into the canonical contract.

---

## 27. Existing Money Model

The existing canonical Money model is the preferred shared representation.

Before implementation, its currency representation must support all currencies that the business and integrated suppliers may legitimately return.

Currency must be represented as a canonical ISO-compatible value rather than a supplier-specific enumeration that artificially limits Availability.

If the existing enum is too restrictive, it must be generalized at the shared Money/currency boundary.

A second Availability-only Money model is prohibited.

---

## 28. Result Consumer Contract

Consumers must discriminate Availability results using `kind`.

### 28.1 Accommodation

Consumers handling:

    kind === "ACCOMMODATION"

may access:

- accommodation;
- requested occupancy;
- availability options;
- room options;
- rate options.

### 28.2 No Availability

Consumers handling:

    kind === "NO_AVAILABILITY"

must not attempt to access accommodation or rate information.

### 28.3 Inventory

Inventory freezing/cloning must preserve:

- accommodation;
- requested occupancy;
- availability options;
- room options;
- rate options;
- pricing;
- cancellation;
- taxes;
- supplier references;
- metadata.

---

## 29. Multiple Accommodation Search

A package search may return:

    AccommodationAvailabilityResults

        results: [
            AccommodationAvailabilityResult,
            AccommodationAvailabilityResult,
            ...
        ]

Ordering is significant and must be preserved from the application/provider orchestration layer.

The provider adapter must not silently discard valid returned accommodations.

The result collection must not contain fabricated accommodations.

## 32. No-Availability Mapping

A supplier response explicitly indicating zero available hotels may map to:

    {
        kind: "NO_AVAILABILITY",
        available: false,
        metadata: ...
    }

No accommodation is fabricated.

No room or rate option is fabricated.

No supplier reference is generated.

Malformed supplier responses must remain errors.

Supplier errors must remain errors.

Transport failures must remain failures.

A missing collection must not automatically be interpreted as no availability.

## 34. Canonical Invariants

The following invariants are mandatory.

### Request

- at least one room;
- each room has at least one adult;
- child count equals child-age count;
- stay dates are valid;
- room ordering is preserved.

### Positive Result

- accommodation exists;
- availability options exist;
- every rate belongs to a room option;
- every selectable rate has a booking reference;
- every monetary value has currency;
- pricing basis is explicit;
- offered occupancy is valid.

### No Availability

- no accommodation;
- no room options;
- no rate options;
- no pricing;
- no booking reference.

### Supplier Isolation

- no supplier-specific field names in canonical models;
- no supplier response envelopes in canonical models;
- no provider-specific rate key semantics in canonical models.

### Booking Continuity

- selected rate can be associated with a supplier reference;
- provider adapter can resolve the reference during booking.

## 35. Serialization

Canonical Availability serialization must preserve the same semantic hierarchy:

    results[]
        accommodation
        requestedOccupancy
        availabilityOptions
            roomOptions[]
                rateOptions[]

Serialization must not:

- flatten room/rate relationships;
- rename canonical fields to supplier fields;
- expose Hotelbeds response envelopes;
- discard booking references;
- discard cancellation or tax information.

The serialized contract must remain canonical.

---

## 36. API / Client Boundary

The eventual client-facing package-search response may expose the canonical Availability hierarchy.

Client-facing presentation concerns must not redefine the canonical domain model.

Client UI may choose to display:

- lowest available price;
- room names;
- board;
- cancellation summary;
- taxes;
- payment conditions.

These are projections of the canonical Availability result.

They are not replacements for the canonical result.

---

## 37. Architecture Migration Rules

Implementation of CAN-003-C1 must not be performed as a series of compatibility patches.

The implementation sequence must be:

1. establish canonical types;
2. establish canonical invariants;
3. update provider mapping contract;
4. update R7 orchestration;
5. update consumers;
6. update serialization;
7. update tests;
8. remove obsolete assumptions;
9. run full regression;
10. only then implement R5-C2 supplier mapping.

No transitional canonical aliases such as:

    hotels.codes
    hotels.hotel

are permitted.

No duplicate room/rate models may be introduced merely to preserve old implementation behavior.

---

## 38. Legacy Sentinel Policy

The existing `"unavailable"` accommodation sentinel may remain temporarily for legacy R2/R3 no-candidate/no-request paths.

It must not be used for supplier-confirmed `NO_AVAILABILITY`.

Future removal of the sentinel is a separate migration and is outside CAN-003-C1.

## 43. Final Architectural Position

APP-008.3 Accommodation Availability is a commercial availability capability, not a supplier-response wrapper.

The canonical architecture is therefore:

    Availability Search
        ↓
    Accommodation Results[]
        ↓
    Accommodation
        ↓
    Availability Options
        ↓
    Room Options[]
        ↓
    Rate Options[]
        ↓
    Pricing
    Cancellation
    Taxes/Fees
    Payment
    Packaging
    Occupancy
    Supplier Reference
        ↓
    Client Selection
        ↓
    Booking
        ↓
    Provider Adapter

This structure is the implementation baseline.

Hotelbeds is one provider of availability data.

It does not define the GCT Core Availability model.

No implementation may weaken this architecture merely to accommodate an existing supplier adapter.
