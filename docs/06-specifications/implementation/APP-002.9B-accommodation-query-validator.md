# Objective

Introduce a canonical Accommodation Query Validator responsible for validating all accommodation search requests before provider discovery begins.

The validator establishes GCT Core as the owner of business request validation.

Validation shall be completely supplier-independent.

---

# Architectural Principle

Validation belongs to GCT Core.

External providers execute searches.

External providers shall never determine whether a request is valid.

The Accommodation Discovery Engine shall only execute validated queries.

# AccommodationValidationErrorCode

Create

```typescript
enum AccommodationValidationErrorCode {

    MISSING_DESTINATION,

    MISSING_CHECK_IN,

    MISSING_CHECK_OUT,

    INVALID_DATE_RANGE,

    INVALID_ADULT_COUNT,

    INVALID_CHILD_COUNT,

    INVALID_ROOM_COUNT,

    MISSING_REQUEST_ID,

    MISSING_SOURCE,

    MISSING_TIMESTAMP

}
```

The enum replaces free-form string codes.

Benefits

- compile-time safety
- consistent diagnostics
- structured logging
- API consistency
- future localisation
- future API error mapping

# Canonical Validation Rules

Implement the following validation rules.

---

## Destination

Destination is mandatory.

Empty destination is invalid.

Return

```text
MISSING_DESTINATION
```

---

## Travel Dates

Check-in date is mandatory.

Return

```text
MISSING_CHECK_IN
```

Check-out date is mandatory.

Return

```text
MISSING_CHECK_OUT
```

Check-out must be after check-in.

Return

```text
INVALID_DATE_RANGE
```

---

## Travellers

Adults

Minimum

```text
1
```

Violation

```text
INVALID_ADULT_COUNT
```

Children

Minimum

```text
0
```

Violation

```text
INVALID_CHILD_COUNT
```

---

## Rooms

Minimum

```text
1
```

Violation

```text
INVALID_ROOM_COUNT
```

---

## Search Context

Mandatory

- requestId
- source
- timestamp

Missing requestId

```text
MISSING_REQUEST_ID
```

```text
MISSING_SOURCE
```

Missing timestamp

```text

```

# Implementation Notes

Inject the validator into the Accommodation Discovery Engine using dependency injection.

The Discovery Engine shall not contain validation logic directly.

The validator is the single authoritative component responsible for determining whether a search query is eligible for provider execution.

Validation errors shall always use the strongly typed `AccommodationValidationErrorCode` enumeration.

---

# Future Evolution

The validator is intentionally designed to support future business rules without changing the Discovery Engine public API.

Future enhancements may include

- supported currencies
- supported locales
- maximum stay duration
- maximum traveller counts
- occupancy validation
- child age validation
- destination eligibility
- campaign restrictions
- partner-specific rules
- package compatibility
- seasonal availability rules

These enhancements shall extend the validator only.

No provider implementation or Discovery Engine interface changes shall be required.

---

# Milestone Outcome

Upon successful completion, GCT Core shall contain a canonical Accommodation Query Validator that validates every accommodation search before provider discovery begins.

The validator establishes a single, supplier-independent validation layer owned entirely by GCT Core.

The introduction of the strongly typed `AccommodationValidationErrorCode` enumeration creates a stable validation contract that supports future analytics, diagnostics, API integrations, localisation and business rule evolution without requiring changes to the Accommodation Discovery Engine or provider implementations.

This milestone completes the canonical request lifecycle of the Accommodation Discovery Engine and finalises the public request validation API for all future consumers of the Accommodation Engine.
