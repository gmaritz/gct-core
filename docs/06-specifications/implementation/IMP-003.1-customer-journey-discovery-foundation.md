# 3. PURPOSE

IMP-003.1 establishes the **Customer Journey Discovery Foundation** for the GCT Core frontend.

Its purpose is to replace the current placeholder navigation from a homepage Journey Card with a real customer-facing discovery entry point.

The target transition is:

**Homepage Journey Card → Journey Discovery Entry**

IMP-003.1 establishes the routing, identity, application resolution boundary, and minimal presentation contract required for the next Journey Detail implementation.

This iteration deliberately stops short of implementing the complete Journey Detail experience.

---

# 4. ARCHITECTURAL CONTEXT

GCT Core contains two intentional journey/product flows.

## 4.1 Dynamic Homepage Merchandising

The homepage dynamically composes journey offers from current commercial inputs.

The existing flow is:

**Pre-selected accommodation opportunities**
→ `HomepageJourneyShowcaseService`
→ `JourneyCompositionService`
→ dynamically composed Journey
→ presentation mapping
→ Homepage Journey Card.

The dynamic journey is a merchandising result.

It is not automatically a persisted catalogue Journey.

## 4.2 Established GOCAPE Tours / Packages

Established GOCAPE tours/packages are separately defined products containing:

- GOCAPE-authored itineraries;
- fixed tour/package structure;
- defined costing;
- optional extras where applicable;
- pre-selected Hotelbeds accommodation establishments/codes.

This architecture remains separate.

## 4.3 Architectural Principle

IMP-003.1 MUST preserve:

**Dynamic homepage journey composition ≠ persisted established tour/package.**

No new persistent Journey entity shall be introduced merely to support this frontend capability.

# 5. CURRENT BASELINE

The existing frontend architecture is:

**Express → `/ui` routes → frontend controller → application layer → View Model provider → View Model → EJS**

The homepage already has:

- homepage merchandising;
- homepage journey composition;
- Journey Presentation Mapper;
- Journey View Model Provider;
- Homepage Journey View Model;
- Journey Card View Model;
- Journey Card EJS component.

The current Journey Card CTA is not yet a real customer-facing journey route.

There is currently no dedicated customer-facing Journey Discovery route.

The existing dynamic homepage journey contains richer application information during composition than the Journey Card exposes.

IMP-003.1 establishes the boundary required to carry the dynamic journey identity into a subsequent request.

# 7. PUBLIC JOURNEY IDENTITY

The homepage Journey Card shall expose a public journey identity suitable for navigation.

The implementation MUST inspect the actual identity generated by the existing homepage composition architecture.

The identity MUST:

- be URL-safe;
- be validated;
- identify the dynamic homepage journey;
- not be assumed to be a database primary key;
- not expose unnecessary infrastructure information;
- remain compatible with the existing homepage journey identity.

The implementation MUST NOT introduce an arbitrary unrelated identifier if the existing composition identity is suitable.

Validation must accept the actual identity format used by the homepage composition.

---

# 8. JOURNEY RESOLUTION CONTRACT

IMP-003.1 shall introduce an application-level capability responsible for resolving a dynamic homepage journey from its public identifier.

The contract should express the business/application responsibility rather than an infrastructure mechanism.

Conceptually:

`resolveDynamicHomepageJourney(journeyId)`

The exact class/interface naming shall follow existing repository conventions.

The resolver shall:

1. validate the public identifier;
2. identify the corresponding homepage journey definition;
3. invoke the existing homepage journey composition mechanism;
4. return the resulting application-level journey representation;
5. distinguish invalid, unknown and unavailable journeys.

The resolver MUST NOT duplicate the existing journey composition algorithm.

---

# 9. DYNAMIC HOMEPAGE RESOLUTION

The current homepage journey is composed in memory.

IMP-003.1 shall use the existing composition path as the authoritative source.

The implementation must NOT:

- persist dynamic homepage journeys solely for this purpose;
- create a second journey-generation algorithm;
- reconstruct journeys inside the frontend controller;
- embed journey definitions in EJS;
- use the legacy persisted Journey repository merely because it exposes `findById`.

The distinction between dynamic homepage journeys and persisted established journeys must remain explicit.

---

# 10. RESOLUTION OUTCOMES

The application resolution contract shall support these outcomes:

## Valid

The dynamic homepage journey is successfully resolved.

## Invalid

The supplied public identifier is malformed.

## Not Found

No corresponding homepage journey can be resolved.

## Unavailable

The journey definition exists but cannot currently be composed/resolved.

The application layer shall expose these outcomes without exposing infrastructure exceptions.

---

# 11. FRONTEND ROUTE

Add a dedicated customer-facing route under `/ui`.

The preferred route is:

`/ui/journeys/:journeyId`

The route shall:

1. receive the public journey identifier;
2. delegate resolution to the application layer;
3. obtain the discovery View Model;
4. render the discovery/entry page;
5. handle invalid/not-found/unavailable outcomes.

The route MUST NOT:

- access Prisma directly;
- access repositories directly;
- call Hotelbeds directly;
- construct business objects;
- perform journey composition;
- contain business rules.

---

# 12. HOMEPAGE CTA

Replace the current Journey Card placeholder fragment target with the new customer-facing route.

The CTA shall resolve to the equivalent of:

`/ui/journeys/{journeyId}`

using the existing dynamic journey identity.

No unrelated homepage layout or styling changes are permitted.

The Journey Card remains a reusable presentation component.

---

# 13. FRONTEND CONTROLLER

Extend the existing frontend controller.

The controller action shall:

1. receive the route parameter;
2. pass it to the dynamic homepage journey resolver;
3. obtain the minimal discovery View Model;
4. render the discovery page;
5. delegate unsuccessful outcomes to established frontend error handling.

The controller must remain orchestration-only.

---

# 14. DISCOVERY VIEW MODEL

Create a dedicated minimal discovery View Model.

This is NOT the final Journey Detail View Model.

It should contain only the information required to establish the discovery transition.

Minimum supported fields:

- public journey identifier;
- title;
- primary destination;
- duration;
- summary/highlight information where already available;
- primary image reference where already available;
- pricing state where already available;
- continuation state.

Optional fields must remain optional.

No fabricated itinerary or pricing information may be added.

The View Model must not expose:

- Prisma models;
- repository objects;
- supplier response objects;
- raw infrastructure structures.

---

# 15. DISCOVERY PAGE

Create a minimal customer-facing discovery/entry page using the existing shared EJS layout.

The page shall establish the real navigation destination and provide enough information to confirm that the selected journey has been resolved.

The page should contain:

1. global navigation;
2. journey title;
3. destination;
4. duration;
5. available summary/highlights;
6. available imagery;
7. pricing state where available;
8. clear continuation indication.

The page is a foundation for the subsequent Journey Detail implementation.

Do not attempt to implement the complete itinerary/detail design in this iteration.

---

# 16. VIEW MODEL PROVIDER

Create a dedicated provider for the discovery View Model.

The provider shall:

- consume the application-level resolved journey;
- map only presentation data;
- handle optional values safely;
- format presentation values consistently with existing frontend conventions.

The provider MUST NOT:

- access Prisma;
- access repositories;
- call Hotelbeds;
- perform journey composition;
- fabricate missing content.

---

# 17. ERROR HANDLING

The customer-facing route shall provide controlled behaviour for:

### Invalid Identifier

Use the established frontend not-found/error experience.

### Unknown Journey

Use the established frontend not-found experience.

### Unavailable Journey

Present an appropriate customer-facing unavailable state.

### Unexpected Failure

Use the existing application/frontend error handling.

Do not expose:

- stack traces;
- database errors;
- supplier errors;
- internal implementation details.

Do not create a competing error architecture.

---

# 18. CONTENT BOUNDARY

Final itinerary content is NOT a prerequisite for IMP-003.1.

The implementation must therefore work with the existing available journey data.

Do not:

- create permanent itinerary JSON;
- create permanent Markdown content structures;
- hard-code final itinerary copy;
- invent day-by-day content;
- embed long-form content in EJS.

The authoritative content model will be introduced separately.

IMP-003.1 must nevertheless leave the discovery contract capable of being extended by the subsequent Journey Detail implementation.

---

# 19. IMAGE BOUNDARY

Final attraction/activity imagery is NOT a prerequisite for IMP-003.1.

Use existing journey imagery/placeholder mechanisms where available.

Do not:

- download external images;
- introduce arbitrary third-party image URLs;
- create a new media repository;
- hard-code large image inventories;
- introduce attraction/activity image entities.

Approved GOCAPE attraction/activity imagery will be integrated through the later content capability.

---

# 20. HOTELBEDS BOUNDARY

No direct Hotelbeds integration shall be introduced into the frontend.

Hotelbeds information may only reach the View Model through existing application-layer journey composition/services.

No Hotelbeds API calls may exist in:

- routes;
- controllers;
- View Model providers;
- EJS;
- frontend JavaScript.

Tests must not call Hotelbeds.

---

# 21. PERSISTED JOURNEY BOUNDARY

The existing persisted Journey retrieval infrastructure remains available for established GOCAPE journeys.

IMP-003.1 must not use it as the dynamic homepage journey source unless repository evidence proves that the selected homepage journey is actually persisted through that mechanism.

This distinction must remain visible in code naming and application contracts.

# 29. FINAL ARCHITECTURAL PRINCIPLE

The MVP frontend is being built against the same customer-facing journey model that will ultimately support the broader GOCAPE journey experience.

For MVP:

**Curated itinerary**
+
**dynamic Hotelbeds accommodation opportunity**
→
**customer journey**

Post-MVP:

**authoritative tourism content**
+
**route/business rules**
+
**AI composition**
+
**dynamic Hotelbeds accommodation**
→
**customer journey**

IMP-003.1 establishes the frontend discovery foundation without prematurely implementing either the final content system or the future AI composition system.
