# 3. PURPOSE

IMP-003.2 extends the Customer Journey Discovery Foundation established by IMP-003.1 into the first complete customer-facing Journey Detail experience.

The customer journey becomes:

**Homepage Journey Card → Discovery → Understand Journey**

The purpose is to allow a customer to understand the selected journey through a richer presentation of:

- journey summary;
- destinations;
- duration;
- itinerary;
- accommodation;
- attractions/activities/experiences;
- approved imagery where available;
- current pricing state;
- appropriate next-step indication.

IMP-003.2 is a presentation and application-readiness capability.

It does not implement booking or the later transaction workflow.

---

# 4. ARCHITECTURAL CONTEXT

GCT Core intentionally supports two related but distinct product experiences.

## 4.1 Dynamic Homepage Journey

The homepage dynamically composes and merchandises journey opportunities.

The existing architecture includes:

- `HomepageMerchandisingService`;
- `HomepageJourneyShowcaseService`;
- `JourneyCompositionService`;
- `JourneyPresentationMapper`;
- `JourneyViewModelProvider`.

The homepage journey is a dynamically composed merchandising result.

It must not be treated as a permanently persisted Journey merely because it has a customer-facing identity.

## 4.2 Established GOCAPE Tours and Packages

Established GOCAPE products have:

- defined itineraries;
- established tour/package structures;
- GOCAPE-controlled costing;
- optional extras where applicable;
- pre-selected accommodation establishments/codes.

The established Catalogue/Product architecture remains separate.

IMP-003.2 must not collapse these two concepts into a single persistence model.

## 4.3 MVP Principle

For the MVP, the journey itinerary is deterministic/curated while accommodation information may be dynamically sourced through the existing Hotelbeds/application integration.

The future architecture may replace deterministic journey composition with controlled AI composition.

IMP-003.2 must remain compatible with that future evolution.

→ **Journey Summary**

→ **Itinerary**

# 8. APPLICATION DATA CONTRACT

The detail page must consume an application-level representation.

The presentation layer must not receive raw:

- Prisma models;
- repository entities;
- supplier responses;
- infrastructure DTOs.

The application contract shall provide the information required to construct the Journey Detail View Model.

Where an existing application object already provides the required information, extend or reuse it rather than creating duplicate representations.

The application layer remains responsible for:

- journey resolution;
- journey composition/reconstruction;
- application-level data retrieval;
- business/application decisions.

The presentation layer remains responsible for presentation mapping.

# 9. DYNAMIC JOURNEY RESOLUTION

The detail request shall continue to use the dynamic homepage journey resolution established by IMP-003.1.

The implementation shall:

1. receive the public journey identifier;
2. resolve the dynamic homepage journey;
3. obtain the richer journey information required for detail presentation;
4. map that information to the Journey Detail View Model;
5. render the detail page.

The implementation must use the existing journey composition mechanism.

Do not duplicate composition logic inside:

- controllers;
- View Model providers;
- EJS;
- frontend JavaScript.

# 10. JOURNEY DETAIL VIEW MODEL

Create or complete a dedicated `JourneyDetailViewModel`.

The final View Model must be presentation-oriented and self-contained.

It should support the following sections.

## 10.1 Identity

Required:

- public journey identifier.

Do not expose internal database identifiers unless they are explicitly part of the customer-facing contract.

## 10.2 Header

Support:

- journey title;
- primary image;
- short summary;
- primary destination;
- duration.

## 10.3 Destinations

Represent the journey's destinations in meaningful customer-facing order.

Where the underlying data contains destination sequence, preserve it.

Do not reduce a meaningful itinerary sequence to an arbitrary comma-separated string where structured presentation is available.

## 10.4 Itinerary

The View Model must support a structured itinerary.

The preferred structure is:

**Journey → Days → Day Content**

Each day may contain:

- day number;
- day title;
- description;
- destination/area;
- attractions;
- activities;
- experiences;
- accommodation/overnight information;
- imagery where available.

Optional values must remain optional.

The implementation must not fabricate missing itinerary information.

If only a shorter itinerary representation exists in the current application data, expose what actually exists and preserve the contract for richer curated content to be integrated later.

## 10.5 Accommodation

Support customer-facing accommodation information where available.

Potential fields include:

- establishment name;
- destination;
- category;
- star rating;
- number of nights;
- summary;
- primary image;
- board basis if actually available;
- other customer-facing accommodation information supported by the application contract.

Do not expose raw Hotelbeds supplier data.

Do not expose Hotelbeds codes merely because they exist.

## 10.6 Experiences / Activities / Attractions

Represent the journey's actual included components.

Support, where available:

- name;
- type;
- sequence;
- destination/location;
- description;
- duration;
- primary image.

Only map information actually supplied by the application layer.

No invented tourism descriptions are permitted.

## 10.7 Pricing

The View Model shall explicitly represent pricing state.

At minimum:

**AVAILABLE**

or

**UNAVAILABLE**

If pricing is available, provide:

- amount;
- currency;
- price basis.

If pricing is unavailable:

- do not invent a value;
- do not imply a confirmed package price;
- expose the established unavailable-price state.

Pricing calculation remains outside the View Model.

## 10.8 CTA

The View Model shall support the next customer journey step without implementing that step.

The CTA must not:

- claim that booking is complete;
- initiate payment;
- initiate reservation;
- imply room selection is available;
- point to an unfinished internal endpoint.

Where IMP-004 or the subsequent capability will own the next step, the CTA may be represented as a controlled placeholder/disabled state or the existing approved continuation surface.

# 11. ITINERARY CONTENT

The MVP requires curated/set itineraries.

The itinerary is therefore business content and must not be generated by the frontend.

IMP-003.2 shall establish the presentation structure required to render that content.

Do not embed final itinerary content directly into EJS templates.

Do not duplicate itinerary content between:

- homepage;
- discovery;
- detail pages.

The same journey representation must be capable of being consumed by both homepage merchandising and customer-facing journey pages.

The final authoritative storage mechanism for curated itinerary content will be established separately after the content architecture has been confirmed.

---

# 12. IMAGERY

IMP-003.2 shall support imagery through the existing frontend/media conventions.

The page should be designed to support:

- journey hero imagery;
- attraction/activity imagery;
- accommodation imagery;
- optional itinerary/day imagery.

Where approved imagery is not yet available:

- use the existing controlled placeholder mechanism;
- do not source arbitrary external images;
- do not invent image URLs.

The future GOCAPE-controlled attraction/activity image library will be integrated through the appropriate content/media capability.

Images must have meaningful `alt` text where they communicate information.

Decorative imagery shall use appropriate accessibility semantics.

---

# 13. ACCOMMODATION DATA

Accommodation is a dynamic commercial component of the MVP.

The detail page may display the accommodation associated with the resolved dynamic journey.

The page must distinguish:

- accommodation identity/content;
- availability;
- pricing;
- future accommodation selection.

IMP-003.2 does not allow the customer to select a room or rate.

If current availability/pricing data is unavailable, present an appropriate unavailable state.

Do not fabricate availability.

---

# 14. HOTELBEDS BOUNDARY

Hotelbeds remains behind the application/integration boundary.

No direct Hotelbeds access is permitted from:

- EJS;
- frontend controllers;
- View Model providers;
- frontend JavaScript;
- presentation components.

Existing application services may provide the required accommodation information.

Tests must use controlled/mocked application responses and must not call live Hotelbeds APIs.

# 19. ERROR STATES

The existing IMP-003.1 resolution outcomes remain authoritative.

The page must handle:

### Invalid Journey ID

Use the established not-found/error response.

### Unknown Journey

Use the established not-found response.

### Unavailable Dynamic Journey

Present a customer-facing unavailable/expired state.

### Partial Optional Data

Render the available information without breaking the page.

For example:

- no image → controlled placeholder;
- no pricing → unavailable pricing state;
- no optional description → omit the section rather than invent content.

### Unexpected Failure

Use established frontend/application error handling.

Do not expose infrastructure details.

# 33. FINAL ARCHITECTURAL PRINCIPLE

IMP-003.2 establishes the customer-facing:

**UNDERSTAND JOURNEY**

experience.

The MVP architecture is:

**Curated Journey Definition**

→ **Dynamic Hotelbeds Accommodation Opportunity**

→ **Journey Detail**

The future architecture can evolve to:

**Authoritative Tourism Content**

+

**Route / Business Rules**

+

**AI Composition**

+

**Dynamic Hotelbeds Accommodation**

→ **Journey Detail**

The customer-facing Journey Detail model is therefore intended to survive the transition from deterministic MVP composition to future AI-driven dynamic itinerary composition.

IMP-003.2 builds the reusable customer-facing journey experience; it does not implement the future AI engine or the transactional booking workflow.
