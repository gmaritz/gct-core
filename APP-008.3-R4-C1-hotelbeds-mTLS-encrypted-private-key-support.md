## 2. Purpose

Correct the accepted R4-C1 Hotelbeds mTLS transport implementation so that it supports both unencrypted and password-protected client private keys.

The existing R4-C1 transport correctly uses Node's built-in `https.request` rather than the previous unsupported custom `tls` fetch property. However, the current transport does not support the passphrase required by an encrypted PEM private key.

The correction shall:

- add optional private-key passphrase configuration;
- determine whether the configured private key is encrypted using Node's built-in cryptographic key parser;
- reject encrypted keys without a passphrase before supplier execution;
- accept valid unencrypted keys without a passphrase;
- validate encrypted keys with the supplied passphrase;
- pass the validated passphrase to Node HTTPS when configured;
- preserve all existing R4 transport behaviour;
- avoid breaking valid unencrypted mTLS configurations.

No R2-R7 boundary or canonical model shall change.

## 4. Architectural Decision

The implementation shall use Node's built-in `crypto.createPrivateKey` to validate the configured private key.

The implementation shall **not**:

- require a passphrase for every TLS configuration;
- parse PEM headers manually to determine encryption;
- defer all private-key validation to `https.request`;
- introduce an explicit operator-controlled "encrypted key" configuration flag.

The actual private-key material is authoritative.

The validation rules are:

| TLS configuration | Result |
|---|---|
| No certificate and no private key | Valid non-mTLS configuration |
| Certificate only | Invalid |
| Private key only | Invalid |
| Certificate + unencrypted private key + no passphrase | Valid |
| Certificate + unencrypted private key + passphrase | Valid, provided the key parser accepts the supplied passphrase |
| Certificate + encrypted private key + no passphrase | Invalid |
| Certificate + encrypted private key + correct passphrase | Valid |
| Certificate + encrypted private key + incorrect passphrase | Invalid |
| Invalid private-key material | Invalid |
| Trusted CA absent | Valid |
| Trusted CA present | Valid |

The private-key passphrase is therefore **optional configuration**, not universally required TLS configuration.

## 5. Environment Configuration

Add support for:

`HOTELBEDS_TLS_PRIVATE_KEY_PASSPHRASE`

Existing variables remain:

- `HOTELBEDS_TLS_CLIENT_CERTIFICATE`
- `HOTELBEDS_TLS_PRIVATE_KEY`
- `HOTELBEDS_TLS_TRUSTED_CA`

The resulting TLS configuration is:

- `clientCertificate`
- `privateKey`
- `privateKeyPassphrase`
- `trustedCa`

The passphrase shall be loaded from the environment and trimmed consistently with the existing configuration loader.

An absent or empty passphrase shall be treated as not configured.

A passphrase without a private key shall be invalid configuration.

## 6. TLS Configuration Model

Extend both existing TLS configuration representations, where applicable, with:

`privateKeyPassphrase?: string`

Do not introduce a second TLS configuration model.

Do not expose the passphrase through unrelated configuration objects.

The passphrase must remain confined to the Hotelbeds configuration and transport infrastructure.

## 7. Private-Key Validation

Private-key validation shall occur during Hotelbeds integration configuration validation, before provider construction or supplier execution.

Use Node's built-in:

`crypto.createPrivateKey`

The implementation shall validate the configured PEM private key according to the following process:

1. Read the configured private-key PEM.
2. If no passphrase is configured, attempt to create the private key without a passphrase.
3. If that succeeds, the private key is considered valid and unencrypted for configuration purposes.
4. If that fails because the key requires a passphrase, the configuration is invalid unless a passphrase is supplied.
5. If a passphrase is supplied, attempt to create the private key using that passphrase.
6. If that succeeds, the private key configuration is valid.
7. If validation fails, throw the existing generic Hotelbeds configuration error type without exposing raw cryptographic error details.

The implementation must not depend on manually inspecting PEM headers.

The implementation must not expose Node's raw cryptographic exception text because it may contain sensitive or implementation-specific information.

---

## 8. Passphrase Validation Semantics

### 8.1 Unencrypted Private Key

An unencrypted valid private key without a passphrase is valid.

This behaviour is required to preserve compatibility with existing valid mTLS configurations.

### 8.2 Unencrypted Private Key With Passphrase

If a passphrase is supplied for an otherwise unencrypted valid private key, the configuration may be accepted provided Node's key parser accepts the combination.

The implementation must not unnecessarily reject valid configuration solely because a passphrase was supplied.

### 8.3 Encrypted Private Key Without Passphrase

An encrypted private key without a passphrase must fail configuration validation.

The failure must occur before `https.request` is invoked.

### 8.4 Encrypted Private Key With Correct Passphrase

An encrypted private key with its correct passphrase must pass configuration validation.

The passphrase shall subsequently be available to the transport for the HTTPS request.

### 8.5 Encrypted Private Key With Incorrect Passphrase

An encrypted private key with an incorrect passphrase must fail configuration validation.

No supplier request may be attempted.

### 8.6 Invalid Private-Key Material

Malformed or otherwise invalid private-key material must fail configuration validation.

No supplier request may be attempted.

### 8.7 Passphrase Without Private Key

A passphrase without a configured private key is invalid configuration.

---

## 9. Certificate and Private-Key Pairing

The existing certificate/private-key pairing rule remains unchanged.

The following are invalid:

- certificate without private key;
- private key without certificate.

The following is valid:

- certificate + private key.

The passphrase does not change the pairing rule.

The specification does not require certificate/private-key cryptographic matching validation at configuration time unless the existing implementation already provides it.

Certificate/key mismatch may remain a TLS handshake concern.

---

## 10. Trusted CA

`HOTELBEDS_TLS_TRUSTED_CA` remains optional.

The implementation shall not introduce a mandatory CA requirement.

When configured, the CA shall continue to be passed to Node HTTPS as the `ca` option.

When absent, no custom CA option shall be supplied.

TLS certificate verification must remain enabled.

The implementation must not use:

`rejectUnauthorized: false`

or any equivalent insecure TLS override.

---

## 11. Transport Behaviour

The existing `FetchHotelbedsTransport` class remains the active transport implementation despite its historical class name.

It shall continue to use Node's built-in:

`https.request`

through the existing injectable HTTPS request seam.

The TLS request options shall include:

- `cert` — client certificate;
- `key` — private key;
- `passphrase` — only when configured;
- `ca` — only when configured.

No unsupported custom `tls` property shall be passed to Node HTTPS.

The transport interface exposed to callers remains unchanged.

---

## 12. Passphrase Handling in HTTPS

When a private-key passphrase is configured and the TLS configuration has successfully validated it, the transport shall pass the passphrase to Node HTTPS using the standard:

`passphrase`

request option.

When no passphrase is configured, the transport shall not invent, derive, or substitute a passphrase.

The passphrase must not be included in:

- HTTP headers;
- request bodies;
- API authentication;
- Hotelbeds payloads;
- logs;
- result objects;
- errors;
- application-level objects outside the integration boundary.

---

## 13. Security Requirements

The private-key passphrase is sensitive configuration.

The implementation must ensure:

- no logging of the passphrase;
- no console output containing the passphrase;
- no exception message containing the passphrase;
- no test assertion that prints the passphrase;
- no raw TLS configuration object containing the passphrase is logged or returned;
- no inclusion in HTTP headers;
- no inclusion in request payloads;
- no inclusion in canonical results;
- no inclusion in supplier error objects.

Generic configuration errors shall be used instead of exposing raw cryptographic failures.

The `.env` file remains excluded from Git.

The `certs/hotelbeds/` directory remains excluded from Git.

No certificate, private key, passphrase, API key, or Hotelbeds secret may be committed.

## 15. Configuration Validation Order

The intended validation sequence is:

Environment
↓
TLS configuration parsing
↓
TLS certificate/private-key pairing validation
↓
Private-key cryptographic validation
↓
TLS configuration accepted
↓
Provider / executor construction
↓
Transport execution

Invalid private-key configuration must never reach `https.request`.

The implementation must fail closed.

Configuration errors must occur before supplier execution.

---

## 16. Failure Handling

If the private key is invalid or requires a missing/incorrect passphrase, the configuration loader shall throw the established generic Hotelbeds configuration error.

Do not create a new R4-C1 error taxonomy unless required by the existing architecture.

Do not expose raw `crypto.createPrivateKey` errors.

Do not retry private-key configuration failures.

These are configuration failures, not transient supplier failures.

R6 retry classification remains unchanged.
